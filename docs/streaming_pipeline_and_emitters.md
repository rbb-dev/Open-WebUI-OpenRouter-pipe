# Streaming Pipeline & Emitters

This document describes how the pipe converts OpenRouter Responses **SSE** (Server-Sent Events) into the incremental UI updates Open WebUI expects: text deltas, status updates, citations, notifications, and a final completion frame.

> **Quick navigation:** [Docs Home](README.md) · [Valves](valves_and_configuration_atlas.md) · [Concurrency](concurrency_controls_and_resilience.md) · [Errors](error_handling_and_user_experience.md)

---

## 1. High-level architecture

The streaming path is implemented by `send_openai_responses_streaming_request()` and the streaming loop that consumes it.

Conceptually:

```text
OpenRouter SSE (aiohttp) → chunk queue → JSON parse workers → ordered event drain → emitters → Open WebUI client
```

Key design goals:
- Preserve event ordering, even with multiple parser workers.
- Avoid unbounded memory growth under load (tunable queue sizes).
- Degrade predictably under backpressure rather than silently dropping events.

## 2. SSE ingestion and ordering

### Producer (SSE reader)
The producer reads the OpenRouter `text/event-stream` response and:
- extracts `data:` lines into full SSE “data blobs”
- recognises the `[DONE]` sentinel **per line**, not per blob: a `data:` line whose payload is exactly `[DONE]` ends the stream, and any event still pending behind it is flushed first. An empty line separates SSE events, so a provider whose final `data: [DONE]` is not followed by one would otherwise leave that line in the pending parts, where the next join fuses it into the preceding event's blob and the whole blob fails to parse. A blob is never rewritten to strip the sentinel: a legitimate event whose JSON *contains* the literal would be silently corrupted.
- on the chat leg, an ending recovered by that rule is **delivered, and not marked**. The per-line rule is what makes such an ending reachable at all: a provider whose final `data: [DONE]` never got its blank line still ends the stream, and the events queued behind it are flushed first, so the turn emits its `response.completed` record and the text that arrived is delivered. The cut-off guard is `if not done and not tool_calls_completed:` — `done` is set by every `[DONE]` arm, so a recovered ending never reaches it: the record carries no `status`, no `incomplete_details`, and the breaker stays quiet, whether or not the ending carried a `finish_reason`. A body that **simply stops**, with no `[DONE]` at all, is the opposite case: the guard fires, `_record_failed_call` counts it toward the breaker, and `cut_off` returns no terminal event at all, so a truncated answer is never reported as a completed one. The one thing it does still return is a refusal that was buffered before the cut, published as an `output_text` delta on the same join the clean exit uses; a cut-off turn publishes that delta and no `response.completed` and no `response.incomplete`. Only a `finish_reason` the provider actually sent marks a record — `max_output_tokens`, from the provider's own `length` termination — and that one is delivered **and** marked `status: "incomplete"` with `incomplete_details.reason: "max_output_tokens"`. The reasons that **end** the turn are a separate set, and it is wider: every non-null value OpenRouter publishes in `ChatFinishReasonEnum` — `tool_calls`, `stop`, `length`, `content_filter` and `error` — ends the `/chat/completions` turn with or without the `[DONE]` sentinel, so a provider that ends the turn itself and then stops is not read as a cut-off. `error` is in that set and is the one ending delivered **unmarked**, because the provider giving up is not a budget that ran short and Continue Response cannot help it; `length` is the only reason that marks the record. A turn ended by one of those reasons without the `[DONE]` sentinel still completes, and still does not count against the breaker, but OpenRouter sends its counters as a frame of their own just before that sentinel -- so a connection cut in that window leaves a turn that finished and cannot say what it used. Its closing record and the snapshot it files then carry the marker `incomplete_usage` rather than the empty usage a turn that reported nothing files, which is what makes the gap countable after the fact. A turn that reached `[DONE]`, or whose provider sent real counters, is unaffected.
- assigns an incrementing sequence number (`seq`)
- enqueues `(seq, data_blob)` into the **chunk queue**

### Tool-call slots (the `/chat/completions` leg)
A provider that streams parallel tool calls is supposed to label every fragment with the call's `index`. The `/chat/completions` reader matches a frame to the call it continues by three keys, in order: the frame's `id`, then its `function.name`, then neither. **A frame carrying no `index`, no `id` and no `function.name` continues the newest call whose accumulated arguments do not yet parse** — the call the provider opened last and is still writing — and opens a new call only when no call is open. A keyless frame used to answer `max(slots) + 1` whenever more than one call was open, which minted one call, and one announced card, per continuation frame. A call is **closed the moment its arguments parse**: a closed call is not extended by a later keyless fragment, and it is not decoded again while its argument string is unchanged, so the completeness test costs a bounded number of bytes per call rather than one whole-argument parse per delta. (A tool call's arguments are a JSON **object**, and a JSON object's last non-space character is `}`, so an accumulator that begins with `{` is decoded on `}` and on nothing else. That is what makes the bounded-bytes claim above true: the other sixteen characters of the seventeen-character `_ARGUMENTS_VALUE_TERMINATORS` set — `]`, a quote, a digit, `e`, `E`, `l`, `L` — are the ones a JSON *value* can end on, and a provider fragmenting a `write_file` call across them was charged a whole-argument parse per delta for an answer that could not be anything but `no`. The whole set is still the gate for an accumulator that does **not** begin with `{`, so a provider streaming a bare scalar keeps today's latch, and with it `json.loads`' acceptance of `NaN` and `Infinity` — which end in characters that set does contain — stays reachable on that path rather than being ruled out. A slot the explicit-`index` path appends to re-opens, because its bytes no longer match what was declared whole.)

### Citations on the `/chat/completions` leg
The reader turns each citation frame into a `response.output_text.annotation.added` event. When the request offered
the web search tool, a wrapper between the reader and the loop holds back the first run of consecutive such events
until the first event that is not one, or the end of the stream, and then emits a `web_search` item that lists the
held pages (`response.output_item.added`, then `response.output_item.done`) followed by the held events, so the loop
sees the sequence a `/responses` search produces: the item first, its citations after. The item carries no query and
is marked `query_not_returned`, which makes the record open with a note entry instead of a query. Once the item is
open, later citations pass through unchanged, so the first run of consecutive citation frames forms the round and
frames after that run reach the sources panel only. When the request offered no web search tool the wrapper passes
every event through unchanged. The whole-reply reader passes through the same wrapper. A stream that fails inside the
held run loses the held citations and opens no item.

### End of body
The read buffer is consumed line by line, so when the body ends the buffer still
holds the bytes after the last newline. A `data:` frame the body ended without a
terminator is dispatched from that residual rather than dropped, and a complete
frame already pending at end of body is dispatched first, on its own — the two are
never joined into one blob, because a worker parses a blob as a single JSON unit and
the pending frame would be lost with the residual. A body cut mid-frame produces a
residual that is not valid JSON; it takes the same per-chunk parse path as any other
malformed frame and is discarded, so a truncated tail is not reported as a transport
fault unless nothing in the body decoded. A `[DONE]`-terminated body is unaffected.

That is a malformed frame **inside** a stream, and it is discarded. A malformed **whole
body** behind an accepted status is a different failure: nothing was ever streamed, the
provider answered with something that is not an OpenRouter response, and the fault belongs
to whatever rewrote it — a proxy, a CDN or a WAF. It is reported under
`SERVICE_ERROR_TEMPLATE`, never retried and never charged to the breaker, and it is
reported on the streaming leg too, where a body carrying no `data:` line at all is not a
stream: it leaves as the same card, while a body that carried `data:` lines and decoded none
of them is a different fault and still arrives as a `ClientPayloadError`. Where the
streaming loop's own arm renders it, the card names the endpoint and the `Content-Type`
in `{reason}` and quotes the provider's first 200 characters in `{body_excerpt}`, inside a
code fence: the text is what the proxy sent, and a fence is what stops a WAF page's
`![beacon](…)` or unclosed ``` from being rendered rather than read. A body that was
accepted and then **lost on the way** is not this case: nothing was rewritten, the
connection simply died before the body finished arriving, so the call is charged once and
is still not re-POSTed. See
[Errors and how they surface](error_handling_and_user_experience.md).

A `data:` line is normally dispatched on the blank line that follows it, but a provider may end its stream without one. Both readers therefore flush whatever is left over when the response ends — bytes that never got their newline, and blobs already split out but not yet dispatched. Each complete leftover frame is dispatched as its own event rather than joined with its neighbours, so every complete frame the provider sent survives the missing blank line; a frame that is itself truncated mid-JSON is still rejected and not delivered. On `/chat/completions` a flushed end-of-stream marker also ends the turn, so the call is not counted as failed; see [Streaming errors and how they surface](#5-streaming-errors-and-how-they-surface) for how that differs from `/responses`.

### Workers (frame forwarders)
The pipe spawns `SSE_WORKERS_PER_REQUEST` worker tasks. The JSON parse happens once, in the producer: the reader decodes every SSE frame and hands the object on, and a frame it could not read never leaves the producer. Each worker:
- dequeues `(seq, event_obj)` from the chunk queue
- forwards the decoded object
- enqueues `(seq, event_obj)` into the **event queue**

There is no `await` between the dequeue and the enqueue, so on one event loop a worker cannot overlap another's parse: extra workers buy drain overlap while the producer awaits, and cost one extra queue crossing per frame and one task per concurrent stream. The `seq` reorder buffer makes the order the same either way.

### Drain (ordered emission)
The drain loop:
- stores out-of-order events in a `pending_events` map
- emits events strictly in ascending `seq` order
- discards any event that is not a JSON object (an array, a string, a number, a
  boolean) and does not pass it on, so one such frame does not take the reply down

Non-visible events are held only until the first user-visible event **or the end of the stream**, whichever comes first: the `/responses` adapter buffers them so a fallback can drop them, and drains what it holds when the stream ends normally rather than carrying it past the end. The exception path is not that drain — an attempt that fails still hands over to `/chat/completions` with its own events discarded.

The in-band error guard is a single shared function the consumer calls on every event it takes off the queue, whichever loop fetched it, so an error is raised and counted identically in either path rather than only in the ordered one.

A turn that ends — by `break` on the terminal event, by exhaustion, by an error or by cancellation — closes its own event iterator as the first act of the streaming loop's `finally`, so the producer, its `SSE_WORKERS_PER_REQUEST` workers and the aiohttp response are released at the end of the turn rather than whenever the garbage collector gets to them. The close is delegated, three generators deep, to the adapter whose `finally` owns that teardown; the release is therefore bounded to one turn's worth rather than instantaneous, because that teardown awaits its workers. The tasks are gone by the time the turn returns, not before.

## 3. Queue sizing and backpressure

The streaming pipeline uses two queues with valve controls, plus a third that has a monitoring valve and no size valve:

- `STREAMING_CHUNK_QUEUE_MAXSIZE`: raw SSE JSON blobs (pre-parse)
- `STREAMING_EVENT_QUEUE_MAXSIZE`: parsed JSON events (post-parse)

Defaults are `0` (unbounded) for both queues.

**Warning:** A bounded queue applies backpressure: when it fills, the pipe stops reading from OpenRouter until the backlog clears. The chain runs the other way from what it used to — a slow drain (tool-heavy or persistence-heavy workloads) → event queue fills → workers block → chunk queue fills → producer blocks on its next put → and the source stops being read. As long as the consumer keeps draining, the cost is added latency on a slow drain, not a stalled stream: the reply still ends on its own. A consumer that stops reading entirely, such as a closed browser tab, does not hang the request: cancelling it tears the pipeline down and returns, and no producer or worker task is left behind.

Monitoring:
- `STREAMING_CHUNK_QUEUE_WARN_SIZE` emits one backend `WARNING` per request per queue when the raw-chunk queue backlog crosses it, and repeats it at `DEBUG` at most once every second while the backlog stays high; the bound is on how often a line is emitted, not on its level.
- `STREAMING_EVENT_QUEUE_WARN_SIZE` emits one backend `WARNING` per request per queue when a buffered-event backlog crosses it, and repeats it at `DEBUG` at most once every second while the backlog stays high; the bound is on how often a line is emitted, not on its level. It watches two queues: the `/responses` event queue above, and the pump queue a `/chat/completions` reply is drained through, which no size valve reaches.

**The pre-first-output buffer is a third buffer, and no size valve reaches it.** On `/responses` the producer parks every frame the reader cannot see — `response.created`, `response.in_progress`, `response.queued`, `response.heartbeat` — in a plain list until the first user-visible frame arrives, so an attempt that is handed back for a fallback can discard them. Those frames have not been enqueued yet, so bounding the chunk queue does not bound them: with `STREAMING_CHUNK_QUEUE_MAXSIZE=1` the queue still never holds more than one item while the producer holds every frame the provider sent before the first visible one. **No valve reaches this buffer and it is uncapped today**; the two named above, and their monitoring valves, cover the queues only. The frames cannot be dropped to save it — the Fusion clock reads the `response.created` and `response.in_progress` frames (`streaming/streaming_core.py`) — and OpenRouter documents exactly two of them as a stream's opening, which is what a provider is expected to send. It holds lifecycle frames, and it is released in order, ahead of the visible frame that released it, on the first visible frame or at the end of the stream. On `/chat/completions` there is a fourth buffer behind it: the pump queue `nagle_coalesce_stream()` builds and drains through, which is uncapped like this one but does have a monitoring valve on it — `STREAMING_EVENT_QUEUE_WARN_SIZE` watches its depth and logs the same way it watches the `/responses` event queue, so an operator who lowered that valve to catch a slow consumer is no longer blind on the chat path. It stays a monitor: the same events reach the consumer, in the same order, with the same bytes, either side of the threshold.

### Middleware streaming bridge queue (Open WebUI generator)

When `pipe(..., body={"stream": true})` is used, the pipe returns an async generator that yields Open WebUI-compatible chunks, except for a request that has no chat (the paragraph on a caller with no chat below), which gets a `StreamingResponse` whose body writes the same drain as server-sent events. Internally, request-scoped tasks enqueue items into a per-request queue that the generator drains.

This bridge is controlled by:
- `MIDDLEWARE_STREAM_QUEUE_MAXSIZE` (default `0` = unbounded)
- `MIDDLEWARE_STREAM_QUEUE_PUT_TIMEOUT_SECONDS` (only applies when maxsize > 0)

Rationale: a stalled or slow client should not allow unbounded memory growth, and teardown should not hang while attempting to enqueue the final sentinel. What a bounded queue drops of the answer text is not lost output: the pipe counts a frame as sent only once its put returns, so the next whole-message snapshot re-sends the span the consumer missed. A citation (`source`) or Fusion panel (`embeds`) frame the queue drops is not re-sent, so the saved message lacks what that frame carried.

Invariant: the generator ends on whichever comes first — the `None` terminator a job puts on its queue, or its future reaching a terminal state. The check is the `future.done() and stream_queue.empty()` test in the `_stream` generator of `Pipe._pipe_impl`, re-evaluated on every `asyncio.wait` that generator makes against the future, so it holds whether the consumer is parked inside the get or sitting between items, and at every `MIDDLEWARE_STREAM_QUEUE_MAXSIZE` including the shipped `0`. The generator makes that wait only when its queue is empty: a frame already queued is taken at once, and the wait it falls back to is what ends a stream whose job settled while nothing was queued. **One** exit settles a request's future without putting a terminator: the drain that abandons a queue replaced under a hot reload (`_abandon_request_queue`). The other three sit above the job's own teardown, where nothing would put one for them — the admission refusal the dispatch worker hands a job it will not run (`_admission_failed`), the worker's own `Semaphore unavailable` arm, and the same arm inside `_execute_pipe_job` — so each calls `_put_streaming_refusal` on the job itself and ends its stream on the `None` rather than on the reader. That put is a best-effort `put_nowait`, so a capped buffer whose slots are all taken drops it rather than waiting for one, and the generator's own check is what ends such a stream. Each of those four exits now puts a **refusal frame** on the job’s own queue before the terminator, so a job that was declined rather than answered says so on the wire: a fixed sentence (`Request failed. Please retry.`, and the non-streaming 503’s own `Server busy (503)` on the admission refusal), never `str(exc)`, which would leak the exception’s text on a fourth path. The cancellation branch of `_admission_failed` is not one of the four, and is not silent either: `_wake_refused_stream` gives it the same `Server busy (503)` frame, closed, so a person who pressed Stop is told the same thing. The put is a `put_nowait` for the same reason the terminator’s is, and for one more: `_abandon_request_queue` must also answer a job whose future belongs to an event loop that is already closed. A job resolved that way whose future was settled with an exception, and whose queue delivered no `{"error": ...}` item of its own, yields one error chunk first, carrying the same sentence the non-streamed leg returns, so the turn is recorded as failed rather than closed as a completed empty answer; a future that was cancelled — the person pressing Stop — is not this backstop's to answer, because the site that cancelled it has already put its own frame and closed it, and a job that already delivered such a chunk is not told about it twice. **A turn whose queue carried no answer frame hands the job's parked result over before the stream ends, once.** The hand-over is decided by the frame's shape, not by whether anything was yielded: a `status`, a `notification`, a `files` frame, a card and a `usage` record are not answers, and a refusal announces itself with one before the text it owes the reader arrives, so a “did anything reach the queue” guard suppresses the hand-over on exactly the turns that need it. A frame that does carry an answer — a `choices[]` chunk, a `response.*` frame, a `chat:message` / `chat:message:delta` / `chat:completion` event with string `content` — settles it, and the parked value is the same answer the queue already had, so the turn is not told twice. A future settled with an exception hands over nothing (the failure item is the turn's report and is already on the wire, and reading the result would re-raise inside the consumer loop), and neither does one that was cancelled: a person who pressed Stop gets the silent end they get today, not a `CancelledError`. A turn whose stream has already reported a failure is in the same position on both exits: the refusal card is its report, and the value a settling site parks beside it is the same sentence rather than an answer — the admission refusal's `set_result(“Server busy (503)”)` is the live case, and a bounded queue drops that card's put, which is why the two exits have to agree on this rather than only the `future.done()` one. Both exits run it — the `future.done()` arm for the abandon drain and for a bounded queue whose terminator put gave up, and the `None`-terminator arm, which is the one that fires on the ordinary path, because the job resolves its future before it puts the sentinel. A `str` is yielded verbatim, which the plain-string branch of `process_line` in `generate_function_chat_completion` wraps in a `delta.content` chunk itself (for a request with no chat the pipe wraps it, as the paragraph on a caller with no chat below says); a dict is converted rather than forwarded, because `delta.content` is the only channel Open WebUI's consumer reads (the `choices[0].delta` read in `streaming_chat_response_handler`'s `chat.completion` chunk arm) and a `chat.completion` dict handed over as it stands accumulates as an empty turn. The conversion reads `choices[0].message.content` as a string and as a list of `text` parts, then `output` as a list of message parts, and a dict carrying none of those produces no frame rather than an empty delta. Nothing else rescues the rest: Open WebUI's consumer (the `async for` tail of `stream_content` in `generate_function_chat_completion`) has no timeout — it reads whatever arrives and then, for a chat, emits the finish chunk and `[DONE]` itself (a request with no chat is ended by its own body, below). A frame already on the queue when the resolve lands is still yielded first. A job that reaches the worker's `try` puts the terminator itself, and that includes the emitter-construction path — a fault raised while building the middleware stream emitter is handled by the job's own guard, which puts the error chunk and then the terminator. `future.set_result` is a terminator in its own right, in `Pipe._execute_pipe_job`, and so is the `None` sentinel: whichever fires first decides whether the queue is drained or abandoned, which is why a streaming job defers its `set_result` until the request's tool workers have stopped, and with it the invariant holds on both queue sizes. That holds on a capped buffer because the failure item and the terminator are not put through the drop valve, and neither is the turn-ending `chat:completion` that carries the answer and `done`: the valve applies to incremental output only, and the items that report or end a turn are put past it on a ceiling of their own, which `MIDDLEWARE_STREAM_QUEUE_PUT_TIMEOUT_SECONDS = 0` does not remove. A reader still looping frees the slot those two waits need; a reader that has stopped entirely makes both give up, which costs the close and the failure notice but never the end of the stream, because the generator's own check is what ends a job whose queue nobody drains. Every arm of the middleware adapter that carries a frame returns that frame's delivery verdict, so a drop reads the same way whichever arm lost it: under a bound, `False` on `chat:tool_calls` and on `response.*` alike, and on a multi-frame `chat:completion` a drop of any part is a drop of the frame. An arm that carried no frame returns `None`, which the same rule ("what counts as published is what has been handed to the consumer") reads as published — it published nothing and lost nothing, and the empty-`chat:tool_calls` arm of the non-passthrough hand-back leg is read live by `_publish_turn_frame`, so reporting a drop there would close the retry barrier for a frame that was never on its way.

**A caller with no chat gets only the chunks an OpenAI-compatible client reads.** Open WebUI's chat middleware builds a reply from the `event`-wrapped frames and the `response.*` frames only for a request that carries a truthy `chat_id` and `message_id` (`get_event_emitter_and_caller`). A request without them has its stream returned as it is, and `generate_function_chat_completion` forwards what the pipe yields without looking inside it (`process_line` for a generator, the body as it stands for a `StreamingResponse`); the middleware reads that stream only to run the model's stream filters and, when the model has outlet filters, to collect the reply for them (`update_assistant_message_from_stream`), and the pipe's own filters define `inlet` only. A client that checks every chunk against OpenAI's chunk format failed on the first frame that was not one, measured on the dev box with Open WebUI 0.12.3: a loop that reads `choices[0]` raised, a strict chunk schema reported an error for each such frame, and a coding agent ended its turn on the first one with no answer shown. So for a request that streams, has no chat and is not an internal Fusion member's own (`_is_chatless_caller`), `_pipe_impl` returns a `StreamingResponse` and not a generator. Its body is the drain through `_standard_frames`, the one place every frame of that stream passes, written as server-sent events: `data: ` and the frame as JSON with every non-ASCII character escaped, then a blank line. Open WebUI hands a `StreamingResponse` on as it is, so what `_standard_frames` lets through is what the program reads, and it lets through the following. A chunk that carries `choices` (answer text, tool calls, the closing sentence for an attachment the pipe left out) goes on as it is, and a plain string becomes a chunk of answer text. A Fusion turn with the live panel does not stream its answer text as the model writes it: a chat is shown that answer by a message item and by `fusion:event` frames for its panel, and this stream carries neither, so the loop sends the answer text of such a turn once, as one `chat:message:delta`, when the turn ends in an answer, right after it publishes the item and before the closing sentence for an attachment. The text that a phase marker, a picture or the note on the tool-call limit adds to the answer waits for that chunk as well. The chunk is the string the same request without streaming returns, the bare answer without the `<details type="fusion_answer">` wrapper (see the Fusion answer item in section 4.1); a turn that ends on a call to a tool the program sent ends on a `tool_calls` chunk and sends none of it. This request is served the same way in both tool modes: `open_webui_runs_the_calls` is false for a request with no chat, because Open WebUI runs no tool loop for it, and the pipe runs none of the calls the model makes either, so a call to a tool the program declared itself and a call to an Open WebUI tool the program named with `tool_ids` both go out as a `tool_calls` chunk, and so does a call to a name nobody offered. An error goes on as `{"error": {"message": …}}`: a `{"error": {"detail": …}}` frame (the refusal frames above and the job's own failure frame) and a `chat:message:error` event carrying `error.content` are reshaped into it with the same text, and an error that already has a `message`, the in-band envelope with its `code`, goes on as it stands. When the body asks for usage with `stream_options.include_usage`, a `usage` record becomes one chunk, sent after the finish chunk described below, with one choice that has an empty delta and repeats the finish reason (`finish_reason: null` when the stream has no finish chunk, after an `error` frame), the form OpenRouter documents for the usage chunk of its own stream and sends to Open WebUI's own OpenRouter models, instead of OpenAI's empty `choices`, which a loop that reads `chunk.choices[0]` on every chunk cannot take: `prompt_tokens`, `completion_tokens` and `total_tokens` come from the record's keys of those names (the first two from `input_tokens` and `output_tokens` where the record has none, `total_tokens` as their sum where it has none), `prompt_tokens_details` from `input_tokens_details`, `completion_tokens_details` from `output_tokens_details`, and OpenRouter's own `cost`, `is_byok`, `cost_details`, `cache_discount` and `cache_discount_pct` as they stand, while `turn_count` and `function_call_count`, the pipe's own tally, stay out. As in the chat frame above, `prompt_tokens` and `completion_tokens` are the size of the last call and the other counters are the turn's totals, so a turn that made several calls reports counters that do not add up. Open WebUI sets `stream_options.include_usage` on its own for a model whose Usage capability is ticked, which the capability sync (`UPDATE_MODEL_CAPABILITIES`) sets on the models the pipe writes, and a caller can send it; without it no usage chunk is sent. The model's reasoning goes on as chunks whose delta is `{"reasoning": "…"}`, the field OpenRouter's own stream carries. Open WebUI reads it too: its stream handler, its outlet-filter collector and its Anthropic Messages converter take `reasoning_content`, then `reasoning`, then `thinking`. The pipe sends `reasoning` and no `reasoning_content`: the AI SDK's OpenAI-compatible provider (3.0.78) takes `delta.reasoning_content` and, when that is absent, `delta.reasoning`, so it reads one field whichever the stream carries, and the OpenAI Python SDK declares neither and keeps an undeclared field of a delta as an extra. The text is what a chat's reasoning box is given, and it goes out as the box is given it: whenever the streaming loop adds text to a block of thinking it also sends the added text at once as a `pipe:reasoning.delta` event, before it handles the next event from the provider, but only for a request that streams and has no chat, and only when `THINKING_OUTPUT_MODE` puts thinking in the box (`open_webui` or `both`); `_standard_frames` turns each event into a chunk. With `status` the caller gets no reasoning, and a model that returns none gives it none. A chunk holds what the loop added from one event, and the pipe's own batching of streamed text comes first: with the shipped `STREAMING_DELTA_CHAR_LIMIT` it joins pieces that arrive together and holds back a batch of fewer than `STREAMING_NAGLE_MIN_FLUSH_CHARS` characters until more arrives or `STREAMING_IDLE_FLUSH_MS` milliseconds pass with nothing new, and with that setting and `STREAMING_IDLE_FLUSH_MS` both 0 every piece goes out as it arrives. A provider that gives its thinking only as a finished block (a summary, or a reasoning item at its end) gives the caller that block as one chunk, because that is when the loop has it. A chunk that has gone out cannot be taken back, so an attempt whose reasoning has reached the caller is not sent again. The loop records that in `retry_handoff` when the stream accepts a chunk, and the orchestrator then skips its three retries (at a reasoning effort the model accepts, without the replayed thinking blocks, without reasoning); the failure it reports reaches the caller as the `error` frame, after the reasoning chunks. The retries of the `/responses` and `/chat/completions` adapters and the fall back from `/responses` to `/chat/completions` already stop at the first event a reader could see, and a reasoning event is one. While nothing at all is sent to the caller, `_stream` keeps the connection busy: when `_CHATLESS_KEEP_ALIVE_SECONDS` (15 seconds, a constant and not a setting) pass without a frame the stream lets through, it yields one chunk with an empty delta, `{"index": 0, "delta": {}, "finish_reason": null}` (`{"role": "assistant"}` as the delta when it is the first chunk of the stream), and another every 15 seconds until something else is sent. A reverse proxy that closes a connection after a read timeout (nginx's `proxy_read_timeout` is 60 seconds unless it is set) and a client that gives up after a chunk timeout then see bytes while the model has not answered, while it reasons and while a tool runs. The count is the caller's silence, not the pipe's: `_standard_frames` restarts it when it sends a frame, and a frame it does not send (a status line, a tool card) does not restart it, so a stream that publishes a status line every few seconds still gets its empty chunk; a chunk of answer text or of reasoning restarts it, so no empty chunk comes between pieces of an answer, or of the thinking before it, that arrive less than 15 seconds apart. The empty chunk is built by hand, because Open WebUI's chunk template marks a chunk with no content as the last one (`finish_reason: "stop"`). The keep-alive is this chunk and not a comment line such as the `: OPENROUTER PROCESSING` that OpenRouter's own stream uses. The timer is the timeout of the `asyncio.wait` the generator already makes for its next frame, so no empty chunk is sent once the job has settled and the queue is empty, and the drain of a chat makes that wait with no timeout. What stays out of that caller's stream is every other frame the turn publishes: `status`, `notification`, `source`, `files` and `embeds` events, `chat:completion` events, `response.*` events and the bare `usage` record. A model's outlet filter therefore gets the reply collected from these chunks: its `content`, its `usage` when the request asked for usage, its `finish_reason`, and, when the turn sent reasoning, an `output` array holding that reasoning and the answer message, which the collector builds when it meets a `reasoning` delta and not otherwise. **The ending is the pipe's own.** Open WebUI puts a finish chunk with `finish_reason: "stop"` and `data: [DONE]` after the stream of a pipe that returns a generator, and a reader that keeps the last finish reason it sees read `stop` for a turn that ended on a tool call and for one the provider cut off. Measured in-process with `stream_content` and the Anthropic converter of Open WebUI 0.12.2 run from its source files, the OpenAI Python SDK's stream helper returned `stop` for such a tool-call turn and the Anthropic Messages mount answered `end_turn` for it. Open WebUI passes a `StreamingResponse` on as it is, so the body of this stream ends by itself: one finish chunk, `{"index": 0, "delta": {}, "finish_reason": …}`, then the usage chunk when usage was asked for, then `data: [DONE]` and its blank line. The finish reason is `length` when the last round of the turn ended with `incomplete_details.reason` `max_output_tokens`, `content_filter` when it ended with `content_filter`, otherwise `tool_calls` when a chunk with tool calls went out in the stream, otherwise `stop`; the streaming loop records the provider's reason on the job (`outcome["incomplete_reason"]`) for `_standard_frames` to read once the stream has drained. A stream that carried an `error` frame gets no finish chunk; its usage chunk, if it has one, and `data: [DONE]` still end it: the AI SDK's OpenAI-compatible provider (3.0.78) stores the last finish reason it reads and an error chunk sets its reason to `error`, so a finish chunk after an error would turn the failure into an ordinary ending. The first chunk with `choices` carries `delta.role: "assistant"` and every chunk with `choices` carries the id of that first chunk, as the chunks of an OpenRouter stream do (a recording of Open WebUI's own OpenRouter model streaming a tool call shows one id on every chunk): the OpenAI Node SDK's stream helper throws `missing role for choice 0` on a stream whose chunks never name a role (measured with openai 6.15.0 on streams this pipe produced before the role was added). An exception raised inside the body itself, as opposed to a failed model call, is logged and ends the stream with `{"error": {"message": "Request failed. Please retry."}}` and `data: [DONE]`, because Open WebUI would otherwise end that stream with `{"error": {"detail": …}}` and no `[DONE]`. A turn that fails into a card inside its answer text ends `stop`, as any answer does, and so do the five pre-job refusals, which leave as text and are ended by Open WebUI. A client that goes away cancels the model call and frees the request's slot as it did when the stream was a generator: the body closes `_standard_frames`, which closes `_stream`, and `_stream` cancels the job. A chat, a temporary chat, a channel and an internal Fusion member's own request are unchanged, and Open WebUI's middleware still gets every frame it reads from them; a request that does not stream is unchanged too, except that a program's Fusion answer is the bare answer on that leg as well.

A Stop at the end of a turn still publishes the terminal status, `response.completed` and `chat:completion(done=True)`, and still releases the request's `SessionLogger.logs` entry: nothing in the finalisation `finally` is skipped, and the shielded session-log write still completes behind the shield. Every await in the `finally` absorbs and, for a `CancelledError`, records: each one is guarded the way Open WebUI guards its own two shields, with `except (asyncio.CancelledError, Exception)`, so a cancellation delivered at any of them is absorbed there — the tail runs to its end, and a Stop that lands at the finalize artifact flush or the committed-row markers beside it still leaves the turn its terminal pair — and is remembered for re-raising afterwards. There is no count to keep in step with the code, which is the point: the rule is what stays true as awaits are added, and a tally of them goes stale at the next one. Naming what the block holds today is still worth it, because each entry is a place a Stop has been seen to land: the turn's own event-stream teardown, the plugin dispatch, the trailing-reasoning flush, the terminal `status`, the session-log segment, the replayed-reasoning cleanup, the Fusion embed await, the Fusion terminal synthesis, the Fusion answer output item, the final Fusion panel, the final artifact flush and marker append, the seeded-output capture, the terminal `response.completed` and the terminal `chat:completion`. The replayed-reasoning cleanup is the one that clears a turn's own reasoning rows, down to empty markers, once the next reply has replayed them, so it is guarded for the same reason as the publications beside it: a database that refuses the cleanup is a fault in a row the person will never see, not a fault in the answer they are reading, and it must not replace it. A cancellation absorbed this way leaves the closing frame intact: running to the end of the block is what reaches `SessionLogger.release`, so the turn still gives its session-log request back. A cancellation absorbed at either of the two *terminal* publications, at the cleanup or at the Fusion embed await, is not dropped: it is remembered and re-raised once the tail has run, so the turn still ends cancelled and a Stop is never reported to `pipe()` as a finished turn, which would clear the request failures the person never cleared. The Fusion embed await is the one place a Stop can arrive that the turn did not ask for and that raises nothing on its way through — the detached embed task swallows its own cancellation, so the await can return normally while the turn's own `cancelling()` counter is the only evidence — so it reads that counter as well as its own `except` arm. One site is a deliberate exception, and it is not a cancellation site at all: a *second* cancellation delivered inside the window still unwinds it, since the block runs as an ordinary `finally` rather than as a shielded task. This is scoped to a Stop that lands *inside* the finalisation window; a turn the body already recorded as cancelled is still published as incomplete, with no `response.completed` and no `chat:completion(done=True)`. **A turn that failed is published exactly as a completed one is.** A completed turn's reasoning sits above its answer, and a failed turn's now does too: each of the four error arms closes the turn's reasoning items before the card is joined onto the answer, so the closing `output` array and the live browser list both read `reasoning` then `message` on the failure path as on the success path. The `finally`'s flush is the backstop for the exits those four arms do not cover — a Stop and a hand-back — and on the paths they do cover it is a no-op, because a key already published is popped from the set it walks. The four error arms report the fault on a frame of their own, and that frame carries `done=False`: it is where the banner rides, and a card that closes the turn is a card whose finalisation work, output array and usage can no longer reach anybody. The `finally`'s own terminal is therefore the turn's single `chat:completion(done=True)` and its last frame, on the failure path as on the success path. The two guards that stay shut are deliberate: a cancelled turn is a Stop rather than a fault, and a hand-back turn publishes its own terminal when it re-runs, so a second one would insert a phantom message item.

## 4. What Open WebUI receives (emitters and event types)

The pipe emits Open WebUI-compatible events via the provided `event_emitter` callable.

**An emitter being attached does not mean there is a chat.** the metadata `chat_completion` assembles always carries the keys — `chat_id` defaulting to `''`, `session_id` popped from the form into its base dict, and `message_id` set from the message-ids entry on both the per-model fan-out and the direct path — and the `all(k in metadata ...)` guard in `generate_function_chat_completion` tests key *presence*, so a caller with no chat is given an emitter too. The truthiness rule on `chat_id`/`message_id` — the same one `get_event_emitter_and_caller`'s `metadata.get('chat_id') and metadata.get('message_id')` test uses — is what actually distinguishes a chat from an API caller; `__event_emitter__` is not a discriminator.

Common event types:

| Event type | Purpose |
| --- | --- |
| `chat:message` | Sets the visible assistant message to `content`, replacing what is there (whole-text snapshots). The pipe emits it on every turn **except a continuing non-channel one**: on a continuing turn this frame is the one that would replace the prefix the turn is continuing, so the card goes out as `chat:message:error` instead — except on a channel, where it has to be sent. A channel has no `chat:message` branch in `_make_channel_emitter` (`socket/main.py`), and its message is folded from the host's `output` array rather than from this frame, so `chat:message` is the only frame the pipe's own translator turns into an SSE chunk (`event_emitter.py`, into `middleware_message_delta`, which appends the part the buffer has not already accepted). Without it `output` lacks the card, and the terminal `chat:completion {done: True, output}` writes `get_output_text(output)` over the `Error: ...` that `chat:message:error` had just stored (`Messages.update_message_by_id` writes `message.content` absolutely). |
| `response.reasoning_summary_text.delta` | The pipe's own growth event for a published thinking box: carries only the tail the box has not been sent, at the box's own `output_index` and `item_id`, with `summary_index: 0`. Open WebUI's backend appends it into `item['summary'][summary_index]['text']` and its browser does `part.text = appendDelta(part.text ?? '', event.delta)`, so both reducers **append** it. It is not `response.reasoning_text.delta`, whose reducer writes `item['content']` — under that name the box's text silently relocates and the person loses their thinking. Because it is a tail, a growth step that crosses a **block boundary** may open with the boundary space described below — the reducer appends the space along with the text, which is why that space must be there. A close still ships the whole buffer as a `response.output_item.done`, which both reducers *replace* on. |
| `response.function_call_arguments.delta` / `.done` | The argument frames of a call handed back under the Open-WebUI passthrough, at the item's own `output_index`. The two reducers agree on both: Open WebUI's backend **appends** the delta into `output[output_index]['arguments']` (the `function_call_arguments` arm of `handle_responses_streaming_event` in `utils/response.py`) and **replaces** the whole value with the terminal frame's payload (the same reducer's done arm, `item['arguments'] = final_value`), and its browser does the same (`applyResponseStreamEvent`: the `.delta` arm appends, the `.done` arm replaces). The replace is why the frame carries the provider's whole terminal payload and not a tail. |
| `chat:message:delta` | Appends `content` to the visible assistant message. |
| `chat:completion` | Final frame that ends the request. A frame carrying `error` is **terminal whatever its own `done` says**, because the browser's `chatCompletionEventHandler` calls `handleOpenAIError` on any `error` and that sets `message.done` from the presence of `error` and never reads the frame's `done` (`chatCompletionEventHandler` hands every `error` to `handleOpenAIError`, which sets `message.done` itself); so a notice the turn is not over must not travel on it, and does not. A turn that has already published its card -- on a channel, or on a continuing turn -- emits no `error` on this frame at all. On any other turn a plain refusal (the open breaker, a failed start-up, a full queue, a failed setup) is delivered by this frame alone, as its `error` and its `content`; a templated card has already travelled as a `chat:message` snapshot, and this frame carries an `error` only for a reader that acts on failure: an automation run, which gets the card's text, and a realtime voice call, which gets one short fixed sentence (see [Error Handling & User Experience](error_handling_and_user_experience.md)). In a saved chat, a streamed reply that stopped at the tool-call limit carries the sentence `Tool-call limit reached (<cap> iterations).` as this frame's `error`, a bare string, which Open WebUI's streaming handler saves on the message as `error.content`, the way it saves its own tool-call limit. A streamed reply to a caller with no chat carries the sentence as answer text instead, because an OpenAI client raises on any streamed chunk that carries an `error`. A **non-terminal** refusal arm publishes no `chat:completion` at all — it rides `chat:message:error` (the row below). May include `usage` and normally includes `content` (even when empty). Published in exactly one place — the finalisation `finally` — and it is the last frame the turn publishes. An error arm's templated card publishes a frame of its own first, carrying the banner, and that frame carries `done=False`: the arm reports the fault, the `finally` ends the turn. On a **continuing** turn it carries no truthy `content`, because the browser assigns that field absolutely (`if (content && !output) message.content = content`) and a replacement write would overwrite the prefix the turn is continuing. That withholding also covers the two error funnels' raw `completion["content"] = shown` writes, which bypass `_emit_completion` and so bypass every guard in front of it. It is withheld on a second condition too: a turn that has **published an item of its own** — a thinking box, a tool card, a tool result, or a Fusion answer — carries no bare `content`, because the browser assigns `content` to `message.content` absolutely, and on a streamed leg the visible view is the `output` array Open WebUI has already folded from the pipe's `response.*` events, so a bare answer string is a second, competing copy of text the array already owns. `content` is withheld, not replaced: `output` stays Open WebUI's to fold, because its backend reducer replaces rather than folds (the generic done arm of `handle_responses_streaming_event` in `utils/response.py`) and its translator only forwards a `chat:completion` whose `content` is a `str`. The frame is still published: it is what carries `done` and `usage`, and with `content` absent the translator forwards it for its `usage` alone. On a turn that reported usage, that terminal frame is the turn's **only** `usage` record on the wire: no per-round frame carries one, because Open WebUI folds every payload it is given (the `merge_usage` fold in `streaming_chat_response_handler`'s chunk arm) and a second copy of the same figure would be a second charge for it. That usage block carries two things side by side: `input_tokens`, `output_tokens`, `total_tokens` and the cost keys are the turn's totals, while `prompt_tokens` and `completion_tokens` are the size of the last call the turn made, the pair a reader's client counts as the conversation's current size and its context compaction acts on. A round without token counts never displaces the counts of the last round that reported them, and a Fusion turn reports its synthesis call rather than the panel's sum. Note what that means for the record Open WebUI writes from it — a `{'usage': ...}` entry carrying no content at all, which is not a content write and must not be read as one. |
| `status` | Progress and warning messages displayed as status updates. Opened and closed within each attempt, so no line is left open across a retry. **Persisted**: on a saved chat the socket emitter appends each one to that message's `statusHistory` (`Chats.add_message_status_to_chat_by_id_and_message_id`), and the whole history is rendered behind a toggle, so a status is still there after a reload. The collapsed header shows only the newest entry, which is what a progress line wants; a notice that has to be read after the fact therefore travels on a status as well as on a toast. The **last** status a turn publishes is never left open either: `StatusHistory.svelte` renders `history.at(-1)` with no `done` prop of its own and `StatusItem.svelte` shimmers on `(done || status?.done) === false`, and Open WebUI appends to the history without ever revisiting an entry, so an unclosed newest entry animates in the live chat and in the reopened one. The artifact flush therefore runs *before* the terminal close rather than after it, so a database write is never in front of the person-visible terminal line and the notice it can emit cannot become the newest entry. The storage-failure notice carries `done: True` because it reports a terminal fact rather than progress — including on the failed path, where the close is gated on `(not error_occurred)` and so no close follows it at all. |
| `chat:message:error` | Carries `error.content`. Honoured by the **browser**, whose `chatEventHandler` `chat:message:error` arm stores `message.error` and leaves `message.content` alone, and by Open WebUI's **channel** emitter, which stores `Error: <content>` and closes the message. The socket emitter ignores it for *persistence* only — the frame is forwarded to the browser room, and the frontend's next save writes `message.error` with the history. A **continuing turn** is the case where this frame is the card's only delivery -- and for that reason, and for a channel, the following `chat:completion` carries no `error` key: this frame has already delivered the card in full, and a completion that says the response failed replaces it with the browser's generic prefix. A refusal the turn is not over for -- an attachment the pipe dropped, or a picture a tool returned that it would not forward -- does not ride this frame. The browser's close is not gated on the frame's `done` key in 0.12.3: the arm hands the error to `handleOpenAIError`, which stores it and marks the message done, so a notice sent here would fill the error area and close the reply while the model is still answering. It travels as a `status` event instead, shown when the answer's text starts and carried again on the turn's closing status. A card published ahead of the turn's own `chat:completion` carries no `done` key, the shape Open WebUI's own mid-turn failure helper uses (`emit_message_error` in `streaming_chat_response_handler` emits `chat:message:error` with no `done` on a failed tool-call continuation, a mid-stream response error, or the tool-call limit). That holds on every leg that publishes one, not only the plain-chat one: the **continuing** turn's card and the **channel** card are built by the same one call, so a `chat:message:error` on either carries no `done` key either, and the turn is finished by exactly one frame -- its own `chat:completion`. A terminal error on any leg is unchanged, byte for byte; the channel emitter's close is not gated at all (its `chat:message:error` and `chat:completion` arms). That is the host's behaviour, accepted rather than fixed, because no frame the pipe can send leaves a channel message open after one. On a channel the card it carries is reduced first: the account's own money — `required_cost`, `account_balance` — the requester's `session_id`, `user_id` and the text they wrote — `detail`, `sanitized_detail`, `reason`, `openrouter_message`, `upstream_message`, `upstream_type`, `moderation_reasons`, `flagged_excerpt`, `raw_body`, `metadata_json`, `provider_raw_json`, `body_excerpt` — render as though empty, because every member of the room reads what this frame writes. That list is the **templated** arm's placeholders. The plain arm carries no template and is reduced in its own two places: the file-error messages that reach it never hold the requester's reference to begin with, and the emission chokepoint reduces whatever plain message does reach a channel through `loggable_link()` and `_data_url_log_subject()`, so a `http(s)` reference arrives as scheme and host and a `data:` URL as its media type. `error_id`, the model, the provider, `openrouter_code` and `status_code` still render. A temporary chat's card is reduced by that frame's one key instead: its `session_id` alone is withheld, because Open WebUI mints a temporary chat's id from the browser's socket id and that value is a live session handle rather than a shared audience; `user_id` still renders there, and `error_id` is the only handle the reader and the operator share. A saved chat's card is not reduced. |
| `source` | Normalized citation payloads (documents/metadata/source). The pipe's sources are Open WebUI's own five citing tools (`fetch_url`, `view_file`, `view_knowledge_file`, `query_knowledge_files`, `query_chat_files`), the provider's own `url_citation` annotations, and OpenRouter Fusion item sources. No other tool's result produces one, under any name, alias or origin, on any endpoint or mode: the result still reaches the model and its card, but a link in it is never published as a source — except when Open WebUI's extractor cannot be imported, where the harvester fallback publishes what it finds in the result text of those same five tools. The pipe stores no citation itself: Open WebUI's socket emitter appends each `source` frame to the saved message's `sources`. Those five tools' sources are withheld as well when the model's `Citations` capability is off, which is the same verdict Open WebUI reaches from the same model row; withholding the frame is what leaves the chat row alone. The provider's own annotations and Fusion item sources are not gated by that box, because Open WebUI does not gate its own. A citation type the pipe cannot render (anything ending in `_citation` other than `url_citation`) produces no source, and produces a `notification` naming the type exactly once per turn: on `/responses`, and on `/chat/completions` and on a fallback hop too. |
| `notification` | Toast-style notifications (info/success/warning/error). **Not persisted**: Open WebUI's socket emitter has no `notification` branch, so a toast is shown once and is gone after the page is reloaded — which is why a notice about something that already happened is also published as a `status` (the refused-write notice on a turn that lost rows is the one that does both). |

**An answer emitted only on `output_text.done` is invisible to a Direct Connection.** The pipe's Fusion read of the engine's `response.output_text.done` sits inside the `fusion_armed` block, and `_resolve_fusion_live_enabled` is `ENABLE_OPENROUTER_FUSION and is_fusion and not is_direct` — so a Direct Connection has `fusion_armed = False` and that read never runs. An answer stage must therefore emit its text as a `response.output_text.delta` as well, which is the leg the non-`fusion_armed` path does read: a close-only answer reaches a Direct caller as `""` on both the streaming and the non-streaming setting, because the `done`-adoption is inside the same block either way. The companion fact on the non-streamed `/responses` leg is the same shape: an item whose `output_text` parts are all whitespace publishes **no** `response.output_text.delta` at all, because there is nothing on that leg for it to say, and its `output_item.done` frame goes out exactly as before — that frame is not inside the guard the empty text is dropped at.

Which of these survives a page reload depends entirely on whether the turn is streaming, and the two legs do not share a channel. A third distinction runs across both: a `channel:` chat id is emitted to a **different emitter** entirely, one with its own, much smaller set of types. Open WebUI's channel emitter honours exactly `chat:completion`, `response:completion`, `files`/`chat:message:files` and `chat:message:error` — it has **no `chat:message` branch at all**, and it stores `data['content'] or get_output_text(output)`. So a card on a channel travels as a `chat:message:error` frame, which Open WebUI stores prefixed with `Error: `, followed by a closing `chat:completion` whose `content` is the whole message, which overwrites that prefix with clean text. That is why a channel turn that **failed** is granted the whole message on its terminal even though it had already published output items of its own: a channel folds its message from the `output` array, and the array on a failed turn does not carry the card — so publishing it alone leaves the channel showing the answer and not the fault. A channel turn that did not fail keeps the array and no bare content, because there the array is the whole record. Because the channel leg *replaces* the message rather than appending, the closing frame's content must be the entire message: a `chat:completion` with empty content on a channel writes `''` over everything the channel already held. Because a channel card is reduced and a saved-chat card is not, the same template reads differently in the two places: on a channel a line whose placeholder came out empty is omitted, so a card that exists only to show the session id or the flagged excerpt is simply not there. Not every channel request reaches the stream translation at all — the pipe's five pre-job refusals (a tripped circuit breaker, warmup, a missing request queue, a full queue's 503, and a pre-enqueue failure) return before the job is handed to the dispatch worker and emit straight to the channel emitter, so they take the replace-not-append leg whatever the streaming setting is. The sixth refusal is not pre-job: one the pipe sheds at the **dequeue site**, with the job already out of the queue and parked on a `MAX_CONCURRENT_REQUESTS` permit, publishes from the stream generator's own `finally`. That publication used to run with both of the turn's own contextvars already reset — the generator's body does not start until its first `__anext__`, which is after `pipe()` and `_pipe_impl` have both returned — so it took the replace-not-append leg too, and a channel was left with a bare terminal frame and no `chat:message:error` to badge. The generator's body now sets `OWUI_CHAT_ID` and `CONTINUED_REPLY` for its own turn and resets them as it ends, so a streamed dequeue-site refusal on a channel publishes the card shape (`chat:message`, `chat:message:error`, `chat:completion`) like every other refusal, and a continuing turn keeps the answer it was continuing.

**Streaming on.** The pipe does not hand its events to Open WebUI as events at all. It returns an async generator (a request with no chat gets a `StreamingResponse` of the chunks the paragraph on a caller with no chat above lists), and its own translator converts each event into the OpenAI-style stream chunks Open WebUI's streaming handler accumulates. Both `chat:message` and `chat:message:delta` become answer text there — a delta contributes its `content` verbatim, and a `chat:message` contributes only the part of its snapshot that has not been sent yet, so alternating the two on one turn does not duplicate text. The subtraction is against **what the buffer accepted**, so a frame the drop valve refused is never recorded as sent and the next snapshot re-derives it rather than assuming it arrived. That subtraction is conditional: the translator forwards the remainder **only when the snapshot starts with everything already sent**, and forwards nothing at all when it does not. So a card — an error card, a notice, any block the pipe appends to an answer in progress — goes out as a snapshot of the **whole message**, the answer so far joined to the card, never as the card alone. A bare card is a non-prefix write the moment any text has streamed, and it is now forwarded as a **full replacement** rather than dropped: the user sees it. Three things make that true, and are worth stating separately because the record and the queue disagree about it. First, the replacement is delivered *through an accumulator that appends* — Open WebUI calls `append_output_text` and there is no replace path — so a snapshot sharing no prefix with what was sent renders as `already_sent + content`, not as `content`. That is the same outcome `join_answer_and_card` produces for the common case and is strictly better than showing nothing. Second, the asymmetry after a `fusion_open` reset: the *record* is correct, because the accumulator it is built from was reset with `assistant_message`, while the *queue* is not, so a user comparing a reloaded turn to the live one can see different text. Third, the same split on a bounded bridge queue: a delta whose put timed out is not counted as sent, so the translator's subtraction still names the span the browser never received and the next `chat:message` snapshot re-sends it. A **provider refusal** — the sentence the model wrote instead of, or alongside, an answer — is forwarded as answer text on **both** transports: joined to the answer with a blank line when the same message carried content, and delivered as the whole reply when it did not, on both the streamed and the non-streamed leg. Three shapes are read, on either endpoint: a `refusal` sibling of `content` in a `/chat/completions` message or delta; a `{"type": "refusal", "refusal": <str>}` part in a `/responses` output message, whether the body is non-streamed or the part rides in a terminal `response.output_item.done`; and the `response.refusal.delta` / `response.refusal.done` pair on a streamed `/responses` call, the deltas accumulated and published on the `.done`. Every combination of endpoint and stream setting hands the streaming loop a refusal as a refusal, not as answer text: as the pair, or a message item with a refusal part, on a streamed `/responses` call, and as a `response.refusal.done` event, which the pipe sends after the answer text that came with it, on a streamed or non-streamed `/chat/completions` call and on a non-streamed `/responses` call. The loop sets it apart in one place, so one rule holds on all four: a blank line before the refusal when text came before it, a blank line between it and the text the model writes directly after it, and a line of its own first when it opens a Continue, so the refusal stays a paragraph of its own. A blank or whitespace-only refusal is not a refusal and contributes nothing, so it never suppresses a sibling `output_text`. The one exception is a housekeeping task request, where Open WebUI takes the return value as the title, the summary or the query rather than as an answer a person reads: there the non-streamed leg fails the attempt on a non-blank `refusal` instead of folding it in, so the refusal never becomes that value. It is forwarded on every exit the turn can take, including a stream cut off before its terminal frame, and the blank-line join is the same one on each. It travels on `delta.content` because that is the only channel Open WebUI reads. When one turn carries both streamed `delta.refusal` fragments and a closing `message.refusal`, the closing whole is what is shown and the fragments are dropped: the two are never concatenated, and the whole is never a truncation of them, whichever order the two channels arrive in. A closing chunk that carries answer text on `choices[0].message.content` rather than on `delta.content` is read when no `delta.content` has been seen for the turn, and is not read again once one has: both the `str` and the list-of-`text`-parts spellings are accepted, matching what the pipe's own non-streamed leg already reads off a message. The tie-break is the same in both directions and for both fields: whichever channel carries a field first is the one the reader gets, and the other is suppressed for the rest of the turn, so a `delta.content` or `delta.refusal` fragment arriving after a `message.content` or a `message.refusal` is not written on top of it, whichever of the two the provider sends first. Without it, a reply whose answer lived only on `message` produced no `output_text` delta at all. Where a card instead reaches Open WebUI as an event rather than through the translator, a bare one is worse than invisible — `chat:message` assigns there, per the table above, so it would overwrite the partial answer rather than follow it. `chat:completion` is **not** answer text: a frame carrying `content` is forwarded out of band — the browser assigns that field, so it replaces the whole live message rather than appending to it, which is why a refused terminal frame costs the reader a real write and why the next snapshot has to carry the tail it was meant to restore — one carrying `error` or `usage` is forwarded as an error or usage record, and a frame carrying none of the three is dropped. The drop valve applies to incremental output only; the items that report or end a turn — this frame's `content`, `error` and `usage` records alongside the failure item and the terminator — are put past it. So a whole answer sent only as `chat:completion` reaches the reader as its own absolute assignment, whatever the deltas it also sent were dropped for.

Each stretch of answer text streams into a message item that the pipe publishes first, under its own id: a `response.output_item.added` event carrying the empty message, then the text. Open WebUI puts a chunk's text into the reply's last item when that item is a message, so the text lands in the pipe's item, and Open WebUI names that item when it passes the text on to the browser. Every item the pipe publishes - a message, a tool card, a thinking box, a Fusion answer - also carries `output_index`, its place in the reply, and on a hand-back turn under the passthrough the pipe publishes the call itself as a `response.output_item.added`, so that numbering is the call's own position and there is no competing writer: Open WebUI skips its own append when the `call_id` is already in `output` (the streamed call arm and the after-stream call resolution of `streaming_chat_response_handler`, both keyed through `output_by_call_id`), which is why one item is published rather than two. A thinking box is published in the position the provider gave it, so it precedes a tool call the model emitted after the thought and follows one it emitted before, and the closing record is in the provider's own order. That holds on the failure path too: the four error arms close the turn's reasoning items before the card is joined, and the `finally`'s flush remains the backstop for every other exit. That holds for a server-tool card too, and it takes two mechanisms to hold, because the two reasoning forms register differently. A card for a tool OpenRouter ran itself is published the moment that tool's `output_item.done` closes, in the middle of the round, while a card for the model's own call is published after the round ends; reasoning the provider streamed as text has no `output_item.done` of its own, so `response.output_item.added` closes its window and publishes nothing and the box would reach no publication site until the round boundary -- below the card the provider listed it above. The card path therefore publishes the open boxes itself first. A thought closed by its own `output_item.done` instead registers as *deferred* against a count of the model's own call cards -- the model cards already emitted when the round began, plus the calls the provider listed before this thought -- and that count is what the flush inside `_emit_tool_start` reads: a card for a server tool is not a model call, so it does not move it, and the box waits for the call it was written about. A box the provider listed in the closed output **after** a call — the delta-only form, which has no `output_item.done` of its own to register at the round boundary — is deferred against that call's **turn-wide** index, which is the same scale the flush reads; the two registrations therefore differ by the round's offset, so a second tool round's box waits for its own call rather than for a call of the first. Card against card is a separate matter and is not settled by either mechanism: a server card is always published before a model call's card in the same round, whatever order the provider listed them in, so a round the provider listed `call, server-tool` reads server card first. The re-arm that times a re-published box from its own round is `_rearm_reasoning_window`, and it runs on the three append paths: a key that has already published and comes back in a later round is opened again by the `reasoning_summary_text.done` that carries it, by the delta, or by the snapshot, so the block is measured from that round rather than from wherever the first one opened. On the chat-completions path a streamed `reasoning.summary` is folded into the text its own key already holds — keyed by `index` then `id`, exactly as Open WebUI's `merge_streamed_reasoning_details` does — so a fragmenting provider keeps every fragment instead of overwriting all but the last, and the cumulative `reasoning_summary_text.done` it sends carries all of them. What a path adds depends first on the kind of event it carries, and a piece is never dropped for looking like the start or the end of the text so far. A fragment (a `.delta` or `.added` event) is added whole, so a piece that is a single character, or that repeats the start or the end of the text so far, reaches the box like any other; the one exception is a fragment that is longer than the text shown and begins with all of it (when that text is more than blank), which is read as the provider restating the text so far and adds just its tail. A whole text (a `.done` event, the reasoning item at the end of the stream) is added whole when its key has shown nothing, adds just the tail when it begins with the text its key shows, and adds nothing otherwise, so the repeat of text that was streamed adds nothing however the provider joined its parts, and thinking that arrives only as a whole text is shown as the model wrote it: a `reasoning_summary_text.done` keeps its own bold titles in the box, and the title-and-text form it is given is for the status line alone. A key that comes back in a later round is judged against that round's own text: its first whole text is added unless it is exactly what an earlier round, or all the earlier rounds together, showed, and a whole text that restates everything shown so far adds only its tail. On the chat-completions path a chunk can carry the same fragment twice, as `delta.reasoning` and as a `reasoning.text` or `reasoning.summary` detail of that chunk (OpenAI models send their summary this way); the reader forwards it once, as a `response.reasoning_text.delta`, and keeps the detail for the closing item and the stored record, so the box, the stored item and a program with no chat each hold it once. A summary detail that no `reasoning` field repeats still goes on as a cumulative `reasoning_summary_text.done`, and the closing `message` of a streamed reply and a reply that is not streamed follow the same rule. A piece of `reasoning` that is only whitespace, such as the blank line between two paragraphs, is kept once the stream has delivered reasoning text, because the model wrote it; before any text it is ignored, since it could not make a box. In the `status` and `both` settings the status line is fed from the text the box would receive: each piece reaches the throttle once, which puts out a line when a piece ends a sentence or a line, when 160 characters are waiting, when 12 are waiting and either no line has gone out yet or 0.75 seconds have passed since the last one, and when a reasoning event closes; and a `reasoning_summary_text.done` also sets the line to its title and text. A whole text that repeats what was streamed adds nothing, so the throttle is no longer fed a second copy of the thinking at a `.done` event or at the closing item; the line a `reasoning_summary_text.done` sets for itself, with the summary's title and text, is separate and unchanged. A summary the provider sends only as `reasoning.summary` details has no piece to feed the throttle, so the line follows its cumulative `reasoning_summary_text.done` events instead, one line per fragment, and in `status` the closing reasoning item adds the whole summary as one more line, because no box holds it. A key that arrives again in a *later* round is that round's own thinking and is published as a second box, not merged into the first: every tool round re-sends the previous round's reasoning item, `id` included, because the pipe normalises only `function_call` and `function_call_output` and mints an id for nothing else, so the reuse is the pipe's own doing and the ordinary shape of a tool turn with a reasoning model. What distinguishes a new block from a continuation is the round, not the key: two fragments under one key in one round are one block, and a key that recurs in a later round is published again with a **fresh** id, because every reducer the pipe feeds — Open WebUI's backend, the browser, and the pipe's own recorded output — replaces by id, so a second box published under the reused id would overwrite the first in the record rather than stand beside it. The *first* publication keeps the provider's id, because that is the id Open WebUI merges the stored record by. The re-publication carries only the text the pipe has not already published: a snapshot that arrived whole leaves the buffer holding both rounds' text, and publishing that whole buffer would show round one's thinking twice. A round that re-sends exactly what it sent before adds no box, and a late fragment inside one round continues its own block rather than splitting it — it **grows** that block in place, at the same id and the same `output_index` the `added` carried, by two mechanisms that answer different questions. A **growth step** — a fragment arriving after the block was already published, with text beyond what was published — ships only its own tail, as a `response.reasoning_summary_text.delta` at that box's own index with `summary_index: 0`; both of Open WebUI's reducers append a `reasoning_summary_text` delta into `item['summary'][summary_index]['text']` (the backend reducer in `utils/response.py`, and the `.delta` arm of `applyResponseStreamEvent`), so the box the person is already reading grows and nothing moves. The **whole** buffer still goes into the record on every call, because the record is what a reload renders and what the provider is replayed, and a **close** — the end of the reasoning window, the end of the turn, or a growth step with nothing new to add — still ships a `response.output_item.done` carrying the whole buffer. A close does not ship a tail instead: both reducers *replace* on `output_item.done` (the `response.output_item.done` arms of `handle_responses_streaming_event` in `utils/response.py` and of `applyResponseStreamEvent`), so a tail-only `done` would erase everything before it. The round boundary also closes each key's timing window, and it is the `_rearm_reasoning_window` re-arm above, not that close, that re-dates a re-published block: the block is measured from its own round instead of from wherever the first one opened. The contract has a non-streamed half: with streaming off no deltas are published, and a stretch of answer text written before a later item is announced is split off and published as its own message item first, at the index the record gave it, so the two legs fold the same list - but only when that later item is a **tool card**. A thinking box that grows is published in place and does **not** close the message, so the record holds one message item across a growth, and `get_output_text`, which joins distinct items with a newline (`get_output_text` in `utils/misc.py`, and `getOutputText` in `structuredOutput.ts`), reads the answer back as the model wrote it. A message segment is announced even though its deltas are not. A reasoning item published from a round that carried several summary blocks carries all of them, in the order they arrived, one `summary_text` entry per block; a block whose identity the provider repeats merges into its own entry, adding only what it has not already been sent. Where blocks are *joined into one string* — the cumulative `reasoning_summary_text.done` snapshot, and the snapshot `_extract_reasoning_text_from_item` builds for itself — two adjacent non-whitespace neighbours are separated by **exactly one space**, and a block's own text is never rewritten to fit the join (an internal blank line or a double space survives; a block already ending in a space does not gain a second one). **All four producers must agree on that rule**: the two chat-completions arms, the non-streamed chat leg, and the item-extracting snapshot. The box compares a whole text with the text it already shows by prefix, so a producer that joins its blocks differently is not recognised as extending that text: the tail it carries is not shown, and the round is never shown twice. Without `output_index`, the browser puts an item before the last one it holds, which showed a card above the text written before it. A tool card is therefore published after any text the model wrote in the same round, which is where the tool-call resolution loop of `streaming_chat_response_handler` puts it, appending the call items after the stream's message: the round's text is one message item and the card follows it, so a round of text, a call and more text keeps the sentence whole rather than wedging a card between its halves. That is also why one turn's prose can be split across several message items, and it puts a constraint on where a segment may begin: Open WebUI's own `get_output_text` joins *distinct* message items with a `\n` and drops an item whose text is blank, so a segment that follows another must not open with a line break of its own, or the stored and replayed text grows a second break at every boundary the pipe made. The trim is applied at both places a segment is minted - the mid-turn flush and the closing record - and only where an earlier, non-blank message item exists, since a blank one is dropped by the join and supplies no break to double. On a streamed `/responses` call a card between two message items of one response splits the text at the same kind of boundary, and the line break the streaming loop puts between those two items is the one this trim takes off the later segment. The pipe's closing record reuses the same ids. That matters because Open WebUI's browser merges the record by id into what it already shows: a record under fresh ids showed the answer twice until Open WebUI's final update.

**Streaming off.** The translator does not exist; the events go straight to Open WebUI's emitter, which forwards them to the browser and writes only a subset to the database. For a saved chat that emitter is the socket emitter: `status`, `message`, `replace`, `embeds`, `files` and `source`/`citation` are written, and `chat:message`, `chat:message:delta` and `chat:completion` are **not** — the browser shows them and the database never hears about them. (For a `channel:` chat id it is the channel emitter instead, which writes only the four types listed above and replaces the message on every write, so the streaming setting does not describe what a channel does.) What Open WebUI stores on this leg is the value the pipe RETURNS. For a finished chat reply that is a completion carrying the reply's text and its structured record (`output`), which Open WebUI saves exactly as it saves a streamed reply's record, so tool cards and thinking survive a reload. That includes a reply that ended in an error: its record carries the error card with the rest, and the turn still published its terminal `chat:completion` and its `response.completed` before returning, so a failed turn's output array reaches the plugins and the dashboard exactly as a successful one's does. A reply that produced nothing but text comes back as that text, error card included. An empty return also fails the outer guard in Open WebUI's `non_streaming_chat_response_handler`, `not continuing and choices and (content or response_output or tool_calls)`, and the `chat:completion` frame, the message save, the outlet filters and the title, tags and follow-up tasks all sit behind that one guard, so none of them runs: the turn reloads blank *and* no title is generated, because no assistant message was ever written. A non-streamed 200 from `/responses` that carries no `output` key, or an `output` that is `[]` or `null`, is refused before it can reach that guard: it costs the whole `TRANSIENT_RETRY_MAX_ATTEMPTS` budget and is then reported, so the person reads a card and can send the message again rather than an empty bubble. The connection-failure card covers the missing-key case; the empty and null ones say the model returned an empty answer, because the connection worked. A non-streamed `/responses` body is read the way Open WebUI reads the same body: the `output_text` parts of **one** `message` item are one value and are published with **no** separator between them, distinct items are separated by a single newline, and an item whose text is empty or all whitespace publishes no answer delta at all. The streaming loop puts that newline, in one place, so a streamed `/responses` call, whose message items arrive as events, separates them the same way: the text of a message item that comes after a finished message item of the same response starts on a new line unless the answer so far already ends with one. A `/chat/completions` reply is one message, so it has no second item to separate. A blank line therefore never appears between the parts of one value; the only blank line a reader sees inside a turn's text is the one between an answer and a refusal, which is a different thing and is described under **Streaming on.** above.

**An API caller's rejection is not stored at all.** A caller with no truthy `chat_id` **and** `message_id` has no chat to write a card into, so the rejection leaves the pipe as an HTTP error (the resolved upstream status on the status line and the same number in the body's `code`, and `502` on both when the pipe could not read an upstream status because the whole body was mangled) instead of as a return value — see [API callers with no chat](error_handling_and_user_experience.md#c-api-callers-with-no-chat-http-error-instead-of-a-card). A **streamed** chatless caller cannot take an HTTP error at all: Open WebUI returns a pipe's non-2xx inside a `StreamingResponse` that carries no `status_code`, so a status built there would arrive as a bodyless `200`. That leg takes the same envelope as a terminal in-band frame instead — a `chat:completion` whose `data.error` is the error object, which the middleware emitter puts on the queue as `{"error": {...}}` and which ends the stream in place of the card. The gate is the `chat_id`/`message_id` pair, both absent or both empty, with two legs held back from it: a **chat**, which keeps the card because a person is reading; and an **internal Fusion member**, which carries a `chat_id` and no `message_id` and would otherwise have its panel card replaced by a frame the collector ignores. A streamed caller on an Anthropic Messages mount takes the frame like any other: Open WebUI's converter for those mounts reads a `data:` frame that carries `error` and answers with an Anthropic `error` event. What those mounts cannot carry is the HTTP error, because the converter reads only `data:` lines, so a request there that did not ask for a stream keeps its card. With no chat there, a **refusal** the emitter would have carried is folded into the returned value instead: it joins the answer, so the `200` that this leg answers with says what the transform declined to send. A **mangled body** — a 200 whose body is not a decodable JSON object — takes the same escape, and it takes it on every leg, including the Fusion internal-divert leg, which runs before the streaming loop rather than inside it, and the **image** leg, where it now escapes for a chatless caller too. On that path the `chat:message` and `chat:completion` frames are **not** emitted either, only `status`: the escape returns before the emitter that would have sent them runs, because there is nothing to show and nowhere to put it. A caller with no chat does not receive that `status` either, so the stream it reads on this leg is the error frame alone. The turn reaches plugins exactly as a chat's does, recording `"failed"` once — on an internal-Fusion turn too, where a member's own escape is a stage of that turn rather than a turn of its own, so it reaches this hook not at all and the one report is the turn's: the escape dispatches `dispatch_on_generation_complete(…, "failed")` itself before it returns, and that dispatch marks the request id, so the backstop in `pipe.py` — a fallback for the turns no primary reached — stands down rather than closing the same turn a second time with `"ok"` derived from a job future that resolved cleanly. The video leg is the one exception to the dispatch half: its escape builds the same envelope and returns it without dispatching, because the video adapter never dispatches `dispatch_on_generation_complete` at all — a plugin hears nothing about a video request finishing or failing, on any path. The **image** leg is a second exception to the dispatch half, and it needs its own spelling out so a future reader does not "fix" it by adding a second dispatch: there the failure arms settle and dispatch `"failed"` themselves, through the image adapter's own `_settle`, *before* the escape is built. The dispatch therefore happens exactly once either way — once whether the turn ends in an envelope or in a card — and adding a dispatch to the escape would double-book the generation.

The rule that covers both legs: **an answer must be both shown and returned.** Showing it satisfies the live view on either leg; returning it satisfies persistence with streaming off and costs nothing with streaming on, where the return value is discarded. A card that is only emitted is a card the user loses on reload; a card that is only returned is a card that appears late. A **continuing turn** is the case where the card deliberately does not go inline at all: it is published as `chat:message:error` and lives in the error area, so what the person is looking at stays what they had.

Notes:
- Answer text streams as `chat:message:delta` frames, and the turn ends with a `chat:completion` frame. The whole-message `chat:message` snapshot is the channel for cards, not for incremental text. On a **streamed** continuing turn the closing frame carries no truthy `content` and no `output`: the browser assigns `content` absolutely, so a frame carrying this generation's text alone would shorten the message below the prefix the turn is continuing. The same withholding applies to the per-round frame that fires after every round that reports usage — a tool round or not — and the two frames now share the same three terms: a turn that has published an item of its own — a thinking box, a tool card, a tool result, or a Fusion answer — carries no bare `content`, because the browser assigns it to `message.content` absolutely, and the visible view on a streamed leg is the `output` array Open WebUI has already folded from the pipe's `response.*` events, which already owns that text. The withholding is position-relative rather than turn-relative: the frame that fires before the turn's first item still carries its text, so a turn that publishes no item of its own keeps the answer text it would have published, and the pipe's own open message item does not count as one. The same withholding applies to the **card** on a continuing turn, and to the `chat:message` snapshot that would otherwise carry it: a failed continuation publishes the card as `chat:message:error` rather than as replacing content, so the bubble keeps the prefix and the card goes to the error area under the message. `done` still rides those frames, and the live merged array the person sees on a continuing turn is the `output` list Open WebUI's own `streaming_chat_response_handler` folds, not the pipe's. With streaming off there is no such assignment to fear and no `chat:message` to carry the text, so the closing frame does carry the answer: that frame is the only settle a non-streamed turn gets. A `chat:completion` omits `usage` entirely when nothing was reported, so a reader never has to tell an absent cost from `{}`. **The per-round frame never carries `usage` at all.** Open WebUI folds every `usage` payload that arrives on a streamed reply additively — `merge_usage` over `USAGE_SUMMABLE_KEYS` (both in `utils/response.py`), applied in `streaming_chat_response_handler`'s chunk arm and again at its `response.*` metadata arm — and writes the folded total to the chat row in the handler's turn-closing `Chats.upsert_message_to_chat_by_id_and_message_id`, so a per-round frame carrying the running accumulator had each round's cumulative figure summed in once more: a one-round turn stored twice its cost and a three-round turn stored six times it. The turn's total rides the terminal frame once, which is where Open WebUI's own providers put it and the only shape that folds back to the turn's true counters. The live bubble does not notice the difference — the `usage` arm of `chatCompletionEventHandler` assigns a frame's `usage` and the last frame wins — and neither does the pipe's own dashboard, which assigns rather than sums (`SessionTracker.update_usage` in `session_tracker.py`); the stored row is where it lands. That stays true of the frame itself -- the marker never reaches it -- but the *closing record* and the snapshot the turn files are two other places it is read, and on those a turn that lost its counters to a cut after the `finish_reason` carries `incomplete_usage` inside `usage`, so the row written from it is distinguishable from the one written for a turn that reported nothing.
- A generated image is put to the SSRF address gate on the way OUT as well as on the way in. A picture that arrives as an `http(s)` address is published into the reply only when the host resolves to a public address — including in the three cases where the pipe ends up holding the provider's own link rather than a stored copy (a chat with nowhere to store a file, a failed download, a store that did not succeed), and including a check that reaches no verdict inside its budget, which is a refusal. A refused one is left out and reported as an `Images: skipped N (...)` status; a public link the pipe merely failed to download is still published.
- An answer produced whole rather than streamed — a generated image, a finished video, a help panel, an error card — must go out as `chat:message` or `chat:message:delta`, never as `chat:completion` alone, and must also be the return value. Which of the two depends on two independent things — what has already been sent, and whether the turn is a continuation. On what has been sent: a `chat:message:delta` carries exactly the text appended to the running message and nothing that preceded it, while a `chat:message` carries the running message and the new block together. On the continuation, which is a separate term and not a consequence of the first: a continuing turn publishes neither, and the block travels as `chat:message:error` instead, because both of the first two assign `message.content` absolutely and a continuing turn already holds text that must survive. Neither may carry the new block by itself — a delta that repeats the answer duplicates it on screen, and a snapshot that omits the answer is a non-prefix write, which the translator forwards as a full replacement rather than dropping.
- With streaming off, the wrapper the non-streaming path puts around the emitter suppresses `chat:message` and `chat:message:delta` outright: the answer's text is travelling home in the record, which is what the turn returns whenever any output item was published. Its text is not published as deltas, though the message *item* that carries it still is, whenever a later item would otherwise be announced ahead of it. Anything raised inside the response loop that is only emitted as a card is therefore invisible on that leg; it has to come back as the return value to be seen at all.
- When `SHOW_FINAL_USAGE_STATUS` resolves True — the reader's own copy where they have set it, otherwise the site default an administrator chooses — the pipe formats a final status description using usage/cost/tokens when present, and writes the cost segment only for a charge above zero. The same description carries an `Answered by <model>` segment, right after the time, when a round's final response names a model other than the one the pipe dispatched: every round that completes records the `model` of its terminal `response.completed`, which `/responses` returns as it is and the two `/chat/completions` adapters copy from the chunks or the body into the event they build, and a turn lists the distinct models in order of first use. A retry and the `/responses` to `/chat/completions` fallback leave only the round that completed, and a Fusion turn (the live panel, the internal engine, or a panel member's own request) shows none.
- The notices for anything the pipe left out of the request - `Images: skipped N (…)`, `Files: skipped N (…)` and `Images: dropped N over the limit of M.` - and for a tool's picture the pipe would not forward are collected while the turn runs. A streamed chat reply shows them as a status entry with no `done` key when its first answer text goes out, after any status the turn has already sent (the status line animates an entry whose `done` is exactly false, and a turn the person stops sends no closing line to end that); the entry goes out again when answer text resumes after another status or after the turn has collected a further notice, once for each start or resume and not once per delta. They are carried on the last status line of the turn, before its closing `chat:completion` frame. When the turn ends in an answer they ride the final status line, joined to it after a ` | `; with `SHOW_FINAL_USAGE_STATUS` off they follow it as a status of their own. When the turn ends in an error message they are a status of their own after the error's status (the loop emits them once the error is published, and an error card published by the orchestrator, an image generation or a video generation emits them straight after its own status), and a generated image or video that is delivered carries them in its own closing status. A turn that ends before any answer text, a reply with streaming off and a Fusion turn with the live panel carry them on the closing status alone; a Fusion panel member's own request and an API caller with no chat emit no status line for them. A turn the person stops emits none of the closing copies either, except a video turn: its job keeps running after Stop and closes its status line, notice included, when it finishes; a copy already shown while the answer was written stays in the status history. None of them is an error frame; a channel shows no status, and on a reply from a text model an API caller with no chat gets the sentence at the end of its answer text instead. With streaming off the pipe appends it to the returned body. With streaming on it sends it as one last `chat:message:delta`, joined to the answer after a blank line the same way, after the answer and any error card and before the closing `chat:completion` frame, which a caller with no chat does not receive, so the sentence is the last text chunk of its stream. It is the whole text when the model wrote none. A reply that goes back to the caller as a call to a tool the caller sent carries none on either leg, and a chat, a channel and a Fusion panel member's own request get none as answer text.

### 4.1 The stored output array, and who owns it

Every finished chat reply hands Open WebUI an `output` array, which it saves against the assistant message: a
streamed reply publishes it in its closing `response.completed` event, and a non-streamed one returns it with its
text. It holds the reasoning items, the tool cards that were shown, and the messages.

The **Fusion** answer item is no exception to what an item in this array carries: in a chat, its `content[].output_text` is the
answer inside its `<details type="fusion_answer">` wrapper, exactly as the string the turn returns is. The wrapper is
applied to `assistant_message` *before* the item is built, recorded and emitted, so the recorded copy, the emitted copy
and the terminal array agree — which is what makes the array usable as the whole story on a **channel**, where there
is no `Chats` row behind the message and `__channel_emitter__` renders `get_output_text(output)` in place of `content`.
A record taken before the wrapper was applied is a stale copy, and on a channel it is the only copy there is.

Two turns leave the wrapper off, so that the item, the recorded copy and the returned string carry the bare answer. A turn
answered on a realtime voice call is the first: Open WebUI's realtime voice call passes a message item's text to the
voice model as it stands, and the markup would reach it. The same turn writes no hidden marker lines either (see
[History Reconstruction & Context Replay](history_reconstruction_and_context.md), section 4.2). A turn for a caller with
no chat (`_is_chatless_caller`: a program that calls Open WebUI's API with no `chat_id` or no `message_id`) is the
second, streamed or not. The wrapper folds the answer under a chat's live panel, which such a program has no use for;
Open WebUI's own models hand a program their plain text, because its middleware builds a reply only for a request with
a chat; and a program that sends the reply back as history would otherwise carry the markup into every later prompt.
A streaming program gets that answer as the one chunk described in the paragraph on a caller with no chat under
*Middleware streaming bridge queue*, and a program that does not stream gets it as `message.content`.

The `response.output_item.done` ladder resolves an item by its `type`, and an item type it has no arm for is not
rendered at all — it falls through with the round's debug `title` still set, which only a `logger.debug` reads. The
types it names are `message`, `reasoning`, `function_call`, `web_search_call`, `file_search_call`,
`image_generation_call`, the seven `openrouter:*` server-tool types, and the four shell types — `shell_call`,
`local_shell_call`, `shell_call_output`, `local_shell_call_output`. The shell family is keyed on the item's
`call_id` rather than its `id`, because a `ShellCallItem` and its `ShellCallOutputItem` share a `call_id` and differ
in `id`, and keying on `id` opens a second card for one command; the card names the commands the item asked to run and
carries the item's own stdout or stderr as its result. A type the ladder does not name is still stored verbatim and
replayed, so a provider-native round the pipe has no card for is remembered rather than lost.

A chat turn that is nothing but tool calls stores `[function_call]` and no message item at all, on both the
streaming and the non-streaming leg. A message item carrying no text, no annotations and no reasoning details
is kept in exactly one case: the blank **round divider** that separates one tool round from the next, and it is
a deliberate marker rather than a phantom the model wrote. Nothing displays it - Open WebUI's renderer ignores
blank messages when it draws (`buildOutputDisplayItems` guards on `text.trim()`) - and nothing is sent to the
provider for it either; what it does is hold the round boundary in the stored turn. The host writes this
exact item itself: Open WebUI's own middleware tool loop appends the same blank assistant message to the
output array after a round of tool calls and saves the turn with it, trimming only the trailing one when a
continuation starts, so a chat Open WebUI drove itself carries the divider at every round boundary and a
chat the pipe drove carries the same shape. Open WebUI's own `convert_output_to_messages`
(`utils/misc.py`) is what reads the rounds back out of this array, and it reads them
from there: with the divider stored, a two-round turn converts to
`assistant(tool_calls=[a]) | tool | assistant(tool_calls=[b]) | tool`; without it, both calls batch into a
single assistant message and the turn comes back as `assistant(tool_calls=[a, b]) | tool | tool`, which is
not the turn that ran. The mechanism is the flush guard in `convert_output_to_messages` — `item_type != 'function_call_output'`, so the
pending tool outputs flush on any item that is not itself a call output — and its `if text:`, which then drops the divider's blank
text. So the item is a boundary marker Open WebUI drops from the text it sends and depends on for the shape of
the text it does send, and a turn with only one tool round has no boundary to record, so it stores none. A
message item that *does* carry something is kept even when its text is empty, because that is where the turn's
`reasoning_details` live: a turn whose only content is OpenRouter's structured `reasoning_details`
keeps its message item for exactly that reason. The turn's citations do not live there; they live on the
message record beside it. A turn that carries only plain `reasoning` or
`reasoning_content` - the shape DeepSeek-, Qwen- and Kimi-style OpenRouter models emit rather than the
structured form - keeps no message item, and that reasoning is still published and stored, as its own reasoning
item rather than as message text. The annotations that a web search round's cited pages are attributed from are collected
off every round of the turn, in round order, not off the round the loop ended on.

The pipe writes no `annotations` onto the message record. It collects them from **both** places a provider puts
one: the `output_text` content part and the message item, parts first, because that is where each endpoint puts
them (`/responses` carries them on the part, the pipe's own `/chat/completions` leg on the item) and parts-first
is the order the live path already renders them in. The list is the provider's own: no type filter, no url
normalisation, no rewrite into the pipe's `source`/`document`/`metadata` citation shape. A history message that
carries an `annotations` list anyway, one an earlier version stored or one a client sent, has it attached to the
replayed assistant item. Open WebUI 0.12 neither writes nor reads the field — `MESSAGE_REPLAY_KEYS` excludes
it, and its own citation emitter reads the annotation off a response event's content part rather than off the
record.

Its messages carry the ids of
the items their text streamed into, so Open WebUI's browser replaces the items it already shows rather than
adding a second copy. Everything later turns replay comes from there, so who writes it matters.

Open WebUI saves a reply's citations, Fusion panel and tool-loop-limit note from the events the pipe publishes,
so the pipe writes none of them into the message record. A citation is a `source` frame that Open WebUI's socket
emitter appends to the saved message's `sources`. The live Fusion panel is one `embeds` frame per attempt, and a
retried attempt re-sends it with `replace: true` after dropping the earlier Fusion panel from the message's
embeds. The closing panel, built from the finished deliberation, is a second `embeds` frame with
`replace: true`, sent after the pipe has read the message's embeds and dropped the Fusion panels from them, so the message
ends with one Fusion panel and keeps the other embeds it held. In a saved chat, a tool-loop-limit note rides the closing
`chat:completion` frame as its `error`, the bare sentence `Tool-call limit reached (<cap> iterations).`, which Open
WebUI's streaming handler saves on the message and the browser shows as the message's error. A reply that is
returned whole rather than streamed, a reply with no emitter and a streamed reply to a caller with no chat carry the
note at the end of the answer text, as a content delta on a stream. The
replayable reasoning of a reply is kept in the pipe's own artifact rows, and the pipe writes no
`reasoning_details` onto the message. Open WebUI's upsert is a whole-document rewrite: it takes the chat row
(the `with_for_update` get in `Chats._chat_transaction`), mutates `chat['history']` and commits, so a write of
the pipe's own would cost a row lock and a rewrite of the whole chat after every answer.

The one chat-message write the pipe makes is the `error` mark of an automation reply it refuses before the model
is called: a tripped circuit breaker, a failed warmup, a missing or full request queue, or a failed request
setup. Open WebUI's chat route stores an error when the pipe's answer is an HTTP error response or raises, and
an automation reply, which always carries a chat id and a message id, is refused with the card's text, which is
neither. Open WebUI's automation runner reads the stored message's `error` to decide whether a run failed, so
the refusal's reason is written to the message as `{"error": {"content": <reason>}}` and nothing else.

Every other chat-store call the streaming loop makes is a read: the seeded-output capture and the Fusion panel's embed merge. Each
reads the one message row by its primary key, `ChatMessages.get_message_by_id` on the `<chat id>-<message id>` key, and checks that the row
belongs to the chat. It takes Open WebUI's `Chats.get_message_by_id_and_message_id` instead when Open WebUI has no
`chat_message` table or method, when the row is missing (a message the frontend saved straight into the chat has none yet) or when the
row read fails; that getter loads every message of the chat, so a large chat pays for it on those reads only. The reads
and the write are all skipped when the chat id has no row — a `temporary:`, `local:` or `channel:` chat. Open
WebUI's own middleware pre-checks chat ids the same way, at two dozen sites, rather than relying on its store to
drop what cannot be written. On a chat that *does* have a row, the write also requires that the caller may write
it: owner, admin, or the write access Open WebUI grants. The grant
is the write access of Open WebUI's own `Chats.get_accessible_chat_by_id` with `permission="write"`, the check
Open WebUI applies when it accepts the turn, before the row is written. The pipe cannot assume the route in
front of it checked: a chat id is caller-supplied and unvalidated all the way down, and a task route builds its
metadata from the request's own `chat_id` without an ownership check anywhere on the path. There is one
implementation of the predicate (`chat_write_allowed`, in `storage/owui_files.py`, reached through its logging
wrapper `caller_may_write_chat`), applied inside the one accessor the write goes through, `_chats_upsert`, which
takes the caller's user id as a required argument: no shape of the write reaches the store without a user to
check. A refused write is silent to the person and latched in the operator's log. The reads are gated on
linkability only. The chat's owner for the Zero Data Retention check is read from the owner column alone, and
takes the whole-chat read when that select fails. A chat row that records no owner has no owner either way,
which the Zero Data Retention check treats as an owner it cannot determine.

Open WebUI's bookkeeping depends on what it is doing, and the pipe has to match it:

- **Continuing a message.** Open WebUI sets the message's existing stored output aside at stream start and puts
  it back in front afterwards. It already holds those items, so the pipe must publish only this generation's:
  republishing would store the earlier generation twice - and with it every hidden marker it carries, so the
  replayed reasoning would double as well. The pipe recognises this by the message id the frontend sends only
  when continuing. The same turn also withholds the bare `content` from its `chat:completion` frames, for the
  separate reason above: the stored array is Open WebUI's to fold, and the live message is the one the absolute
  assignment would shorten. The merged array a continuing person watches being built is the `output` list Open WebUI's own
  `streaming_chat_response_handler` folds, not the pipe's. The message's `sources` accumulate across generations: Open WebUI's emitter
  appends each `source` frame a Continue publishes to the citations the message already holds, so the message
  ends the second generation holding both generations' citations in order.
  See [History Reconstruction & Context Replay](history_reconstruction_and_context.md), section 6.2.
- **Its own tool loop.** Each time Open WebUI runs a round and calls the pipe back, it sets the turn's output
  aside the same way, but sends no such id. The pipe therefore reads the stored output on that path - and finds
  nothing, because Open WebUI writes a message's output once, when the message finishes. Measured on a live
  server: across a two-round turn the row carried no output at all until the moment it was marked done.

So the read exists for one caller only: a client posting to the completions endpoint directly with the id of a
message that already holds output. Open WebUI's own chat never produces that state, and for the direct caller
republishing is the right answer, because nothing else will put those items back.

One consequence is worth stating plainly, because it is a deliberate choice rather than an oversight: a tool call
left genuinely unfinished — one whose function never returned, whether the turn ended on an error or a dropped
connection — on a message that is then continued, stays unfinished in Open WebUI's saved copy instead of
being repaired, so Open WebUI does not replay it. A tool call left running only by Stop is not in that class: a Stop
now runs the finalisation to its end, so the turn still publishes its terminal record and
still releases its session-log request. The events that would repair
an unfinished call cannot reach storage -
`response.output_item.added` matches ids only within the new output, and `response.output_item.done` replaces by
position - so an attempt to heal it would duplicate or corrupt the saved copy instead. A thinking box's growth is not one of those events and is not affected: it travels as a `response.reasoning_summary_text.delta`, which both reducers append, so healing a box is not a position-sensitive write. The model still learns the
round's calls before the first one still running, in the order the model emitted them: Open WebUI saves their cards as finished and hands them back, and
with cards off the pipe's own copy does (not in a temporary chat, where the pipe keeps no copy), since the pipe writes
a round's calls when the round starts and each result when its call returns, that is as the calls are answered, so a
refused call's answer is written ahead of the results that were still to come (see
[History Reconstruction & Context Replay](history_reconstruction_and_context.md), section 5.4).

## 5. Streaming errors and how they surface

OpenRouter sends `200 OK` as soon as a provider accepts a request, so a failure after that point arrives inside the answer. On both `/responses` and `/chat/completions`, the pipe detects such error payloads (for example `response.failed`, or a chunk carrying an `error` block) and converts them into an `OpenRouterAPIError`. The guard runs for every event it takes off the queue, whichever of the two consumer loops fetched it, so a failure is surfaced and counted the same way in both. A non-streaming reply whose body carries an `error`, at the top level or in its first choice, is treated the same way.

That is what separates a provider-sent `error` **reason** that carries a payload from the same reason without one. On `/chat/completions` a chunk that both carries an `error` object and names `finish_reason: "error"` is the documented mid-stream failure, and the error-object guard runs first: it raises, charges the breaker once and shows the error card, and the reason is never consulted. The same `finish_reason: "error"` **without** an error object is not a failure at all — the provider said the turn ended, so the turn ends (see the set of ending reasons in section 2): the record is delivered unmarked, the breaker is not charged, and a tool call the model had already named is published rather than discarded. Adding `"error"` to the terminal set therefore does not weaken the in-band path; the two are decided by different inputs, and only one of them is present on each shape.

That error is then handled by the same OpenRouter template system described in:
- [Error Handling & User Experience](error_handling_and_user_experience.md)

This keeps user-facing failures consistent between streaming and non-streaming calls. A retryable in-band failure — one carrying a `429` or a `5xx` — is retried before anything has streamed, on the same terms as a `429` or `5xx` status at the HTTP boundary, honouring `Retry-After` up to the `TRANSIENT_RETRY_MAX_WAIT_SECONDS` cap; once content has been shown it is rendered immediately, as below. Each failed request counts once toward the user's request breaker (see [Concurrency Controls & Resilience](concurrency_controls_and_resilience.md)), however many attempts it took; errors in housekeeping tasks such as title generation are not counted.

An attempt that has already published something Open WebUI keeps is not retried: the reader keeps the thinking box or the tool card they were watching and the error card is appended below it. Only an attempt that has published nothing is handed back for a retry. A streaming caller with no chat has no thinking box to publish to. For it the first chunk of reasoning the stream accepts does not count as something published, so the loop still hands a failure up and it reaches the caller as the `error` frame after the reasoning chunks; but the orchestrator does not send the request again, because the caller would get the thinking a second time. What counts as published is what has been handed to the consumer, not what merely arrived: the `delta.role` frame every `/chat/completions` stream opens with, and the `response.created` event every `/responses` stream opens with, carry nothing the reader can see, so they leave the attempt still retryable. The third is a `delta.tool_calls` entry that carries neither a function name nor any argument text: it has opened a call nobody can see yet, so it leaves the attempt retryable too, while an entry that names a tool or writes any of its arguments closes the window on its own. This is why the in-band check on `/responses` lives in the **producer**: the consumer that would have to know whether anything was published runs outside the retryer, so moving the check back to the consumer silently disables the retry for every in-band failure.

A stream can also stop before its final event, without an error. If nothing the reader can see has arrived, the attempt counts as a failed call and is retried, up to `TRANSIENT_RETRY_MAX_ATTEMPTS` extra tries; if every attempt comes back empty, the request ends with `CONNECTION_ERROR_TEMPLATE`, or with the `STREAM_INTERRUPTED_TEMPLATE` notice if answer text arrived earlier in the same reply or the model had already named the tool it was calling. If anything the reader can see has arrived, whatever text has streamed (possibly none) is kept, the `STREAM_INTERRUPTED_TEMPLATE` notice is appended, and the call counts as a failed one. A frame that arrived but delivered nothing does not close the retry window, so a drop in the first second of a reply is retried rather than costing the whole reply. The same is true of a stream that closes cleanly on both readers: a proxy that truncates and closes without a `finish_reason` has published nothing, so on `/chat/completions` it is re-POSTed on the same budget and ends in the connection notice rather than the interruption one. The two readers do not draw the completion line in the same place: on `/chat/completions` a flushed end-of-stream marker is enough to end the turn, while on `/responses` a terminal event is required, so a `/responses` stream that ends with the marker but no `response.completed` still counts as a failed call. A terminal event that arrives carrying no `response` object -- the key absent, an empty object, or something that is not an object -- counts the same way, because there is nothing in it to read as the run's record.

A connection that drops or times out is handled identically on both transports, and the request counts once against the breaker, however many attempts it took. If this happens before any answer text has arrived, a streaming attempt that has sent nothing the pipe could read is retried; if the request still fails, it ends with `NETWORK_TIMEOUT_TEMPLATE` for a timeout or `CONNECTION_ERROR_TEMPLATE` for a failed connection. If it happens after answer text has arrived, that text is kept and the `STREAM_INTERRUPTED_TEMPLATE` notice follows it. A stream that ends with `response.incomplete` is a finished answer, not an interruption: its usage is reported as usual, and a warning says the answer ended incomplete.
A retryable rejection hands the turn back to the orchestrator, which re-runs it on the same turn and the same emitter, and Open WebUI never discards what it has already accumulated. So a turn that has published an **accumulated** frame - `chat:message:delta`, `chat:tool_calls`, or a `response.function_call_arguments.delta` - ends in a card rather than being retried: the reader never sees two attempts of one turn spliced together. What counts as published is the emitter's own verdict on the frame, not the fact that the pipe sent it: a frame the drop valve discarded has not been published and leaves the turn retryable, because what the next whole-message snapshot re-sends is exactly the span the reader missed. Every accumulated frame the loop publishes on the streaming leg goes out through one helper that reads that verdict, so there is a single place where a frame crosses the barrier rather than one per publisher. The barrier stops the *second* publish, not the first, so the abandoned tool call stays in Open WebUI's list at `status: in_progress` with half its arguments and the turn ends on a card; that is no duplication, not no residue. `status` and `source` frames are additive rather than accumulated, and both are persisted, so a retried turn can carry two attempts' notices in its status history. That is also why each attempt opens and closes its own status: Open WebUI appends to the history and never marks a prior entry done, so an attempt that hands the turn back without closing the line it opened would leave a shimmering notice with no successor to close it. For `chat:tool_calls`, the gate is the streaming leg, because there the pipe's own translator rewrites it into the OpenAI chunk Open WebUI folds; with streaming off the wrapper suppresses only `chat:message` and `chat:message:delta`, and `chat:tool_calls` leaves the pipe and is discarded by Open WebUI's own socket emitter (the `__event_emitter__` in `socket/main.py`'s `get_event_emitter`, and the `chatEventHandler` switch in `Chat.svelte`) - the string occurs nowhere in Open WebUI - so a hand-back on that leg costs nothing. `chat:message:delta` is gated the same way: with streaming off the wrapper drops it before it leaves the pipe, so it ends the turn on the streaming leg only, and a hand-back on the non-streaming leg costs a retry that would have succeeded. The rewrite itself is not covered by the test suite: were `chat:tool_calls` ever given the reshape-or-drop treatment `chat:message:delta` already has, the same splice could return with the tests still green. The passthrough leg is not that hop: it publishes the frames Open WebUI reduces itself, and the tests for it fold the host's own compiled reducer rather than a transcription of it. See [Plugin System](plugin_system.md) for the three rejections that are retried.

**What the backend log records.** On `/responses` and `/chat/completions`, streamed or not, for a chat and for a caller with no chat, three kinds of failure are logged once each, where the failure is reported. An error reply from OpenRouter, including one reported inside a `200` reply, is one `WARNING` with no traceback. A response body that is not an OpenRouter response (a proxy's error page) is one `ERROR` line with no traceback. A fault in the pipe's code, and a connection that drops, are each one `ERROR` with one traceback, beside the `ERROR` line that carries the card's error id. The `/responses` reader that takes the events off the wire logs none of them itself: it arms the credential pause for a rejected credential and passes the exception on. An attempt the pipe retries, or hands to `/chat/completions` (`AUTO_FALLBACK_CHAT_COMPLETIONS`), therefore leaves no `WARNING` or `ERROR` of its own. Picture generation through OpenRouter's image API and video generation log the refusals and the unreadable bodies of the request that starts the picture or the video the same way: an error reply from OpenRouter is one `WARNING` with no traceback and a response body that is not an OpenRouter response is one `ERROR` line with no traceback, for a chat and for a caller with no chat, whether or not the caller asked for a stream. A status reply for a running video job that is not an OpenRouter response is one `ERROR` line that carries the job id.

## 6. Nagle-inspired adaptive delta coalescing

### Problem

During heavy reasoning turns, OWUI's `serialize_output()` is called on every event emitted by the pipe. Each call rebuilds the entire HTML output — an O(n*m) cost. When the model streams hundreds of small reasoning deltas per second, OWUI's UI freezes because it cannot keep up with per-delta processing.

### Solution: RFC 896 Nagle algorithm adapted for async generators

The pipe uses a Nagle-inspired coalescing strategy (implemented in `streaming/nagle_coalescer.py`) that **self-regulates based on consumer backpressure** — no tuning parameters needed for the core mechanism.

The key insight from RFC 896: *”inhibit the sending of new TCP segments when previously transmitted data remains unacknowledged.”* In our async generator pipeline:

| TCP concept | Async generator equivalent |
|---|---|
| Send segment | `yield` event to consumer |
| ACK received | Consumer calls `__anext__()` — generator resumes |
| Data in flight | Generator suspended at `yield` |
| New data arrives | Events arriving in queue from OpenRouter |

**Behavior:** When OWUI is fast, events pass through with minimal latency (near 1:1). When OWUI is slow (processing a previous yield), events accumulate in the queue and are delivered in larger batches — automatically reducing the number of expensive `serialize_output()` calls.

### Multi-buffer architecture

Two independent buffers prevent reasoning floods from blocking text output:

```text
events  -->  [bounded micro-drain]  -->  process in order
                                       |
                    +------------------+------------------+
                    v                  v                  v
              text_buffer       reasoning_buffer    yield immediately
              (output_text)     (reasoning_text,    (non-batchable:
                                 reasoning)          tool calls,
                                                     structural, etc.)
```

Flush triggers:
- **Type boundary** — text delta while reasoning has content (or vice versa): force flush
- **Routing boundary** — a text delta whose `item_id`, `output_index` or `content_index` differs from the buffer's: force flush, and the batch carries the keys of the delta that opened it. The reasoning arm guards on `item_id` alone, because a reasoning block legitimately moves between content parts and summary parts inside one item, and a wider key set there would fragment every multi-part reasoning block. `summary_index` is not a text key: it belongs to `reasoning_summary_text.delta`, which is not batched.
- **Non-batchable event** — flush both buffers, pass event through
- **Idle timeout** — `STREAMING_IDLE_FLUSH_MS` flushes buffers when producer pauses
- **End of micro-drain cycle** — flush if buffered chars >= `STREAMING_NAGLE_MIN_FLUSH_CHARS` (drain is bounded to 32 events and only runs while no output has been produced yet)
- **End of stream** — unconditional final flush
- **Error mid-stream** — the buffered tail is force-flushed before the streaming error is re-raised

### Coverage: both streaming paths

- **Responses API path** (`responses_adapter.py`): Uses `NagleCoalescer` directly in the existing consumer loop (already has `event_queue` with workers).
- **Chat Completions API path** (`chat_completions_adapter.py`): Wrapped with `nagle_coalesce_stream()` which creates a lightweight pump task, an unbounded queue, and a bounded micro-drain. The queue is the fourth buffer of §3: it is watched by `STREAMING_EVENT_QUEUE_WARN_SIZE` and bounded by nothing.

On both paths the tail the coalescer is holding is delivered to the consumer when a
streaming error arrives, on the Responses path by the consumer loop's own force flush
before the re-raise and on the Chat Completions path by the final flush in
`nagle_coalesce_stream()`.

### Valves

| Valve | Default | Effect |
|---|---|---|
| `STREAMING_DELTA_CHAR_LIMIT` | 256 | **Toggle.** `> 0` enables Nagle coalescing. `0` (with `IDLE_FLUSH_MS=0`) = passthrough mode (1:1 emission). |
| `STREAMING_IDLE_FLUSH_MS` | 30 | Idle timeout (ms). Ensures buffered content is delivered even when the producer pauses. |
| `STREAMING_NAGLE_MIN_FLUSH_CHARS` | 3 | Minimum chars before end-of-cycle flush. `3` smooths single-char jitter. `1` = pure Nagle. `5-10` = aggressive event reduction. |

**Operator note:** The default `NAGLE_MIN_FLUSH_CHARS=3` eliminates single-character jitter in low-backpressure phases while keeping latency imperceptible (the 30ms idle timeout guarantees delivery). Set to `1` for pure Nagle, or `5-10` if OWUI still struggles during heavy reasoning.

## 7. Tuning checklist

- Raise `SSE_WORKERS_PER_REQUEST` only after measuring something it can change. It no longer parallelises the JSON parse: that happens once in the producer, and a worker runs from its dequeue to its enqueue without an `await`, so extra workers neither speed decoding nor add throughput here. What more of them cost is one extra queue crossing per frame and one task per concurrent stream; what they can buy is a little drain overlap while the producer is awaiting the network.
- Bound memory or latency: keep `STREAMING_CHUNK_QUEUE_MAXSIZE=0` and `STREAMING_EVENT_QUEUE_MAXSIZE=0` unless you have a measured reason to bound them. As long as the consumer keeps draining, a bound trades a larger buffer for a slower drain, not for a stream that stops early. This is about the two queues and nothing else: the producer's pre-first-output buffer is a third buffer that these two settings do not reach, and it is uncapped; on `/chat/completions` the pump queue is a fourth, reached by no size valve at all (§3).
- Improve observability: set `STREAMING_EVENT_QUEUE_WARN_SIZE` low enough to signal stress early, but high enough to avoid constant warnings. It covers `/responses` and `/chat/completions` replies alike; non-streaming replies buffer through neither queue.
- Reduce UI freeze during heavy reasoning: increase `STREAMING_NAGLE_MIN_FLUSH_CHARS` (2-5 for moderate reduction, 5-10 for aggressive).
- Disable all coalescing (debugging): set `STREAMING_DELTA_CHAR_LIMIT=0` and `STREAMING_IDLE_FLUSH_MS=0` for passthrough mode.

All related defaults and ranges are listed in [Valves & Configuration Atlas](valves_and_configuration_atlas.md).
