# Multimodal Intake Pipeline

This document describes how the pipe transforms Open WebUI message content into OpenRouter-compatible multimodal blocks (images, files, audio, and video), including storage behavior, SSRF protections, HTTPS-only defaults for remote URLs, and size limits.

If you are specifically trying to **bypass Open WebUI RAG for chat uploads** and forward uploads as **native OpenRouter attachments**, see:
- [OpenRouter Direct Uploads (bypass OWUI RAG)](openrouter_direct_uploads.md)

## What this pipeline does

For user messages that include multimodal content, the pipe normalizes content blocks into the structures it sends to OpenRouter.

At a high level:

- **Images** are converted to Responses-style `input_image` blocks. A `data:` URL within `BASE64_MAX_SIZE_MB` has its media type resolved from its own bytes, the declaration deciding only when those bytes identify nothing, a payload that settles on a non-image type being refused and reported and a type the bytes disagree with being rewritten; otherwise it is sent with its declared type and parameters preserved, its payload de-wrapped and validated once, and one over it is not sent, the picture being skipped and the person told in a status on their latest message; a remote image is downloaded, and its media type is resolved from the bytes before it is sent inline (or forwarded as its link when it cannot be downloaded, unless the pipe's own address check refused the host), a downloaded payload that settles on a non-image type is not inlined but refused and reported,  a link the pipe cannot resolve into an image is refused on the inline leg with an `Images: skipped N (not a link the pipe can resolve into an image)` status, a picture the pipe refuses to forward is dropped and reported rather than sent, and an Open WebUI file URL is read with the requester's access, typed from its bytes by the same gate rather than by the type its storage row recorded, and sent inline. A picture the pipe reaches through a content block of a type it does not recognise is measured the same way and refused the same way, and it is named in the `Files:` status rather than the `Images:` one, because it takes the unrecognised-block route rather than a picture converter's. A picture on a model that cannot see pictures is dropped before any converter runs: one status names it on the person's latest message, and a turn whose only content was that picture carries the attachment note naming it rather than the empty-message line.
- **Files** are converted to Responses-style `input_file` blocks and forwarded as they came: a `data:` URL or inline payload goes out unchanged, as does a link in `file_data` or `file_url` whose host resolves to a public address, and the pipe never downloads a file link. A `file_url` with no scheme at all -- a bare path, a relative reference, a `host/path` written without a `scheme://` -- is a link in name only, and is gated and refused on its scheme rather than forwarded; raw base64 in `file_data` and a `data:` URL in either field are inline payloads and are never checked. Inline data over `BASE64_MAX_SIZE_MB` is the exception: it is not sent, and the person sees "Files: skipped …" for their latest message, as with pictures. A block carrying none of `file_id`, `file_data` or `file_url` — a filename on its own, or an empty `file` part — is also skipped rather than forwarded, because Open WebUI's own converter drops such a part (for the keys it recognises) and because a part that declares only its type is accepted by OpenRouter and then unreadable. The pipe keeps a `file_url` that Open WebUI's converter drops, which is a deliberate superset of its rule. An Open WebUI file URL -- any URL whose path names `/api/v1/files/<id>`, in any scheme, host, letter-case, userinfo, query or encoding -- is read with the requester's access and sent inline, and one that names the path but yields no readable id is refused with a message the person sees rather than sent to the provider as a link. A block may carry both shapes at once: a provider-side `file_id` (`file-…`, an identifier the provider already holds, so there is nothing for the pipe to read or to authorise) beside a `file_url` or `file_data` that names Open WebUI storage. The `file-` id shields such a block only when the block names no reference of its own; one that does is resolved from local storage with the requester's access, or refused, exactly as the block beside no id at all would be. A `file-` id on its own — with no reference beside it — still goes out as it arrived, unpriced and unauthorised, because there is nothing here to resolve, nobody to authorise and nothing the pipe could read. The name is the one field on this block a caller chooses as free text, and it is forwarded with any hidden marker line the pipe recognises removed from it, because the pipe's own framing is line-based and a name carrying one would let the caller write the framing of a turn they do not own; a name that is nothing but marker lines loses the field and the block goes out on its `file_id` alone.
- **Audio** is converted to Responses-style `input_audio` blocks and must be **base64/data URL** (remote URLs are rejected). A clip the pipe refuses — a remote URL, a data URL that is not audio, a payload that is not base64, a block with no audio at all, or one over `BASE64_MAX_SIZE_MB` — is dropped from the turn and reported to the person in a status on their latest message, never replaced with a payload-less `input_audio` block. On a turn with no chat to write a status into — an API caller with no truthy `chat_id` **or** no truthy `message_id`, asking for `stream: false` — the same sentence is carried in the returned body's `choices[0].message.content` instead, joined after the answer; the turn is still a `200`, because a clip that was declined did not fail the answer.
- **Video** is passed as `input_video` blocks, with `video_url` a bare string, on a turn that resolves to `/responses`; a turn that resolves to `/chat/completions` keeps the Chat Completions-style `video_url` block, whose `video_url` is an object. The two shapes are not interchangeable, and each endpoint is sent the one it reads. The context budget rates both spellings identically, so the choice between them is a wire-shape change only and never a cost change: a turn that resolves to one endpoint pays for its clip exactly as the same turn resolved to the other. Videos are **not** downloaded or re-hosted by the pipe. At ingress all three video spellings a caller can send — `video_url`, `input_video` or `video` — are validated identically to `video_url` itself, by the same cleartext gate, the same SSRF address check and the same refusal of an Open WebUI file URL. On the conversion leg the check is not the same three things: the pipe downloads nothing there, so there is no address to resolve and the SSRF address check does not re-run. What is re-checked there is the transport (the same cleartext gate), the scheme, the same refusal of an Open WebUI file URL, and the inline size bound. (`video` is the Chat Completions spelling; `_rewrite_video_blocks_for_responses` rewrites only `video_url` and `input_video`, and only for the `/responses` leg.) The address checks share the request-wide budget with the picture ones, so a turn carrying many video links is bounded by that budget rather than by one lookup per link, and a link written more than once in the three spellings is resolved once and every occurrence of it takes that one verdict. That budget is spent by address checks alone: it is not charged to the time this turn's stored artefacts took to load, nor to the time a remote picture's download took. A video link whose check reached no verdict at all — a resolver that never answered, or a check the budget could no longer start — is refused with its own wording, which says the check did not finish rather than describing it as a link to a private network address the gate never decided on. On the conversion leg `input_video` is judged on its payload, under the same rule as `video_url`: one carrying a link is sent as a `video_url` block, and one carrying nothing is named `a video clip carried no video data` on the turn rather than forwarded. And it is judged on resolvability as well as on payload, exactly as every other media block there is: a link naming an Open WebUI file path, a bare path on this server's disk or a `file:` URL is refused, on either spelling and on either arm, and named both on the turn the person sees and on the turn the model sees.

Nothing a person attaches is written to Open WebUI storage by the pipe, in any chat and by any request of a turn.

### What a user turn is allowed to carry

Every user turn the pipe dispatches carries at least one usable block. The pipe strips the wrappers itself, wherever they appear — including beside a usable sibling, which is the ordinary case, because a refused clip or recording usually arrives next to what the person typed about it. What is dropped:

- a text block that is **only whitespace**;
- a text block that is **only hidden marker lines** — the pipe's own transport markers, which carry no words for the model. A block mixing prose with a marker keeps the prose and loses the marker; a block that is nothing but markers is a block with nothing in it, and is judged on what is left after the marker lines are removed rather than on the raw string, which is non-empty. This holds on both the `/responses` and the `/chat/completions` leg, and on the chat leg it holds the same way for a caller that hands the converter a Responses-shaped `input` directly. A user turn whose blocks are all of this shape takes `[The user sent an empty message.]` on the `/chat/completions` leg exactly as the same turn spelled as a string, a blank string or a whitespace block already does, rather than putting the pipe's own markers back in front of the provider;
- an `input_file` with no `file_id`, `file_data` or `file_url`;
- a media block whose wrapper is present but whose payload is not — an `input_image` with neither a usable `url` nor a `file_id`, an `image_url` whose `url` is `""`, an `input_audio` whose `data` is `""` inside a non-empty `{ "data": …, "format": … }` wrapper, a `video_url` whose `url` is `""`; a `file_id` is honoured, and an `input_image` that carries one is converted to the `file` block the endpoint reads rather than dropped;
- a media block a converter produced and then refused — a cleartext `http://` link, a link naming an Open WebUI file path, a scheme the provider cannot dial, a private-network address, an over-size `data:` payload, or a conversion that raised — which none forwards, and which is dropped on the same terms, with the same reason string, when the converter itself produced the payload-less form. The private-network-address clause belongs to ingress alone: the conversion leg forwards a link for the provider to fetch and downloads nothing, so it has no address to check.

A picture the selected model cannot see is not a fifth shape: its block is well formed and carries a payload, and the gate drops it before any converter runs, so what it is reported by is the vision status rather than a payload test.

A `content` which is one block dict rather than a list of them is read as that one block on the same terms, so the two spellings of a block decide the same thing: sent, refused and named, or dropped as a payload-less wrapper, whichever way the caller wrote it. A dict carrying a block and its own `text` or `content` sends both, the text first and the block after it. A dict naming no type the transformer knows is read for its `text`/`content` as before, which is how stored history and a filter's own output spell a text turn.

Where the block came from decides who reports it. A **source-derived** shape is one that arrived carrying no payload: the pipe drops it and says so on the same turn, in the `Images:` or `Files:` status line, whether or not the turn also carried text. A **converter-produced** shape is one this pipe built and then refused; it is dropped the same way, with nothing forwarded in its place, and the report is the error card the arm itself emitted, because a converter refusal is a fact the arm has already said and adding a `Files:` status for it would say that one *attachment* twice. "Twice" is counted per attachment, not per sentence: two attachments refused for the same reason are two entries, both reported, and the count is 2. A carded refusal is **recorded** as well as reported: the card is the report the person reads, and the recording is what the placeholder reads when the turn carried nothing else. An arm that emits no card — a conversion that raised — is reported the other way, in the same aggregated `Files:` status a source-derived shape gets: nothing anywhere else names that recording, so nothing anywhere else would.

The media cases are decided on the **payload**, not on the wrapper. `{"url": ""}` and `{"data": "", "format": "mp3"}` are non-empty objects, so a plain truthiness test passes exactly the blocks being dropped; the payload itself is what has to be there. This is also why the empty `data`/`url` wrapper is not a thing Open WebUI produces and the pipe does not forward it as one. On the live arm a payload-less media block beside real text is **dropped**, not forwarded: the status says "skipped" for a source-derived refusal, and where a converter emitted its own card, or the vision gate emitted its one status, nothing at all is added — the status is the report and the note is the record, so neither is duplicated — and in neither case is anything the pipe called skipped or refused put in front of the provider.

The conversion leg — the derivation that rewrites a Responses `input` array into Chat Completions messages — names a block it removes on the turn, after the blocks that survived: one `[An attached item was not sent: …]` note appended to whatever the turn still carries, the same wording the emptied turn takes, and the same refusal additionally raised to the person as one `Images: skipped N (<reason>).` status through the channel every other leg uses, so a picture cannot disappear off the reader's own turn in silence. Nothing is put in front of the provider, and a block carrying a payload is never named, whatever its spelling. What reaches the provider from that leg is what survived: a text block, a picture block, a clip block, a file block or an audio payload, in that order, and nothing else — an unknown block type is still passed through untouched, because preserving unknown fields is that arm's contract, unless it carries a link only this server can read, which is refused and named on both arms. The gate that removes a media block there is the converter's own, and it is one shared decision: both endpoints send the same verdict for the same value, so the two legs cannot drift apart on what a link is.

A whitespace text block beside a block that *is* usable is **kept**: only a wholly void turn is emptied. So a person who sends a real picture and a blank box gets both blocks, in the order they wrote them.

What an emptied turn carries instead depends on what was dropped:

- A turn that was **blank text with no attachment at all** carries `[The user sent an empty message.]`. It states the fact in the same bracketed register as the attachment note and tells the model nothing false.
- A turn that was **blank text beside a block that carried no payload**, or that was **only an attachment that could not be converted**, carries `[An attached item was not sent: <reason>.]` — one note for both. "Could not be converted" covers a malformed payload and an over-limit one alike: a 41 MB audio clip the pipe declined to send is a clip that could not be converted, not a turn that was empty. A person who attached something that did not go out did not send an empty message, whatever else was on the turn, so the two are no longer told apart. An image named by a `file_id` is carried and never given that note. Open WebUI's own empty-block rule (`strip_empty_content_blocks`, `utils/misc.py`) drops the blank text here and invents nothing; the note is this pipe adding what did not go out, in the register it already uses for exactly that.
- A turn whose void block was removed by the **conversion leg** while its text survived carries that same note **after** the blocks that survived, not in place of them. The third shape, on a different leg from the two above: the live arm reports a source-derived refusal by status, so on that leg a note would say the same fact twice. The conversion leg has no status, so the note is the only report there. One note per turn still holds, whatever emptied the turn.

A turn whose `content` is absent or `None` is not one of these: it carried no block to drop, so it is forwarded as an empty list, unchanged. `content: ""` is the third spelling of the same thing and is forwarded as an empty list too, which is why it is named separately from `content: []` below: a caller that sent an empty *block list* carried a block list, and on the live leg that turn takes the empty-message line, while an empty *string* carried nothing at all. The **replay** leg is the other half of that sentence and decides none of it: it hands back the caller's own spelling unchanged, so `content: []` stays `[]` and takes no empty-message line there (B378's operator decision 1(b)). The line belongs to the transformer, which owns it on both legs; the replay normaliser preserves a block list rather than inventing a turn, and a `content` *string* stays that string rather than being read as a missing block.

The line a turn carries in place of its content is a *statement to the model*, and the
pipe reads these turns back. The image adapter derives its prompt from the transformed
body, so a turn that carried nothing reads there as that literal sentence, and a turn whose only
content was an attachment that did not go out reads there as the attachment note. Neither is to
be taken for a prompt: the adapter refuses before sending any turn whose only user text is either
line, exactly as it does for a blank message, so a turn where the person said nothing is not sent
as a generation. The video adapter reads the raw body rather than the transformed
one, so it never sees the line and must not grow this guard: a refactor that unified the
two adapters would silently re-open the image case.

## Storage context resolution (uploads to Open WebUI)

This input path never writes to Open WebUI storage. Open WebUI already converts a saved chat's stored pictures back to base64 before each model call, so a copy the pipe made would only be read straight back. Copies an earlier release made of a person's attachments stay where they are: ordinary files owned by that person (or by the fallback account below), listed in their Files. Nothing reads them, and the pipe does not delete them.

The pipe stores only what a model generates, and for that it resolves a storage context `(request, user)`:

- If a real Open WebUI request/user context exists, the pipe uploads via Open WebUI’s file APIs.
- A plain mapping is not a usable context: Open WebUI hands a background-task or automation turn its user as a dict, which carries no `email`, `id` or `name` for Open WebUI to read an owner from. It takes the fallback arm exactly as a missing one does.
- If a user context is missing or is such a mapping (for example some automations), a picture a model generates — and a file a tool returned on that turn — is stored under a dedicated “storage owner” identity configured by:
  - `FALLBACK_STORAGE_EMAIL`
  - `FALLBACK_STORAGE_NAME`
  - `FALLBACK_STORAGE_ROLE`

  An account the pipe creates for that address is created with no linked identity, so it never appears in a SCIM listing or an OAuth merge of its own; with `OAUTH_MERGE_ACCOUNTS_BY_EMAIL` enabled, a login whose IdP asserts the same address still adopts it. The resolved account is memoised, but the memo is keyed on the email it was derived from: an unchanged email reuses the same account, and a changed one re-resolves on the next request that needs a storage owner.

If storage cannot be resolved (for example in tests or synthetic contexts), the pipe skips the upload.

## Reading Open WebUI files (storage gateway)

When the pipe needs to **read** an already-stored Open WebUI file (for example an `/api/v1/files/...` URL to inline as a `data:` URL, or an `input_file.file_id`), every read routes through a single backend-agnostic gateway: `OwuiFileGateway` in `storage/owui_files.py`.

For each read the gateway:

- **Authorizes** the requester against the file (owner, admin, or Open WebUI’s `has_access_to_file`), failing closed if access is denied — once per **request**, per file, against the requester of that request. That requester is the resolved user of the turn, and it is the identity on **every** read the pipe makes: a file link inlined as a `data:` URL, an `input_file.file_id` attachment, and a prior video read to extract a frame for a video turn ([frame plan](openrouter_video_intent_classifier.md)) alike. The pipe's storage service account is the identity for **writes** only — it owns what the pipe uploads — and never reaches a read authorisation, so a turn whose user could not be resolved reads no file at all. The verdict is carried for the rest of the request, so a body that leaves the pipe twice is authorised once. A second request is authorised again: one that re-sends the same body, and one by a different person, each reach Open WebUI afresh, so a grant revoked between two turns takes effect on the next turn. A denial is carried the same way as a grant, which is the safe direction to remember — a failing access check is caught and treated as a refusal, so a remembered refusal cannot become a grant. The carried verdict is keyed on the requester's resolved id, so a caller whose id the pipe could not resolve is not shared with any other such caller: it reaches Open WebUI afresh on every read rather than being handed the verdict recorded for a stranger, at the cost of one extra check on that rare turn.
- **Routes the read through Open WebUI’s `Storage` provider**, so it works on any backend — `local`, `s3`, `gcs`, or `azure` (this fixes [issue #46](https://github.com/rbb-dev/Open-WebUI-OpenRouter-pipe/issues/46), where cloud-backed files were previously unreadable). `FileModel.path` is treated as an opaque storage key; the local provider's read is a no-op (no remote download).
- **Size-gates** the content against `BASE64_MAX_SIZE_MB`.
- **Copies every real OWUI file read to a request-owned private temp** (regardless of provider) before any bytes are encoded, then cleans the temp up. A record's stored path is the file: its own extracted text — the `data["content"]` Open WebUI's RAG and speech-to-text passes write — is served only for a record with no stored path at all, which is the case Open WebUI's own `/files/{id}/content` route serves it in.
- **Resolves the same references the context budget prices.** The size index (`index_referenced_file_payloads`) and this gateway read one shared rule for which of a block's three keys names Open WebUI storage and which one of them wins, so a reference the gateway inlines is a reference the budget was charged for and a block neither resolves is charged nothing. The two are not two opinions about the same body: a block the index resolved for 4 MB and the gateway forwarded verbatim was bytes that travelled unpriced, and a block the gateway inlined for a request the index read nothing for was bytes that travelled uncharged.

For cloud/unknown backends, a file whose declared `meta['size']` is missing or invalid is **refused by default** to avoid an unbounded download. The global `ALLOW_UNKNOWN_SIZE_CLOUD_READS` Valve opts back in (the download is still capped by `BASE64_MAX_SIZE_MB`); it is a download-safety gate, not an authorization bypass. See [Valves & Configuration Atlas](valves_and_configuration_atlas.md) for its exact default and semantics.

## Images (`image_url` → `input_image`)

### Inputs accepted
- Open WebUI content blocks containing `type: "image_url"` with:
  - a nested object `{ "image_url": { "url": "..." } }`, or
  - a string `{ "image_url": "..." }`.
- Open WebUI's own native `type: "image"` blocks, `{ "type": "image", "url": "..." }`, are accepted and
  converted to the same `input_image` block, with a `detail` on the native block honoured. Open WebUI's
  live chat path does not write this shape into a message, but the chat-completions gateway forwards
  `messages` verbatim and third-party filters and pipes write it directly, so it arrives. Before this it
  was passed through unchanged and the literal string `image` reached the provider as a content type.
- A block of a type the transformer does not recognise is still passed through unchanged, with two exceptions. A `data:`-scheme string leaf inside it, at any depth and under any key, is measured against `BASE64_MAX_SIZE_MB` on the same terms a typed block's payload is, and a block carrying one over the limit is not sent — the turn reports it as `Files: skipped N (larger than the M-byte inline limit).`, the same sentence a typed inline file is refused with, and a turn whose only content was that block carries the `[An attached item was not sent: …]` note. The limit is per payload, not per block and not per request, so a block that breaches neither is forwarded byte for byte. And a block that carries a link only this server can read (an Open WebUI file path, a bare path on this server's disk, or a `file:` URL) is refused and named on **both** arms. That is the one case on which the two arms are made to agree, because the backstop sits in the shared replay guard every block passes rather than in either arm's readers.

### What is sent (important)

The pipe never writes an image the person attached to Open WebUI storage: not for a saved, channel or temporary chat, and not for any request of a turn (its first answer, a Regenerate, each further model answering it, a Continue, or Open WebUI's calls back after each round of tool calls). Every request sends the image as the message carries it:
- A **data URL** (`data:image/...;base64,...`) within `BASE64_MAX_SIZE_MB` has its media type resolved **from its own bytes** on this leg exactly as on the download and reuse legs, and the declaration only decides when the bytes identify nothing: a payload that settles on a non-image type is refused, with `Images: skipped N (not identifiable as an image).` on the turn that carried it, and the picture is not sent. The size check is applied first, so a payload refused for being too large is reported as too large and never as unidentifiable. A payload that settles on **`image/svg+xml`** is refused on that same sentence, and it is a ground of its own rather than a case of the type being unreadable: SVG *is* an image type, and Open WebUI's own `is_raster_image_content_type` declines to draw it at both places it turns a file into a model image block, so the pipe sends neither what its own interface would not draw nor what theirs would not. The rule keys on the **resolved** type, not on the declaration, and it is Open WebUI's function transcribed -- split on `;`, trimmed, lower-cased -- so `;charset`, `;BASE64` and an upper-case spelling are all answered identically on both sides. A type the bytes disagree with is rewritten, and that re-spell is the single exception to the verbatim forwarding described here; apart from it the URL is sent with its declared type and parameters preserved. One over the limit is not sent, the picture is skipped and the person sees `"Images: skipped N (…)."` on their latest message. Whitespace inside the payload is removed before sending, so an RFC 2045 line-wrapped body arrives at the provider as one line, and the payload is validated once, before it is sent: one that is not decodable as base64 — including a URL-safe-base64 payload, whose alphabet is not the one this data-URL form declares — is refused rather than forwarded, with the same `Images: skipped N (not decodable as base64)` status. A data URL carrying no payload at all — an empty body, or one that is only whitespace — is refused the same way, rather than forwarded as a header with nothing after it. The `;base64` marker is matched case-insensitively, as the data-URL standard requires, so `;BASE64,` is a spelling of the same thing and the URL is still forwarded with its own spelling intact. A token-free `data:` URL — the word `base64` in a payload, or a parameter that merely starts with those letters — is not base64 and is refused, in every spelling.
- A **remote URL** (`https://`) is downloaded (with retries/limits/SSRF protection) and its bytes are sent upstream as a `data:` URL; one that cannot be downloaded is forwarded as its link **unless the pipe's own address check refused the host**: a host that does not resolve, or resolves to a non-routable address, fails closed and is not sent, and the person sees `Images: skipped N (could not be fetched, so it was not sent).` On this leg that sentence is the completed refusal's -- the download is attempted first and the verdict is read after it -- so a check on a link that ran out of its budget is refused here as a picture left with no time rather than as a fetch that failed. A public link the pipe merely failed to *download* (404, timeout, slow host) is forwarded as before, so OpenRouter may fetch it. A failed download costs one further address check on top of the one the download already ran, so a picture the pipe cannot fetch is refused after two address checks, and both of those checks draw on the same request-wide `ADDRESS_CHECK_BUDGET_SECONDS` (20.0) the video links, the reuse arm and a tool result's picture link draw on, each one still held to at most one `ADDRESS_CHECK_SECONDS` (5s) and a repeated link checked once per request. A turn carrying N such pictures therefore waits for at most that budget in total rather than 2 x N x `ADDRESS_CHECK_SECONDS`; a picture left with no time on the clock is refused, and because the picture cap counts what was *forwarded* rather than what was checked, the budget bounds how long those checks may take and the request's own ceiling of 16 resolved addresses bounds how many there are: a turn carrying more than 16 unfetchable remote pictures loses the rest, and each one lost is reported with the ceiling named. A download that returns no bytes counts as a failed download, so it is forwarded as its link rather than shipped as a zero-byte `data:` URL. One larger than `BASE64_MAX_SIZE_MB` once downloaded is not sent. The media type is resolved **from the bytes** on this leg exactly as on the reuse leg, and the declaration only decides when the bytes identify nothing: a payload that settles on a non-image type is not inlined but refused, with `Images: skipped N (not identifiable as an image).` on the turn that carried it, and the picture is not sent. The same `image/svg+xml` ground applies here, read from the same resolved type, so a downloaded SVG is refused rather than inlined and a PNG that declares itself an SVG is inlined as the PNG its bytes are. The size check is applied first, so a payload refused for being too large is reported as too large and never as unidentifiable. Plain `http://` is disabled by default and requires explicit allowlisting, and a picture refused for it is reported the same way as every other picture refusal: one `Images: skipped N (…)` line on the turn that carried it, naming both valves so the person can undo the refusal. A turn whose only content was that picture is not dropped either; it goes to the model as a `[An attached item was not sent: …]` placeholder naming the reason.
- An **Open WebUI file URL** (for example `/api/v1/files/...`) is streamed with the requester's access and inlined as a `data:` URL to avoid requiring OpenRouter to fetch from your Open WebUI host. Its media type is resolved from the bytes exactly as on every other leg, so the type the storage row recorded is not taken on trust: a payload that settles on a non-image type is refused, with `Images: skipped N (not identifiable as an image).` on the turn that carried it. The `image/svg+xml` ground applies here too, and matters most here: a **stored** SVG is exactly the reach, because the pipe reads the bytes back and the interface that stored them will not draw them. A payload that resolves to `image/svg+xml` is refused on the same sentence, as a separate ground from a payload no media type could be established for at all. The test for one is on the **path**, not on the spelling: any URL whose path names `/api/v1/files/<id>`, whatever its scheme, host or letter-case, is a reference to be resolved from local storage -- never a link for the pipe or the provider to fetch, and never a link to be forwarded when the resolve finds nothing to resolve. A sibling `file_id` does not change that reading, with one carve-out: a provider-side `file-` id (which names a file the provider already holds) shields a block that names no Open WebUI reference of its own, and nothing else. Beside a path it is no shield at all, so the path is resolved or the turn is refused. A reference the pipe cannot read (an empty id, a doubled slash, a dot segment, a percent escape, a leading underscore, or the path hidden behind a query value or a fragment) is refused with `RequiredInternalFileError`, so the turn stops and says why. On the conversion leg the reference is never resolved and never forwarded: it is refused at the last boundary before the request leaves, reported to the person as `Images: skipped N (<reason>).` on the turn that carried it and named on the turn the model sees, in the same words and with the same cause slug every other leg uses, so which leg refused it is not something a reader can tell. That access is the access of the request being sent, resolved once per request per file: a request that is sent twice — the `/responses` to `/chat/completions` fallback is the in-tree one — reads and authorises the file once rather than paying the check twice, and a later request pays it again.
- A **picture a tool result carries** - the `{"type":"image","url":...}` entry a tool server, an MCP server or a stored round hands over - is not downloaded and not fetched. It is forwarded unchanged, on the same terms a file link is: a `data:` URL within `BASE64_MAX_SIZE_MB`, or an `http(s)` link whose host resolves to a public address. A URL is one or the other, not both. The one thing that is not a link is a **relative, host-less** `/api/v1/files/…` reference: it names no origin the provider could dial, so it is exempt from the plaintext valve, the scheme gate, the address check and the verdict memo, and it is left for the gateway to inline from local storage. That is now true on the `/chat/completions` leg as well: an `image_url` block naming a file reference is resolved before the request goes out, rather than forwarded as a link. An absolute URL carrying that path — in any scheme, behind any netloc — is a link like any other and is put to both valves; on a private, loopback or link-local address it is skipped with a status rather than sent, and the turn is not lost. Anything else is refused, and on the `/responses` legs the person is told on the round being answered, not on their next question. That is now true of every leg a tool's picture travels on: the **sanitizer leg**, where a picture is dropped as the request is sanitized on its way out to the provider, and the **chat-completions leg**, where the payload conversion drops it on the way to `/v1/chat/completions`. Withholding follows the same rule on both message shapes: with `PERSIST_TOOL_RESULTS` off, a tool round that is not in the current turn contributes no picture to the request on the list-content shape, and on the flattened shape whenever the hand-off sits next to its result, which is how Open WebUI 0.11.4 builds it (`flush_tool_outputs()` and `flush_tool_images()` run back to back, and `merge_system_messages` hoists any system message to position 0). On a flattened history whose hand-off is separated from its result -- a shape only an API caller, an imported or hand-edited chat, or a filter can build -- the round's picture **is** forwarded: the pipe cannot tell that history apart from a person's own message carrying Open WebUI's fixed hand-off sentence and their own photo, and reading it as the round's hand-off would withhold the person's picture too. What the caller built is the caller's own posted bytes, so nothing the pipe stores is exposed by it (TODO T1163, to reopen only if Open WebUI ever builds the gapped shape). Both raise the same aggregated `Images: skipped N (<reason>).` status as the live tool loop and the stored-round replay, once per turn, so which leg dropped a picture is not something a reader can tell from the wording. A link the pipe cannot resolve, or one naming a loopback, link-local, private or otherwise reserved address, is refused with `Images: skipped N (could not be fetched, so it was not sent).` -- that sentence is the completed refusal's, and a check on one of these links that runs out of its budget instead is refused with a second one, `Images: skipped N (could not be checked in time, so it was not sent).`, because that link is forwarded rather than downloaded and it is the check that did not finish rather than a fetch that failed; A third outcome has its own sentence again, `Images: skipped N (could not be checked, so it was not sent).`, for a check that could not run at all -- the address pool shut under a hot reload that landed mid-turn, a fault in the gate's synchronous half, or the inline payload's worker submit against a loop whose default executor a hot reload closed -- which is neither of the other two: a spent budget is the check being too slow, a broken gate is the check never happening. That refusal belongs to the composite rather than to the address check: `_is_safe_url`'s own caller turns a raise out of that await into the no-verdict sentence above, and these are the three call sites that drive a whole composite -- the tool-message leg, the live tool loop's per-round gate and the live Pipeline-mode tool result -- each wrapping the composite itself. A gate that fails refuses the picture rather than admitting it, so a link the pipe could not check is never forwarded on the strength of a fault; the tool's own text result and the turn around it are unaffected on every leg. A tool result whose `image_url` is an object is **read**, not stringified, so it is gated and inlined exactly like the string spelling: `str()` on the dict destroys its scheme, which refused a benign `data:` picture as not a link the pipe can resolve and forwarded a mangled `{'url': ...}` that still named the endpoint. A `file:` or `javascript:` link is refused as not a link the pipe can resolve into an image; plain `http://` is refused unless both plaintext valves permit it, and the refusal names them. An inline `data:` URL is put through the two gates an attachment is: the `BASE64_MAX_SIZE_MB` cap above, and the type resolution the attachment leg runs, so a payload that is not decodable as base64 is refused as `not decodable as base64` and one whose bytes are not a picture at all is refused as `not identifiable as an image`, whatever it declares itself to be. Both are the shipped words the handoff leg already uses, and both now go through the same code on both arms. This covers every leg a tool's picture travels on - the live tool loop, the stored round a saved chat replays, a `role: "tool"` message posted in `messages`, a request handed straight to `/v1/responses`, and the chat-completions gateway - and the rules are the ones above, unchanged. That claim became true of the type rules when the gap was closed, and it was false before it: the **sanitizer leg** and the **chat-completions leg** reach `_tool_picture_gate`, which checks the scheme, the cleartext valve and the inline size cap and never resolved a media type at all, because the type is resolved on the way *in*, on the legs that hand a picture to the transformer. An SVG travelling either of those two legs therefore reached the provider untouched while the same picture was refused on every other leg. Both now run the same type resolution the attachment leg runs -- the sanitizer leg on the URL's own head, the chat leg on the head of the `data:` URL it is about to re-spell -- and neither downloads anything to do it, so a link is still forwarded as a link. A refused tool picture reaches a caller with no chat of its own in the returned body, after the answer and once, rather than only on a status nobody reads: the pipe emits the `Images: skipped N (…)` sentence as a status whenever there is an emitter for it, and always records the same sentence in the notices it joins onto the answer for such a caller. When every picture of a round is refused, the turn is sent with the tool's own text and the images message carrying **no** picture after its sentence: the round's text result is the round's answer, and dropping the message would take it with the picture. Every sentence above about a declaration the bytes do not corroborate describes what the pipe **forwards**. What it **stores** is a different contract, because there the type reaches a stored filename and a file's `content_type` rather than a provider's request: a picture the pipe generates is stored under the type its bytes identify, the declaration decides only where the bytes say nothing, and an entry that resolves to no storable image type is not materialised as a picture. See `docs/openrouter_image_generation.md`.

An image the pipe **reuses** from an earlier turn is inlined as a `data:` URL too. The pool it reuses from holds only blocks that name a picture source: a block that names none never enters it, so it can neither be reused nor displace a picture that could be, and the turn is answered from the picture an earlier turn really did send. A remote picture a saved chat reuses is cached in the worker's memory for the life of the process so later turns fetch it once, and the cache is per-person: an entry is only ever served to the person whose own turn downloaded it, so in a shared or channel chat where two people alternate on one `(chat_id, url)` the second person's turn re-downloads rather than being handed the first person's bytes, and a caller the pipe could not resolve to a user is re-downloaded rather than being served a named person's bytes; two such unresolved callers share one partition, so a caller the pipe could not resolve is re-downloaded only when a named owner wrote the entry (TODO T569 in tests/test_one_persons_reused_picture_is_never_sent_to_another.py); in a temporary chat it is re-fetched per request and kept nowhere. Bytes that carry a recognisable image signature decide its media type, whatever the source declared; where they carry none, the declaration decides. That is one rule, not four: a remote picture attached to a turn, a `data:` URL attached to a turn, an Open WebUI file attached to a turn and a picture reused from an earlier turn are typed by the same gate on the same terms, and a payload that settles on a non-image type is refused on any of the four with the same `Images: skipped N (not identifiable as an image).` A reuse is subject to `BASE64_MAX_SIZE_MB` per picture, the same ceiling an attachment is; a picture over it is refused and named. A reuse is subject to the remote-download cap as well, and so is a fetch: the cap is read once per request, on whichever leg asks first, rather than per picture: a picture memoised while the cap was higher is neither sent nor kept once the cap is lowered, so the decision to forward it is the same one a cold fetch of the same link at that moment would have made. The two arms are worded differently on purpose, because what happened on them is different: the warm arm is giving up bytes it already holds, and the cold arm had a transfer genuinely aborted mid-flight. The residual is the same on both legs: an `image/*` declaration the bytes do not corroborate is forwarded under the declaration, BMP and TIFF among them. A reuse is also dropped when the SSRF gate, re-run for it on every send, now refuses the URL, so tightening `ENABLE_SSRF_PROTECTION` or editing a host allowlist takes effect on the next turn rather than the next fetch. That re-run costs one address resolution and no download; a URL it then refuses is fetched once more through the already-gated path, which runs its own address check, so a refusal pays two resolutions. A held picture is measured against `REMOTE_FILE_MAX_SIZE_MB` on the same terms, and against the admin's stored Max Upload Size: the effective limit the downloader would have applied to those bytes, not the one in force when they were fetched. That number is read once per request rather than once per picture, so a turn citing many links pays for one lookup however many pictures it reuses. A held picture that no longer fits is discarded and fetched once more, which the downloader then refuses on the same ground it would have refused the first fetch, and the entry is gone for good rather than re-refused on every later turn. The two arms refuse on the same ground and word it differently: the warm arm reports `Images: skipped N (N bytes, over the M-byte download limit, so it was not sent).`, naming the byte count it is giving up and the effective limit it exceeds -- which may be Open WebUI's stored Max Upload Size rather than this valve, so the number is the one in force and not the valve's name -- while a cold over-cap fetch reports `Images: skipped N (could not be fetched, so it was not sent).`, because that transfer really was aborted. A resolution that does not finish inside the address-check budget reaches no verdict, so a slow nameserver never buys a permission; on the picture arm that no-verdict refusal is worded as an unfinished check rather than as a refused address, and is not reported as a private address. On this leg it also never costs a re-fetch: the entry survives a check that never finished and the picture is served from it, because the question here is not whether a fetch may start but whether the bytes already in hand are still permitted, and no answer is not a denial of them. Contention can cause that same absent verdict as a stall: the checks run on a private bounded pool, so a check that cannot start inside its budget — one queued behind other checks because the pool is full — reaches no verdict either, and only a check that completed and refused the address evicts the entry. A check that could not run at all -- the address pool shut under it, or the check itself faulted -- is refused as well, with its own words rather than either of those, because a broken gate never admits the picture. A download has no bytes to keep, so on that path a check with no verdict still sends nothing. What the private pool buys is that only address checks can pay that price, never media, thumbnails, file reads or Open WebUI's own endpoints. Nothing has to be refused for the re-check to be paid for: a request pays one blocking resolution per **distinct host** it reuses this turn, each one inside the same request-wide address-check budget, so a picture cited twice in one reply -- and two different pictures on one host -- are checked once and a turn carrying many pictures is bounded by that `ADDRESS_CHECK_BUDGET_SECONDS` (20.0) rather than by a lookup per picture. That budget is spent by address checks alone: it is not charged to the time this turn's stored artefacts took to load, nor to the time a remote picture's download took. That per-request dedup and that shared budget are now the picture cold arm's rule too, and a tool result's picture link draws on them as the third arm: an attachment the pipe cannot fetch, a tool picture the provider would fetch and a picture reused from an earlier turn are each checked once per request and draw on the same `ADDRESS_CHECK_BUDGET_SECONDS` -- a picture reused from an earlier turn once per distinct host, a tool picture once per link, the two granularities each arm has always used -- so the three legs cannot drift apart. Otherwise a reuse is dropped only when the type settled on this way is not an image type - so a payload declaring an image type whose bytes the pipe does not recognise (BMP and TIFF among them) is forwarded under its declaration, and one the pipe could not fetch at all is dropped. An `http(s)` reuse that the pipe could not fetch is reported as "could not be fetched, so it was not sent" rather than "could not be fetched, so its type could not be established": the fetch fails before any type gate runs, so the type-gate wording no longer describes it, and the type-gate cause now covers non-`http(s)` schemes only. A dropped reuse is reported to the person with the same `Images: skipped N (…)` status as a refused attachment, on the turn that triggered it. So is a picture refused for being served over plain `http://`; the status line names the reason, and a turn whose only content was that picture goes to the model as a `[An attached item was not sent: …]` placeholder rather than as an empty turn. Nothing on this input path writes a file - images the model *generates* are stored separately, and that is an output-side behavior.

### Limits and selection
- `MAX_INPUT_IMAGES_PER_REQUEST` caps how many images one turn forwards, counting a picture reused from earlier in the conversation, and counting every one of the person's messages in that turn: a request whose `messages` array carries several of them back to back is one turn, not several, so their pictures share the one budget. Pictures are kept in the order they were sent, so on a turn over the limit the earliest survive and the rest are dropped, and the turn is reported once with the turn's total. Pictures a tool returns are never cut by this limit. Whenever a tool round's result reaches the model, every one of its pictures that clears the tool-picture gate goes with it. A picture the pipe refuses is not sent, and the person is told, as for one they attached: the refusal is reported on the turn whose round carries the picture, which for a tool's pictures is the round being answered, not the person's next question.
- `IMAGE_INPUT_SELECTION` controls whether the pipe can fall back to the most recent image already in the conversation - the model's or the user's - when the current user turn has no attachments. It governs every picture this pipe re-sends, including one the model itself wrote into an earlier reply: see below.
- `IMAGE_REUSE_MAX_TURNS` bounds how long that image stays available, so a long text conversation stops resending a picture nobody is discussing.

### A picture the model wrote into a reply

A generated picture reaches the person's chat as a Markdown image in the assistant's text, and what that link holds is a `data:` URL for a chat with nowhere to store a file and an Open WebUI file destination (`/api/v1/files/.../content`) for a saved chat. On the next turn the stored message is replayed, and the Markdown used to go to the provider exactly as written - so the whole picture travelled as prose inside an `output_text` block, at prose price, to a model that could have had it as pixels. On a vision model with a following question it travelled twice, once as that prose and once as the typed `input_image` the reuse window builds.

A picture that arrives as an `http(s)` address rather than a `data:` URL is put to the same address gate on the way OUT as on the way in: it is published only when the host resolves to a public address. That covers all three ways the pipe can end up holding the provider's own link instead of a stored copy -- a chat that cannot store the file at all (temporary, local or channel), a download that failed, and a store that did not succeed -- and a check that reaches no verdict inside its budget is a refusal, so an address the gate cannot judge is never written into the reply. Every one of this arm's checks -- the gate an unlinkable chat puts to the address, the check the download itself runs, and the re-check a failed download costs -- draws on the same request-wide `ADDRESS_CHECK_BUDGET_SECONDS` (20.0) the request side and the video links draw on, each still held to at most one `ADDRESS_CHECK_SECONDS` (5s), and the deadline is taken the first time this arm asks rather than at the top of the turn, so a provider that streamed for a long time before its pictures landed is not charged for that time. A turn's own output item is the only bound on how many links reach the arm, so a reply carrying many model-written links is bounded by that budget rather than by one lookup a piece. A refused one is left out and the person is told the count in the same `Images: skipped N (...)` status the request side uses; that count may now include links the budget could not cover, and those are named apart in their own words -- `Images: skipped N (could not be checked in time, so it was not sent).` -- because what ran out of time was the check and not a download that failed. A public link that merely failed to download is still published, so a CDN timeout costs the picture nothing.

The URL is now lifted out of the replayed text and sent only as a picture, wherever the reuse window can still reach it. The sentence keeps its Markdown link with a stable placeholder in place of the URL, so it still reads as an image having been produced, and the stored message is not touched: the person's chat still holds the original `data:` URL and still renders the picture. Only what goes to the provider changes. Where the window cannot reach - a Continue, where nothing follows the reply, a tail of tool rounds where only a round and its handoff follow it, a follow-up more than `IMAGE_REUSE_MAX_TURNS` turns later, a follow-up that attaches a picture of its own other than the one the model wrote, a model that takes no image input, or the per-request cap on images - the destination stays in the prose exactly as the model wrote it, so the sentence in the text still points at a picture the model can see. Re-attaching the very picture the model wrote is not one of those shapes: that destination is lifted like any other, and the picture rides along on the turn as the person's own attachment, so it reaches the provider once rather than twice. A link is lifted on exactly the same terms as a `data:` URL: an `https://` or `/api/v1/files/...` destination the model wrote and the pipe could resolve is re-sent as a picture and no longer left in the prose beside it, and one it could not resolve is left exactly where the model wrote it. The one picture that never goes back into the prose is one the reuse leg refused as over `BASE64_MAX_SIZE_MB`: those bytes the pipe has already declared unsendable, so the sentence keeps its placeholder and the refusal is reported. Under `user_turn_only` the lift does not run at all and the picture is sent to nobody, as the valve says it should be; under `user_then_assistant` it is re-sent by the reuse window on the same terms as any other earlier picture, including `IMAGE_REUSE_MAX_TURNS`.

## Files (`input_file` / `file` → `input_file`)

### Fields accepted
The file transformer extracts and forwards the following Responses-compatible fields when present:

- `file_id` (already in Open WebUI storage)
- `file_data` (base64/data URL, or a URL-like string depending on upstream)
- `file_url` (URL to a file)
- `filename` (the caller's label for the file, forwarded with any hidden marker line removed from it — a name the pipe would read back as its own framing is not the person's name)

### What is sent
Every request forwards `file_data` and `file_url` as they came, except inline data over the size limit and a link the address gate refuses, for every chat and every request of a turn, and the pipe writes no file the person attached to Open WebUI storage:

- Inline data (a `data:` URL in either field, or raw base64 in `file_data`) up to `BASE64_MAX_SIZE_MB` is sent unchanged.
- Larger inline data is not sent. Without a `file_id` the file is dropped, and the person sees "Files: skipped …" for the turn that carried it, as with pictures; when the block has a `file_id`, only the oversized field is dropped and the `file_id` is sent.
- A block with no `file_id`, no `file_data` and no `file_url` is dropped for the same reason and with the same status: a `filename` is a label, not a source, and the part would otherwise go out declaring only its type.
- A link the HTTP security policy refuses is dropped, and the person sees "Files: skipped …", the same as an oversized file; when the block also has a `file_id`, the refused field alone is dropped and the `file_id` is sent, with no status.
- A link the address gate refuses is dropped in the same shape as the cleartext one above, with the same "Files: skipped …" status and the same `file_id` degrade, and the two rules are told apart in words: a link on a private, link-local or unresolvable address names that address, a link whose scheme is neither `http` nor `https` names the scheme, and a check that reached no verdict names the check instead, because no name was resolved in that case either. A link refused for its scheme never enters the request's address-verdict memo, because that memo holds verdicts about addresses and no address is consulted for a link the provider could not dial; the gate is still asked about it, once, so the refusal can name what it refused. The rule is the video arm's ([Validation and SSRF behavior](#validation-and-ssrf-behavior)); the only differences are that a file link is not downloaded and so the size valve never applies to it, and that the file check draws on the same request-wide `ADDRESS_CHECK_BUDGET_SECONDS` as the rest of this turn's and resolves a repeated link once per request.
- An `https://` link in either field is sent unchanged for the provider to fetch, so long as `ENABLE_SSRF_PROTECTION` says its host resolves to a public address; the pipe does not download it either way. The exception is a link whose path names `/api/v1/files/<id>`: that is a reference to Open WebUI's own storage, not a third-party link, and it is resolved from local storage or refused -- it is never forwarded and never downloaded. Plain `http://` is disabled by default and requires explicit allowlisting: a cleartext link whose host is not allowlisted has its **whole block dropped**, and the person sees "Files: skipped …", the same as an oversized file.
- An Open WebUI file URL in either field becomes a `file_id`, which is read with the requester's access and sent inline as `file_data`. One that names the path but yields no readable id is refused instead, with `RequiredInternalFileError`, and the turn stops; when the block also carries a **usable internal** `file_id` — one the pipe can read out of Open WebUI storage — the unreadable field is dropped and that id is sent. A provider-side `file-` id is not such an id: it names a file the provider already holds, so beside an unreadable Open WebUI path it is not a degrade to that id but a refusal, the same one the path alone would get.
- The inliner works on a body it owns: it deep-copies the `input` list it was given **only when a block names an Open WebUI file**, and always returns a new body, writing to no dict the caller handed it. A body naming none is handed straight back on a new list of the caller's own items, so nothing in it is shared for a rewrite to land in. A body sent twice within one request is therefore authorised once, the second send reading the verdict the first recorded rather than finding the first send's inlined payload and no reference left to authorise.

## Audio (`input_audio` / `audio` → `input_audio`)

OpenRouter audio inputs require base64-encoded audio, and the pipe enforces that:

- Remote URLs (`http://` / `https://`) are rejected: the block is dropped, and the person is told in a status on their latest message that the clip had to be base64-encoded, because the pipe does not fetch audio.
- Data URLs (`data:audio/...;base64,...`) are accepted if valid and within size limits, whether they arrive as a bare string or inside `{"data": ...}` or `{"data": ..., "format": ...}`: the dict spellings are unwrapped and forwarded exactly as the bare-string spelling is, and are not read as raw base64. All three spellings are judged by the payload rather than by which arm read it, and where two of them declare a format the **data URL's own head wins**: `data:audio/flac` sent alongside `format: "wav"` goes out as `flac`, because the head is attached to the bytes and the `format` key is only an envelope field. A head that names a media type the pipe cannot place — one that is not audio at all, or an audio container it does not send — refuses the clip in every spelling, and a head that names none declares nothing, so the sibling `format` (or the `mp3` default) still decides. The conversion leg reads the same two string spellings, and converts them into the object form as well: it takes the format from the data URL's own mime and defaults to `mp3` when the string names none, which is what the live arm does for a clip whose mime cannot be resolved. One over `BASE64_MAX_SIZE_MB` is not sent at all, the block is dropped, the person is told by an error card on the turn that carried it, and it is logged as a size refusal rather than an encoding failure. That card is a **notice**, not the end of the turn: it travels on `chat:message:error` with no `done` key, so the model goes on to answer and the reply stays open while it does. A channel message is the exception, and the notice does not survive it: the host closes that message on any `chat:message:error` whatever the frame's `done` says (`socket/main.py:1137-1144`) — and the turn's own closing `chat:completion` then stores its `content` over what the refusal wrote, so a channel reader sees the answer alone. That is the host's reduction, not the pipe's, and no frame the pipe can send leaves a channel message open after one. The refusal is also *recorded*, so a turn whose only content was that clip carries `[An attached item was not sent: larger than the <limit>-byte inline limit.]` naming the limit and is never reported as an empty message. "Valid" is enforced rather than assumed: the payload must be the base64 alphabet with RFC 2045 line wrapping and nothing else, so a payload of stray characters is refused instead of decoding to silence. The same parser serves pictures and audio, so the `;base64` marker is matched case-insensitively here too: `;BASE64,` is the same marker, spelled differently, and is accepted rather than refused as a malformed data URL.
- Every other content refusal — a remote URL, a data URL that is not audio, a payload that is not base64, a block carrying no audio at all — is dropped rather than replaced with a placeholder, and is reported the same way a size refusal is: an aggregated `Files: skipped N (…)` status on the person's latest message naming what was wrong with that clip. On the conversion leg a data URL it cannot map — one that is not audio — is dropped as it is today, as is a string that is neither a data URL nor a clip, and the turn keeps its own text either way; that leg has no status channel, and the two legs' vocabularies are deliberately different. The aggregated line is also the sentence that reaches an API caller with no chat: with no truthy `chat_id` **or** no truthy `message_id` and `stream: false`, there is no emitter to send it on, so it joins the answer in the returned body instead — the same text, on the only channel that caller reads. A size refusal is reported by its own error card instead, and that card never suppresses the status for a *different* block: an over-limit clip and an over-limit document are two refused attachments, and the `Files:` line counts the one the card does not already cover. Nothing is forwarded in any case, so the provider is never told a clip was attached and handed no bytes. Each refusal keeps its own server-log line, so an operator still sees which arm refused what. Every refused attachment is named once on its turn: by its own card where that arm already emitted one, and by the aggregated `Files: skipped N (…)` line otherwise, decided by the arm's own severity and never by whether two refusals in the same turn happen to share a sentence.
- Raw base64 strings are accepted if valid, and refused by size the same way.

The pipe passes a recognised audio format through unchanged, so `wav`, `mp3`, `flac`, `m4a`, `ogg`, `aiff`, `aac`, `pcm16` and `pcm24` all reach OpenRouter as themselves, and it never renames a clip to a format it does not send: a format the pipe cannot send — a `webm` container among them, which OpenRouter documents on neither endpoint — is left out of the request rather than normalized to `mp3`, and the refusal is never silent, because a clip dropped from a turn that still runs is reported on the status line while a format the direct-upload gate refuses ends the turn on the `Direct Upload Issue` card. The two paths label a clip differently, and both refuse rather than guess. A hand-built block is labelled by what it declares, and only a block that declares no format at all still defaults to `mp3`. A native audio attachment is labelled from the sniffed container where the pipe can read one and from the declared format where it cannot — an ISO base-media box is only claimed when its major brand names MPEG-4 audio — and what is left over is refused rather than announced as something it is not. Only native audio attachments sent directly are checked against `Direct responses audio format allowlist` before routing; a hand-built `input_audio` block is not.

The pipe never writes audio to Open WebUI storage; it stays inline in the request it sends upstream.

## Video (`video_url` / `video` → `video_url`)

### Block format
The pipe uses Chat Completions-style `video_url` blocks:

```json
{
  "type": "video_url",
  "video_url": { "url": "https://example.com/video.mp4" }
}
```

### Validation and SSRF behavior
- Data URLs (`data:video/...;base64,...`) are accepted only if their size is at or below `VIDEO_MAX_SIZE_MB`. A base64 payload's size is its decoded size; a token-free payload's is its own length, which is the actual size rather than an estimate. One over it is refused with the clip's own error card and recorded the same way an over-limit audio clip is, so a turn that carried nothing else names the limit in `[An attached item was not sent: …]` instead of being reported as an empty message. That card is a **notice** too: it rides `chat:message:error` with no `done` key, so the reply the oversized clip was attached to is still open when the model answers it. On a channel message it does not survive, for the same reason an over-limit audio clip's does not: the host closes that message on the frame and the turn's own closing `chat:completion` stores its `content` over the refusal.
- Every `data:` head the pipe builds is checked against the media-type grammar `type/subtype` before it is built, not after. The declared or recorded type is lowercased and its parameters are stripped first, so `video/mp4; codecs=avc1` is accepted, and whatever is left is either a media type or the empty string. A value that is not a media type -- `video/mp4, text/html`, `video/`, `video//mp4`, `12`, anything carrying a comma, a space or a newline -- produces **no head at all**: the attachment is refused and named on the person's turn rather than forwarded with a truncated, defaulted or empty type. This covers the direct-upload video head, the head built from a referenced Open WebUI file's recorded type, or from its name where the record carries none, and the type the relay publishes a clip under.
- YouTube URLs are allowed when the host resolves to a public address (and may only work on certain model/provider combinations). A YouTube-shaped link whose host resolves to a private, loopback or link-local address is refused with `Video URL blocked by security policy (private network)`, like any other video link.
- A `video_url` block carrying no URL is dropped and reported the same way an audio refusal is: an aggregated `Files: skipped N (a video block carried no video URL)` status on the person's latest message, with a `Video block has no URL` line in the server log. The other four arms are reported on both routes each one has: the cleartext, private-network and over-size blocks each emit their own error card **and** are recorded, so a turn carrying nothing else names the reason in `[An attached item was not sent: …]` instead of being reported as an empty message; a conversion that raised is written to the server log **and** lands in the aggregated `Files: skipped N (…)` line, the same pairing the audio converter has, because that arm emits no card and that line is its only route to the person. None of the five forwards anything: no arm produces a `video_url` block with an empty `url`, and a block the loop is handed that carries no payload is dropped whatever produced it, so the provider is never told a video was attached and handed nothing to look at.
- Every non-`data:` video URL is checked by the SSRF guard when `ENABLE_SSRF_PROTECTION=True`, whichever arm it is classified into -- YouTube-shaped, schemeless, a plain `http(s)` link, or a link inside one of the filter's JSON controls (`VIDEO_KEYFRAMES`, `VIDEO_BACKGROUND`, `VIDEO_CAPTION`, `VIDEO_VOICE_SETTINGS`, `VIDEO_CONTENT_MODERATION`, which travel as the JSON document that was typed and are walked into by the same check) -- and the link is passed on only when the guard says yes. The `data:` scheme is what excludes a URL here, and it is what excludes one from the internal-file-path test in the next bullet: both gates read the scheme first and neither runs on an inline clip. A link whose scheme is neither `http` nor `https` is refused with `Video URL blocked by security policy (only http and https links are allowed)`. Remote `https:` (and `http:` only when allowlisted) URLs that are not Open WebUI file URLs reach the provider unmeasured but only after that check. Those checks share the request-wide address-check budget with the picture ones, so a message carrying many video links is bounded by that budget rather than by one lookup's budget per link, and a link that gets no time left reaches no verdict and is refused rather than sent, and is not reported as a private address; the reason it gets names the check reaching no verdict (`Refusing to send the address in '<where>': the address check reached no verdict before its budget ran out ...`) rather than the refused-address one, which would be a claim about the address no finished check made. That budget is spent by address checks alone: it is not charged to the time this turn's stored artefacts took to load, nor to the time a remote picture's download took. A link whose check reached no verdict at all is refused with `Video URL could not be checked against the address policy in time, so it was not sent` and its own cause, not with the private-network wording: the guard produced no verdict, so the pipe does not report one. A link whose scheme is neither `http` nor `https` keeps the scheme wording whatever the check did. An attachment already in the chat whose address check reached no verdict is dropped and counted separately from one that resolved to a refused address, so the two are not reported as one problem.
- Two classifiers read the **path**, not the spelling, and they answer different questions. The resolve arms — the attachment picture, the attachment file, and the video — read the host-agnostic `names_an_owui_file_path`, on **every** arm — including both of the `/chat/completions` converter's arms, where it runs on the **scheme** first, so a bare server path and a `file:` URL are refused there too and not only a URL that names the endpoint — and any URL whose path names `/api/v1/files/<id>`, whatever its scheme, host or letter-case (`https://owui.example.com/api/v1/files/abc/content`, `//host/api/v1/files/abc/content`, `HTTPS://OWUI.EXAMPLE.COM/API/V1/FILES/abc/content`), is a reference to Open WebUI's own storage -- the one exception is a `data:` URL, which is covered in the next bullet. The classifier that used to gate these paths, `is_internal_file_url`, stays relative-only -- an absolute URL is external to it, and widening it would silently change every gate it feeds -- so each arm now carries a second, path-based gate immediately after its own resolve step. What the arms do with a reference is where they differ, and the difference is deliberate: a picture and a file are **resolved** from local storage with the requester's access, exactly as Open WebUI's own image route does with the same path, and one that yields no readable id is refused with `RequiredInternalFileError`; a video is **refused** outright, because a video is never inlined, so there is nothing to resolve it into. No arm downloads such a URL and no arm forwards it. Four arms read this test, and which of them is right is not something the next reader has to re-audit: two of them changed, and the other two were already closed. The two that changed are the `input_file` arm of the in-place rewriter (`OwuiFileGateway.inline_internal_responses_input_files`) and the context-budget size index (`_referenced_file_ids`) — each used to read the keys as an if/elif chain whose first arm was any non-empty `file_id`, so a provider-side `file-` id ended the chain before either `file_data` or `file_url` was looked at, and a block carrying both went out with the path on it and charged nothing for it. The two that were already right are the transformer arm (`_to_input_file`), which rewrites `file_id` to whatever the path yields and drops the path on both its branches, and the gate (`_names_an_internal_reference`), which falls through to its own `file_data`/`file_url` loop rather than short-circuiting on the id. Because the pipe has no configured base URL for Open WebUI to compare a host against, the resolve test is host-agnostic: a foreign host that happens to serve that path is refused as one, which is what Open WebUI's own image router does for the same situation. The six **gate** arms read the narrower `names_a_hostless_owui_file_path` instead, because a gate is not resolving anything: it is deciding whether to forward a link, and an origin the caller wrote is an origin, not a storage reference. So the host-agnostic defence above is scoped to the resolve arms, and on the gate arms a relative, host-less `/api/v1/files/…` reference is the only OWUI-path spelling that is exempt — which is the spelling Open WebUI itself mints. That is the half the chat-completions leg was missing, and its `image_url` arm in `ChatCompletionsAdapter._inline_internal_chat_files` is what closed it: an `image_url` block naming a reference is now resolved from local storage before the request leaves, in both the dict form and the bare-string form, where only the `file` block was walked before. So "no arm downloads such a URL and no arm forwards it" is true on all five legs for the first time, and no shape a leg emits carries a file reference to the provider. A URL `urlsplit` cannot parse is judged on its raw text, so a malformed one that names the path still hard-fails rather than being reported as a broken video and forwarded.
- The video arm asks the **scheme** before it runs that test, and never runs it on a `data:` URL. Two reasons, and the second is the one a person meets. The scan reads the URL's parsed path with a regex, and a `data:` URL's path is its media type plus the clip itself, so the scan is linear in the clip -- roughly 215 ms and a copy of the whole string on a 100 MB video -- spent looking for a stored file in a URL that carries no location at all. And the scan used to refuse clips that happened to contain the marker's own bytes: every character of `/api/v1/files/` is a legal base64 character, so a well-formed inline clip whose payload spelled it was hard-refused as though it were a reference to Open WebUI's storage. Those clips are forwarded now. The guard is unchanged for every other spelling, and the decision reads the scheme rather than a `data:` prefix because `url_scheme` resolves nine spellings to `data` -- including a leading space, tab, newline or NUL, and an interior tab or newline -- where a prefix test takes six.

**Limitation:** Videos are not downloaded or stored by the pipe; it passes the URL (or data URL) through after applying basic checks. If you need durability for video content, you must ensure the URL remains reachable or implement a storage policy outside this pipe.

## Remote downloads (`_download_remote_url`)

Remote downloads are used for picture links: one in the conversation, or one a model returns for a picture it generated. The pipe never downloads a file link. The downloader enforces:

- **Outbound too:** a generated picture that arrives as an `http(s)` address is put to the same gate before it is published into the reply, so a link inside a model's own answer is checked exactly as a link the person typed is. See "A picture the model wrote into a reply".
- **Protocols:** `https://` only by default; `http://` requires `ALLOW_INSECURE_HTTP` + allowlisting. On the conversion leg the same transport rule is applied to each media link it copies, together with the scheme, the refusal of an Open WebUI file path and the inline bound; the SSRF address check does not re-run there, because that leg downloads nothing.
- **SSRF protection:** blocks private/internal address targets when enabled.
- **Retry/backoff:** retries on network errors and transient HTTP statuses (`>=500` and `408/425/429`), with exponential backoff controlled by valves.
- **Size limits:** enforced via `REMOTE_FILE_MAX_SIZE_MB`, and — whenever an admin cap is stored, RAG bypass on or off — additionally held to the value the Open WebUI admin last saved under **Admin → Settings → Documents → Max Upload Size**, the same number Open WebUI applies to the same file on its own upload leg, read from its own store so a change takes effect without a restart. Normally the lower of the two wins; the one exception is this valve left at its default of 50, where a larger admin cap wins instead, clipped to the pipe’s own 500 MB ceiling. A cleared admin box lifts Open WebUI’s cap, not the valve’s: left at its 50 MB default the valve still refuses anything over 50 MB.

## Configuration summary (key valves)

| Valve | Default (verified) | What it controls |
| --- | --- | --- |
| `ENABLE_SSRF_PROTECTION` | `True` | Fetches only addresses that are provably globally routable, so private/internal ranges, carrier-grade NAT and IPv6 site-local are all refused. It also decides every non-`data:` video link, YouTube-shaped, schemeless and `http(s)` alike: the link is passed on to the provider only when its host resolves to a public address, a link the turn names more than once is resolved once and every occurrence of it takes that one verdict, and a link whose scheme is neither `http` nor `https` is refused outright. It decides every `file_data` / `file_url` link the provider would have to fetch in the same way, in both fields, a `file_url` with no scheme at all included, which is refused on its scheme whether or not the valve is on; those checks draw on the same request-wide address budget as the rest of the turn, so N attached links cost at most that budget in total and a repeated link is resolved once per request. A turn's video links draw on the same request-wide `ADDRESS_CHECK_BUDGET_SECONDS` as its pictures and a tool result's picture link. So do the pictures the model wrote into a reply: one that arrives as an `http(s)` address is checked before it is published, and every check that arms makes -- the download's own included -- draws on that one budget. That budget is spent by address checks alone: it is not charged to the time this turn's stored artefacts took to load, nor to the time a remote picture's download took. A picture a tool result carries as a link is checked on the same terms - the pipe forwards that link rather than fetching it, so the check is on the address the provider would reach - and a refused one is not forwarded, whether the check completed and refused the address or ran out of time before it could answer. Its one exemption is a relative, host-less `/api/v1/files/…` reference, which names no origin the provider could dial: it is inlined from local storage rather than forwarded. An absolute URL carrying that path is a link like any other and is put to both valves, on every leg, `/chat/completions` included. The one exemption is the admin's own `BASE_URL` origin: a generated clip the pipe itself downloads from it is not put to the address check, so a self-hosted gateway on a private address can deliver its own clips, compared as a parsed origin (scheme, hostname, effective port) and never as a string prefix. It covers that one download only, so a link a person attaches or pastes is still checked even on the gateway's own host; a cleartext `http://` gateway still needs `ALLOW_INSECURE_HTTP` and an allowlisted host; and that one download is the only fetch not pinned to a validated address. HTTPS-only defaults still apply even if SSRF protection is disabled. |
| `ALLOW_INSECURE_HTTP` | `False` | Allow plaintext HTTP remote URLs when explicitly enabled. HTTP is disabled by default. |
| `ALLOW_INSECURE_HTTP_HOSTS` | `""` | Comma-separated list of hosts or host:port entries allowed for plaintext HTTP. Exact match only (no wildcards). A bare host is port 80 and nothing else, so a service on another port needs a `host:port` entry. Empty means no HTTP allowed. |
| `REMOTE_DOWNLOAD_MAX_RETRIES` | `3` | Retry attempts for remote downloads. |
| `REMOTE_DOWNLOAD_INITIAL_RETRY_DELAY_SECONDS` | `5` | Initial retry delay (exponential backoff). |
| `REMOTE_DOWNLOAD_MAX_RETRY_TIME_SECONDS` | `45` | Max total retry time budget for one download. Also caps any single retry wait, including one a server asked for in a `Retry-After` header. |
| `REMOTE_FILE_MAX_SIZE_MB` | `50` | Size cap for downloading a picture from a link (a file link is never downloaded) and related payload guards. |
| `BASE64_MAX_SIZE_MB` | `50` | Base64 payload size guard before decoding. It applies to a tool's inline `data:` picture too, which the pipe forwards rather than downloads, where a file link a person attaches is passed on unmeasured. |
| `IMAGE_UPLOAD_CHUNK_BYTES` | `1048576 (1 MiB)` | Chunk size used when inlining Open WebUI-hosted images as `data:` URLs. |
| `MAX_INPUT_IMAGES_PER_REQUEST` | `5` | Maximum images one turn forwards, counting every one of the person's messages in that turn and a reused picture; pictures a tool returns are not counted and are never cut by it, so every picture of a round that clears the tool-picture gate goes with the round. |
| `IMAGE_INPUT_SELECTION` | `user_then_assistant` | Image selection policy when the user attaches no images. |
| `IMAGE_REUSE_MAX_TURNS` | `3` | How many turns an earlier image stays available for reuse. |
| `VIDEO_MAX_SIZE_MB` | `100` | Size guard for base64 (`data:`) videos and for stored videos re-read to extract frames. |

## Troubleshooting checklist

1. Image attachments are ignored: confirm the selected model supports vision and that `MAX_INPUT_IMAGES_PER_REQUEST` is not exceeded for the turn.
2. “Download blocked” / “URL blocked”: check SSRF controls (`ENABLE_SSRF_PROTECTION`) and confirm the URL is not internal/private.
3. Large payload failures: review `REMOTE_FILE_MAX_SIZE_MB`, `BASE64_MAX_SIZE_MB`, and `VIDEO_MAX_SIZE_MB`.
4. Video inputs do not work: provider/model support varies; the pipe does not download or store video and cannot force upstream providers to accept the URL.
