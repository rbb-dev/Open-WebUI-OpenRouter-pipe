# Valves & Configuration Atlas

This document is the authoritative reference for the pipe’s configuration surface: **Open WebUI valves**.

Defaults and valve names are verified against the source code and are intended to match current runtime behavior.

## How valves work

- **System valves** (`Pipe.Valves`) apply globally to the function (all users).
- **User valves** (`Pipe.UserValves`) allow per-user overrides for a limited subset of settings.
- When both are present, the pipe merges user valves into system valves; unset values are ignored.
  - When user valves are provided as a dict, the literal string `inherit` (case-insensitive) is treated as “unset”. Open WebUI does not build that dict: `parse_user_valves` returns a model and a stored row is validated into one, so the sentinel is what the **merge** reads, not what a production caller sends. A value outside the destination field’s declared `Literal` is treated the same way — the administrator’s value stands, because there is no reading of that value the field could hold.
  - The pipe does **not** allow per-user overrides of the global `LOG_LEVEL`.
  - An **unreadable** user setting is not an unset one, and is decided the other way round. A setting the pipe could not read — a stored row that will not decode (a rotated application secret is the usual cause), a row Open WebUI’s reader never returned, or a stored value that no longer parses — falls back to that user valve’s **own per-user default**, never to the administrator’s site-wide value. That default is the fallback regardless of which side of the administrator’s value it sits on: it may be more restrictive than the site-wide value, and for a site-wide value already set to its most restrictive option more permissive. The administrator’s value is never the fallback, and only settings the user actually chose are kept. A value the pipe *can* evidence still wins over both, so a readable row is unaffected.

**Secret handling**
- Some valves use `EncryptedStr` to mark secret values (for example API keys and zip passwords). Open WebUI’s handling of encrypted values depends on Open WebUI’s own secret configuration (for example `WEBUI_SECRET_KEY` or the deprecated `WEBUI_JWT_SECRET_KEY` it falls back to). Treat `EncryptedStr` as *sensitive* and protect backups accordingly.

**A stored value this release no longer accepts.** When a release tightens a bound, removes a `Literal` member or narrows a type, an installation still carrying the old value is not taken down: the value is left at that field’s default, the field’s name is written to the log with the value it read as, and the name is dropped from the row on the next save from Open WebUI’s own valves panel (admin only). Every other saved value is kept exactly as stored. **Secret valves are never replaced, and neither their stored value nor their default is ever written to the log.** A secret valve stored as something other than text — which is what a hand-edited valve column leaves behind — is kept and read as text rather than being replaced, so a single-element list round-trips back to a working key; any other shape is kept unchanged and named in the log, which is the point at which the operator re-enters it by hand.

## System valves (`Pipe.Valves`)

### Connection and authentication

| Valve | Type | Default (verified) | Purpose / notes |
| --- | --- | --- | --- |
| `BASE_URL` | `str` | `env OPENROUTER_API_BASE_URL, else https://openrouter.ai/api/v1` | OpenRouter API base URL. Override this if you are using a gateway or proxy. Changing it makes the next image request re-read every image model's published settings, so a gateway's own limits are never taken from the host they were read from before the change; a trailing slash is normalised away and is not read as a repoint. A gateway on a private address is exempt from the address policy by origin for the generated clip the pipe itself downloads from it, compared as a parsed origin (scheme, hostname, effective port) and never as a string prefix, so a self-hosted gateway can deliver its own clips; nothing else on that origin is exempt, a cleartext `http://` gateway still needs `ALLOW_INSECURE_HTTP` and an allowlisted host, and that one download is not pinned to a validated address. |
| `DEFAULT_LLM_ENDPOINT` | `Literal["responses", "chat_completions"]` | `responses` | Which OpenRouter endpoint to use by default. `responses` applies prompt caching via a top-level `cache_control`; `chat_completions` uses per-block breakpoints, needed for Bedrock/Vertex-routed Claude caching and some provider features. Per-model force lists override it. |
| `FORCE_CHAT_COMPLETIONS_MODELS` | `str` | `""` | Comma-separated glob patterns of model ids forced to `/chat/completions`. Matches both slash and dotted ids; case-sensitive. Globs are literal about the `~` prefix, so `~anthropic/...` router aliases need their own pattern (e.g. `~anthropic/*`). A match on a Fusion model is not overridden: on the hosted OpenRouter backend the valve holds and the turn is refused with the endpoint-conflict card, because Fusion on `/chat/completions` returns a flattened text transcript with no structured events; on the internal backend the panel runs in the pipe and there is no conflict to refuse — *unless* the request carries `{"id": "fusion", "enabled": false}`, or is a housekeeping task request (a chat title, summary or tags): with no panel to run, the model does reach OpenRouter and the pin refuses it with the same endpoint-conflict card. |
| `FORCE_RESPONSES_MODELS` | `str` | `""` | Comma-separated glob patterns of model ids forced to `/responses`. Overrides `FORCE_CHAT_COMPLETIONS_MODELS` when both match. A matched model is not retried on `/chat/completions` when `/responses` fails, so the error surfaces instead; housekeeping task requests are exempt. |
| `AUTO_FALLBACK_CHAT_COMPLETIONS` | `bool` | `True` | Retry once against `/chat/completions` if `/responses` fails with an endpoint/model-support error before any visible output has streamed. A failure OpenRouter reports inside a reply already under way is **not** retried against `/chat/completions` — the endpoint is not the problem once a reply has started. If it is a temporary failure (a `429` or `5xx`) and nothing has been shown yet, it is re-sent **on the same endpoint**, governed by `TRANSIENT_RETRY_MAX_ATTEMPTS`; otherwise, and once those tries are spent, its message is shown straight away, appended below whatever answer was already streamed. Skipped for a model pinned by `FORCE_RESPONSES_MODELS` to `/responses`, which is not a model that merely sits on the `responses` default, and for a Fusion turn carrying a live `{"id": "fusion"}` entry, whose panel the `/chat/completions` payload would lose — both surface their error; housekeeping task requests are exempt from both and always fall back. A Fusion turn whose entry is `enabled: false`, and a Fusion entry on a non-Fusion model, are still retried. |
| `API_KEY` | `EncryptedStr` | `env OPENROUTER_API_KEY (empty if unset)` | Your OpenRouter API key. Defaults to the `OPENROUTER_API_KEY` environment variable. Clearing it removes the stored value and returns the setting to that default: the `OPENROUTER_API_KEY` environment value when one is set, and no key at all when one is not. Rotating it makes the next image request re-read every image model's published settings under the new account, so one account's published limits are never applied to another's. Re-saving an unchanged key does the same, because the stored value is re-encrypted with a fresh nonce on every save. |
| `HTTP_REFERER_OVERRIDE` | `str` | `""` | Override `HTTP-Referer` for OpenRouter app attribution. Must be a full URL including scheme (e.g. `https://example.com`), not just a hostname. Applies to every request to an openrouter.ai host, including the catalogue, endpoint and maker-page refresh reads; not to user- or model-supplied asset downloads or the GitHub self-update check. Surrounding whitespace is trimmed, so a URL pasted with a trailing newline is used as typed. When empty, the pipe uses its default project URL. A value that is still not a full `http(s)` URL after trimming is ignored, a warning is shown, and the default is used. |
| `HTTP_CONNECT_TIMEOUT_SECONDS` | `int` | `10` | Seconds to wait for the TCP/TLS connection to OpenRouter before failing. |
| `HTTP_TOTAL_TIMEOUT_SECONDS` | `Optional[int]` | `null` | Overall HTTP timeout (seconds) for OpenRouter requests. Set to null to disable the total timeout so long-running streaming responses are not interrupted. The Config tab expresses `null` as an empty box: clearing the box and saving returns the setting to unset. |
| `HTTP_SOCK_READ_SECONDS` | `int` | `300` | Idle read timeout (seconds) applied to active streams when `HTTP_TOTAL_TIMEOUT_SECONDS` is disabled. |

### Remote downloads, multimodal intake, and SSRF

| Valve | Type | Default (verified) | Purpose / notes |
| --- | --- | --- | --- |
| `REMOTE_DOWNLOAD_MAX_RETRIES` | `int` | `3` | Maximum number of retry attempts for downloading a picture from a link or a video a model generated. Set to 0 to disable retries. |
| `REMOTE_DOWNLOAD_INITIAL_RETRY_DELAY_SECONDS` | `int` | `5` | Initial delay in seconds before the first retry attempt. Subsequent retries use exponential backoff (delay * 2^attempt). |
| `REMOTE_DOWNLOAD_MAX_RETRY_TIME_SECONDS` | `int` | `45` | Maximum total time in seconds to spend on retry attempts. Retries stop if this time limit is exceeded. It also caps any single retry wait, including one a server asked for in a `Retry-After` header. |
| `TRANSIENT_RETRY_MAX_ATTEMPTS` | `int` | `2` | How many extra tries a chat request to OpenRouter gets after a temporary failure — a `429`, a `5xx`, a connection that drops or times out, or the same reported inside a reply before anything has streamed — on top of the first try, so at most three requests in all. `0` makes such a failure final. A body carrying a content decision is the exception and is never retried, whatever status it arrived on. So is a reply OpenRouter had already accepted: if that body dies on the way, the generation already ran whatever reached the pipe, the fault is reported on that one request, and nothing is re-sent. Independent of the `REMOTE_DOWNLOAD_*` valves above, which govern downloads only. A failed request counts once against `BREAKER_MAX_FAILURES`, however many tries it took. |
| `TRANSIENT_RETRY_MAX_WAIT_SECONDS` | `int` | `30` | The longest single wait, in seconds, between two tries of one chat request to OpenRouter. A `Retry-After` header is honoured up to this cap, so a longer one is truncated to it rather than replaced by it. Independent of the `REMOTE_DOWNLOAD_*` valves above, and stopping the request cancels the wait and leaves no failure counted. |
| `REMOTE_FILE_MAX_SIZE_MB` | `int` | `50` | Maximum size in MB for downloading a picture from a link: one in the conversation, or one a model returns for a picture it generated. A picture over this limit is neither downloaded nor sent from the memo. A picture the pipe is already holding from an earlier turn is measured against this limit again on every send, exactly as one just downloaded is; one that no longer fits is given up and fetched once more, which this limit then refuses, and that refusal names the limit in force and the byte count it is over. The Open WebUI Max Upload Size counts the same way on that leg as on a fresh download. A file link a person attaches is not downloaded, so this limit does not apply to it; it is passed on to the provider instead, subject to the address check and the plaintext-HTTP policy, which can refuse it first. When Open WebUI RAG is enabled, downloads are also held to the cap the Open WebUI admin last saved under **Admin → Settings → Documents → Max Upload Size**, read from Open WebUI’s own store, so a change there takes effect without a restart. Normally the smaller of the two applies; the one exception is this valve left at its default of 50, where a larger admin cap wins instead, clipped to the pipe’s own 500 MB ceiling. Clearing that box lifts Open WebUI’s cap, not this one: left at its 50 MB default the valve still refuses anything over 50 MB. The admin’s cap is inert until an admin saves the box — the stored row exists on every current Open WebUI deployment, but it holds the environment seed until that save, so testing this without saving first shows no change. A `RAG_FILE_MAX_SIZE` environment value set after Open WebUI’s first boot has no effect at all now, because the stored admin value wins. |
| `BASE64_MAX_SIZE_MB` | `int` | `50` | Maximum size in MB for inline files, images and audio. A base64 payload is measured as its decoded size; any other inline payload is measured as its own length. Larger payloads are dropped: an uploaded payload is left out with a note, a file a tool returned that the pipe could not store is not shown, and a warning names the tool that returned it, and a picture inside one generated-image reply is dropped from that reply and named in the chat, while the pictures in that reply that did fit are still delivered. Every entry in such a reply is named for what it is, over that ceiling or not a picture, and raising this limit cannot make a non-picture entry fit: an entry that is not a picture does not count against the reply's ceiling at all, so a bad entry cannot displace a good one. A picture a tool returns is capped here on every path, as its own picture: it is left out of that round and named on the turn whose round carries it, while the round's text result and lead-in still go out. A picture a tool returns as an inline `data:` URL is capped where a file link a person attaches is not: the pipe forwards such a picture unchanged rather than downloading it. |
| `IMAGE_UPLOAD_CHUNK_BYTES` | `int` | `1048576 (1 MiB)` | Max bytes buffered when loading Open WebUI-hosted images before forwarding them to a provider. Lower values reduce peak memory usage. |
| `VIDEO_MAX_SIZE_MB` | `int` | `100` | Max MB for inline (`data:`) videos and for stored videos re-read to extract frames; an oversized video is not sent at all — the block is left out of the turn and the refusal is reported. A base64 payload is measured as its decoded size; a token-free payload is measured as its own length, and is a real gate on it. A remote `http(s)` or YouTube video link is not downloaded, but it is address-checked before it is forwarded: with `ENABLE_SSRF_PROTECTION` on, the provider is given the link only when its host resolves to a public address, and a link whose scheme is neither `http` nor `https` is refused outright. Forwarded links reach the provider unmeasured, except an Open WebUI file URL, which is refused outright in every spelling -- any URL whose path names `/api/v1/files/<id>`, whatever its scheme, host or letter-case, is refused rather than forwarded or inlined, because it names an endpoint that needs an authenticated user. An inline `data:` video is the one exception: the pipe asks the scheme before it runs that test, since a `data:` URL names no endpoint and carries the clip itself, so a clip whose own bytes happen to spell `/api/v1/files/` is forwarded rather than refused as one. |
| `FALLBACK_STORAGE_EMAIL` | `str` | `env OPENROUTER_STORAGE_USER_EMAIL, else openrouter-pipe@system.local` | Owner email for the pictures a model generates in a request with no signed-in user (for example, API automations). The resolved account is memoised, but keyed on this email: editing it re-resolves the owner on the next request that needs one, creating a new account if none matches and leaving the old account in place. |
| `FALLBACK_STORAGE_NAME` | `str` | `env OPENROUTER_STORAGE_USER_NAME, else OpenRouter Pipe Storage` | Display name for the fallback storage owner. |
| `FALLBACK_STORAGE_ROLE` | `str` | `env OPENROUTER_STORAGE_USER_ROLE, else pending` | Role assigned to the fallback storage account when auto-created. Defaults to a low-privilege role; override only if your deployment needs a dedicated service role. |
| `ENABLE_SSRF_PROTECTION` | `bool` | `True` | Enable SSRF protection for remote URL downloads. When enabled, an address is fetched only if it is provably globally routable, so loopback, RFC1918, link-local, carrier-grade NAT (`100.64.0.0/10`, Tailscale's default range), IPv6 site-local and anything else not marked globally routable are all refused; IPv6 forms carrying an IPv4 address (`::ffff:`, 6to4, Teredo, NAT64) are judged on the addresses inside, and a form carrying more than one (Teredo carries the tunnel server as well as the client) is allowed only when every one of them would be allowed on its own. HTTPS-only defaults still apply even if SSRF protection is disabled. The gate re-runs on every send, including a picture already in the worker's reuse memo, so turning it on or tightening a host allowlist takes effect on the next turn rather than the next fetch. Every link in `file_data` or `file_url` the provider would have to fetch is gated the same way, in both fields: a file link is not downloaded either, a link on a non-public host is refused with `Files: skipped N (...)`, and a block that also carries a `file_id` keeps that id and drops only the refused field. An inline `data:` URL, raw base64 in `file_data` and an Open WebUI file path are not links and are never checked. Those file checks draw on the same request-wide `ADDRESS_CHECK_BUDGET_SECONDS` as the picture and video checks, and a repeated link is resolved once per request, so N attached links cost at most that budget in total rather than a lookup apiece; setting this valve to False restores the old forwarding, for an intranet or internal-docs host and for the plaintext exposure it exists to close alike. A turn's remote video links draw on the same request-wide `ADDRESS_CHECK_BUDGET_SECONDS` as its pictures, so a message with many links is bounded by that budget rather than by one check per link, and a link that gets no time left reaches no verdict, is not sent, and is reported to the person as a check that reached no verdict rather than as a refused address. That budget is spent by address checks alone: it is not charged to the time this turn's stored artefacts took to load. A remote picture a turn attaches draws on that same budget for both of its checks — the download's own and the further one a failed download costs — and a repeated link is checked once per request, so a turn carrying many unfetchable pictures is bounded by it as well. A picture a tool result carries as a link is gated on the same terms, where it first enters the request and again on every turn a stored round replays it, for the address and for plain HTTP alike: the pipe forwards that link rather than fetching it, so the check is on the address the provider would reach. It also covers the one link the pipe fetches itself, the content URL of a generated clip: a generation whose clip the gate refuses still fails and still shows its card, and a refusal there costs the user no request failure. A check on one of those links that runs out of its budget is refused too, and is told apart from a completed refusal in the person's own words: the completed one says the link could not be fetched, the stalled one says the check could not be checked in time, because that link is never downloaded and it is the check that ran out. The one exemption is the admin's own `BASE_URL` origin: a generated clip the pipe itself downloads from it is not put to the address check, so a self-hosted gateway on a private address can deliver its own clips, compared as a parsed origin (scheme, hostname, effective port) and never as a string prefix. It covers that one download only, so a link a person attaches or pastes is still checked even on the gateway's own host; a cleartext `http://` gateway still needs `ALLOW_INSECURE_HTTP` and an allowlisted host; and that one download is the only fetch not pinned to a validated address. |
| `ALLOW_INSECURE_HTTP` | `bool` | `False` | Allow plaintext HTTP remote URLs when explicitly enabled. HTTP is disabled by default; only enable alongside a narrow allowlist. It covers a picture a tool result carries as a link in the same way as one the person attached. |
| `ALLOW_INSECURE_HTTP_HOSTS` | `str` | `""` | Comma-separated list of hosts or host:port entries allowed for plaintext HTTP. Exact match only (no wildcards). Empty means no HTTP allowed. Example: `example.com, example.org:8080, 203.0.113.10`. |
| `ALLOW_UNKNOWN_SIZE_CLOUD_READS` | `bool` | `False` | Global Valve only (not user-overridable). When `STORAGE_PROVIDER` is non-local (s3/gcs/azure) and a referenced Open WebUI file has no declared size in its metadata, reads fail closed by default to avoid an unbounded cloud download. Set `True` to permit such reads; the file is still copied to a private temp and capped by `BASE64_MAX_SIZE_MB` after download. This is a download-safety gate, not an authorization bypass. |
| `MAX_INPUT_IMAGES_PER_REQUEST` | `int` | `5` | Maximum number of images one turn forwards to the provider, including every one of the person's messages in that turn -- a request carrying several of them back to back is one turn and they share the budget, with pictures kept in the order they were sent so the earliest survive -- counting a picture reused from earlier in the conversation. Pictures a tool returns are not counted: they are never cut by this limit. Whenever a tool round's result reaches the model, every one of its pictures that clears the tool-picture gate goes with it, as in Open WebUI's own tool loop; one the gate refuses is named in the chat rather than dropped silently. |
| `IMAGE_INPUT_SELECTION` | `Literal[\"user_turn_only\", \"user_then_assistant\"]` | `user_then_assistant` | Controls which images are forwarded to the provider. `user_turn_only` restricts inputs to the current user message; `user_then_assistant` falls back to the most recent image already in the conversation, from either side, when the user did not attach any; a tool round ends the window for pictures from before it, so nothing older is reused after one whether or not it returned a picture. A round that asked you a question is not a media round and does not end the window, and neither does a picture the model shows you in its own reply to a round. It also governs a picture the model wrote into an earlier reply: that picture is re-sent as a picture where the reuse window can still reach it, and is otherwise left in the reply as the destination it was written as, which is a base64 data URL for a chat with nowhere to store a file and an Open WebUI file link for a saved one. The window cannot reach it when the reply is more than `IMAGE_REUSE_MAX_TURNS` turns back, when a tool round has closed the window, when you attach a picture of your own, when the model takes no image input, or when `MAX_INPUT_IMAGES_PER_REQUEST` has no room left for it. One picture is left in the reply neither way: one over `BASE64_MAX_SIZE_MB`, which the pipe has already refused to send, is reported and keeps its placeholder rather than riding along as the text it was written as; `user_turn_only` sends it to nobody. |
| `IMAGE_REUSE_MAX_TURNS` | `int` | `3` | How many turns an earlier picture stays available for reuse under `user_then_assistant` when the user attaches nothing. |

### Models, catalog refresh, and reasoning

| Valve | Type | Default (verified) | Purpose / notes |
| --- | --- | --- | --- |
| `MODEL_ID` | `str` | `auto` | Comma-separated OpenRouter model IDs to expose in Open WebUI. `auto` imports every available Responses-capable model. Each id may be written as OpenRouter's `author/model` form or as the exact id Open WebUI shows in the model picker, which begins with this pipe's function id followed by a dot; both forms resolve to the same model. An entry holding `*`, `?` or `[` is a glob pattern rather than one id, matched case-insensitively against every catalogue row on both the `author/model` and the dotted spelling, so `deepseek/*` publishes that whole family; it is matched as written, never split on `:` or `@`. A `!`-prefixed entry excludes, and exclusions run after the includes, so `deepseek/*, !deepseek/*:free` keeps the paid rows and drops the `:free` one. A list made only of exclusions starts from the whole catalogue, which `auto, !openai/*` also says; a `!`-only value published nothing before this and now publishes the catalogue minus what it removes. A `*` crosses a date stamp, so `openai/gpt-4o*` reaches `openai/gpt-4o-2024-08-06`; globs are literal about the `~` prefix, so `openai/*` does not cover `~openai/...` and `!~openai/*` is what removes one. A restricting list that matches no catalogue row now fails closed: the picker publishes nothing, every request is refused with the `Blocked model message`, and one `WARNING` names the unresolved entries, the include patterns that matched no row and the exclusions that emptied the selection. This list governs every model the pipe calls, including each Fusion panel member, the Fusion judge and the final answer, and including preset members: one this list excludes is a failed panel member carrying the reason, never silently substituted or dropped. A `~` pin is part of a model's identity for this list, so `~anthropic/claude-opus-latest` must be allowlisted **with** the tilde; written without it the entry matches nothing in the catalogue. The one exception is a value of only commas or spaces, which is read as blank and imports the whole catalogue. An `@preset/slug` entry resolves to the model before the `@`. A `base_id:tag` entry resolves to that exact tagged model when the catalogue lists it as one in its own right — `openai/gpt-4o:free` publishes the `:free` model, not the paid base — and otherwise to its base. |
| `MODEL_CATALOG_REFRESH_SECONDS` | `int` | `3600` | How long to cache the OpenRouter model catalog (seconds) before refreshing. The failure backoff after a failed chat-catalog fetch is tracked per OpenRouter account, so one account's outage never holds up another account's catalog read. The video and image catalogs are gated on this same interval and back off on the same ladder after a failed fetch -- 5 seconds, then 10, 20, 40, 80 and 160, capped by this interval whenever it is set below 160 -- with the count kept per account and per media catalog, so one key's outage never paces another's video or image list; a fetch that returns no models stamps the clock without counting. The image catalog's two clocks -- the model list and the published-settings sweep -- are stamped with that same account and keyed the same way, so a changed key refetches both at once. The video catalog's clock is stamped with the account that asked on the same terms, one fingerprint rather than two. The adapter's own cache of each image model's published settings follows the same window, is keyed on the account as well as the model, and, along with the cache of the contracts those settings were read from, is dropped at once when `BASE_URL` or `API_KEY` changes rather than kept for the rest of it, together with the 30-second window a failed read of one model opens. |
| `VARIANT_MODELS` | `str` | `""` (empty) | Comma-separated virtual routing variants, each `base_id:variant_tag` — e.g. `openai/gpt-4o:exacto,anthropic/claude-sonnet-4.5:extended`. Each adds a picker model that reuses the base model's description, icon and capabilities with the tag appended to the display name, gets the base model's reasoning settings unless the catalog lists the suffixed id itself (a `:free` row, for example, follows its own entry), and sends the full `base_id:tag` upstream so OpenRouter applies that routing. Documented tags: `free`, `thinking`, `online`, `nitro`, `exacto`, `extended` (the tag is lower-cased and passed through, not validated against that list). A case-sensitive `base_id@preset/slug` form adds an OpenRouter preset instead; the pipe adds no reasoning settings of its own to a preset, so the preset's saved ones apply, but a reasoning effort the chat itself sets still goes out and overrides them for that request. A `*` or `!` entry here is `MODEL_ID` selection syntax, not a variant spec: this valve takes exact base ids, and an id `MODEL_ID` excludes is not added as a variant either. An entry whose base model is absent from the catalog is skipped, with a warning naming it. A variant of an image model is the same model, so the image settings panel (`AUTO_INSTALL_IMAGE_FILTERS`) covers the variant too. |
| `NEW_MODEL_ACCESS_CONTROL` | `Literal["public","admins"]` | `admins` | Default access grants for **new** OpenRouter model overlays inserted into Open WebUI (existing access grants are preserved on update), read once per pass, so a pass already running when you save it finishes under the value it started with. `public` grants read access to all users (wildcard access grant). `admins` creates no access grants (private) and relies on Open WebUI's `BYPASS_ADMIN_ACCESS_CONTROL` for admin access; otherwise admins must be granted access explicitly. |
| `FREE_MODEL_FILTER` | `Literal["all","only","exclude"]` | `all` | Filter models based on summed OpenRouter pricing fields. `all` disables filtering; `only` restricts to free models (sum==0 and at least one numeric pricing value); `exclude` hides free models. |
| `TOOL_CALLING_FILTER` | `Literal["all","only","exclude"]` | `all` | Filter models based on tool calling support (supported_parameters includes `tools` or `tool_choice`). `all` disables filtering; `only` restricts to tool-capable models; `exclude` hides tool-capable models. |
| `ZDR_MODELS_ONLY` | `bool` | `False` | Hide models that are not ZDR-capable (based on `/endpoints/zdr`). Catalog filter and request admission: a hidden model is also refused if requested directly. Never sends `provider.zdr=true`. A `~`-prefixed `-latest` id is answered for the model its catalog `alias_target` names and for its own key. |
| `ZDR_ENFORCE` | `bool` | `False` | Enforce ZDR on every request by sending `provider.zdr=true` and rejecting non‑ZDR models. Routing suffixes the pipe synthesises (`:nitro`, `:floor`, `:online`) are checked against their base model, while a suffix OpenRouter lists as its own model (`:free`, `:thinking`) is judged on its own endpoints; a `~`-prefixed `-latest` id is answered for the model its catalog `alias_target` names and for its own key; `provider.zdr=true` then restricts routing to ZDR endpoints server-side. |

The exemption from shortening is the built-in `ask_user`'s alone, decided from the builtin's registry and the round's stored stamp rather than from the spelling of the name, so a long answer given through any other tool -- including one of your own called `ask_user` -- is still shortened, and stored rows are unchanged. |

Behavior note (no valve):
- Tool output budgeting is dynamic and model-aware: on every request, in either tool execution mode, oversized replayed `function_call_output` payloads -- and in `Pipeline` mode each round's new ones -- can be replaced with omission stubs so the model stays in-context.
- When `MAX_FUNCTION_CALL_LOOPS` is reached, pending tool calls receive stub responses advising the model to synthesize from existing context, and the model gets one additional generation turn after them to write the answer, so a turn that reaches the cap bills `cap + 2` model requests. The opening turn is unconditional, so the cap counts tool rounds and never the first call; its floor is `1`, and `0` or below is stored as `1`.
- Failed/omitted tool outputs remain model-visible for continuation. An omission stub replaces a result only in what is sent to the model, for the rest of that turn; a shown card and the saved message keep the full text, and the omission is announced by a notification. With `PERSIST_TOOL_RESULTS` on, a later turn hands the result over in full again once it fits; with it off, an earlier turn's result is a placeholder anyway.

Notes:
- The image catalog uses the **shared** `MODEL_CATALOG_REFRESH_SECONDS` TTL (no separate cache valve), and the published-contract sweep behind both the per-model panels and the Image Generation tool's panel runs on that same TTL whenever any of the four image filter valves is on. The image catalog has two clocks — the models clock, stamped by every pass, and the contract clock, stamped only by a pass that actually swept contracts — and only the second is what suppresses a sweep. The video catalog has one clock on this same TTL, and both media lists now back off on the chat catalogue's ladder after a failed fetch rather than waiting out the flat interval: 5, 10, 20, 40, 80, 160 seconds, capped by this interval below 160. The count is per account and per media catalog and is cleared by a successful fetch of either, and a fetch that returns no models is treated as an answer rather than a fault — it stamps the clock and leaves the count alone, so a quiet proxy is never paced like a sick provider. Both of those clocks are stamped with the credential that asked and carry that account's fingerprint, so a changed key refetches the list and re-sweeps every contract at once rather than answering the new account from the previous one's state for the rest of the window; the two clocks share one account stamp, so a half-keyed state cannot be reached. The cost is knowingly accepted: a deployment that alternates two keys re-reads on every model-list build. The video catalog's own clock carries that account's fingerprint beside its timestamp, so a window is a hit only for the account that earned it: a changed key refetches the video model list for the same reason the two image clocks do. Its per-model modality read follows the model-list path's clock rather than a single request's, so a request arriving mid-refresh is answered from the previous catalog instead of waiting. Where that catalog is still empty -- a cold registry, which is every worker's first video sweep -- a request for a video model is told the video catalogue is still loading and that the next turn will carry the model, instead of being refused as restricted. The adapter's own cache of one model's published settings, keyed on that account's fingerprint as well as the model id, follows the same window but carries an extra rule: it and the 30-second window a failed read of one model opens are dropped at once when `BASE_URL` or `API_KEY` changes, because a contract read under one target is not a fact about another -- and a read still in flight when the target moves answers its own caller and is published to no one. So is the shared published-contract cache the panels read, which is bound to the same pair and dropped on the same event.
- Generated images are stored, linked to the chat and rendered by the same path that has handled `gpt-5-image` end-to-end since long before this feature, so they behave like any other attachment in the conversation. On the chat route a temporary, legacy-temporary or channel chat — and a call carrying no `chat_id` at all — has no row to hold the link, so nothing is stored there and the picture stays inline in the message instead; the direct image and video routes still store, because they have no inline form to fall back to.
- `OR Web Tools` and `OR Web Search` overlays are **capability-gated to skip picture-only models** — a model that returns pictures and no text has no endpoint that accepts tool use, and would fail with HTTP 404 ("No endpoints found that support tool use") if web search were attached. A model that returns text as well as pictures keeps the overlay, and carries the Image Generation toggle on the same four facts. Video-generation models are skipped for the same 404 reason.
- Validation: a setting the model does not publish is dropped before the request goes out and the user is told which one, rather than being sent and refused by the provider. The video family's own panels are checked the same way, on the way out, against the model's current catalog entry: a row the pipe never refreshed can carry a value that entry no longer lists, and that value is withheld and named in the chat rather than sent. A provider option typed as a JSON list or object that does not parse is rejected as soon as it is entered, with the setting named.
- Multimodal image models on the chat route are validated the same way. Their settings are put through the same published contract on the way out, so a value outside it is withheld and named rather than sent.

See: [OpenRouter Image Generation](openrouter_image_generation.md).

#### Companion filter user valves (per-user, per-filter)

One filter is installed per image model, named after that model, and attached
only to it.

Its user valves are not fixed and are not listed here: they are built from the
settings the model publishes to OpenRouter, so they differ per model and change
when the model does. A typed parameter becomes a field named `IMAGE_<PARAMETER>`
— `IMAGE_ASPECT_RATIO` for `aspect_ratio`, and so on. A provider-specific option
becomes a free-text field under the same naming rule.

Because the fields track a live contract, a value the model no longer publishes
is dropped on read — one field falls back to its default and every other stored
value on the panel survives. A key the model has never published is dropped the
same way. Which fields a model publishes, and what it accepts for each, is
re-read on every panel construction, so this follows the model rather than the
version of the pipe that first installed the panel.

For a worked example, `recraft/recraft-v3` publishes `aspect_ratio` (six
choices), `n` (1 to 6) and the provider options `style`, `controls` and
`text_layout`, so its filter carries `IMAGE_ASPECT_RATIO`, `IMAGE_N`,
`IMAGE_STYLE`, `IMAGE_CONTROLS` and `IMAGE_TEXT_LAYOUT`.

`IMAGE_SIZE` appears on **every** image model that has a panel at all, whatever
its contract publishes, because a request carries it for any model, and a
contract that does describe it decides the shape of the control. The other three
below are drawn only for models
that answer only with a picture: a model that answers with text as well takes
its references from the message itself, and the chat route it answers on takes
no provider options object, so those three are left off its panel:

| Valve | Title in chat | Type | Default | Maps to |
| --- | --- | --- | --- | --- |
| `IMAGE_PROVIDER_OPTIONS_JSON` | Provider options | `str` (JSON object) | `""` | `provider.options`, keyed by provider slug |
| `IMAGE_REFERENCE_MODE` | Reference images | `Literal["auto", "latest-only", "none"]` | `"auto"` | which images, attached or linked, become `input_references` |
| `IMAGE_REFERENCE_URLS` | Reference image links | `str` (JSON array) | `""` | extra `input_references` entries, placed first |
| `IMAGE_SIZE` | Output size | `str`, or `int \| None` bounded by the published range where a contract publishes `size` as one | `""`, or `None` | top-level `size`; exact pixels sent as typed, a tier checked against the model's published `resolution` where it publishes one and against OpenRouter's four tier names where it publishes none, and a number clamped to the published bound where it publishes a range |

`IMAGE_PROVIDER_OPTIONS_JSON` is the image sibling of
`VIDEO_PROVIDER_OPTIONS_JSON` and writes the same place the provider routing
filter writes, merging into it rather than replacing it — so a user typing one
option does not discard an operator's routing choice. Nine of the fifty-one
recorded models publish an empty passthrough list, so it is the only way to
address a provider on those. `IMAGE_SIZE` is rendered on every model because **no**
endpoint record publishes a `size` descriptor. A contract that did publish one
would draw a whole number bounded by that range and nothing else, and the request
would be measured against the same bound. As things stand OpenRouter documents the
two forms it takes for the free-text box, and the pipe treats them differently:
exact pixels go out as typed,
because no contract describes pixel sizes, while a tier stands in for
`resolution`. What a tier is measured against then depends on the model.
Nineteen of the fifty-one recorded models publish a `resolution` list; on those, a
tier the model does not publish is withheld rather than sent, and named in a
toast. The other thirty-two publish no such list, so a tier is measured only
against OpenRouter's own four names and then goes out for the company running
the model to interpret. Anything that is neither one of those four names nor
pixels is withheld and named on every model. Open WebUI does not keep a toast
with the message, so that naming does not survive a reload.

`IMAGE_REFERENCE_MODE` chooses which images are sent as references, from both
sources: `auto` sends every one, the attached pictures oldest first; `latest-only`
sends just the most recent; `none` sends none of them, and it governs the links in
the sibling box as well as the pictures on the turn. `IMAGE_REFERENCE_URLS` takes a
JSON list of `https` links or `data:` URLs, placed ahead of the attached ones so
an explicit choice survives on the many models that take a single reference.
Those links go through the same safety gate as every other URL the pipe fetches,
and a refused link fails the request rather than generating without it. A
request carries at most 16 references, the request format's own ceiling; where a
model publishes a lower limit the lower one applies, and anything over it is
dropped with a toast saying how many and why. Open WebUI does not keep toasts
with the message, so that notice is gone once the page reloads.

A provider option whose accepted values OpenRouter publishes renders as a choice
rather than free text — today that is `moderation` (`auto`, `low`), delivered on
the eight OpenAI image models that name it.

Where a model is served by several providers whose published choices differ, the
values only some of them accept are still offered, marked on the control; picking
one pins the request to the providers that accept it, so it is sent and honoured.
Where OpenRouter names none of those providers for routing, the value is still
sent and a warning goes out beforehand. Measured across all fifty-one recorded
models this affects one value: `4K` for `resolution` on
`google/gemini-3-pro-image`, whose two providers are both named for routing.

The prompt a model receives is the message typed in the chat with the model's
own system text in front of it, so a Workspace model's house style reaches an
image model instead of being dropped. A turn with no typed text is still refused
rather than generating from the system text alone.

Where every provider that could serve a request publishes native streaming, the
request asks for the streamed form and each preview is reported as a status
line, provided the request asks for one image and carries no input reference;
the carve-out fires only when `n` is a non-boolean `int` greater than 1, so a
quoted `n` such as `"2"` is not a count to the pipe and does not suppress
previews. A model streaming a text-based format instead of preview pictures — SVG —
is reported once as `Drawing the image…`. No recorded contract publishes both,
so today only the eight OpenAI image endpoints stream at all and they send
previews. Either way the answer is the same finished-image markdown.

**Skip-when-default sentinel**: an empty string for text and choice fields, and
an empty numeric field for numbers, means "not set" and is left out of the
request, so the model's own default applies. Numbers use an empty field rather
than `0` because `0` is a legal value for some published settings.

**Routing**: the filter writes the chosen values flat into `body.image_config`.
The image adapter then splits them, using the same published record, into
top-level request parameters and provider-scoped options. A filter writes only
for the model it belongs to, in any of the id forms Open WebUI produces.

- The adapter persists a hidden `videojob` marker into the assistant message immediately after `submit()` returns a job_id, by emitting an OWUI socket `'message'` event (which routes through `Chats.upsert_message_to_chat_by_id_and_message_id`). A later request for the same message resumes polling that job instead of submitting a second job.
- Chats with no stored row (`chat_id` beginning with `temporary:`, `local:` or `channel:`) cannot persist markers or final assistant content to Open WebUI chat storage. The on-submit `'message'` emit is skipped for them. They remain in-process only. What is lost is the chat's own message history: a generated image or video in a `channel:` conversation **is** attached to that channel, as a `channel_file` row, so its members can open it.
- The link a generated file gets is made under **the account it was uploaded as**, and only on a turn that carried a real message id — a turn without one is stored but not linked, because `chat_file` must name the message the file belongs to. That account is the only one that can open it (`routers/files.py:919`, `access_control/files.py:41-43`). A request whose user could not be resolved falls back to the storage account, so the link exists and the chat's shared viewers can load the file, but the requester of a **private** chat still gets a 404 on their own picture. The row is a link into a chat, never an access grant for the requester.
- `Pipe.close()` cancels in-process video lifecycles. OpenRouter has no cancel endpoint here; the on-submit `videojob` marker is what allows the next user request for that message to resume polling rather than submit a duplicate job.
- Video filters are generated per model from OpenRouter video metadata. Unsupported controls are not exposed: for example Sora text-only models do not show frame controls, and a model with no negative-prompt passthrough does not show that control. Because the field set tracks a live contract, one that later narrows does not cost a person the rest of their settings: a stored value the model no longer publishes falls back to that model's own default, and every other stored value stays in force. On a save, a value the model no longer publishes is dropped from the stored row and the rest of the settings are written. A row the pipe never refreshes -- the install valve is off, the activation write was refused, or the entry publishes no contract at all -- keeps the values it was built with; those values are withheld on the way out and named in the chat.
- Seed and audio are offered unless the catalog says outright the model has neither. A published `false` hides the control; a published `null` — which the catalog uses for some models — shows it, and leaving it alone sends nothing so the model's own default applies. On the recorded catalog the seed control is shown on that basis for `minimax/hailuo-2.3`, `x-ai/grok-imagine-video` and `x-ai/grok-imagine-video-1.5`, and the audio control for `alibaba/happyhorse-1.0`, `alibaba/happyhorse-1.1`, `x-ai/grok-imagine-video` and `x-ai/grok-imagine-video-1.5`.
- Attachments the frame controls do not claim — extra images, a clip, a sound file — are sent as `input_references` rather than left out; a request carries at most 16 references, and past that the excess is left out with a notice in the chat naming it and the reason. An attachment Direct Uploads has already taken is not among them: the video filter honours the diversion and does not hand it back. Each is checked against the same limits as a frame, but a reference that fails one is left out with a warning notice in the chat naming it and the reason, and the render proceeds; a frame that fails one fails the whole request. A **picture** over the per-picture cap is left out; a **clip or a sound file** over the relay cap stops the request instead, naming the cap it broke, because a clip the person attached is the thing being edited. Frames and reference pictures draw on one combined-size budget, the frames first.
- User-supplied passthrough URLs (`VIDEO_AUDIO_URL`, `VIDEO_LAST_IMAGE_URL`, `VIDEO_REFERENCE_VIDEO_URL`, and JSON-array references) go through the same safety gate as every other URL the pipe fetches before being forwarded to OpenRouter — blocks `file://`, private IPs, loopback, and unallowlisted `http://`. When `VIDEO_REFERENCE_ALLOWED_DOMAINS` is set, a user-supplied reference URL must additionally name a host it lists (exactly or as a parent domain) on the port it lists, where it lists one; the free-text `provider.options` hatch is covered by the same gate, because the same check runs over every address in the built request rather than over a named field.
- A request needs a prompt: a turn with no words is refused, even when it carries an attached image, reference or clip. The reply names the missing thing rather than the attachment the person has already made: *Video generation needs a prompt in your message. Add words describing the video you want — an attachment alone is not enough.* That card also keeps the **Not sent with this video** list, as the submitted and failed paths do.
- A job that returns several clips has all of them delivered, each stored as its own file.
- An explicit `VIDEO_SIZE` wins over a `VIDEO_RESOLUTION` tier or a `VIDEO_ASPECT_RATIO` that contradicts it: the losing one is dropped with a warning notice in the chat naming it, rather than sent and rejected upstream.

See: [OpenRouter Video Generation](openrouter_video_generation.md).

### OpenRouter video intent classifier

A task-model classifier that reads recent chat turns and attachments before an OpenRouter video request to decide what the new video should reference (reuse a prior frame, adopt an attached image, or start fresh), optionally asking one clarifying question. Every failure degrades open — the paid video still generates from the latest message. See [openrouter_video_intent_classifier.md](openrouter_video_intent_classifier.md).

Notes:
- Provider routing filters are generated dynamically from OpenRouter's public per-model endpoints API (`/api/v1/models/{author}/{slug}/endpoints`), which lists every provider serving the model; the frontend catalog is only a degraded single-provider fallback when that fetch fails.
- Each filter exposes an **ORDER dropdown** (human-readable provider names): full priority permutations for up to 4 providers, and a linear "X first" preference per provider beyond that (full permutations would grow factorially). Crossing that 4-provider threshold preserves a stored order's leading provider as "X first" rather than discarding it, and logs a warning naming what it kept.
- Admin-only filters use `toggle=False` (always run, cannot be disabled per-chat).
- User-configurable filters use `toggle=True` (can be toggled on/off per-chat) and start enabled in new chats while `AUTO_DEFAULT_PROVIDER_ROUTING_FILTERS` is on.
- Provider routing is **not applied** to task model requests (title, tags, follow-ups), because Open WebUI runs pipeline inlet filters on task routes but not function inlet filters, and the provider routing filter is a function filter. No `provider` block is ever written *for* a task model; what the pipe's gate drops is the chat model's block, inherited by the task through the shared metadata object. A `provider` block the caller sent in the request body is a different key and is applied on every path, tasks included. See [OpenRouter Provider Routing](openrouter_provider_routing.md).
- The controls a generated filter draws depend on the model's request format: chat completions carries all of them, the dedicated image format carries only `ORDER`, `ONLY`, `IGNORE`, `SORT`, `SORT_PARTITION` and `ALLOW_FALLBACKS`, and the video format carries none — so no filter is installed for a video model and an existing one is deactivated. See [OpenRouter Provider Routing](openrouter_provider_routing.md).
- Variant-only providers (e.g., Venice serving only `:free` variants) are excluded from base model routing options.

See: [OpenRouter Provider Routing](openrouter_provider_routing.md).

Picture-only image models, video models and the panel, judge and final-answer calls inside internal Fusion report failures in their own way: a Fusion panel member that never got out is reported with a fixed, pipe-authored reason rather than a copy of its response — and so is one that did get out and whose call then failed, and a final-answer call that dies mid-stream keeps the text it had streamed and appends a short degrade marker naming that failure, which is stored with the reply rather than shown as a card. |
| `CONNECTION_ERROR_TEMPLATE` | `str` | `built-in default` | Markdown template a chat reply shows, after the retries of `TRANSIENT_RETRY_MAX_ATTEMPTS` — at most three attempts — are spent, when its connection to OpenRouter fails before any answer text or named tool call has arrived: it cannot be opened, it drops, a stream sends nothing the pipe could read on every attempt or whose readable frames published nothing a reader could use, or a non-streamed 200 carries no `output` key on `/responses`, or an `output` that is neither a list nor null, and no `choices` on `/chat/completions`. The request is counted once against the breaker, however many attempts it took. Once answer text has arrived, or while the body of a stream OpenRouter has already answered is still arriving — whether or not the frames it did publish were ones a reader could use — `STREAM_INTERRUPTED_TEMPLATE` is used instead and nothing is retried, because a request that was accepted is billed again by every re-send. A non-streamed 200 on `/responses` whose `output` is present but empty or null is not one of these: the connection worked and the model returned nothing, so it is retried on the same budget and then shown with `OPENROUTER_ERROR_TEMPLATE`, whose reason says the model returned an empty answer. Picture-only image models, video models and the panel, judge and final-answer calls inside internal Fusion report failures in their own way: a Fusion panel member that never got out is reported with a fixed, pipe-authored reason rather than a copy of its response — and so is one that did get out and whose call then failed, and a final-answer call that dies mid-stream keeps the text it had streamed and appends a short degrade marker naming that failure, which is stored with the reply rather than shown as a card. |
| `SERVICE_ERROR_TEMPLATE` | `str` | `built-in default` | Markdown template for OpenRouter 5xx errors, for an accepted response whose body is not a JSON object (a proxy, CDN or WAF rewrote the reply) on the chat, `/responses`, task and Anthropic routes **and on a picture-only image generation whose `/images` reply was rewritten**, and for a provider that fails, is overloaded, is unreachable or times out while a reply is already under way. A decline — a body whose metadata carries `patterns`, `reasons` or `flagged_input` — is not a server fault whatever `5xx` it arrived on, and shows `OPENROUTER_ERROR_TEMPLATE` instead, with the `5xx` still the number the pipe retried on and counted against the breaker. On the unreadable-body case `{reason}` names the endpoint and the `Content-Type` and the provider's own first 200 characters arrive in `{body_excerpt}`, already inside a code fence; a template must not fence it a second time. A video generation's card is the one unreadable-body delivery this template does not serve: it keeps its own `### Video generation failed` heading and its `[openrouter:v1:videojob:…]` markers, which is what lets a persisted job resume, and withholds the excerpt on a channel chat itself. |
| `INTERNAL_ERROR_TEMPLATE` | `str` | `built-in default` | Markdown template for unexpected internal errors the pipe itself owns. An unreadable upstream body is not one of those: that is `SERVICE_ERROR_TEMPLATE`, because the network path produced it. |
| `MODEL_RESTRICTED_TEMPLATE` | `str` | `built-in default` | Markdown template emitted when the requested model is blocked by `MODEL_ID` and/or model filter valves. `{model_id_filter}`, `{free_model_filter}` and `{tool_calling_filter}` carry the valve values themselves, so all three are withheld on a channel chat and all three default rows are left out there; `{restriction_reasons}` still names the rule in words, without printing the list. |
| `VIDEO_CATALOG_LOADING_TEMPLATE` | `str` | `built-in default` | Markdown template emitted when the requested video model is absent from the catalogue only because the video catalogue is still being read for this worker, so the sweep has not registered it yet. It replaces the blocked-model message in that one case, because nothing is misconfigured: the next turn will carry the model. |
| `STREAM_INTERRUPTED_TEMPLATE` | `str` | `built-in default` | Markdown appended when a reply's stream stops before its final event, either because it closes early or because its connection fails, drops or times out after answer text or a named tool call has arrived; partial content is preserved. The calls inside internal Fusion never get the notice. When none of the answer has arrived, a timeout shows `NETWORK_TIMEOUT_TEMPLATE` and a failed connection or a stream that published nothing a reader could use shows `CONNECTION_ERROR_TEMPLATE` instead. |

**Note:** Every valve in this table whose name ends in `_TEMPLATE` restores itself: clear the box and save, and the built-in default text is written back for that valve alone, ready to edit again. Whitespace-only counts as cleared, and the restore applies whether the edit is made in the pipe's Config tab or Open WebUI's own Functions valve panel.

**Note:** To customize templates safely, prefer small edits and validate with real error cases. Template variable sets and formatting expectations are described in [OpenRouter Integrations & Telemetry](openrouter_integrations_and_telemetry.md) and [Error Handling & User Experience](error_handling_and_user_experience.md).

## User valves (`Pipe.UserValves`)

User valves provide per-user behavior overrides for a subset of settings.

| Valve | Type | Default (verified) | Purpose / notes |
| --- | --- | --- | --- |
| `SHOW_FINAL_USAGE_STATUS` | `bool` | `True` | Display tokens, time, and cost at the end of each reply; the cost appears only when it is above zero. |
| `THINKING_OUTPUT_MODE` | `Literal[\"open_webui\", \"status\", \"both\"]` | `open_webui` | Choose where to show the model’s thinking while it works. |
| `ENABLE_ANTHROPIC_INTERLEAVED_THINKING` | `bool` | `True` | When enabled and the selected model is Anthropic (`anthropic/...` or a `~anthropic/...` router alias), send `x-anthropic-beta: interleaved-thinking-2025-05-14` to opt into Claude interleaved thinking streams. |
| `REASONING_EFFORT` | `Literal[\"none\", \"minimal\", \"low\", \"medium\", \"high\", \"xhigh\"]` | `medium` | Choose how much thinking the AI should do before answering (higher depth is slower but more thorough). |
| `REASONING_SUMMARY_MODE` | `Literal[\"auto\", \"concise\", \"detailed\", \"disabled\"]` | `auto` | Choose how detailed the reasoning summary should be. |
| `PERSIST_REASONING_TOKENS` | `Literal[\"disabled\", \"next_reply\", \"conversation\"]` | `next_reply` | User-level reasoning retention preference: `disabled` writes nothing, withholds rows already stored from every later turn and deletes them on the same terms as `next_reply`, and does not save each reply's `reasoning_details` onto the stored chat message; `next_reply` keeps thoughts until the following assistant reply finishes; `conversation` keeps them for the full chat history. The copy of the reasoning written onto the Open WebUI assistant message follows the same choice, and at `next_reply` that copy is not removed when the following reply finishes; only the rows are. A setting the pipe cannot read (an undecodable stored row, after a rotation of the application secret) falls back to this per-user default, not to the administrator's site-wide value. |
| `PERSIST_TOOL_RESULTS` | `bool` | `False` | Let the AI reuse outputs from tools later in the conversation. When off, a round that arrived before the chat's first turn counts as earlier too, and a question the AI's built-in `ask_user` tool asked you and your answer always go back to it. The turn the request ends in is never withheld: a round is withheld only when its turn is earlier than the final one, so a round whose assistant message opens the chat is kept while no later turn follows it. A temporary chat stores none of its tool results. Tool cards, while shown, still show every result. A setting the pipe cannot read (an undecodable stored row, after a rotation of the application secret) falls back to this per-user default, not to the administrator's site-wide value. |
| `TOOL_EXECUTION_MODE` | `Literal["Pipeline","Open-WebUI"]` | `Pipeline` | Where this user's tool calls run: inside the pipe, or handed to Open WebUI to run. |
| `SHOW_TOOL_CARDS` | `bool` | `True` | Show each tool the AI uses as a card in the chat; off, no card appears, except for a file the AI shows through Open Terminal while Open WebUI shows terminal files inline. The AI still remembers which tools it used, except in a temporary chat, for which the pipe keeps nothing; after Stop, the calls before the first one still running if the reply was streamed, and none if it was not. Tools Open WebUI runs itself (Tool execution mode set to Open-WebUI) always show their cards. |
| `REQUEST_ZDR` | `bool` | `False` | Request ZDR routing for this chat. |

Only the names in this table (those on both the base `Pipe.UserValves` and the base `Pipe.Valves`) are settable per user. Any other name a stored row carries is not a setting this version knows: it is reported, the pipe logs one line naming it and saying the site-wide value is in force, and it is never applied to a field it does not belong to — so a setting renamed or removed between versions surfaces in the log rather than quietly ceasing to apply. A value that does not fit the field's declared type is ignored too, and the administrator's value is kept — nothing is coerced into shape, and the pipe logs one line naming the field.
