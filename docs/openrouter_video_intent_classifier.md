# OpenRouter Video Intent Classifier

The pipe runs a small classifier model before each video generation to figure out what the user actually wants. Without it, the OpenRouter `/videos` endpoint is single-shot and stateless — every request only knows about the latest user message, so a follow-up like "change colour to black" produces an unrelated video instead of a recoloured version of the previous one.

## Why this exists

The OpenRouter `/videos` endpoint takes `prompt`, optional `frame_images`, and optional `input_references`, then returns a video. It does not know about prior turns in a chat. If the user's previous turn produced a video of a cat and they then say "change colour to black", the model has no idea what the cat looked like — it just makes a new video about a black cat (or a black anything).

Other UIs work around this by automatically attaching a frame from the prior video as a reference. The pipe does the same thing now: a small task model reads the chat history, the latest message, and any attachments, then decides what visual reference (if any) to wire into the request before it's submitted.

## What it costs, and how the classifier is found

Every video follow-up that is not short-circuited makes **one small task-model call per candidate it tries**. How many candidates that is depends on the fallback valve and on how many Task Models the host actually has configured: at the shipped default (`VIDEO_INTENT_TASK_MODEL_FALLBACK = other_task_model`, with both of Open WebUI's Task Models set) two candidates are *tried*, not necessarily spent: one call when the first candidate answers, two when one candidate needs its repair, three when the primary spends its repair before the fallback answers, and four when both do — so a turn costs one to four billable calls, and the cost caps below count the turn rather than the calls inside it. A candidate whose reply cannot be parsed is retried once more — while the window leaves that retry a usable share, and always for the last candidate, which keeps its retry until the window is gone — so a turn where every candidate needs that repair makes twice as many calls again, and the four-call rung is not reached by a turn that has no time to use the third call. Those calls all happen inside one window: the whole classifier step is bounded by `VIDEO_INTENT_TIMEOUT_S` (default `8`) rather than each attempt within it, so a fallback task model no longer doubles the wait, and a candidate whose reply does not parse spends its second attempt out of the same window. Each candidate still to run keeps a quarter of that window reserved for it, so a slow primary cannot consume the fallback's share, though at a small `VIDEO_INTENT_TIMEOUT_S` a slow fallback may still not fit — see the `VIDEO_INTENT_TIMEOUT_S` row below. The whole classifier is skipped on a fresh chat with no prior turns and no attachments (`VIDEO_INTENT_SKIP_WHEN_EMPTY_CHAT`, default `True`), so the call is not wasted where there is nothing to classify against. Each call is billable at whatever the chosen Task Model's OpenRouter rate is, which is why the timeout, the skip valve and `VIDEO_INTENT_MAX_TURNS_PER_CHAT` all exist.

The classifier's model id is read from Open WebUI's **config table** — `task.model.default` and `task.model.external`, the two settings behind Settings → Tasks, and both come from **one** read per turn, which asks for all three Task Model settings together. A host that populates the older `app.state.config.TASK_MODEL` / `TASK_MODEL_EXTERNAL` shape instead is still read, as a fallback. This matters because Open WebUI 0.11.4 assigns no `app.state.config` at all, so a resolver that read only that attribute answered nothing on a stock host and every video follow-up degraded open with the classifier silently inert — no warning, just a plain text-to-video with no cross-turn context.

The **third** setting behind Settings → Tasks, `task.model.params`, is read too, by the same one read per turn, and applied to the pipe's own classifier call. Open WebUI applies it itself on its own housekeeping calls (`routers/tasks.py:202` applies the params before the pipe ever sees the request), but on this route the pipe builds the call and hands it to `generate_chat_completion`, which never applies them — so before this, an admin's `task.model.params.temperature` was not merely dropped but actively overridden.

**Where the row lands depends on the candidate model's owner.** For a task model whose row in `request.app.state.MODELS` carries `owned_by == "ollama"`, the row is nested under the payload's `options` key, and the call's own `temperature` is mirrored onto that same arm; for anything else the row is merged at the top level as before and nothing is mirrored. That is Open WebUI's own rule, not a second one: `utils/payload.py:114-116` nests the whole params dict for an Ollama model, and `convert_payload_openai_to_ollama` (`:357-446`) forwards only `options` plus `model`, `messages`, `stream`, `tools`, `num_predict`, `stop`, `metadata` and `format`. A row merged flat onto an Ollama task model therefore arrived nowhere at all, and so did the classifier's own top-level `temperature`, which the converter drops for the same reason — the arm the payload sets it on is not the arm Ollama reads. The mirror is the classifier's value and only the classifier's: an admin's `temperature` is still refused (the payload's own key wins), and the mirrored copy is added beside the top-level one rather than replacing it. The owner is read per candidate rather than once per turn, because the shipped `other_task_model` default crosses internal and external and the two candidates of one turn can have different owners. A task model with no row — an id absent from `MODELS`, or a host that does not populate it at all — takes the top-level branch, so nothing changes for an install that cannot resolve one.

Two kinds of key in the row are deliberately **not** applied here, for the same reasons Open WebUI does not apply them, and this holds on **both** arms of the placement rule:

- **Keys the call already sets.** The classifier sends its own `temperature: 0` and its own `response_format` carrying the JSON schema. A strict-JSON classifier that samples its own output cannot be trusted to hold the schema, so those stay: an admin's row naming either key does not replace them, and on the `options` arm neither key is nested either — an admin's `temperature` under `options` would reach Ollama, replacing the value the payload's own key just won with. What does reach that arm is the classifier's *own* `temperature`, mirrored there precisely because the converter drops the top-level one: without the mirror the `options` arm the admin's value is refused on would carry no temperature at all, and Ollama would sample the classifier's strict JSON at the server's default. `response_format` is not mirrored — it is hoisted out of `options` by the converter into `format`, and `format` is not a sampling parameter. The `strict` flag *inside* that `response_format` is decided per candidate, from that candidate's own catalog row, and is relaxed to `false` wherever the endpoint does not advertise `structured_outputs` — a shared format is fine, a shared verdict is not, so two candidates in one fallback turn can differ. With no catalog loaded at all (a fresh install, before the first refresh, or a test host) every id downgrades, which turns the fault from "every turn degrades" into "less enforcement, and more reliance on the repair turn" inside `VIDEO_INTENT_TIMEOUT_S`.
- **Open WebUI's request-scoped keys** — `system`, `stream_response`, `stream_delta_chunk_size`, `function_calling`, `reasoning_tags`, `compact_token_threshold`, `note_id`, `tool_approval_mode`. These configure Open WebUI's own request plumbing, not a provider call; `system` in particular would otherwise replace the classifier's own system prompt, which is where the schema lives.

`custom_params` is deep-merged after its string values are JSON-decoded, exactly as Open WebUI merges it: a `custom_params` key **overrides** a top-level key of the same name, and an object named at both levels arrives as the **union** with `custom_params` on top. The call's own keys still win over both. It lands wherever the rest of the row lands — a decoded `custom_params` key is nested on the `options` arm along with every other contributed key, not left behind at the top level. The eight request-scoped keys are dropped from `custom_params` too — a deliberate divergence from `utils/payload.py:101-103`, which deletes them from the top level only. `system` is the key that divergence protects: it is the one whose arrival would replace the classifier's own prompt, and the other seven are dropped with it rather than on their own account. A params row that is absent, or is not a dict, leaves the outgoing payload exactly as it was.

When the task model keeps failing, `classifier_failed` is set, the **60-second** intent breaker opens (so the next turns skip the call instead of retrying quietly forever), and a warning plus a toast say so. See "Failure modes" below.

## How it works

```
user turn ─► VideoGenerationAdapter.generate
                │
                ▼
            short-circuits (help / resume / empty / first-turn-no-attachment)
                │
                ▼
            VIDEO_INTENT_ENABLED?
                │
            ┌───┴───┐
           yes      no ─► send only latest user message (no context, no questions)
            │
            ▼
       resolve_intent (task model + JSON schema)
                │
            ┌───┴────────────────────┐
            ▼                        ▼
       clarification needed?    intent + frame_plan
            │                        │
       emit question            materialise frame_plan
       (return)                 (extract frames, upload thumbnails
                                     unless confirm_mode is never)
                                     │
                                     ▼
                                 inject into video_meta["frame_images"]
                                     │
                                     ▼
                                 render Intent Disclosure Block
                                     │
                                     ▼
                                 submit to /videos with frames + cleaned prompt
```

The classifier returns one of five **intents**:

- `text_to_video` — fresh generation; no prior context wired
- `image_to_video` — user-attached image as anchor
- `modify_prior_video` — re-render the previous video with a change ("make it black")
- `continue_prior_video` — temporal extension ("continue", "what happens next")
- `ambiguous` — needs a clarifying question

For every non-trivial intent, the classifier produces a `frame_plan` array (max 4 entries). A provider that does not enforce the schema may return more, and entries past the fourth are dropped and named once in the disclosure block ("This request can use at most 4 reference frames; the rest of your attachments were not sent with it."). Each entry says: *here's the source* (uploaded attachment / prior video first frame / prior video last frame / prior video at timestamp T), *here's the target* (first_frame / last_frame / input_reference), and *here's the index*. The pipe extracts the actual frame, uploads it as an OWUI image, and injects it into the request. This happens only where the chat can hold files; in a temporary chat — a `temporary:` / `local:` id, or a turn that carries no chat id at all — the plan is dropped whole and the request runs from the prompt alone. A prior video named by several entries is read from storage and copied to a private temp once per turn, and that temp is released when the plan is done on every exit path, including cancellation. That read is **authorised as the requester** — the request's own resolved user, exactly as the file-link and attachment reads in the [multimodal ingestion pipeline](multimodal_ingestion_pipeline.md) are, and never as the pipe's storage service account. A turn whose user could not be resolved therefore uses no prior frame: the plan is dropped whole with the named downgrade `frame_plan_dropped_no_storage_identity`, and the person is told (`⚠️ Previous video could not be loaded.`) rather than quietly sent a frame the service account happened to be allowed to read. The **upload** of the extracted frame is a write and keeps the storage account, which is the correct owner for a file the pipe publishes.

The `index` of an uploaded attachment is its position in the user's attachment list — the order they appear in the chat, counting pictures, clips and audio alike. Every attached picture is listed, whether or not the Frames dropdown claimed it as a keyframe: a turn with three pictures and `first_last` selected still reports indices 0, 1 and 2, not 0 and 2. An `index` that names a picture the dropdown did not claim is promoted into the frame slot the entry asks for.

A frame slot holds one frame. When an entry asks for a slot another row already holds, the collision is resolved before the request is built and named in the disclosure block: the picture you set in the Frames dropdown keeps the slot, and the classifier's instruction is dropped (*That picture was already set as this frame, so it was left where you put it.*). The explicit choice in the dropdown wins over the classifier's reading of your words, and the turn still goes out with one frame per slot.

The `attachments` array in the classifier's payload is that list: one entry per attachment the turn carries, each with `index` (its position, 0-based and gap-free), `kind` (`image` / `video` / `other`), `mime_type`, `id`, `name` and `size`, ordered by `index`. A picture the Frames dropdown claimed as a keyframe and a picture it demoted to a reference both appear once, each at the position the user attached it, and neither is listed twice because it occupies both channels. What the pipe does not send is the bytes and not the role the picture plays downstream — the classifier is told *what* the user attached, and it is the classifier's `frame_plan` that says what to do with it. Under `frame_mode="none"` the array is empty by design: the dropdown sends the pictures nowhere, so there is nothing for the classifier to refer to.

### What reaches the task model

The payload is a **window**, not the whole chat. Two lists in it are capped, and both keep the tail: the most recent 24 conversation rows (each still capped at 2000 characters, unchanged) and the most recent 8 prior videos. The tail is kept because the tail is what the turn is about — a head slice would satisfy every bound and answer what the person wanted at the start of a long chat. The prior-video list is **renumbered** after the slice, so `index` 0 is the oldest video *in the list shown* and the last entry is the most recent; both consumers of that list index it positionally, so a slice without the renumber would resolve an answer to a different video rather than to none. `message_index` is a fact about the chat, not a position in the list, and is left alone. When either cap drops something, the disclosure block says so on a ⚠️ line — *Only the most recent turns of this chat were read…* / *Only the most recent videos from this chat were listed…* — because a turn answered from a window looks identical to one answered from everything, and the reader is the only one who can tell the difference.

Everything in the classifier's payload comes from the conversation, so it is untrusted input and is treated as such on every classifier turn. Two checks run before the task model sees a message. Control tokens (`<|im_start|>`, `[SYSTEM]`, triple-backtick fences) and the invisible characters a control token can be spelled with are neutralised out of the user's text, the pipe's standing instructions and every conversation row. And a `<video>` body in a past assistant message counts as a prior video only when it is a relative Open WebUI file URL with at most one trailing slash — `/api/v1/files/ID`, `/api/v1/files/ID/content`, and either of those with a single `/` on the end. A local path, a foreign `https://` link, a traversal and a malformed file id are not one, and neither is a second trailing slash, a query string or a fragment, so none of them can steer the classifier toward continuing a video the user never asked it to continue. The body is passed on exactly as written; nothing is normalised, because what reaches the task model is the wire contract and the frame extractor re-derives the file id from it under its own stricter check.

### Where the answer is read from

The classifier's reader takes the answer from `choices[0].message.content`. When that value is absent, `null`, empty or blank — and that includes a content *array* that carries no text, whether it is `[]`, a list of empty parts, or a list whose only parts are blank — it falls back to `reasoning_content` and then to `reasoning` — the two spellings OpenRouter documents for one assistant field — and reads the answer from whichever of the two carries text, the same fallback Open WebUI's own title, tags and follow-up parsers use (`utils/middleware.py:3962`, `:4017`, `:3905`). A `content` that carries text always wins and is never spliced with a reasoning channel: a reply that answers in both places is a reply whose answer is in `content`. A reply carrying neither is unchanged by the fallback, and the reader's verdict on it — the fault code, the exception class, whether the corrective retry is offered, and the type name in the message — is the verdict it was before. The 256 KiB cap below measures whichever string the reader actually parses, so a reply that moves its whole answer onto the reasoning channel is capped exactly as one that leaves it in `content`.

On a Responses-shaped reply the classifier's reader finds the refusal on the `message` output item as a `refusal`-typed content part inside it, which is the shape that API documents, and as that item's own `refusal` key, which `OutputMessage` does not carry and which is kept as a provider tolerance. A non-blank refusal is `task_model_refusal` whatever else the item carries, and a refusal wins over an answer in the same message, as it already did on the chat arm; the corrective retry's excerpt reads those same two shapes in that same order, so a refusal is quoted back to the model rather than the answer it happened to arrive beside. A blank refusal value is not a refusal, and an output item of any other type is not a refusal however it is typed or keyed. This paragraph is about the classifier's reader; the housekeeping extractor described in `task_models_and_housekeeping.md` is a different reader with its own rules.

### What a temporary chat keeps of the classifier's own state

A temporary chat (`temporary:` / `local:` id — see `temporary_chat_prefixes()`, which resolves from Open WebUI's own published constants) gets the same inference as any other chat and keeps none of it. Three structures would otherwise hold something, and the rule is that a temporary chat reaches none of them:

- **The frame plan** is dropped whole, and the request runs from the prompt alone (above).
- **The once-per-chat warning latch** is never written, so the person is warned on *every* failing turn rather than once. The id is never a key in it. That latch is a bounded window of the most recent **300** warned chats, oldest evicted first, so a saved chat pushed out of the window by other chats in between is warned a second time — the same bound, and the same cost, as the notification-toast record described under "Failure handling" below.
- **The per-chat turn counter** — `VIDEO_INTENT_MAX_TURNS_PER_CHAT` — is charged in a temporary chat like anywhere else, and holds nothing about it: the key is a one-way SHA-256 prefix of the chat id rather than the id itself, and the tally keeps only the most recent 300 chats, so a temporary id is in neither. What that costs is the window: a chat pushed out of those 300 by other chats in between starts a fresh budget.

## Intent Disclosure Block

When `frame_plan` is non-empty, the assistant message includes an **Intent Disclosure Block** rendered before the video appears:

```
🎬 Modifying previous video — using its first frame as anchor.

![ref](/api/v1/files/THUMB/content)

Prompt: "a black cat walking through tall grass"

[generated video appears below]
```

The block also appears on a turn that reuses no frame at all, whenever the classifier wrote the prompt that was sent instead of the person's own words, or stopped asking because the clarifying question limit was reached and guessed. Both need no frame to be worth showing, so on a text-to-video turn the block carries the `Prompt:` line, the `⚠️` note, or both, and no thumbnail. The `VIDEO_INTENT_CONFIRM_MODE` setting still decides: `never` suppresses the block in every one of these cases.

The `Prompt:` line, the clarifying question and each clarification option are each whitespace-flattened onto one line — every run of whitespace becomes a single space — so nothing a person or the classifier writes can be read back as a hidden marker. A two-line prompt therefore reads back as one line; the words and their order are unchanged.

The block is wrapped in hidden markdown markers (`[openrouter:v1:intent_block_start:1]: #` … `[openrouter:v1:intent_block_end:1]: #`) so the next turn's classifier can strip it before parsing — the thumbnail won't be mistaken for a fresh image input. The flattening above is part of what makes that strip hold: those markers are read one line at a time, so a line of somebody's own text sitting where one of them would be is the thing being kept out. Those lines are CommonMark link-reference definitions and render as nothing, which is why a marker body may not contain a square bracket: an unescaped `[` inside the label would turn the line into an ordinary paragraph.

If the user wants to abort because they see something wrong (e.g. the wrong reference video was picked up), they hit Open WebUI's stop button and the `/videos` call is cancelled before the paid request goes out.

## When a model can't visually modify a previous video

The classifier's `modify_prior_video` intent (triggered by prompts like "change colour to black") emits a `frame_plan` entry with `target="input_reference"` — meaning: *use the prior frame as a style/content reference, not as a hard pixel anchor.* This is the only target type that lets the underlying video model repaint or transform the frame.

Most current OpenRouter video models (Seedance, Veo, Kling, Wan, …) only support `first_frame` and `last_frame` — hard anchors that lock the output to the exact input pixels. None of them currently advertise `input_reference` support in the catalog.

When the selected model cannot honor `input_reference`, the pipe **does not** stop to ask the user — it degrades open, and the paid `/videos` call still proceeds:

- The validator drops the `input_reference` frame entry (recorded as the `dropped_input_reference_no_frame_support_for_model` downgrade, which the person reads as "Style reference skipped (not supported by model yet)"). If that leaves a `modify_prior_video` intent with no usable frames, the intent is downgraded to `text_to_video` (`modify_prior_video_dropped_to_text_no_frame_support`, read as "Your request to change the previous video had no frame left to work from, so the new video was made from your words alone.") and the request runs as a plain text-to-video generation from the classifier's rewritten prompt.
- There is no catalog branch to take. The catalog's `supported_frame_images` is a fixed two-value enum (`first_frame`, `last_frame`), so it cannot name `input_reference` and that branch is never taken. Where a model entry does carry `input_modalities`, the pipe withholds a reference whose kind that model does not declare, with a notice; where it does not, the pipe sends the reference and cannot know whether the model read it.

Either way there is no confirmation prompt and no `1`/`2` question; the downgrade is surfaced in the disclosure block — including on the turn it left with no frames at all — and in the telemetry `downgrades` list.

## Frame extraction at arbitrary timestamps

The classifier supports `prior_video_at_timestamp` with `timestamp_seconds`. Examples the system prompt recognises:

- *"use the frame at 5 seconds"*
- *"from the 5-second mark"*
- *"at 0:30"*

The pipe validates the requested timestamp against how far the previous video's **picture** runs — the point on the file's own clock where the last video frame sits, which is not the file's length at all on a clip muxed with a longer audio bed, because such a file is as long as the audio rather than as long as the frames. That point is read from the video stream's own header: with ffprobe present the pipe asks ffprobe for the stream duration, and otherwise it reads the same value out of the container header with ffmpeg. Both of those reads, and both frame producers behind them, begin with the same refusal: a file whose bytes are a playlist a demuxer would auto-select is turned away before any decoder is handed its path, and the refusal is recorded with the extractor's existing downgrade vocabulary rather than as a fault of its own. A handful of headers carry no per-stream length — AVI, MPEG, WMV and ASF, and any other header in that class — and there the pipe asks the same ffmpeg binary how long the **video track** is, isolating that track and reading the last moment it decoded to. When the track measures materially shorter than the container, the pipe's seeks for `last_frame` and for the failed-timestamp retry are aimed at the picture's own end and that measured position is what it reports; when the track cannot be read, is within half a second of the container, or the file has no audio bed at all, the container's length stands and the comparison the pipe already made is unchanged. A track length that lands a frame or so short of the last frame is why the reported position can sit slightly before the picture's very end; it is a measurement, not a constant. A second, separate gap comes from the seek itself: the pipe aims the `last_frame` extraction one frame period, or 0.04 s whichever is larger, before the end it measured, so from 25 fps upward the 0.04 s floor decides and the frame it lands on is that many frames short of the last one — 2 frames at 50 fps, 2.4 at 60 fps and 4.8 at 120 fps. A container whose header carries no length at all — a Matroska or a WebM written as a live stream is one, and so is any headerless variant of an accepted format — is not a container the pipe gives up on: the readers are asked whatever the header read said, and where the two header reads carry nothing the pipe falls back on the reader that times the video track by decoding it, which is the same one the audio-bed comparison already uses. Only a clip no reader can time is left with no measured end, and there a request past the picture is not called an overshoot. A length every reader declined leaves the pipe unable to call a request an overshoot, so the seek is made as asked and a frame is substituted only if the seek itself comes back empty; the disclosure block then says the moment could not be read rather than that it was past the end. The seek itself is made at microsecond resolution, so a moment landing a hair before the clip's own measured length still seeks to the frame rather than being refused as an unparseable duration, and it is capped at the largest position the seek can carry, so a moment the classifier reported as an unbounded number still seeks rather than failing the extraction. The frame still comes back in that case, but whenever the end-seek ladder supplies it, its position is unmeasured: the ladder searched backwards from the end of the file, so there is no moment in the video it can honestly be reported at, and the number the pipe already had is a position the direct seek had just been told has no frame. A request that named a frame outright reports no position at all on that arm, because the frame was reached by seeking from the end of the file rather than at a moment in it. When the requested time is measured as past the end, the pipe downgrades to the frame `Reused frame position` selected and surfaces a note in the disclosure block:

> ⚠️ The requested time was past the end of the previous video; used its last frame instead.

A seek that misses the last decodable frame is retried against the end of the file in one-second hops, taken back from its end and outward, and a damaged tail is walked hop by hop before the frame is given up on, so a tail of up to 30s still yields a frame at a cost of up to thirty children on a file that decodes nothing at all, with the whole walk bounded at 60s. Each hop decodes at most one second of the reach, so what one hop costs does not grow with how far back the arm had to reach, and each hop's own wait is clamped to what is left of the 60s budget rather than to the full 30 s, so the hop the deadline admits cannot carry the walk past 60s. A hop cut short that way ends the walk retryably rather than aborting the entry, so the fall back to the file's first frame below is what a damaged file gets. Every leg of that is bounded, so the worst case is a bound rather than an open end: a `first_frame` extraction spends at most 30 s in imageio and then one 30 s ffmpeg window, and a `last_frame` one spends up to 60 s on the probe — the whole of which the three reader attempts share, so the timing fallback adds no bound of its own — up to 60 s on the end-seek walk, and a final 30 s imageio read; a leg that runs out of time drops that one entry with a note saying which leg ran out. A hop that hits damage inside an otherwise readable file keeps the walk going before the frame is given up on; an input ffmpeg cannot open at all fails on the first hop, because no later hop will read it either. Damage found at any leg before the one that supplied the frame is what the disclosure names, whether the direct seek walked past it on the way in or the end-seek walk did: the substituted frame is reported as coming from later on in a damaged video, which is the one relation to the requested moment that holds on either path. When no hop reads but the file still holds a decodable picture, the pipe falls back to the file's first frame and says so in the disclosure block rather than dropping the frame entry — saying the file is damaged only where a hop actually walked past a decode error, and otherwise that the end of it could not be read. An intact clip with a long audio bed no longer reaches either of those: its picture is measured and the seek is aimed inside it, so it returns its own last frame with nothing disclosed.

Before a `first_frame` extraction decodes anything, the pipe reads the source's declared frame size from the container header and refuses to decode a source over the 25-megapixel pixel budget; the caller then obtains the frame through ffmpeg's long-edge bound, which is the bound the other two targets already return. That rescue answers every plan entry whose target is not `last_frame` -- a first-frame slot, and a style reference, which is written without a `frame_type` label -- and never a `last_frame` one, whose label the provider's capability check reads. The frame that bound returns is the end `Reused frame position` names — the clip's opening still when the setting says `first`, its closing one when it says `last` — except on a model that accepts only a first frame, where there is no last frame such a model could be sent and the first one is substituted whatever the setting says. Before this the rescue asked for the opening frame whatever the setting said, so the setting's published promise did not reach this row of the plan. The frame it sends in place of the refused one is therefore not that frame at all but the end `Reused frame position` names, read within ffmpeg's long-edge bound — so it is a smaller copy of one of that video's frames. The disclosure footer says so in as many words: *"The previous video was too large to use at full size; a smaller copy of one of its frames was used instead."* *"The previous video was too large to read directly; used its first frame instead."* *"The previous video was too large to read directly; used its last frame instead."* Whatever the size asked for, a frame the pipe reads out of an earlier video is bounded to 1920 on its long edge, so a clip generated past that on its long edge is reduced before it is sent, and nothing is disclosed for it: a smaller frame is the frame that was asked for, not a loss. A source whose frame no substitute can rescue — a clip nothing can decode within the bound, or one the byte budget refuses again on the second reading — still comes back as no frame at all; that entry is dropped with its own line saying no frame was used from the previous video, which is a different statement from the one above. That header read costs roughly one extra container open on every `first_frame` extraction, and it is the difference between allocating a few kilobytes and allocating the whole decoded frame (180 MB on a 10000×3000 source) for a source the budget already refuses. The ffmpeg leg now predicts the same scaled size from the same header before it spawns any child, so a source the header already settles costs that header read instead of a decode, while a source the bound rescues costs the decode it always did — the cap is settled before the child exists, and the decoded-size check behind it stays as the backstop for a header that lies. The same entry guard runs *before* that header read: a file whose bytes are a playlist a demuxer would auto-select — `ffconcat`, an HLS/M3U manifest, a DASH or other XML manifest — is refused there, so no decoder is handed a path it could follow into a second file. The guard is two halves rather than one: the header check above is the belt, and it strips leading whitespace, a byte-order mark and `#` comment lines before it matches a header, so a manifest written with any of those in front of its own first token is still the pipe's own refusal and the pipe's own `reason=playlist` line; the demuxer being named on every ffmpeg read is the braces, because that header check only ever sees the first 64 bytes and a manifest padded out past that window is still a file the named container will not open. The refusal is recorded with the module's existing downgrade vocabulary (see "Frame extraction fails" below) and adds no note of its own; each refusal is also named once in the server log at `INFO` by reason — `argv`, `playlist` or `unnamed_container` — carrying no path and no content, and a repeat of one reason is logged again, so the count of refusals is the count of lines.

Every frame the extractor returns is also held under the `VIDEO_FRAME_IMAGE_MAX_BYTES` byte budget, the same limit video generation reads each uploaded frame back against, and the budget is checked on all five paths out of the extractor — including the retry that re-aims a failed timestamp at the end of the file, which previously returned the producer's frame ungated and so armed the turn to fail later, at a read-back neither caller had refused. The gate is measured on the bytes that are actually sent: the **produced PNG** where the allowlist leaves PNG in, and the re-encoded artefact otherwise, checked after the conversion and before the frame is written, so an over-budget frame is never stored and then refused on the way back. A frame over it is dropped with its own ⚠️ note and the turn continues; on the ffmpeg leg the child is stopped part-way through the read once the budget is passed, so a frame that is going to be refused is not buffered whole in the parent first; before this it failed the whole video request from a call site nothing caught. Because a PNG's size follows its entropy and the two producers encode the same frame to slightly different byte counts, the boundary where a frame stops being accepted is a band a few tens of kilobytes wide whose position depends on the ffmpeg build, not a line: a frame inside that band can be accepted for one target and refused for another. With the byte budget at its 12 MiB default and the long-edge bound in front of it, that band sits far from the reachable geometries rather than across them: the largest picture the bound permits is 1920x1920, whose worst case as an incompressible lossless PNG measures about 10.6 MiB, some 88% of the 12 MiB cap. A frame the pipe extracts from a previous video is therefore bounded inside the budget before it is ever encoded, and the budget is a real limit on what the pipe can be handed rather than on what it produced — which is exactly what an **attached** frame still is, and what a previous video's frame is not.

The switch is enforced at request time regardless: it is re-read live on every request and treated as a floor, so a filter row installed while it was on (which keeps pushing `video_intent` into request metadata) cannot re-enable a classifier the operator has switched off.

Two of the other three are enforced the same way, at the off position rather than at the whole range. `VIDEO_INTENT_MAX_CLARIFICATIONS` at `0` and `VIDEO_INTENT_CONFIRM_MODE` at `never` are each a floor: the stored row's value is the value in effect whenever the admin valve is at any other position, and the admin's own off position is the value in effect whenever the valve is there — whatever the row says. So the answer to "can a saved row overrule me?" is: no, not past the off position. `VIDEO_INTENT_FRAME_EXTRACTION_INDEX` has no off value (`first` and `last` are both ordinary settings), so it is never floored, and a value this person actually chose applies as chosen. Nothing here rewrites a saved panel: the pipe writes filter rows, not user settings, and with `AUTO_INSTALL_VIDEO_FILTERS=False` a row is never refreshed, so a panel nobody ever saved carries no choice at all and the admin valve's own value is the one in effect.

## Anti-overasking guardrails

The classifier is biased to act, not ask. Clarifying questions only fire when:

- The user references "it"/"that"/"the previous one" but **multiple prior videos** exist with no positional cue, AND
- The candidate options would produce **meaningfully different outputs**, AND
- The user has not explicitly opted out (e.g., "just do it", "your call", "you decide").

The classifier obeys explicit wiring instructions ("use the previous video as first frame", "use the frame at 5 seconds") without asking. One-word continuations like "more", "again", "encore" trigger continue-prior-video with a default last-frame anchor, no question.

What the classifier writes is bounded before it is shown. A question longer than 280 characters is shortened to its first 280 and still asked, and the shortening is recorded as `clarification_question_truncated`; a question the pipe has no text for is not asked, and that is recorded as `clarification_question_empty`. The menu beside it is capped at five entries — the cap the schema states to the task model — and options past the fifth are recorded as `clarification_options_dropped`. An option longer than 200 characters is shortened at the last whitespace at or before that bound, so what the person reads is whole words rather than the middle of one, and the shortening is recorded as `clarification_options_truncated`; an option with no whitespace to cut at — a URL, a hash, an identifier — is cut at the bound itself rather than delivered empty, because an unbroken token shortened mid-token is still something the person can act on where an empty one is not. Shortening and dropping are different facts and carry different codes: a shortened option is still on the card, renumbered and selectable. All three of these losses are shown **on the question card itself**, each on its own ⚠️ line beneath the menu — the disclosure block is a different surface that a clarification turn returns before it reaches, so a loss recorded only there reached nobody. The pipe's clarification budget is separate from all four and still binds: a chat that has already spent its `VIDEO_INTENT_MAX_CLARIFICATIONS` questions is not asked again, however the question would have been shortened.

## Failure modes

Every failure path in the classifier returns a fallback result equivalent to "no classifier ran": `intent=text_to_video`, `frame_plan=[]`, `prompt=<latest user text>`. The video call still fires; it just doesn't carry cross-turn context. Failures handled:

- **Task model returns invalid JSON** → at most one corrective retry per candidate, while the window leaves it a usable share; on second failure, fall through to the next candidate; if all candidates fail, fallback. The retry is a *correction*, not a replay: the second request carries a repair turn naming the failure and quoting a bounded, control-character-stripped excerpt of what the model produced on that attempt, and lifts `temperature` off 0. On an Ollama-owned task model the lift reaches `options.temperature` too, since that is the copy Ollama samples at, so the repair turn really does escape the determinism it exists to escape. The excerpt is that attempt's own reason, not always a malformed parse: the malformed text for a parse fault, the text the model put on its reasoning channel when it left `content` blank, the refusal text for a policy refusal, the provider's `error.message`, then Open WebUI's `error.detail`, then its `error.code` for an error envelope, and the fixed marker `[the model returned no choices]` when there is nothing to quote. The excerpt is always one of those *named* fields and never a serialisation of the envelope, so a provider's verbatim body sitting in `error.metadata` cannot reach the request; and a content part with no `text` and no `content` key contributes nothing, so an empty excerpt is a real outcome and not a bug. The correction is built from the pipe's *own* payload rather than from whatever the previous attempt's request became, so a callee's in-place rewrite of that dict — Open WebUI's `generate_chat_completion` merges its `request.state.metadata` into it — cannot reach the second request, cannot change what the operator's `structured_task request payload` line records for it, and cannot carry a browser socket id or user id into either. That holds of the *first* request too, and of the classifier's own `metadata`: it carries a chat id only on a chat that is neither temporary nor `local:`-prefixed, and only when `SEND_CHAT_ID` is on, so a Temporary Chat's browser socket id is withheld from the classifier's request and not only from its repair turn. A `channel:` chat is not a temporary chat and keeps its id. Only a model-*output* fault is retried -- invalid JSON, an empty response, a refusal, no choices, an oversized response, or a schema mismatch. A timeout, a cancellation, an `OpenRouterAPIError` of any status, and a wrong response *shape* are not retried: no second request turns those into a 200.
- **Task model answers with an object that is not an answer** → a `choices[0].message.content` that is an object rather than text, carrying none of the eight keys the schema names, is a shape fault: it is refused with `task_model_invalid_schema`, which earns the same corrective retry as a parse fault, and a second failure of the same kind degrades open with `classifier_failed` true. An envelope such as `{"result": {...}}`, `{"json_schema": {...}}` or `{"output_text": "{...}"}` used to be read as the answer and handed to the validator, which found no `intent` in it and settled for its default — a confident, unclassified text-to-video built from the user's own words, with nothing anywhere recording that the model was never actually asked. The predicate is not "every object": one that carries any key the schema names *is* the answer, is returned unchanged, and is validated as before. One key is enough, so a partial answer is completed by the validator's own defaults rather than refused.
- **Task model reply exceeds 256 KiB** → the reply is refused before it is parsed and the candidate fails, on every response shape: the joined `output[].content[].text`, the un-stripped `choices[].message.content` string (or the `reasoning_content` / `reasoning` string that replaces it when `content` is absent, `null` or blank, or is an array carrying no text — the array shapes are replaced too, and are capped as the one string they became), and the `json.dumps` serialisation of a `choices[].message.content` **dict** (the shape the live non-streaming caller receives, and the only one of the three a production call takes). The cap is a content bound in **characters**, so a dict — which has no character count of its own — is measured on its serialised length when the dict **is** the answer, and a dict which is **not** the answer is measured on that same serialised length before it is refused for its shape: the two orderings are the cap's, and a dict that clears the cap is still refused afterwards if it carries none of the schema's keys, while a dict that **is** the answer is still returned verbatim, the same object it arrived as. A dict that is a content-part *envelope* is first normalised to its extracted text and measured on that instead, so a small answer inside a large envelope is no longer refused for the envelope's sake. And a value the guard cannot serialise at all (a circular or 2000-deep object) counts as oversize rather than as a pass. It is also not the only bound: reading a streaming body holds at most four times that cap of task-model text at once and refuses a larger body with the same `task_model_response_too_large` while it is still arriving, so the read itself cannot become unbounded no matter how large the body is. That is a safety bound on the read, not a second opinion about a reply's size, and a reply that should be refused is still refused by the 256 KiB content cap above. The reply is never truncated and parsed as a prefix: that raises `task_model_invalid_json`, which reads as "the model spoke nonsense" and sends the operator looking at the model instead of at a provider returning a 4 MB body.
- **No task model configured** → fallback, and the turn is recorded as a classifier failure with `failure_reason` `no_task_model_candidates`. This is the one failure mode with no provider, no request and no exception behind it: the candidate list came back empty, so no call was made, and the reported code carries no exception-class prefix for that reason. `task_model_latency_ms` stays `0` and `task_model_fallback_triggered` stays `false`, both of which are already correct on this path and are the honest values — nothing was called and no candidate was passed over. The per-user breaker is **not** armed (see the `breaker tripped` row below), the person is warned once per chat through the first-failure toast latch, and the paid video generation proceeds from the latest user message.
- **The task model's window is the limit, and it is now bounded by the pipe** → the payload carries the most recent 24 conversation rows and the most recent 8 prior videos, so its size no longer grows with the chat. Before this, a chat of a few hundred turns produced a payload large enough to exceed the task model's own context window; the failure arrived as an `OpenRouterAPIError`, which the retry ladder does not correct, so the turn degraded to plain text-to-video having spent the classifier call to learn that. The rows that were left out are named on ⚠️ lines rather than being invisible. The recorded latency on that turn covers every attempt, not just the last, and every one of them is charged against that one window. A timeout is not retried, so it costs one call per candidate, all of it inside the step's single budget rather than a fresh one apiece.
- **Frame extraction fails** (corrupt prior video, unsupported codec) → drop that frame_plan entry, append a downgrade note to the disclosure block, continue with other entries; if every entry fails, send text-only. A clip whose tail is damaged but which still decodes is not this case: the end-seek walk takes one-second hops back from the end of the file until one reads, and the frame that comes back is never presented as one from past the end. Nor is a clip no window reads but whose first frame still decodes: the pipe falls back to that frame and keeps the entry, and what the disclosure block says about it depends on what was actually seen — a damaged video where a hop walked past a decode error, and otherwise that the end of the video could not be read, because on an intact clip whose picture ends long before the file does every end-seek hop lands in the audio. A file neither ffmpeg nor the imageio fallback can read at all is this case, and so is an entry past the plan's ceiling of four: it is dropped before anything is extracted, recorded once as `frame_plan_capped_at_4`, and named on a single ⚠️ line in the disclosure block however many entries it was. A frame over the `VIDEO_FRAME_IMAGE_MAX_BYTES` byte budget is this case too, and is named as the size drop it is rather than as a failed extraction. So is a leg that runs out of time — 30 s for an imageio read, 60 s for the duration probe — which drops that one entry and lets the turn continue, exactly as a file neither producer can read does. So is a file whose bytes are a playlist — an `ffconcat` list, an HLS/DASH manifest — and a name beginning with `-`, or in a container the pipe does not name: all three are refused before any decoder is handed the path, and each drops the entry with this same note rather than with a refusal code of their own. Each of the three is also named once in the server log at `INFO` by reason, carrying no path and no content. A frame the pixel cap refuses before decoding is the exception, and an exception that says which half of it happened: a source whose frame the cap would not decode keeps its entry and is named as a smaller copy of one of that video's frames, and a source no substitute can rescue is dropped under a line of its own saying no frame was used from the previous video.
- **A frame is substituted, and the entry is kept** → the `frame_type` slot keeps the name the request gave it even though the picture is another one. `frame_type` is a position in the **output** video — OpenRouter's own field is *"Images to use as the first and/or last frame of the generated video"* — not a claim about the source file, and the slot says where the image anchors the new clip. Reading it off the picture instead is what makes a paid, already-extracted anchor unsendable: a model publishing only `last_frame` refuses a `first_frame` label outright, and the whole render is lost at the provider after the classifier has been billed. Which picture actually filled the slot is stated in the disclosure block instead, so the two are allowed to disagree — and do, only on a substituted frame. The two other `frame_type` write sites already label by the requested target (the uploaded-attachment retargeting and the user-driven filter renderer), so the extraction site follows them.
- **The request carries no `frame_images` key at all** — the filter claimed no frame, so a plan entry naming an uploaded attachment as a `first_frame` or `last_frame` has nothing to re-target and is recorded as `retarget_skipped_no_frame_images_idx_<n>` instead of being applied. The key is absent whenever the filter claims no frame: a turn whose only attachment is a clip, a model the Frames dropdown leaves frame-free, or a stale filter row. Nothing is invented to fill it — no `frame_images` list is created and the attachment is not promoted — so the turn still renders; the entry is only named, in the log and in `downgrades_count`, and an `input_reference` target names nothing because that picture still travels as a reference. The two sibling codes beside it are `retarget_skipped_invalid_index_<n>` (the entry named an attachment this turn does not carry) and `retarget_skipped_non_image_frame_<n>` (the attachment is there but is not a picture).
- **A plan entry names a moment that is not a usable timestamp** — a non-finite `timestamp_seconds` (`NaN` or `Infinity`, both of which a well-formed JSON reply can carry) or a number too large to be a float → the validator drops that entry as `dropped_invalid_timestamp` and the rest of the plan proceeds. The moment is never coerced to `0`, so a request for a named instant cannot silently become a request for the first frame.
- **The classifier writes more than the pipe will carry** → each loss is named in the telemetry `downgrades` list under a code of its own, so an operator greps for the turn rather than inferring it from a quiet video. A clarifying question over 280 characters is shortened and still asked (`clarification_question_truncated`); a `needs: true` reply carrying no question text is not asked (`clarification_question_empty`); a menu longer than five options keeps the first five and drops the rest (`clarification_options_dropped`); an option over 200 characters is shortened at a word boundary and still offered (`clarification_options_truncated`); and a `frame_plan` entry the loop cannot use at all — not an object, a `source` or `target` outside the schema enum, or an uploaded attachment whose `source_index` is not an integer — is dropped as `dropped_malformed_frame_plan_entry`, `dropped_unknown_frame_plan_source_or_target` or `dropped_non_integer_attachment_index`. The last three are reachable from any provider whose strict mode does not enforce the enum, since nothing between the reply and the validator checks the object against the schema.
- **Thumbnail upload fails** → disclosure block omits that thumbnail and says so on a ⚠️ line ("A preview picture for this frame could not be stored."); the `frame_images` entry still ships. A thumbnail that cannot be *made* is recorded the same way, with "…could not be made." Every per-entry outcome carries the plan position as well as the source index, so two entries asked of the same prior video record two separate codes. Those codes differ in the log and in the block's data, but the ⚠️ line the reader sees is chosen from the base code with its position stripped — so two entries that fail the same way read as two **identical** ⚠️ lines, not one deduplicated line.
- **Frame upload fails** → the same falsy id, one step earlier in the block, and the consequence is the other way round: the `frame_images` entry does **not** ship, because a frame that was never stored has nothing to send, and the entry is dropped with "Frame could not be uploaded." on its ⚠️ line. A falsy id is not an exception, so this arm is not reachable by guarding the `try` alone — `upload_to_owui_storage` answers that way when it has no upload handler, when the handler hands back a row with no usable id, and on any failure to store at all. The two arms differ exactly in what survives: the preview is optional, the frame is the reference the model needs, so a storage refusal between them costs the user the frame and not merely its picture.
- **User cancels mid-classification** → cancellation propagates up; `/videos` is never submitted — but the per-chat / per-user-day cap charge was already spent at admission, with no refund.
- **Model can't honor `input_reference` for modify intent** → the validator drops the reference frame ("Style reference skipped (not supported by model yet).") and downgrades the intent to `text_to_video` ("Your request to change the previous video had no frame left to work from, so the new video was made from your words alone."); the paid call proceeds as text-to-video with no confirmation prompt. See "When a model can't visually modify a previous video" above.

The **first** classifier infrastructure failure per chat surfaces a notification toast: *"Intent inference unavailable; using simple text-to-video."* Subsequent failures within the same chat are silent (logged at DEBUG). The rule covers all three failure branches — a classifier that reported failure, a classifier call that raised, and a classifier that never ran because no task model was configured — and holds whether or not the emit itself succeeded.

**Temporary chats are the exception, and deliberately so.** A temporary chat keeps nothing, so it is warned on **every** failing turn instead of once. Its `chat_id` (a `temporary:` or `local:` id — see `temporary_chat_prefixes()`, which resolves from Open WebUI's own published constants, so a new upstream prefix is covered without an edit here) is never written to the "already notified" record, and never printed in a log line. The toast is *not* suppressed along with the key: suppressing the latch is what keeps the raw id out of a process-lifetime structure, and it is not a reason to stop telling the person. A `channel:` chat is a different case and is latched like any saved chat, because Open WebUI does store it.

The no-task-model warning discussed under `VIDEO_INTENT_TASK_MODEL_FALLBACK` above — the one logged when Open WebUI reports no usable Task Model and the classifier is skipped for the turn — is a **second** latch with the same rule: a temporary chat is warned on every failing turn, its id is never written as a key, and the record is a bounded window of the most recent 300 warned chats. It has its own window and does not suppress the toast record, and vice versa; a chat can therefore see the log line on a turn the toast is silent, and the reverse. The two are **independent except on the no-task-model path**, where a single event drives both: that turn produces the latched log line *and* the once-per-chat toast, because the skip is now recorded as a classifier failure (`classifier_failed` true, `failure_reason` `no_task_model_candidates`) and rides the same first-failure latch. What the guard prevents is the *breaker*, not the notice — see the `breaker tripped` row below.

The "already notified" record is a bounded window of the most recent **300** failing chats, oldest evicted first. It is not valve-gated — it fills on the shipped configuration — and the bound is why a chat that falls out of the window may be shown the toast a second time. In practice eviction is not expected within months of continuous, total classifier failure: a failure arms a 60-second process-global breaker, so the window gains at most one entry per minute, i.e. roughly five hours of unbroken failure just to fill it and five more before the first eviction. Eviction happens on the add path only, so the classifier hot path's membership check stays constant-time. The real cost of the bound is that the attribute is an insertion-ordered mapping rather than a `set`.

A call that carries no `chat_id` at all is a third case, and not the temporary chat's twin. It is not a chat Open WebUI stores, but it is a program calling the pipe, not a person whose browser holds a conversation, so it is warned **once per process** rather than on every failing turn. One process-global slot in the "already notified" record stands in for the missing id: the sentinel key `__no_chat_id__` is a latch key and never a log argument, so the `chat_key` on those lines still reads `<not retained>` like a temporary chat's does.

**Diagnostic log lines** for the toast emission path (search these when the toast doesn't appear as expected):

- `video_intent classifier_failed=True; reason=<...>; breaker tripped` — WARNING, fires every time a classifier infrastructure failure is detected. The breaker it names is the failing user's own, open for 60 s. `<...>` is `"<ExceptionClass>: <fault code>"` describing the last candidate's failure — one of the six codes listed under `failure_reason` above, or the exception's class name when the fault is not one of them. It never carries the task model's own words. **It does not fire when no task model was configured**: that path is recorded as a classifier failure and warns the person through the toast latch, but arms no breaker, so this line is absent for it. A missing task model is a configuration state, not the auth or quota fault the breaker's 60 seconds is for, and arming it would also stop the classifier on the next turn — deleting the record this fix exists to create.
- `first-failure toast emitted (chat_key=<...>)` — INFO, confirms the toast was sent to the OWUI event emitter.
- `first-failure toast suppressed (chat already notified)` — DEBUG, expected on the 2nd+ failure in the same chat.
- `first-failure toast suppressed: event_emitter is None` — DEBUG, fires when OWUI didn't pass an emitter (rare; indicates an upstream integration issue). It fires **once per request** for the life of an emitter-less chat, not once per chat, because no notice is consumed on this path. Nobody was there, so the chat's one notice is **not** consumed: the next request that does have an emitter still warns.
- `first-failure toast emission raised (suppressed): <exc>` — WARNING, `classifier_failed` branch only, fires if the event_emitter call itself raised. Pipe continues; the chat is latched and its one warning is spent, so later failures in it are silent. `video_intent classifier failed (degrade-open)` is the enclosing handler's own log line, and is the one to grep for this path (see the note on its two emitters below).
- The raise branch's emit sits in a bare `contextlib.suppress` and logs nothing of its own. The only record for that path is `video_intent classifier failed (degrade-open)`, written **before** the toast is attempted, so it says the classifier raised, not that the toast was lost — unless the handler that emitted it was `integrations/video_intent.py`'s, in which case the line is sanitised as described next.
- That string has **two** emitters, and only one of them is sanitised. `integrations/video_intent.py` writes it with a bounded fault code, so the classifier's own faults never reach the log in clear. `integrations/video.py` writes the same string with the raw exception and a full traceback, for the fault its handler caught. It can only ever see faults from *after* `resolve_intent` returned — the classifier degrades open and never raises — so the task model's own refusal text cannot reach it, but a later step's provider error text can. Grepping that string therefore finds both a code-only line and a raw one.
- The per-candidate `structured_task candidate '<model>' failed: <Code or Class>` WARNING is the other half of that trade, and it is where the fault you triage on comes from. It names the **fault code** for the six task-model faults listed under `failure_reason` above (`task_model_refusal`, `task_model_empty_response`, `task_model_no_choices`, `task_model_invalid_json`, `task_model_response_too_large`, `task_model_invalid_schema`) and the exception's class name for anything else, and the `failure_reason` line names the same fault's code or class, so the two halves agree literally. Its level is **WARNING for the first occurrence of each (candidate model, fault code) pair and DEBUG for every repeat of that pair within the hour**, re-warning once the hour has passed: a task model the host does not have fails the same way on every attempt of every turn, and without that the record rate follows the failure rate. Because a fault outside that list is keyed on its class, two faults of the same class that differ only in a status the code does not carry — a 401 and a 429, both `HTTPException` — remain one key. **Neither carries the raise site's file or line**: the traceback is withheld deliberately, because a traceback renders every frame's source line and, for a provider fault, the exception's own text — `str(HTTPException)` is its `detail`, which is the channel a refusal text would otherwise reach the log through. A missing `File ".../retry.py", line 74` is the trade working, not a logger misconfiguration.
**`chat_key=<...>` in those lines.** The argument is the chat id for a chat the pipe is allowed to remember, and the literal string `<not retained>` when it is not — that is, for a temporary chat (`temporary:`/`local:`) or a call carrying no `chat_id` at all. The placeholder is a real value in the log, not a missing field, and its presence is expected: it says the key was withheld on purpose, because the pipe does not keep those ids. Two consequences worth knowing before grepping: `<not retained>` is not a chat you can look up, and a `chat_key` that is **absent from the latch** after a temporary chat's failing turn is correct rather than a miss — nothing was written. The `__no_chat_id__` sentinel is the one spelling that does reach the latch, on the id-less path, where it is the process-global slot that makes that warning once per process; it is a latch key only, and no log line carries it.


## Rollback

- **Site-wide kill switch**: set admin `VIDEO_INTENT_ENABLED=False`. The classifier is bypassed for every user on every path; the pipe restores its pre-classifier behaviour with no code redeploy. This switch is admin-only: it is read live on every request, so a stale installed filter row cannot re-enable it.
- **Per-user opt-out**: with the admin switch on, a user can disable the classifier just for their own chats via the filter UserValve (`VIDEO_INTENT_ENABLED` on the per-model video filter). Useful when an individual user prefers raw control. This applies to the per-chat opt-out and to `VIDEO_INTENT_FRAME_EXTRACTION_INDEX` without exception, and to the other two settings up to their off position: `VIDEO_INTENT_MAX_CLARIFICATIONS` at `0` and `VIDEO_INTENT_CONFIRM_MODE` at `never` are floors the user's own saved value cannot lift, so a per-user override of either is inert while the admin valve sits there. The master switch itself is never user-settable.

A classifier failure also opens that user's own breaker for 60 s, suppressing classification for them alone — the classifier re-enters Open WebUI as the requesting user, so a failure is that user's model access or quota rather than a site-wide fault. It is not the site-wide kill switch above, and it never silences another user. Its in-process state holds one entry per user who has ever failed, reclaimed when that user comes back after the window has passed.

## Notes for operators

- Free text interpolated into a rendered block is whitespace-flattened onto one line before it is written, and the block's own delimiters are line-anchored, so no user or task-model text can be read back as a marker: the renderer is the only place that knows which lines it owns. The cost is that a prompt the person typed over several lines is shown back to them as one line, with the words and their order unchanged.
- Frame extraction uses PIL+imageio first, with ffmpeg subprocess as fallback. The input demuxer is the pipe's, not the bytes': every ffmpeg read names it from the materialised file's own suffix (`.mp4`/`.m4v`/`.mov`/`.3gp`/`.3g2` → `mov`, `.mkv`/`.webm` → `matroska`, `.avi` → `avi`, `.ogv` → `ogg`, `.mpeg` → `mpegvideo`, and the raw `.h264`/`.264`/`.h265`/`.265`/`.hevc` streams after their own), and a suffix the pipe does not name is refused rather than handed to ffmpeg to work out. A playlist — `ffconcat`, an M3U/HLS or DASH XML manifest — is refused before either producer sees the path, so no name inside the file can send a decoder looking for a second one; the demuxer half is what makes that hold whatever the file's first bytes are, because a manifest padded out past the header window, or simply written without its `<?xml` line, is still a file the named container will not open. The `imageio-ffmpeg` package ships its own ffmpeg binary, so there is no system dependency to install. A system ffmpeg is used in its place when one is on `PATH`, and the long-edge bound is asked for with a `scale` filter that needs **ffmpeg 4.3 or later** for its `force_original_aspect_ratio` option; the shipped wheel is 7.0.2. A host whose system ffmpeg predates that runs the extraction legs with it anyway and the scaling filter is rejected by ffmpeg rather than honoured, so such a host loses the reused frame from a video larger than the bound with a note naming the failed extraction — install a newer ffmpeg, or let the wheel's binary be the one on `PATH`, before relying on frames from large videos. It ships no `ffprobe`, though: on a wheel-only host it is the video track's own length the seek positions and the past-the-end comparison are taken from. That is the same stream length a system `ffprobe` — the official image, and production — reports, so both host shapes reach the same set of seek values. Both hosts bound the same way: an imageio read gets 30 s and the whole probe leg 60 s, so a header or a decoder that never answers costs one dropped frame with its own note instead of a hung turn. One disclosure is lost with the probe's window: a clip is refused here as too small for the model only when its length could be *read* and measured under the floor, so a probe that times out reaches no measurement, that note stops appearing, and the clip is relayed as any other reference. A last frame whose duration the probe read is reported at that position; a frame the end-seek walk found by seeking back from the end of the file is reported with no position (NaN), because the only length that walk had is the container's, and on a clip with a longer audio bed the container outlasts the picture. Both host shapes are exercised: the pipe seeks at microsecond resolution either way, and a measured stream length that leaves a moment a hair before the clip's end still yields a frame.
- Thumbnails are 256×256 JPEG, generated at intent-resolution time (after the classifier returns, before submission). The 256×256 is the canvas, not the picture: the content is fitted onto a white canvas with its aspect ratio preserved and centred **in the picture's displayed orientation**, so a photo a phone recorded sideways is stored upright, and the bars outside it are white. The fit is in both directions, so a source at or above 256 on its long side is scaled down and letterboxed, and a source below it — a small frame off a small clip — is scaled up until its long side reaches 256, which for a square source means the picture fills the canvas and there are no bars at all. Storage cost: roughly 10–20 KB per thumbnail. Under `VIDEO_INTENT_CONFIRM_MODE='never'` the Intent Disclosure Block is never rendered, so no thumbnail is encoded or stored at all and that plan entry's slot is filled with an empty string; every other mode still builds them, including `low_confidence`, whose block turns on the very downgrades that materialisation records. That holds against a saved panel too: an admin `never` is a floor at the mode's consumer, so a user whose per-model filter row still carries another mode gets no block and no stored picture either.
- Filter-injected `frame_images` (user explicitly attached an image) take precedence over classifier output. Plan entries that reference an uploaded attachment the filter claimed as a frame are kept and applied, so phrases like "use this as the last frame" still work. A plan entry that names an attachment the filter claimed as a **style reference** — a clip, an audio file, or an image past the first — is also kept, but it changes nothing: that reference already goes to the model as a reference, not as a frame, so there is no frame to re-target. Plan entries that reference prior videos are dropped when an explicit attachment is present.
- Attachments are collected into one flat list for the classifier: `frame_images` first, then `input_references`, order preserved within each source list, and the index is 0-based across the flat output. Each entry carries a `kind` of `image`, `video` or `other`; a `frame_images` entry is always `image`, and an `input_references` entry is classified by its `content_type` family (`video/*` → `video`, `image/*` → `image`, anything else → `other`). The family is resolved into a per-entry name, never back into the source-list loop variable, so a reference cannot inherit the previous reference's family.
