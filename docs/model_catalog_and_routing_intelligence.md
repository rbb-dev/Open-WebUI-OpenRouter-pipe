# Model Catalog & Routing Intelligence

This document explains how the pipe loads OpenRouter’s `/models` catalog, derives per-model capabilities/features, and uses that metadata to shape requests (reasoning, multimodal inputs, web search plugin attachment, and model allowlists).

## 1. Catalog ingestion and caching

### 1.1 ID normalization (sanitized vs normalized IDs)

OpenRouter model IDs use slash-separated provider slugs like `vendor/model`. Open WebUI function model IDs are dot-prefixed and dot-separated. The pipe therefore normalizes IDs in two steps:

- `sanitize_model_id("vendor/model")` → `vendor.model` (slash-to-dot conversion for Open WebUI display).
- `ModelFamily.base_model(...)` → lowercase, with:
  - pipe prefix stripped when present (`<pipe-id>.…`) - so a valve entry may be written either as OpenRouter's `author/model` form or as the exact id Open WebUI shows in the model picker, and both forms resolve to the same model,
  - date suffixes like `-YYYY-MM-DD` and `-YYYYMMDD` **kept**.

A dated snapshot is a model OpenRouter prices and serves separately, so it is its own key: a request
for `openai/gpt-4o-2024-11-20` goes out with that id, and `spec()`, `supported_parameters`,
`max_completion_tokens` and ZDR membership are read from that row. This is also what Open WebUI
does with a connection's `model_ids` — it publishes exactly the ids that are listed, and never
normalises dates.

`ModelFamily.undated(...)` is the date-insensitive form (`openai.gpt-4o-2024-11-20` →
`openai.gpt-4o` and `openai/gpt-5.2-20251211` → `openai.gpt-5.2`, with any
`:variant`/`:preset` suffix kept). OpenRouter publishes dated snapshots in either spelling, so
both reduce to the same base. Only the rules documented to be
date-insensitive use it: `Models forced to chat completions`, `Models forced to responses` (a
pattern that names a date stamp still matches only that snapshot) and the phase-capable model list.

The two forced-endpoint valves also strip a run of colon suffixes, after the date, so one entry reaches every
spelling of the model it names: `openai/gpt-4o` covers `openai/gpt-4o-2026-01-15`, `openai.gpt-4o:free`,
`openai.gpt-4o:nitro:exacto` and any combination of the two. It is one-directional -- a pattern that names a
tag or a stamp still matches only that spelling -- and it stops before a `:preset/` tag, which is a saved routing
recipe rather than a routing suffix and is only served on `/chat/completions`. Nothing else strips the tag:
`Model allowlist`, the catalogue keys and the spec and price lookups all keep `openai.gpt-4o:free` as its own row.

The normalized ID is used as the stable key for catalog specs and feature lookups. Routing resolves the **exact** catalogue id: a dated snapshot and its rolling id are separate rows with separate keys, and the id map is keyed by the exact form, so it is never a merge key. An id whose base the catalogue does not list — a routing variant the pipe synthesises for an unlisted base, or any other id with no catalogue row behind it — falls through to reconstruction; a variant whose base is listed resolves through that row.

### 1.2 Fetching `/models` and caching results

The catalog is loaded via `OpenRouterModelRegistry.ensure_loaded(...)`:

- Requires a non-empty API key (`API_KEY` valve or `OPENROUTER_API_KEY` env).
- Fetches `GET {BASE_URL}/models` and parses the JSON payload.
- Stores:
  - a sorted list of models (for Open WebUI selectors), and
  - a spec map keyed by normalized ID, and an id map keyed by the exact catalogue ID (for routing decisions).

Caching:
- `MODEL_CATALOG_REFRESH_SECONDS` controls how long the cache is considered fresh (default `3600` seconds). The cache is keyed on the API key as well as the clock, so a key change refetches immediately instead of waiting out the TTL — on that credential's first round; once it has a failure window of its own, that window is what it waits out (see below). The Zero Data Retention roster that comes back is kept per credential rather than in one process-wide slot, for as long as that credential keeps being used: every read and every write re-stamps it, an entry is dropped once it has gone untouched for four hours (four times the shipped `MODEL_CATALOG_REFRESH_SECONDS`), and a least-recently-used ceiling of 64 sits far above any live set so a burst of rotated one-shot keys inside the window cannot grow the map without limit. The credential in hand is never the victim — its own stamp is refreshed on the way in — and one install, which runs a single key since the pipe reads `API_KEY` and nothing else, keeps exactly one entry. A credential whose roster is dropped is re-read when it returns rather than answered from cache, and that only happens once its retention window has passed with no use: within the window the roster that would answer for it is still on hand, which is why widening the freshness window does not widen what the ZDR gate can be asked about. The model-list path queues behind a media sweep already running, as described below; a chat request arriving during one is answered from the catalogue already in the registry and does not wait.
- A refresh is single-flight: concurrent callers on a stale cache queue behind the one already fetching, and the waiters re-check the clock rather than each starting their own. The video and image loaders carry the same single-flight, keyed the same way, and also carry a per-loop *in-flight marker* set inside the lock and cleared in a `finally`. A chat request that arrives while a media sweep is running passes `wait_for_in_flight=False` and is answered at once from the catalogue already in the registry, rather than queueing behind a fan-out it did not start; the model-list path keeps the default and still joins, so a picker is never published before the registry holds the models. The consequence is deliberate: a request arriving mid-sweep is served from the previous catalogue, and a newly registered model appears on the *next* turn. A request that arrives mid-sweep on a registry the sweep has not written to yet -- a cold registry, which is every worker's first sweep and the state after an `ENABLE_VIDEO_GENERATION` off/on cycle -- would otherwise be told the pipe rejected the model for configuration restrictions nobody set, so that one case says the video catalogue is still loading and that the next turn will carry the model. The marker is keyed on the running loop exactly as the locks are and held weakly, so it goes when that loop object becomes unreachable; it is bounded more tightly than the locks, because `_set_video_sweep_in_flight` clears the marker when the sweep itself ends, so a sweep that has finished releases its marker even while its loop is still referenced. Queueing still applies when the fetch in flight fails or comes back empty, so a burst of callers cannot multiply into a burst of requests. The cost of collapsing a burst that failed is that the same pass stamps both the model clock and the contract clock, so the next retry after an OpenRouter outage is suppressed for `MODEL_CATALOG_REFRESH_SECONDS`; that is deliberate, and it is what makes the two media loaders collapse a burst identically — the image one stamps its model and contract clocks on the same pass, and the video one stamps its model and modality clocks the same way. An `asyncio.Lock` binds to the loop that first contends it and never gives it up, so a single shared lock cannot serve two loops. Each of the four locks that guard these loaders -- one for the model list, one for the image catalogue's contract sweep, plus the `image` and `video` catalogue locks themselves -- is therefore keyed on the running loop and held weakly, so an entry goes when that loop object becomes unreachable and not when the loop finishes: a loop that has finished but is still referenced keeps its entry, and a process that has run N still-referenced loops holds N entries per accessor. The mapping never keeps a loop object reachable itself. The mapping is read without the guard and written under it, so the cost of a cache hit is one dictionary lookup. What this guarantees is that a lock, once given to a loop, is only ever returned to that loop: no loop is handed another loop's fetch. Single-flight within a loop holds exactly as described above, and the two loops a test session runs are independent of each other rather than serialised against one another.
- On refresh failures, the registry records an exponential backoff window. If cached models exist, the pipe can continue serving them; if no cache exists yet, the error is surfaced to the caller. The window is `5 s × 2^(failures−1)` with the exponent capped at 5, so the doubling stops at `160 s` however long the outage runs, and `MODEL_CATALOG_REFRESH_SECONDS` is a further cap on it that binds only when set below 160. The window a failure computes is its own retry deadline; the settle below is what puts it in front of the next call, and it does so only from the second raising round, so the 5 s rung the doubling starts from is written and never waited out. `_record_refresh_success` replaces it, and resets that account's failure count to zero, for a successful fetch **under the same account**. Both the attempt record and the failure count are per credential, so one account's outage no longer makes another account believe the key changed on every call — that would otherwise settle the newcomer on `0.0` and issue a request per model-list build. Those per-credential records are kept for the most recent 4 credentials, by the same oldest-first trim the ZDR maps use: a write re-inserts its own key last and drops the oldest over that cap, so the credential in hand is never the victim of its own write. That cap is a count on purpose — an error string has no age, and `runtime_metrics.py` reads the counts — so it is not the roster's bound and does not move with it. On an empty spec map — a fresh install, before anything has ever been fetched — the cold path consults only the window that credential's own last failure recorded, never the freshness horizon, which is derived from a fetch that has not happened. A model-list build inside that window issues no request and still refuses the request with the catalogue-unavailable card, rather than returning an empty model list that the caller would read as a model it does not carry.
- A per-credential settle rides on top of the backoff. After the second consecutive failing round under one credential, the window that round recorded becomes the clock that credential's next call consults, so a raising endpoint issues no further request per model-list build until that window expires; the first fetch after it expires is a normal one, and any successful round clears the record. The settle is keyed on the raising credential and reads that credential's own recorded value, so one account's outage is never another account's reason to skip a read. It is bounded the same way as the roster — the same four-hour access-refreshed retention window and the same least-recently-used ceiling — and the two share one lifetime by construction, so neither can be forgotten while the other still suppresses a read. The ceiling is 64 and not 1: a cap of one would let an account that reads first suppress the read of the account that reads second, and on a multi-key install the two interleave on every model-list build. A credential older than the cap has its settle record dropped with its roster, so a returning credential finds no recorded window and re-reads rather than inheriting another account's backoff.

The video and image catalogs now carry the same failure backoff as the chat list, keyed per credential and per media catalog. After a failed fetch of either, the next attempt is no sooner than 5 s later, then 10, 20, 40, 80 and 160, capped by `MODEL_CATALOG_REFRESH_SECONDS` whenever that is set below 160 — the chat ladder's own arithmetic with the cap applied outside the 5 s floor, which agrees with the chat path at every interval the shipped `ge=60` bound allows. The count is held per credential and cleared by a successful fetch of either under that credential, so one key's outage never paces another's media list; it is a counter of its own, beside the video clock's account stamp and the image pair's, and all three are keyed per credential — the video clock's since the two catalogues were aligned, the image pair's from the start. A fetch that returns no models is an answer rather than a fault: it stamps the clock and leaves the count alone, so a quiet proxy is not paced like a sick provider. The counts are bounded to the most recent 4 credentials, the same oldest-first trim the failure maps use, so a multi-key install does not accumulate one entry per key it has ever failed under; they are not on the ZDR maps' retention window, which is a horizon rather than a count.

The image catalog's two clocks are keyed the same way. Its model-list attempt and its contract-sweep attempt are each stamped with the credential that asked, and both carry that account's fingerprint, so a changed key refetches the list and re-reads every model's published contract at once instead of serving the new account the previous one's state for up to `MODEL_CATALOG_REFRESH_SECONDS`; the same fingerprint inside the window still reads fresh, whatever credential read in between. With two installed copies configured with different keys, each one's clock and its published contracts belong to that copy alone: the second copy's routine model-list build — or a chat turn on it, which asks for no contracts at all — does not withdraw the first copy's settings panels, and a reader is answered only from the `(base URL, credential fingerprint)` pair it names. The accepted cost is unchanged: a deployment that alternates two keys still re-reads the image list on every model-list build, because the freshness decision itself is still one process-wide clock. The two clocks share one account stamp rather than one each, so "the models were re-read under the new key but the contracts are still fresh from the old one" is not a state the store can be in. The adapter's own per-model contract cache is keyed on the same fingerprint, so a contract fetched under one account is never served to a request made with another.

The video catalog keeps two clocks in that shape, and the fingerprint sits on one of them rather than on both: the list attempt carries the account stamp beside its timestamp, and the modality attempt carries none, because a model's input kinds are a fact about the model rather than about the credential that read them. Its model-list attempt and its modality-sweep attempt are separate records, and only a caller that actually swept stamps the second: a chat request refreshes the video list with `with_modalities=False`, so it satisfies the list half of the freshness check and not the sweep half, and the next picker build performs the sweep that is still owed — against the rows that chat request already registered, reusing the list it fetched rather than re-fetching it. A row the sweep did not answer is republished with the input kinds it last published, so an outage costs a model nothing it had already been told. The video catalog's clock is keyed the same way: one fingerprint beside the one timestamp, not one per clock as the image pair has, because there is one video clock where the image catalogue has two -- a second name for the same window is how the two drifted apart in the first place. The accepted cost is the image one, a deployment that alternates two keys re-reads the video list on every model-list build.

The video catalog is registered on top of the chat catalog, and where they meet, the chat field wins: a normalized ID that already holds a chat spec keeps its `features`, `capabilities`, `context_length`, `max_completion_tokens`, `description`, `pricing`, `architecture` and `full_model`. The name is the one field the registry does not own at display time: what the picker shows for a dual model is the name on the stored `Models` row, because Open WebUI overwrites the published label from that row whenever a matching row is active, and the published id always matches the pipe's own row id, so that overlay always fires. The update path passes that name through unchanged (`name=existing.name`), so a name an operator gives the row in Open WebUI survives every later metadata pass -- and a row inserted while the video catalog held the name keeps it, the operator's to rename rather than the registry's to refresh. The registry's own name is therefore only what the row was first written with, and nothing on the update path corrects it. The video catalog contributes the row's `video_model` and the features and video-only capability flag that go with it, plus two more capabilities on a hybrid -- `vision` and `file_upload`, each derived from the merged feature set rather than from the chat row alone, so a chat twin that takes pictures and a video row that publishes no frame images still agree on both surfaces -- but not its name. That holds across a chat refresh and not only at registration: when a chat `/models` answer republishes a normalized ID the video catalog still publishes, the registry re-applies the same merge rather than replacing the row, so the video contract does not disappear for the length of a catalog cache window. Only the video catalog's own claim decides that -- a normalized ID it claims but has no row for is left alone, and one it stops publishing is still returned to the chat row. The image catalog does not merge: it leaves an existing chat spec alone and registers no image row at all for an ID the chat catalog already lists. A normalized ID in neither catalog registers from its own row alone. The chat side's `image_output` / `image_gen_tool` features are the exception: they are dropped from a dual model, which has no `image_model` row to serve them, and a chat refresh in turn wins over a video or image spec on the same ID.

Ownership runs the other way too, on the retirement side: where a normalized ID is in both catalogs, neither the video catalog's refresh nor the image catalog's sweep may retire it, and the image sweep may not re-register it either — a row the chat catalog still lists keeps the chat catalog's spec, features, `supported_parameters`, `context_length` and `description`, not the bare endpoint listing the image catalog publishes for the same slug. This is why a model with `image` and no `text` in `output_modalities`, which belongs to both catalogues, keeps its chat row. A refresh that stops listing such an ID — a sweep that publishes fewer rows than the last one, since a `/videos/models` answer of zero rows keeps what the last refresh published and is not a withdrawal — returns its row to the chat catalog's own features, capabilities, `supported_parameters`, `pricing`, `free`, `architecture` and `full_model`: the video claims (`video_generation`, `video_output`, `video_model`, `capabilities.video_generation`) are dropped rather than subtracted, because the video row's `supported_frame_images` also contributed `vision`, which is a legitimate chat feature and has to survive, and the passthrough set is restored to the chat catalog's own because the video row's `allowed_passthrough_parameters` is the video endpoint's parameter list, not the chat model's — leaving it behind reads a tool-capable chat model as one that publishes no tools, and the orchestrator then strips every tool the request carried. The same rule takes back the two fields the video arm derived while its contract was attached: `architecture` returns to the chat row's own `output_modalities`, and `free` is re-derived from the chat row's pricing, because `spec_derived_flags` stamps `free: false` for any row carrying a `video_model` and that stamp outlived the contract that made it. Only a normalized ID in neither catalog is retired, the moment it leaves `/videos/models` or the image catalog's own list in a *non-empty* answer, and through the image catalog's master-disable arm (`ENABLE_OPENROUTER_IMAGE_GENERATION` off), which retires the same image-only rows a non-empty sweep does. A *fetch* that answers an empty list retires nothing on either media catalogue: both keep what the last successful refresh published and log, once, that the previous set was kept, because a `200` with an empty `data` array is not distinguishable from a provider withdrawal (Open WebUI's own base-model list keeps its previous answer for the same reason, and the chat registry raises and keeps its cache). The accepted cost is that a genuine *total* withdrawal of the video or image catalogue is not honoured until the worker restarts or the valve is toggled off and on, since no non-empty answer will ever arrive to reconcile it.

### 1.3 Derived spec fields (what the pipe computes)

For each model, the registry stores the full catalog entry (`full_model`) and derives:

- `supported_parameters`: the provider-reported supported parameter set (stored as a `frozenset`).
- `features`: a set of higher-level flags derived from `supported_parameters`, model architecture, and pricing metadata:
  - `function_calling` (based on support for tools-related parameters)
  - `reasoning` and `reasoning_summary` (based on reasoning-related parameters)
  - modality flags: `vision`, `audio_input`, `video_input`, `file_input`
  - `image_gen_tool` (based on output modalities)
- `capabilities`: a dictionary of Open WebUI “capability checkboxes” used for UI affordances (for example `vision`, `file_upload`, `web_search`, `image_generation` — the catalogue's own answer about pictures, which all three media writers publish). On both published surfaces `vision` means **image** input, matching Open WebUI's own label for the box: a `video` input modality alone publishes neither `vision` in `features` nor `vision` in this dict, so a row OpenRouter says takes video but no picture is not offered the picture checkbox. On a model both catalogues list the video writer derives `vision` and `file_upload` from the merged feature set, so the two surfaces cannot disagree: whichever side put the feature there, the checkbox follows it, while the six keys the chat row owns (`web_search`, `image_generation`, `code_interpreter`, `citations`, `status_updates`, `usage`) keep the chat row's values. Video input is published as the `video_input` feature and, republished into the model's own `pipe_meta` capability dict, as `video_input` — a different dict from this one, and the one the Direct Uploads filter reads before it diverts a clip. It is never published as `vision`. Alongside those, the dict always publishes the always-on UI toggles (`code_interpreter`, `citations`, `status_updates`, `usage`). The always-on list is what the *catalogue* writes: it always publishes `citations: True` for a chat model. What a row can *say* is a separate matter once an operator has taken the box over — `citations` is now seeded rather than assigned, like `web_search`, so an admin's untick survives a refresh, and the pipe honours it on the tool path by publishing no tool-derived source for that model (Open WebUI's own `url_citation` annotations and the pipe's Fusion item sources are not gated, because Open WebUI does not gate its own). A row that carries no `citations` key at all is on. The `Files` box inside `meta.builtinTools` is the one entry that is not a capability: the pipe unticks it only on a pass that also unticked `capabilities.file_context` itself, and it records the boxes it filled under `meta.openrouter_pipe.builtin_tool_defaults`, as a list of key names, so a box an operator set by hand is never recorded as the pipe's and never changed by it. A row filled by a version before that record existed carries none and keeps its box.
- When enabled, the pipe can also sync these capability checkboxes into Open WebUI model metadata (`meta.capabilities`) so the UI reflects OpenRouter’s catalog.
- `web_search` is seeded from the model’s published `web_search` pricing and is never overwritten once you have set it, so a model OpenRouter does not price for search can still get Open WebUI’s native search by a manual tick. This applies to rows the pipe writes; a row synced by an earlier version keeps whatever `web_search` value it already has until an admin edits it. `citations` is seeded the same way, with the catalogue's own `True` as the value a row with no setting receives, and so is the `Files` box of `meta.builtinTools` that the `file_context` untick earns — seeded, never overwritten, and recorded by name so the pipe can tell its own fill from an operator's.
- `max_completion_tokens`: taken from the model’s `top_provider.max_completion_tokens` field when present.

The derived specs are shared with `ModelFamily` via `ModelFamily.set_dynamic_specs(...)`, so the rest of the pipe can use `ModelFamily.supports(...)` and `ModelFamily.supported_parameters(...)` without depending directly on the registry.

## 2. How models are exposed to Open WebUI (`pipes()`)

Open WebUI requests the available models from the function by calling `Pipe.pipes()`.

Behavior:
- The pipe loads/refreshes the OpenRouter catalog (best-effort; may serve cached models on failure).
- The tail of the call is best-effort too: a failure in the model-metadata sync, in the image-generation filter lookup, or in the plugin `on_models` dispatch is logged and the pipe still returns the models it has. A raise at any of those points would make Open WebUI's handler serve an empty model list, so every picker would lose the pipe.
- The system valve `MODEL_ID` selects which models are exposed:
  - `auto` exposes the full catalog.
  - A comma-separated list restricts the exposed models. An entry holding `*`, `?` or `[` is a glob pattern rather than one id, matched case-insensitively against every catalog row on both the `author/model` and the dotted spelling, so `deepseek/*` publishes that whole family; a pattern is matched as written and is never split on `:` or `@`. A `!`-prefixed entry excludes, and exclusions run after the includes, so `deepseek/*, !deepseek/*:free` publishes the paid rows and drops the `:free` one. A list made only of exclusions starts from the whole catalog, which `auto, !openai/*` also says. A `*` crosses a date stamp, so `openai/gpt-4o*` reaches `openai/gpt-4o-2024-08-06`; globs are literal about the `~` prefix, so `openai/*` does not cover `~openai/...` and `!~openai/*` is what removes one. A list that resolves to nothing exposes nothing, and the pipe refuses every request rather than serving the whole catalog; one `WARNING` names the IDs it could not resolve, and so does an include pattern that matches no row. The one exception is a value of only commas or spaces, which is read as blank and imports the whole catalog. An `@preset/slug` entry resolves to the model before the `@`. A `base_id:tag` entry resolves to that exact tagged model when the catalog lists it as one in its own right — `openai/gpt-4o:free` publishes the `:free` model, not the paid base — and otherwise to its base.
- The pipe returns a minimal `{"id","name"}` list for the model selector.
- The special `openrouter/auto` model is included in the catalog and can be selected like any other model. Auto Router configuration (allowed model patterns) is managed in the OpenRouter UI (Settings → Plugins) and is not surfaced in Open WebUI.
- Optional: the pipe can schedule a background “model metadata sync” that writes Open WebUI model metadata:
  - `meta.capabilities` (capability checkboxes), and
  - `meta.profile_image_url` (model icon as a PNG data URL, on either a fetched or an inline `data:` source, and only when the decoded bytes are within 2 MiB and the pixels within 25 Mpx — an icon over either bound is skipped with a `debug` log, and that line names the icon's `scheme://host[:port]` only — the path and query of a signed catalogue URL are dropped, so the host the operator allowlists is what the record carries; the download-failure and conversion-failure lines carry the same reduced host plus the HTTP status, the exception's class, or the reason, never the exception's own text, which embeds the request URL, and stored the way it displays, so a logo published with a rotation tag is not shown sideways), stamped with the source URL the icon was downloaded from (`image_source_url`; an inline `data:` source is not stamped, since the stamp is the raw catalogue URL and the payload would then ship whole on every model-list page) and with which of the two sources it was (`image_source_kind`: `frontend` for a catalogue icon, `maker` for a maker's logo) so an unchanged source is not downloaded again, and for a model taking its maker's logo the maker's page is not re-fetched either, which keeps a hand-picked icon on that row until its source URL changes — a change to the image at the same URL is therefore not picked up. The stamp records provenance, not a verdict, so the two ways a `frontend` row can leave that state are told apart by the read rather than by the stamp: a pass whose catalogue read DID NOT ANSWER leaves the row exactly as it is and scrapes no maker page, while a read that answered and no longer names that model's icon moves the row to its maker's logo — and
  - `meta.description` (model description text).
  This behavior is controlled by `UPDATE_MODEL_CAPABILITIES`, `UPDATE_MODEL_IMAGES`, and `UPDATE_MODEL_DESCRIPTIONS`. A sync that fails or is cancelled is retried on the next model-list refresh and its exception is logged at ERROR; a sync whose icon sweep ran out of its whole-sweep budget neither fails nor is cancelled — it completes, logs the abandoned models at WARNING, and is retried on the next sync-key change (a new catalogue fetch or a valve edit). The same holds for the provider-routing endpoint sweep, which has its own whole-sweep budget: when it runs out, the pass still completes and logs how many of the listed models were still unfinished, and the slugs it left behind keep their provider data and their routing rows. A sync that could not write every row — because the write raised, or because Open WebUI's own writer reported it did not save that row — completes as well, but it is not a success: it logs the count and the first failed rows at WARNING, logs at ERROR how many were not written or not attempted, releases the sync key, and is retried no sooner than the 60 s retry floor. A sync that could not read the frontend catalogue it was going to consume is not a success either, and is told apart from a healthy one by the warning that names it: the pass still writes the capabilities and filter attachments it can do without the catalogue, reports every model it was asked about, logs the same ERROR count, releases the sync key, and is retried no sooner than the same 60 s retry floor — but only where a valve that actually reads that catalogue (`Model descriptions` or `Model icons`) is on, so a deployment that never consumes it never arms the floor against a host that is answering. All six outcomes are distinguishable from a healthy one, and each is distinguishable from the other. See: [OpenRouter Integrations & Telemetry](openrouter_integrations_and_telemetry.md).
  - New model access control defaults are set **on insert only, and read once per pass**: `NEW_MODEL_ACCESS_CONTROL` determines whether newly inserted OpenRouter overlays are public (wildcard read grant) or private (no access grants), with the `admins` option relying on Open WebUI's `BYPASS_ADMIN_ACCESS_CONTROL` for admin access. A refresh of an existing model **never rewrites** the field: a pass reads the whole row set once and writes it back at the end, so a grant an admin adds or revokes while a pass is running would be undone by the stale snapshot it read before it. The write carries no access field at all on a schema that uses grant lists, which is what leaves the stored set alone, and on a schema that carries `access_control` it hands back the stored principals resolved out of the row it read, so a row the sync rewrote for a capability, an icon, a description or a filter comes out with the access it went in with — unless the row carries a grant that field has no slot for (any principal outside `user`/`group`, `anyone` today), which it refuses to answer at all: `{}` would make the row private and `None` is Open WebUI's own public wildcard, so either would move it. Such a row keeps the grants you set and stops being refreshed, one `WARNING` per row names the model and the principal type it could not carry, and a sync pass counts the refusal with its other unwritten models. A pass already running when you save the valve finishes under the value it started with, so every row it writes carries the same policy. Saving the valve is itself a term of the sync key, so it schedules a pass: the narrowed policy holds for every model the pipe imports afterwards, without waiting for some other tracked setting to move.

## 3. Model allowlists and enforcement in requests

At request time, the pipe computes the allowed model set based on `MODEL_ID` and the loaded catalog:

- The catalog set, the allowlist set, the enforced set and the virtual-variant map are computed **once per (catalogue, specs, credential, zero-data-retention list in force for that credential, valve snapshot)** on the pipe instance and reused while all five of those are unchanged. A change to any of them — a catalogue or spec refresh, a media-model registration, a different OpenRouter credential in play, a different zero-data-retention list in force for the credential in play, or a change to `MODEL_ID`, `VARIANT_MODELS`, `FREE_MODEL_FILTER`, `TOOL_CALLING_FILTER` or `ZDR_MODELS_ONLY` — is visible on the very next request.
- `VARIANT_MODELS` is a second source of admission: a variant whose base is outside `MODEL_ID` is refused at request time, however it is named.
- For normal chat/API calls:
  - if the requested model is not in the allowed set, the pipe emits a user-facing error telling the user to choose an allowed model.
  - The allowed set is computed from the resolved `MODEL_ID` allowlist, so an unresolvable allowlist leaves it empty and every model is refused — and so does an include pattern that matches no row.
- For Open WebUI “task” requests (`__task__`):
  - **housekeeping tasks** bypass the model whitelist (so titles/tags/follow-ups and similar flows can still run even when end-user models are locked down).
  - `moa_response_generation` follows the normal chat restriction path and does **not** bypass the whitelist.
  - task-specific reasoning overrides apply only to housekeeping tasks when the task model is one of this pipe’s owned/allowed models.

See also: [Task Models & Housekeeping](task_models_and_housekeeping.md).

## 4. Capability-driven behavior (how the catalog influences routing)

### 4.1 Multimodal gating (vision and attachments)

The pipe uses catalog-derived capabilities to decide whether to forward image inputs:
- If the selected model is not vision-capable, user image attachments are skipped and a status message is emitted so users understand why attachments were ignored. The status is emitted once per request, on the request's latest user turn, and it names the pictures the gate left out on *any* turn of the request - the turn that carried them and the turns before it. An operator should not expect one status per picture: the count is the number, so a chat with three skipped pictures reports one status saying three.

Details are in: [Multimodal Intake Pipeline](multimodal_ingestion_pipeline.md).

### 4.2 Tooling and function calling

Tool definitions are built from Open WebUI tool registries and other configured sources, but the pipe only attaches `responses_body.tools` when the selected model supports function calling per catalog-derived feature flags.

A request-parameter gate has the same shape and the same caveat. `include_reasoning` is sent only when the primary model **and every fallback in `models`** list it, because OpenRouter forwards the key to whichever model ends up serving and a provider that does not know the parameter rejects the whole request rather than its own leg of it. An id the catalogue does not know counts as not listing it. The gate cannot live in `reasoning_config.py`, which reads the primary only: `model_fallback` is written into `models` later, on the request payload, after every reasoning decision has been made.

The same chain is what the model restriction valves cover. `MODEL_ID` and the model filters judge the primary, and they judge every id in the fallback array the same way, with the same valves: an entry one of them refuses ends the turn with the `MODEL_RESTRICTED_TEMPLATE` card naming that entry, before any request is sent. The array itself is the pipe's to write — a caller-supplied `models` key is discarded on every leg, and a task request follows the deployment's chain on the task leg too.

See: [Tooling & Integrations](tooling_and_integrations.md).

### 4.3 Reasoning defaults and compatibility

The pipe decides how to request reasoning from the selected model's catalog entry: its `supported_parameters` and its `reasoning` object (`ModelFamily.catalog_norm_id`, `ModelFamily.supported_parameters` and `ModelFamily.reasoning_contract`). Which entry is used:

- A routing variant with no catalog entry of its own (for example `:nitro` or `:online`) uses its base model's entry, so it is sent what its base model is sent.
- A suffixed id the catalog lists as a model of its own (for example a `:free` model) uses its own entry. The tags OpenRouter lists as a model in its own right are `:free` today, and `:batch` since 2026-08-09.
- A preset model (`base_id@preset/slug`) gets no reasoning field of the pipe's own, so the preset's saved settings apply; a reasoning field the chat itself carries still goes out and overrides them for that request.

The pipe decides how to request reasoning from the model's catalog entry:

- If the model supports `reasoning`, the pipe populates a `reasoning` object (with defaults from valves such as `REASONING_EFFORT` and `REASONING_SUMMARY_MODE`).
- If the model does not support `reasoning` but supports the legacy `include_reasoning`, the pipe uses that fallback, and the flag is that model's only reasoning channel: an off the request itself carries (`reasoning.enabled` of `false`, or an effort of `none`, including the `reasoning_effort` spelling that becomes that object) decides it, and `REASONING_EFFORT` decides it only when the request says nothing about reasoning. `reasoning.exclude` of `true` is not one of those offs: it means the model reasons and the trace is not returned, which is what `include_reasoning: false` means too, so it is honoured everywhere and never refused. A request that asks for reasoning does not switch an install whose `REASONING_EFFORT` is `none` back on. On a row that is also `reasoning.mandatory` the off is refused like it is on a modern row: there is no effort to substitute on this arm, so the pipe writes `include_reasoning: true` and a chat says so in a status line naming the model. An owned background task is the exception: it is the task valve that decides there, and the pipe writes `true` on a mandatory row without announcing it, because a task emits no status line.
- If neither is supported, the pipe adds no reasoning field of its own; a reasoning effort or reasoning parameter the chat itself carries goes out as Open WebUI would send it.

Gemini 2.5 models:

- The thinking budget (`GEMINI_THINKING_BUDGET`, scaled by the reasoning effort) is sent as OpenRouter's `reasoning.max_tokens`, with no `effort` beside it. A budget the request brought is the only thinking control that goes out, and the `effort` the request or the valve put beside it is not — OpenRouter takes one of the two, not both.
- A budget of `0` sends `reasoning: {"effort": "none"}`, which switches thinking off, except on Gemini 2.5 Pro, which cannot stop thinking and thinks at its own default.
- Every Gemini 2.5 request the pipe shapes carries a `reasoning` object, so the pipe does not send this flag on its own; the one exception is the retry after a provider rejects reasoning, which resends with `include_reasoning: false` alone (see [Error handling](error_handling_and_user_experience.md)).

A request that sets its own `reasoning.max_tokens` overrides the valve: the pipe forwards that number, reduced to `min(number, cap - 64)` when the request carries its own output cap and not at all when that leaves no room for an answer, and writes no competing thinking budget, on every model family and both endpoints. A budget written as a number in a string is read as that number, whatever its spelling, and a value that expresses no number is left out of the request rather than sent. That reduction holds behind `reasoning.exclude` of `true` too, because excluded reasoning still happens and its tokens still count against the cap. While `REASONING_EFFORT` is `none`, though, that per-chat thinking budget is ignored: on a model that can stop reasoning the request goes out as exactly `{"effort": "none"}`, and on a mandatory model too, where the pipe refuses the off and substitutes the lowest effort the row supports. A request that sets none is unaffected by this paragraph.

Effort `none`:

- A model whose reasoning is mandatory (its entry's `reasoning.mandatory`) is never sent `none`: it gets the lowest level its entry lists other than `none`, and no level at all when it lists no other level.
- On other models, a `none` that comes from the pipe's own settings goes out as exactly `reasoning: {"effort": "none"}`, OpenRouter's off switch.
- A mandatory model cannot be asked to stop reasoning at all: an off arriving from the request (`reasoning.enabled` of `false`, or an effort of `none`) or from the `REASONING_EFFORT` / `TASK_MODEL_REASONING_EFFORT` / `GEMINI_THINKING_BUDGET` valves is replaced by an effort the row supports, and a chat says so in a status line naming the model. The flag-shaped offs are refused the same way on a row that takes only `include_reasoning`: the pipe writes `true` and says so, because there is no effort to substitute there. A request that only hides the trace (`reasoning.exclude` of `true`) is not an off and is never replaced.
- OpenRouter accepts one of `reasoning.effort` and `reasoning.max_tokens`, not both: a request carrying the two is answered with a 400 before a provider is asked. So no reasoning object the pipe writes carries both. Where an off is in play — from the request or from the pipe's own settings — the off switch wins and the request goes out as `reasoning: {"effort": "none"}`, the per-chat number with it dropped, on every row that can stop reasoning. A mandatory model cannot be asked to stop at all: the off is refused, and when the request also carried a budget, that budget is what goes out, with no effort beside it, so the substituted reasoning does not turn the repair into a 400. A request that sends both itself at an effort other than `none` is not corrected by the pipe and takes OpenRouter's own 400.

Provider mismatch recovery:
- If a provider rejects reasoning due to a “thinking” configuration mismatch, the pipe may retry once with reasoning disabled (see [Error Handling & User Experience](error_handling_and_user_experience.md)). A row the catalogue marks `reasoning.mandatory` is not retried that way.

### 4.4 Web search server tool attachment

When the **OpenRouter Web Tools** filter is active and the user has enabled Web Search in their valves, the pipe attaches the `openrouter:web_search` server tool to the API request. The model decides when and whether to search — it may search zero or multiple times per request.

For the full User Interface story (Open WebUI Web Search vs OpenRouter Web Tools, and why OpenRouter Web Tools overrides Web Search), see:
[Web Search (Open WebUI) vs OpenRouter Web Tools](web_search_owui_vs_openrouter_search.md).

### 4.5 Output token cap selection

When `USE_MODEL_MAX_OUTPUT_TOKENS=True` and the request carries no limit of its own, the pipe fills `max_output_tokens` with the smaller of the provider-advertised `max_completion_tokens` in the catalog and half that model's context window, or the advertised value alone when its context window is unknown. When it is disabled, the pipe adds no limit of its own and provider defaults apply. The valve controls the pipe's automatic value, not the caller's: a `max_tokens`, `max_output_tokens` or `max_completion_tokens` of 1 or above is forwarded as a whole number whatever its spelling, and a fractional value rounds. OpenRouter documents the parameter as "1 or above" and Open WebUI's slider reaches -2, so a value below 1 is sent as no cap — and the automatic ceiling then applies if the valve is on. A routing variant resolves through its base's row, so it gets the base's ceiling.

On Gemini 2.5 the same cap bounds the thinking budget: `budget = min(budget, cap - 64)`, never the other way round, because reasoning tokens count against the cap and a budget equal to the cap is the documented failure boundary. When the cap leaves no room the pipe writes no bounded budget at all, writes no off flag, and leaves the cap as the caller sent it — except on a row whose reasoning is mandatory, where a request with no reasoning object is not an off switch but a 400: there the pipe keeps asking for reasoning with no bounded budget beside it, and a chat says so in a status line naming the model.

### 4.6 Auto context trimming (context-compression plugin)

When `AUTO_CONTEXT_TRIMMING=True`, the pipe enables OpenRouter’s `context-compression` plugin by appending `{"id": "context-compression"}` to the request’s `plugins` array only when no context-compression plugin is already present.

The same valve owns `truncation` on `/responses` in both states, whatever the request body carried: off pins `truncation: "disabled"`, on sends no `truncation` at all. A caller-supplied `truncation` is overridden either way. The field is on the responses allowlist only, so `/chat/completions` carries no counterpart.

See: [OpenRouter Integrations & Telemetry](openrouter_integrations_and_telemetry.md).

| `ModelFamily.supports(feature, model_id)` | boolean | Feature gates (vision, tools, web search support, etc.). |

A suffixed id — `:tag` or `:preset/slug` — has the suffix split off before the lookup, so it resolves through its base’s catalogue row with the suffix re-attached (`@` before `preset/slug`, `:` otherwise) and the catalogue’s own suffixed row is not consulted. Only an id whose base the catalogue does not list falls through, and then to reconstruction, which re-attaches the suffix the same way. A single leading pipe function-id prefix is removed on the reconstruction path too, and only when what follows it names a vendor segment. An id that is already double-prefixed, or whose remainder is empty or carries no vendor segment, is left alone, so there the function id does remain the provider's namespace. That is the boundary the two spellings of `open_webui_openrouter_pipe.gpt-4o` force: `sanitize_model_id` maps both a pipe-prefixed id and a catalogue id for a vendor slugged `open_webui_openrouter_pipe` to the same key, and the reconstruction path is reached only when the catalogue has nothing to say, so it cannot tell them apart. Leaving a bare remainder alone keeps a catalogue id for that vendor slug reachable instead of rerouting it to a different provider's model. |

## 6. Failure modes and operator signals

- Missing API key: catalog load fails with a configuration error and the pipe cannot expose models.
- Refresh failures with cache: the pipe can continue serving cached models; logs will show a warning about serving cached catalog data.
- Refresh failures with no cache: the error propagates, and requests that require the catalog cannot proceed.
- Empty catalog: all three registries treat an empty model list as an error rather than as a withdrawal. The chat registry raises and keeps its cache; the video and image loaders keep every model the last successful refresh registered and log, once, that the previous set was kept. A non-empty answer that omits a model still retires it, and the master-disable arm still clears the catalogue.
- Missing provider dropdown: the provider map is retained per slug, so a frontend-catalog cycle that returns nothing for a model the catalog still lists keeps that slug's previously fetched providers instead of dropping them. The same retention covers the provider-routing endpoint sweep: a slug the sweep's 45 s whole-sweep budget abandons is treated exactly like one the 50-model fetch cap dropped, keeping its previous cycle's providers with its routing row left untouched and nothing announced as a spelling problem, while a slug whose read finished and failed is still named by the spelling warning.
- Icon Open WebUI would not store: the pipe's 2 MiB / 25 Mpx bounds are its own, and an admin can narrow the receiver's — `PROFILE_IMAGE_MAX_DATA_URI_SIZE` (`.external/.../env.py:984-985`, unset by default) caps a stored data URI, and `PROFILE_IMAGE_ALLOWED_MIME_TYPES` (`:973-980`) narrowed to drop `image/png` refuses every icon the pipe can produce, since its converter normalises every answer to `data:image/png;base64,`. `ModelMeta.check_image_url` swallows its own `ValueError` and stores `None` (`models.py:85-96`), so the refusal is silent. The pipe reads that verdict back off the `ModelMeta` it just built and, when the icon did not survive, writes **no** `image_source_url` and no `image_source_kind` for it: a row naming a source it does not hold makes the next pass skip the download and never converge. The cost is stated rather than hidden — the icon is still re-fetched on every pass, because remembering that the receiver refused a URL is new state; the row becomes truthful, not cheaper. The row's capability record, description and filter attachments are unaffected.
- Failed stored-row read: a metadata pass reads its model rows in one batched query per chunk of 1000 ids. If that read raises, the pipe logs a warning naming the count of ids it could not read and falls back to reading each model on its own, so a broken *batch* can never be read as "these models do not exist" and cannot produce a duplicate overlay insert per model. If the batch read instead *answers* with no rows, there are two states behind that one value, and the pipe tells them apart with one extra call: `Models.get_all_models()`, made once per pass and only on a short answer, is the one read on that class Open WebUI does not launder — `get_models_by_ids` catches its own exceptions and answers `[]` (`models.py:517-524`), and so do `get_model_by_id` (`:502-508`) and `insert_new_model` (`:205-228`), so a dead table and an empty one are the same value to every other call. A table that reads fine but holds nothing is the ordinary first pass: the line is logged at `debug` (it is a fresh install, not a fault) and every model is still inserted. A table that cannot be read at all is a third state, and it is reported as one: the pass writes **nothing**, names every model it declined in the per-pass summary, and logs that the table itself did not read. The cost is one full `select` with its per-row validation and access-grant fetch, once per affected pass — never on a healthy read, where the extra call count is zero. A write the pipe asked for and did not get is counted the same way on the update path as on the insert path, and at the startup `openrouter_*` filter-ID prune: Open WebUI returns `None` for a write that did not land (`models.py:555-556` returns the re-read row on success), so a `None` is a refusal to report, not evidence that the row is broken. A row that vanished between the batch read and the write is one such refusal and is self-correcting — the next pass's batch read misses the id and takes the insert branch. The startup `openrouter_*` filter-ID prune reaches further than the sync does: a stale `openrouter_` id in **any** owner's `filterIds` is what it exists to clean, so it rewrites rows belonging to other applications. It therefore supplies neither an access field (as above) nor a params change — a foreign row's `params` now carry through exactly as stored, and `reasoning_tags` is no longer stamped into them on every process start. The sync still stamps `reasoning_tags`, because it reads that key back as its "already stamped, nothing else changed" sentinel; the prune has no such read.

Operator guidance:
- Treat catalog failures like an upstream connectivity/credential issue first (API key, network egress, proxy/gateway, OpenRouter availability), then inspect logs for the last refresh failure.
