# Concurrency Controls & Resilience

This document describes the pipe’s admission control, concurrency limits, breakers, and background workers that protect Open WebUI from overload and cascading failures.

> **Quick navigation:** [Docs Home](README.md) · [Valves](valves_and_configuration_atlas.md) · [Errors](error_handling_and_user_experience.md) · [Persistence](persistence_encryption_and_storage.md)

## Admission control (requests)

The pipe applies multiple layers of admission control per process:

Across a loop swap (a test runner that calls `asyncio.run` twice, a supervisor that restarts the loop), everything loop-bound is rebuilt rather than reused: the semaphores, the request queue and its worker, the three background task slots below (warmup, Redis init, artifact cleanup), and the log queue's lock. A task left on the dead loop is dropped, and the drop is also a best-effort cancel: on a loop that is closed the cancel would raise and is suppressed, and on a live loop that is no longer the running one the cancel is delivered there. Either way the task that was in the slot stops being the one the pipe owns. A request queue bound to a dead loop is replaced, and the jobs still on it are refused rather than left waiting, so their callers get an answer — and, for a streaming turn, an answer the browser can see: each of those refusals puts a fixed sentence on the job's own stream queue before the terminator that ends it, so a declined turn reads as a declined turn rather than as a turn that said nothing. The sentence is fixed, never `str(exc)`, for the same reason the log line withholds the traceback; each refused job also gives back the in-flight count it was holding, and so does a job that is dispatched and only then finds the process semaphore gone on the way into its own body.

- **Request queue:** requests are wrapped into jobs and enqueued into an in-process asyncio queue (`maxsize=1000`). If the queue is full, the request is rejected rather than queued: a chat caller sees the user-facing “Server busy (503)” card, and a machine caller — one with no chat to write it into — gets an HTTP 503 with the same sentence as the error message. That status is not this arm's alone: every pre-job refusal the pipe raises locally leaves as a status, each carrying its own sentence — 429 for the per-user breaker, which is a per-entity rate limit, and 503 for the warm-up gate, an uninitialised queue, a pre-enqueue setup failure and this one — because each is raised locally and has no upstream status behind it. A request already dequeued and waiting for a permit is refused the same way if the instance is superseded while it waits, and that refusal is *answered* rather than cancelled: Open WebUI can turn an exception into an error body but not a `CancelledError`, so a cancellation there would reach the person as an empty turn.
- **Global request semaphore:** `MAX_CONCURRENT_REQUESTS` limits in-flight requests per process. The semaphore is re-made for the running event loop, so a process whose event loop is replaced (a test runner that calls `asyncio.run` twice, a supervisor that restarts the loop) starts again at the configured value rather than serving a semaphore bound to a dead loop. A valve change takes effect on the next request, in both directions and with no restart: the same semaphore object is resized in place, so a higher value admits that many more requests at once, and a lower one binds from the moment it is saved, counting the requests already running. Those finish first; no new request starts until the pool is back under the new number. Across a loop swap the semaphore is rebuilt at the configured value instead, because a semaphore bound to a dead loop cannot be reused. A valve change is applied by a live generation only: a request that started before a hot reload and reaches this setup afterwards, after the reload has retired the instance serving it, changes nothing here, so a superseded generation cannot re-apply its own limit over the successor's. It still builds a semaphore that does not exist yet, because the request it is still serving needs one. A request holds its slot from before its own tool workers start until after they have all stopped, on the normal path and on the raise path alike, and it gives the slot back when the person stops the turn or when a fault lands before the request body runs. A job the request worker had already dequeued and parked on the semaphore is not one the retired queue still held, and the drain cannot see it. The trade is admission latency: the next request's wait rises by up to `TOOL_SHUTDOWN_TIMEOUT_SECONDS` per tool-bearing request, and a still-running tool holds a `MAX_PARALLEL_TOOLS_GLOBAL` permit across that same wait (taken when the call starts running, released only when it returns; Open WebUI's `ask_user` excepted, which takes no tool slot), so at a low `MAX_PARALLEL_TOOLS_GLOBAL` a slow drain can occupy a request slot and a tool slot at once. That is a sizing note rather than a defect — both pools default to 200.
- **Redis init backoff:** an attempt to open the Redis client that fails is retried at most once every 5 minutes, not once per request. The request path checks Redis on every message, so without an interval a host that is not answering costs a `from_url` plus a five-second-timeout `ping` per request, forever, with only a demoted warning. Like the warm-up interval this is a fixed constant rather than a valve, and it is not the request rate. The backoff belongs to the URL that failed and to nothing else: turning `ENABLE_REDIS_CACHE` off and on again clears it, so the valve's shipped promise that it comes up on the next request without a restart still holds, and so does a changed `REDIS_URL`. Neither a missing `redis-py` nor a factory that returns no client arms it, because neither attempts a connection; a successful reconnect clears it, so a later outage is not hidden by a deadline set during an earlier one. A live init task on the running loop is left alone, and a task stranded on a closed loop is still replaced — the latch sits after that guard, not before it.
- **Startup warmup gate:** the pipe runs background warmup checks once an API key is configured. If warmup has failed, requests are rejected with “Service unavailable due to startup issues” until a subsequent warmup succeeds. A machine caller — one with no chat to write a card into — gets that sentence as the error message of an HTTP 503, because a failed warmup is a condition of this process and not of one user. A failed warmup is retried at most once every 5 minutes, not once per request: without that interval every request re-arms a full warmup attempt, each of which is itself three tries with exponential backoff, so the warmup cadence would be the request rate. The interval is a fixed constant rather than a valve, and it is never shorter than the ping’s own backoff. A retry genuinely in flight does not refuse the request that found it — a request arriving mid-warmup is served against a service that is being warmed. A mistyped key the operator corrects is not made to wait out that interval: the backoff belongs to the key that failed, and a warm-up that never reached the provider — because no key resolved, or because the caller cancelled it — arms nothing at all.

## HTTP client pool (one per event loop)

Outbound requests share a single `aiohttp.ClientSession` per event loop rather than building one per request, so a reply no longer repeats DNS and a TLS handshake and a streamed reply reuses its connection across its own round trips. The session is closed when the pipe shuts down, and a session left behind by a dead event loop is retired rather than reused. It is pooled per event loop because a connector is bound to the loop that created it.

The pool is not a second admission control. Its per-host limit is unlimited, and its total connection limit follows the concurrency limit actually in force — `MAX_CONCURRENT_REQUESTS` — upward, live, on the pooled session, so a raise can never be admitted by the semaphore and then refused by the connector. A **lowering** narrows only the semaphore; the connector's own ceiling is deliberately left where it is, because the jobs already in flight keep running and the wait for a connection is bounded by `HTTP_CONNECT_TIMEOUT_SECONDS` rather than by the semaphore. In both directions the semaphore is the gate, and the connector is not one.

Timeout valves (`HTTP_CONNECT_TIMEOUT_SECONDS`, `HTTP_TOTAL_TIMEOUT_SECONDS`, `HTTP_SOCK_READ_SECONDS`) are applied **per call** at every site that issues an outbound request, so a valve changed at runtime governs the next request. The pooled session's own default tracks the valves of the request that most recently took it, so it changes from one hand-out to the next rather than freezing at whichever request built it; that default applies only to a site that supplies no `timeout=` of its own.

## Tool concurrency (per request and global)

Tool execution is constrained to prevent a single request (or a single user) from consuming all compute:

- **Global tool semaphore:** `MAX_PARALLEL_TOOLS_GLOBAL` caps the total number of tool executions across all requests in the process. It behaves exactly as the request semaphore does: a valve change is applied in place, in both directions and with no restart, counting the tool calls already running; and it is re-made when the process's event loop changes, so the limit is re-established for the current loop rather than surviving a loop swap.
- **Per-request tool semaphore:** `MAX_PARALLEL_TOOLS_PER_REQUEST` caps tool parallelism within a single request.
- **Plain-function tool pool:** a tool written as a plain function rather than `async def` is offloaded to a thread pool the pipe owns, `min(MAX_PARALLEL_TOOLS_GLOBAL, 8)` threads wide. The two semaphores are the gate — they decide which calls are admitted — while the pool is the isolation boundary that stops an admitted blocking tool from taking the threads the rest of the process shares. An `async def` tool never takes a thread, so it is bounded by the semaphores alone.
- **`ask_user` exemption:** Open WebUI's built-in `ask_user` waits on a person, so it takes no slot from either tool semaphore.
- **Batching and timeouts:** tool loop ceilings and timeouts are controlled by `MAX_FUNCTION_CALL_LOOPS`, `TOOL_BATCH_CAP`, `TOOL_TIMEOUT_SECONDS`, `TOOL_BATCH_TIMEOUT_SECONDS`, and `TOOL_IDLE_TIMEOUT_SECONDS`. A batch ceiling ends its round five seconds after it cancels the calls still running, so a tool whose cancellation cleanup awaits cannot hold the round: one that has not stopped by then is dropped from the round, keeps running, and its result never reaches the model. The warm-up gate above is bounded the same way: a failed warmup buys its next attempt with a five-minute interval, so the warmup's own cost is a ceiling rather than a function of the request rate.

See [Tooling & Integrations](tooling_and_integrations.md) for tool-specific behavior and schema handling.

## Breakers (fast-fail protection)

Breakers stop repeated failures from turning into continuous retries and log storms. The three breakers below are per user, and the video intent classifier's is a fourth; each internal Fusion run also keeps one count per tool, shared by all of its models, which uses `BREAKER_MAX_FAILURES` but ignores the window. The per-user breakers are governed by:

- `BREAKER_MAX_FAILURES`
- `BREAKER_WINDOW_SECONDS`

Breaker scopes include:

- **Per-user request breaker:** refuses a user's new requests once `BREAKER_MAX_FAILURES` failed calls to OpenRouter fall within the breaker window. For chat calls, the failures that count are error replies; connections that cannot be opened, drop or time out; an accepted body lost before it finished arriving; errors OpenRouter reports after accepting a call; and streams that stop before their final event. A 200 whose body was rewritten in front of OpenRouter does not count: the provider answered, the fault is in the network path, and the user is not the one to be punished for it — see [Error handling](error_handling_and_user_experience.md). A generation on a picture-only image model or a video model counts once, when it fails after being answered by OpenRouter, except a generation whose response arrived whole and was not an OpenRouter document — a body a proxy, CDN or WAF rewrote, or one that is not a JSON object at all, which is not a failure of the request and never counts toward the limit. An internal Fusion run counts once, not once per call: it spends one failure when no panel model answered, and none when one did, however many of its panel, judge or final-answer calls failed. A `/responses` failure the endpoint fallback repairs on `/chat/completions` counts none: that one strike is taken back the moment the fallback is decided, which is before the chat leg has run, so a second request from the same user arriving mid-turn is not refused for a call the pipe went on to answer, while the user's other failures in the window and a `/chat/completions` failure of its own are untouched. A request the pipe retried counts once for the whole request, however many attempts it took, and a request stopped during one of its waits counts none. A request that ends without an error clears the count, but a request to a picture-only image model or a video model clears it only once its result is delivered whole, and a stream that breaks after the finished image arrived clears nothing, and an internal Fusion run clears it only if a panel model answered; a request the user stops does not clear it. Housekeeping tasks such as title generation neither count nor clear; Open WebUI's merge-responses task counts but never clears. This breaker never refuses a request whose last message is a tool result, or is Open WebUI's own message that comes right after a tool result and hands the model a tool's images: such a request is how Open WebUI finishes an answer already under way. A question or picture the user sends is refused like any other request. A machine caller — one with no chat to write a card into — gets the refusal as an HTTP 429 carrying that same sentence, because a tripped per-user breaker is a per-entity rate limit; the other pre-job refusals on this path (warmup, a missing request queue, a full queue) are 503.
- **Per-user persistence breaker:** skips a user's database reads, writes and deletes after repeated DB failures within the breaker window; requests continue with reduced durability. A successful read or write clears the count; where Redis buffers writes, a write succeeds once Redis has taken it. Nothing is attempted while the breaker is open, so only failures ageing out reopen it. A user with no live database failure is not tracked at all, so the dashboard's count reflects active records.
- **Per-user, per-tool breaker:** skips a specific tool, keyed by tool type and the tool name it was looked up by, after it fails `BREAKER_MAX_FAILURES` times in a row; other tools keep working. A name the model padded with surrounding whitespace is the same tool and spends the same budget, and a success clears the count whichever spelling of the name it was sent under. The failures that count are an error the tool raises (unless its MCP session has closed), a per-call timeout other than an `ask_user` one, a running call cancelled by the batch deadline, and a call whose tool server cannot be reached or answers with an HTTP error status. When the tool reports a failure in a result it returns normally, the call is shown as failed but neither counts nor clears the count. A tool the breaker has taken out of service is announced once per round, however many of its calls that round asked for. A successful call clears the count, and so does a gap longer than the breaker window between the tool's last failure and its next call, which is why a slow tool that keeps timing out still trips. Each internal Fusion run keeps one count per tool, shared by all of its models: once a tool fails `BREAKER_MAX_FAILURES` times in a row during the run, it is skipped from then on, even after a quiet spell, unless a call to it that was already running succeeds. The user's own count is left unaffected.
- **Per-user video intent classifier breaker:** after a classifier infrastructure failure, the user whose request failed skips classification for 60 s while their video generation proceeds from the latest message alone. It is not governed by `BREAKER_MAX_FAILURES` or `BREAKER_WINDOW_SECONDS`, it is not surfaced on the dashboard, and its state is one entry per user who has ever failed, reclaimed when that user returns after the window has passed.

Breakers also recover on their own: the request and persistence breakers once their failures age out of the window, and a user's tool breaker once a call to the tool comes more than a full window after its last failure. Either way the record is released without a further call of the caller's own: the next write to the breaker — any user's request failure or tool failure — drops every request record and every user+tool pair whose newest failure is older than the window, so a tripped user or tool that never comes back does not keep its record for the life of the process. A turn whose tool calls are all skipped by a tool breaker does not count as a failed request, so a broken tool cannot lock a user out of the pipe.

## Background workers (what runs in the process)

The pipe uses background tasks/threads to keep request handling responsive:

- **Request worker loop:** dequeues jobs from the request queue and spawns per-request tasks. The loop also gates those spawns: it takes a `MAX_CONCURRENT_REQUESTS` permit immediately before creating a task and the job keeps that slot for its whole life, so a queued request waits for a permit instead of being spawned and running anyway. The dispatch loop owns the permit from `create_task` until the task is done, released by its own done callback; the job's body claims it at the point its `finally` takes the release over, and a job cancelled before its first step — one that never reaches that point — has its permit returned by the callback, so a cancel in the window between the spawn and the first step costs the pool nothing. `close()` finishes draining the request queue even when the worker and its jobs are bound to a closed loop, and each abandoned job's counter is released rather than left held; the drop at setup that replaces a queue bound to a dead loop drains the abandoned one the same way, and stops the worker it drops as well as the queue — otherwise the handle to that worker is gone and `close()` can only ever reach the replacement. A job the process semaphore is gone for is answered only if its caller has not already been answered, the queue's unfinished count is still decremented, and the dispatch loop keeps running. A job already dispatched when `close()` runs is cancelled and awaited on that path too, and its future is settled before `close()` returns, so the consumer stops polling and the permit it held is released; the two steps are ordered so nothing new is dispatched after the cancel, and the cancel happens before the drain goes on to wait on the session-log writer, so an in-flight turn is not held on the provider across a bounded join it does not need to sit through.
- **Async log worker:** drains a bounded async log queue (`maxsize=1000`) used by `SessionLogger` so log emission does not block request execution. `close()` finishes draining its queue on every arm: the worker awaited it, the worker was never started, or the worker is bound to a closed loop. The retired generation drains the queue it owns rather than the global one, so a hot reload leaves the incoming generation's queue alone.
- **Redis tasks (optional):** when Redis caching is enabled and available, the pipe starts a Redis client and associated listener/flush tasks. A flush interrupted by shutdown, a hot reload or the valve being flipped returns its uncommitted batch to the pending queue rather than dropping it, so the work is picked up by a peer worker or by the next flush. `openrouter-redis-init` shares one lifecycle guard with the artifact cleanup worker below and with the warmup task named in the loop-swap list above: an instance whose `close()` has begun starts none of the three, so a model-list refresh landing on a retired instance cannot open a fresh client on top of the one the close dropped.
- **Artifact cleanup worker:** periodically deletes persisted artifacts older than `ARTIFACT_CLEANUP_DAYS` (as measured from `created_at`, which is refreshed on every read, database or cache) on an interval It is scoped to artifacts and does not delete the pipe's bookkeeping rows sharing the table, so it cannot remove a coordination lock a live worker holds or a staged session-log segment; those are reaped by their owners (`SessionLogManager`'s segment reaper on `SESSION_LOG_RETENTION_DAYS`, and the stale-lock rules), which run on their own intervals. The sweep also invalidates the Redis cache entries of the rows it deletes in bounded keyset-paginated batches before the delete, so the sweep's memory peak stays flat and a worker lost between the two steps loses a cache entry rather than an artifact. The worker starts on whichever loop is current, and one left on a replaced loop is replaced *and cancelled* rather than kept. An instance whose `close()` has begun starts no worker at all, so a model-list refresh landing on a retired instance cannot leave a sweep behind that nothing will stop. Its `created_at` filter is served by an index that leads with `created_at`, so the range read is an index range rather than a scan of the whole table.
- **Session log storage threads (optional):** when session log storage is enabled, the pipe uses background threads to write, assemble and clean up encrypted zip archives. All three are per-Pipe-instance and stop on every teardown path: an orderly `stop_workers()` signals them and joins each on a bounded 2.0 s budget, and a collection without one ends each of them within one wake slice (the writer on its next queue timeout, the cleanup and assembler threads on their next 30 s slice). A thread still inside a long operation when that budget runs out outlives the join — a cleanup sweep over a large log tree is the case — and keeps running against the set event until it returns; the next start repairs the missing thread per thread, on a freshly armed stop event. That repair does not depend on the sibling thread having retired: with a write and a sweep both still inside their operations when the stop returns, the next start still re-arms the event and still starts a fresh sweep, since a thread alive on a set event is about to retire and does not count as running. A writer still alive is deliberately left in place rather than replaced — its drain window expires on its own and a later start brings one back on the unset event, and the thread slot is a contract rather than a bug (`tests/test_session_logs.py:1215`). The writer and the cleanup thread share one cross-thread invariant: a write reserves the directory it is filling, and the cleanup thread honours that reservation, so a sweep never removes a directory a write is in the middle of. The reservation is a process-level count, so two writers into one directory are both covered, and it is released when the write returns — a later sweep prunes the directory as usual.
- **Tool pool:** a private bounded thread pool for tools written as plain functions, `min(MAX_PARALLEL_TOOLS_GLOBAL, 8)` threads wide, keyed on the Pipe instance and retired on every teardown path. Its width is re-read on each call, so a valve change takes effect on the next tool call without a restart. It exists for the same reason as the address-check pool: a user-supplied tool body can block, so it is bounded on a pool of the pipe's own rather than on the shared default executor that media, thumbnails and file reads use. A teardown or a resize does not cancel work already admitted to it and left queued — the pool is not re-made under a live call.
- **Address-check pool:** a private bounded thread pool for the SSRF gate's DNS lookups, so a stalled nameserver — the host comes from a free-text request field, so the requester picks the resolver — is bounded there instead of holding a slot on the shared default executor that media, thumbnails and file reads use. Its width is the floor of 4, or the `MAX_CONCURRENT_REQUESTS` bound, whichever is larger: the request path is the wide caller, issuing up to `MAX_CONCURRENT_REQUESTS` picture, reuse, generated-image/video and attached-file-link checks on one handler, so a pool narrower than that turns ordinary concurrent load into a refused address. The pool is minted at that width and re-made whenever the valve names a different one, in both directions, so the width a check is dispatched to is the width the valve derives at the moment it is dispatched. Narrowing leaves the retired pool's threads alive until the checks already on them drain, so the threads come back on their own. The background model-icon sweep issues up to 10 lookups at once (under `asyncio.Semaphore(10)` in the catalog manager) and draws on a separate sweep pool (10 workers) of its own, so that background fan-out can never cost a person's check its slot; the maker-page refresh is a second ten-wide background caller, though aiohttp's per-host DNS throttle collapses it to one lookup at a time today. The choice is the CALLER's, not the check's: the icon fetch marks its whole fetch as sweep work, so with `ENABLE_SSRF_PROTECTION=False` the vetted transport's own name resolution inside that fetch lands on the ten-wide sweep pool, and the maker-profile fetch and the dashboard self-update — land on the wide one; the request path is not among them, because with the gate off the vetted transport is not what resolves its name (see `security_and_encryption.md`). With `ENABLE_SSRF_PROTECTION=True` a check that is stalled, or queued behind other checks because the pool is full, reaches no verdict inside its budget rather than being delayed, and that is not the same answer as a check refused by policy. On a path that is about to fetch or forward something -- a download, a generated picture or video, a chat's video link -- a check with no verdict still sends no bytes, and the refusal says the check reached no verdict rather than that the address was refused. On the re-use path the question is not "may I fetch" but "are these bytes still permitted", and there an answer that never arrived is not a denial of them: the picture the pipe already holds is served and its memo entry kept, so ordinary load cannot empty the cache. Only a check that completed and refused the address evicts. The gate-off resolution carries no resolution budget — by design — so a name that queues behind a full pool waits its turn and is then charged to that reach's own hop budget, not to this pool: on the icon reach, fifteen seconds, so an icon that queues behind a full sweep pool can be late where the gate-on path would have dropped it at five. Neither arm can interrupt a `getaddrinfo` already in flight: a refusal releases the caller, not the pool thread, and a stalled lookup holds its slot until the nameserver answers.
- **Video frame extraction (ffmpeg arm):** the ffmpeg fallback arm runs the subprocess on the event loop but hands its PIL work — `Image.open`, the pixel-cap check, `load()` and the mode normalisation that composites onto white and re-encodes — to a worker thread with `asyncio.to_thread`, so a `last_frame` or `at_timestamp` extraction does not stall an unrelated turn. The imageio arm, the duration probe and the video-track length reader offload their own sync helpers the same way, and each of those three is bounded: an imageio read that has not answered in 30 s and a probe that has not answered in 60 s — its own header read plus the three 10 s `subprocess.run` windows it may spend — come back as a `FrameExtractionError` naming the leg that ran out, so the turn discloses one dropped frame instead of waiting. Neither bound can interrupt the work it handed to the thread: a refusal releases the caller, not the worker, and a bound that expires while the leg is still queued releases the permit it was charged too, rather than pinning it for the life of the loop, so a decoder wedged on a file, and the ffmpeg child `imageio-ffmpeg` builds inside its own generator whose handle the module never sees, live until the worker finishes — one thread plus one child per wedged file, in the shared default executor, bounded per file and not accumulating past its width. The probe leg leaks no child, because its `subprocess.run(..., timeout=...)` children are reaped by the interpreter. The video-track length reader is left as it is: it runs no decoder, and its own child is already under the 10 s probe timeout. Each end-seek child decodes at most one hop of the reach it is walking, so the memory one child costs does not scale with how far back from the end of the file the arm had to reach. The substitution note is still written on the coroutine — naming damage where the pipe saw a decode error and an unreadable end where it did not — and the pixel cap is still checked before the frame is decoded. The whole ladder runs under the video concurrency permit, which the turn now takes before any media work rather than only before submission.
- **Video attachment decoding:** a video request's input references and frame images are read as base64 and their decoded length is computed **arithmetically** from that text rather than by decoding the payload — padding, line wrapping and the alphabet are all accounted for, so the number is exact and a request carrying four 12 MB frames costs no whole-payload decode at all. A payload whose *shape* is impossible for a decoder — a length that is not a multiple of four, padding in the wrong place, a character outside the alphabet — is still refused, and with the same reason, because the arithmetic raises on precisely the shapes `base64.b64decode` refuses. The one path here that still decodes a whole payload is the file-host arm, and it decodes **once**: the entry keeps the decoded bytes for the pixel-floor probe and the upload, so both publish the same bytes the length check measured, and an entry that travels inline keeps only the base64 text, so a request does not hold both copies of every attachment it accepted. That remaining decode is still a C call that holds the GIL, so a worker thread stalls the loop just as long as the event loop thread would (measured here at ~460 ms of frozen loop for one 40 MB decode); chunking it the way the inline-payload and the tool data-entry path now do is still TODO T608. The per-picture cap, the running combined reference budget and the frame-image budget are all decided on the same exact length.
- **Inline audio and picture payloads (bounded quanta, on a worker):** the base64 an inline attachment carries is validated and encoded in bounded quanta, each handed to a worker, so a multi-megabyte attachment no longer holds the event loop: the audio validator and the inline picture arm both scan the cleaned payload in 4 KiB pieces on a worker instead of decoding the whole thing to answer a yes/no - the inline arm used to decode the picture and throw the bytes away, and now validates the string it already holds - and a downloaded picture is base64-encoded in 3-byte-aligned pieces off the loop. **`base64` and `json.dumps` hold the GIL, so handing one whole-payload call to a worker is a measured no-op** (24 MB encode: 68 ms inline versus 73 ms in a thread; 24 MB decode: 344 ms versus 335 ms, of which 297 ms is a frozen loop). That no-op is the rule for a single whole-payload C call, and it is why chunking is the primary bound: a thread around one such call moves the work off the loop's *thread* without giving the loop back. A chunked scanner is a Python loop rather than one C call, and the GIL is released between quanta, so offloading it is the complementary case -- on 24 MiB it drops the loop's worst stall from ~350 ms to ~8 ms. The same rule applies to any per-payload work still to come on this path.
- **Tool data entries (bounded quanta, on the loop):** a tool result entry carrying an inline `data:` file -- the shape Open WebUI's OpenAPI-tool branch hoists a non-image `data:` string into -- is decoded in bounded quanta on the event loop, with a yield to the loop between them, so a multi-megabyte entry no longer holds the loop for the length of one C decode. The valve (`BASE64_MAX_SIZE_MB`) still decides the size and is consulted first, so a refused entry is never decoded at all, and an entry that will not decode is still dropped the same way, including a temporary chat's, which keeps nothing and therefore decodes nothing.
- **Generated picture payloads (bounded quanta, on a worker, with an await between):** the base64 a generated-picture reply carries is decoded in bounded quanta cut on base64's 4-character boundary, each handed to a worker, so decoding a multi-megabyte picture no longer holds the event loop. **Only chunking *with an await between chunks* bounds the stall.** Chunking on its own does not: a decode that fills a `bytearray` quantum after quantum without ever awaiting between them never returns to the loop, and measures 332 ms of wall with the loop ticking zero times. A worker is necessary but not sufficient -- the `await` between quanta is the half that gives the loop back, and handing the whole payload to one worker is the half that does not (24 MB decode: 344 ms inline, 335 ms in a thread, of which 297 ms is a frozen loop). Padding is checked before the first quantum rather than by the per-quantum decoder: an `=` anywhere but the tail of the payload is legal inside one quantum and illegal for the payload, so without that check a chunked decode accepts replies the single decode refuses. The pre-decode estimate that refuses an oversized reply without materialising it is unchanged, and is an arithmetic estimate on the payload's length.

- **Replay sanitize and tool-pairing passes (per round, on the loop):** every request the pipe dispatches replays the turn's history through a sanitize pass, and that pass runs once per tool round plus once for the turn. Between the pass that ends a round and the pass that opens the next, `body.input` does not change — that is the invariant the guard is built on, and it is why the pass a round ends with is never redundant. The pass that pairs `function_call` items with their results is linear: one index map over the item list and one stub plan, never a rescan of the tail per output nor a walk of the starved set per emitted row, so a long chat full of unanswered calls costs one pass rather than one that grows with its square.
- **Open WebUI file copy (on a worker):** the copy that writes a referenced Open WebUI file into a request-private temp file is handed to a worker with `asyncio.to_thread`, exactly as the storage read beside it already is, so a large file no longer holds the event loop. The rule above about GIL-holding whole-payload calls does **not** apply to it, and that is the reason it is safe to do with one `to_thread` rather than chunked: `shutil.copyfile` reaches `os.sendfile` on Linux, which releases the GIL, so a worker really does give the loop back (measured here: a 128 MB copy left the loop's longest tick-free stretch at 2.2 ms off the loop against 48.4 ms on it). The size gate that follows the copy stays on the loop — it is one `stat` on a path the loop already holds, and its failure has to unlink the temp before it raises. `BASE64_MAX_SIZE_MB` and `VIDEO_MAX_SIZE_MB` describe sizes rather than threading, so neither cap moves.

**State ownership:**
- **Instance-level**: request queue, log queue, worker tasks, and locks are owned by each Pipe instance. The plain-function tool pool is instance-level too, not class-level: a hot reload closes the predecessor while the new generation serves, and a class-level pool would be torn down under a live sibling's tool threads, orphaning a running tool call and then rebuilding underneath it. A request is counted in the instance's in-flight number from when `pipe()` is entered until its job's cleanup tail has run to completion, not merely until its bytes were delivered, and a model-list refresh is counted for as long as `pipes()` is running, so a superseded generation is closed only once its last request has finished tidying up and its last model list has returned rather than while that request is still shutting down or that refresh is still being built — and that tail is prompt, because the drain that settles it runs before the session-log workers and the artifact store are stopped. A job that is discarded without running -- a queued job abandoned by `close()` or by the setup-time drop of a queue bound to a dead loop, for instance -- has its count released at the moment it is discarded, and a job that never ran has no runner to own that tail, so the drain is that owner. The registry of jobs this instance dispatched is per instance for the same reason the queue is: `swap_in` installs the successor before the predecessor closes, so a class-wide registry would let one pipe's `close()` cancel the jobs of the pipe that replaced it. A closed `ArtifactStore` is terminal in the same sense: once `close()` has returned, no later ensure rebuilds its engine, model or DB thread pool, so a terminal session-log segment persisted inside the drain that follows `shutdown()` cannot leave a retiring generation holding worker threads nothing will ever revisit.
- **Per-instance plugin registrations**: when the plugin system is enabled, the pipe dashboard registers its pipe getter and live-snapshot getter into three module-level globals (the socket handler, the HTTP routes and the publisher) so those request-serving paths can reach the current pipe, and the action route caches a fourth `Pipe` of its own on first use, reconciling against the worker's function-module cache. The plugin's `on_shutdown` clears all four, but only where the global still refers to that plugin instance — a newer pipe that has already re-registered them (hot reload, in either order) is left registered, and the action route's cached pipe is dropped only when it is this pipe by identity, so a newer pipe's live cache survives another pipe's teardown. The same helper runs on every `on_models`, so a pipe that is still live puts the three registrations back after a newer pipe's teardown dropped them; the clear is therefore not a one-way door for a surviving instance, only a way of not stomping on a newer registration. The same `on_shutdown` also retires the dashboard plugin's usage writer for good, and there the retirement *is* terminal rather than the re-armable pause the session-log threads above describe: once its store has been signalled to stop it starts no writer and no purge loop again, so a hot reload leaves no predecessor thread, purge loop or DB connection behind for the life of the worker.
- **Class-level**: rate-limiting semaphores are shared across all instances in the same process (per-process concurrency control), and are re-made when the process's event loop changes. The worker hands each job the pool object it bound before it acquired, and the job's cleanup tail releases into that same object, so a retired pool keeps exactly the permits its own in-flight jobs are still holding and the live pool is untouched by them. The video frame extraction gate is the one thing that does not follow this convention, and the reason is the resource under it. An extraction holds its permit until the worker decoding the frame has stopped, not merely until the coroutine that asked for the frame stopped waiting, so a permit is never handed back while the work it pays for is still running. Both give-back paths return it exactly once, and they are the only two: the worker's own end of the leg, and the caller's give-up — a cancelled turn, or a leg that ran out of its own bound — which takes the permit back at once when the work item is one the executor never started, without waiting for a worker that will not run, and which a worker that does start after that give-up skips entirely rather than decode a frame nobody is waiting for. A rate limiter can be re-made on a loop change and lose nothing by it, because what it counts is jobs waiting for a slot; an extraction gate counts work already running on a machine, and a second gate that does not know about the first one's live workers hands out another four on top of them. The gate is therefore held per running event loop and is never re-made under a live one: one loop's quota is one loop's quota, however many other loops visit the module, and a loop that has been closed takes its gate with it. Across a *module generation* the property does not hold and cannot: Open WebUI loads the pipe by executing the stored content into a fresh module object, and the bundled preamble clears `sys.modules` of every `open_webui_openrouter_pipe` key before installing its finder again, so a Sync or a function-content edit builds a second extraction gate in the same process on the same loop while the first generation's extractions are still running. Those orphaned workers are not counted by the new gate, so for as long as two generations overlap the machine can be decoding up to twice the constant, and a third generation would make it three times; it settles as soon as the older generations drain, which is tied to the reload and not to a valve. That residual is accepted rather than fixed: the case needs a process-wide gate held outside the module, which is a new subsystem for something that takes an admin action to produce.

## Operational tuning (practical guidance)

- If you see “Server busy (503)” frequently, that is a real diagnostic and the first time it has been one. It means the pipe refused a request outright, which is a capacity problem and not a stall: the requests ahead of it are holding every concurrency permit and the bounded request queue behind them is full. Lower upstream load, or raise `MAX_CONCURRENT_REQUESTS` toward the CPU/RAM headroom — those are the levers, and upstream load is the other half of them. The request queue itself is a fixed `maxsize=1000` per worker process, not a setting: there is no valve or environment variable behind it, so when the dashboard’s `requests` / `requests_max` fields show work merely queued rather than slow, the answer is more concurrency permits, not a bigger queue. The status a caller with no saved chat turn receives — 429 from the breaker, 503 from the rest — is what a monitor counts, and it is the envelope for every pre-job refusal, not only a full queue; a request that has one keeps the card, and a card carries no status code to count. A worker wedged by a code reload is no longer one of these: a job that was already dispatched is cancelled and its permit given back before `close()` returns, so a reload cannot present as a stall that answers 503.
- For rate limits and upstream instability, use breakers plus conservative retry windows; avoid “infinite retries”. The chat retry window is bounded by `TRANSIENT_RETRY_MAX_ATTEMPTS` tries and `TRANSIENT_RETRY_MAX_WAIT_SECONDS` per wait — a `Retry-After` is truncated to that cap rather than replaced by it — and a request the user stops mid-wait adds no strike against the breaker.
- For multi-worker deployments, consider enabling Redis caching (when appropriate) to improve artifact replay performance and reduce DB contention.

All tunables referenced here are documented (with verified defaults) in [Valves & Configuration Atlas](valves_and_configuration_atlas.md).
