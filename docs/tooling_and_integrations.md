# Tools, plugins, and integrations

**Scope:** How tool schemas are built, how `function_call` items are executed, and how Open WebUI tool sources (registry + Direct Tool Servers) are attached.

> **Quick Navigation**: [📘 Docs Home](README.md) | [⚙️ Configuration](valves_and_configuration_atlas.md) | [🏗️ Architecture](developer_guide_and_architecture.md) | [🔒 Security](security_and_encryption.md)

This pipe supports OpenRouter tool calling either via an internal execution pipeline (pipe-run tools) or via Open WebUI pass-through (OWUI-run tools). Tool sources and integrations:

- Open WebUI tool registry tools (server-side Python tools).
- Open WebUI **Direct Tool Servers** (client-side OpenAPI tools executed in the browser via Socket.IO).
- OpenRouter web-search (attached as an `openrouter:web_search` server tool in the `tools` array — not a `plugins` entry or a function tool).

---

## Tool backends (`TOOL_EXECUTION_MODE`)

This pipe supports two tool execution backends. Choose based on whether you want the pipe to run tools itself, or you want Open WebUI to run them.

### `Pipeline` (default)

The pipe runs the tool loop itself:

- Provider returns `function_call` items.
- The pipe executes those tools (Open WebUI registry tools + Direct Tool Servers where available).
- The pipe appends `function_call_output` items and re-calls the provider until the model stops requesting tools or `MAX_FUNCTION_CALL_LOOPS` is reached (at which point the model gets a synthesis turn, and each call abandoned at the cap is shown as a **failed** card).

**You gain:**
- Pipe-level concurrency controls, timeouts, and breaker protections around tool execution.
- Its own copy of every tool round it runs, holding the call and its result in full (a web search holds its links and the excerpts the engine returned, within the record caps, and its query except on `/chat/completions`, where OpenRouter does not send the query back and the call has no arguments; a fetched page is cut at 150,000 characters with a note saying how much), so the model learns on later turns which tools it used even with tool cards off, for as many earlier turns as `TOOL_TURNS_TO_REMEMBER` keeps and for the built-in `ask_user` questions of every earlier turn (except in a temporary chat, for which the pipe keeps nothing); `PERSIST_TOOL_RESULTS` decides whether those turns get the results or a note in their place, while the call's name and arguments go back either way (a round that arrived before the chat's first turn is earlier too), and `TOOL_OUTPUT_RETENTION_TURNS` shortens long results from the older of those turns.
- Optional strictification of tool schemas (`ENABLE_STRICT_TOOL_CALLING`) for more predictable function calling. It is off by default, because OpenAI rejects a strict tool whose parameters contain a free-form object and Open WebUI's built-in `ask_user` is one, so strict mode is opt-in.

**You lose / trade off:**
- Tool execution behavior is “owned” by the pipe rather than Open WebUI’s native tool runner (so Open WebUI UX/logs may not exactly match the built-in tool flow).

### `Open-WebUI` (tool bypass / pass-through)

The pipe does **not** execute tools. Instead, it returns tool calls in the native `response.*` shape — a `function_call` item plus its `function_call_arguments` frames — and expects Open WebUI to:

- execute tools locally (registry tools and/or Direct Tool Servers), and then
- replay tool outputs back through the pipe as `role:"tool"` messages on the next request.

**You gain:**
- Open WebUI-native tool execution behavior and UI (tool boxes, retries, and tool server flows are handled by OWUI).
- A simpler “adapter-only” path: the pipe focuses on transport translation between Open WebUI and OpenRouter.
- Better compatibility with OpenRouter streaming quirks: OpenRouter `/responses` can emit tool calls with `arguments:""` early. The `added` frame a call is announced on does carry `arguments: ""` — the item is opened before any argument has arrived — but no `function_call_arguments.done` ever does: the terminal frame carries the whole argument object, or `{}` for a call that had none, so Open WebUI never executes an empty argument string on this leg.

**You lose / trade off:**
- The pipe does not run tool timeouts or tool breakers; Open WebUI’s behavior governs execution. The per-user request breaker still applies.
- The pipe runs none of these tools, so it keeps no copy of their rounds; Open WebUI's saved tool cards carry them. `TOOL_TURNS_TO_REMEMBER` and `PERSIST_TOOL_RESULTS` still decide what the model is handed on later turns, the first how many earlier turns hand over their tool calls at all (a built-in `ask_user` question and answer always go back) and the second what those turns' results are: off, a result from an earlier turn -- or from a round that arrived before the chat's first turn -- is replaced by a note while the call keeps its name and arguments; on, the result comes in full. OpenRouter's own server tools run on OpenRouter in either mode, and the pipe keeps their rounds exactly as in `Pipeline` mode. In a temporary chat those rounds, and the reply's thinking unless `PERSIST_REASONING_TOKENS` is `disabled`, are held only in memory in a streamed reply, for that reply's calls back after each round of tool calls, and dropped when the pipe answers its last call back, or when the provider refuses a call-back the pipe was waiting for, or when the reply is stopped, or after 15 minutes unused (see [Persistence](persistence_encryption_and_storage.md)).
- In pass-through, the pipe does not strictify or mutate tool schemas; Open WebUI’s schemas are forwarded as-is.
- A caller's own tool is offered whatever the model's catalogue says about tool use, exactly as Open WebUI forwards it; a stripped tool is only one Open WebUI or this pipe added.

Every call reaches Open WebUI, including one without arguments or with `null` or malformed ones, and Open WebUI answers it as its own loop does; on `/responses` missing arguments arrive as `{}` and `null` ones as `null`, as Open WebUI's own Responses connection reads them.

## Tool schema assembly

Tool *schemas* are assembled by the tool registry builder and attached to the outgoing Responses request as `tools`.

### Preconditions

- A function tool reaches OpenRouter only if the model's catalogue row lists `tools` or `tool_choice`, publishes no parameters, or does not exist, **except** for a tool the request itself declared, which is offered whatever the row says. This holds in every mode, whatever the tool's **origin**, and for Fusion panel models; a model the catalogue rules out for tool use is sent none of the tools Open WebUI or this pipe added — no resolved tool, no direct tool, no OpenRouter server tool. A tool the request itself declared is the caller's business and goes out as sent, and a `tool_choice`, `parallel_tool_calls` or `stop_server_tools_when` left with nothing to point at is cleared. A named `tool_choice` that points at no tool on a request that does advertise tools is cleared too — the wire's `tools` array is what it has to name an entry of — while a request that advertises no tool at all keeps the caller's own choice as written. The general rule is the same whatever removed the tool: a `stop_server_tools_when` cap reaches OpenRouter only while at least one `openrouter:`-prefixed server tool is still on the request, so a cap whose every tool was switched off or stripped is dropped rather than sent pointing at nothing.
- The same row decides the per-chat Image Generation and Web Tools switches: a model whose tool use is ruled out is offered neither, so the switch and the request-time guarantee cannot disagree.

### Tool sources (in order)

1. **Open WebUI tool registry** (`__tools__` dict)
   - Converted to OpenAI tool specs (`{"type":"function","name",...}`) by `_build_collision_safe_tool_specs_and_registry` (called from `requests/orchestrator.py`), which builds each registry entry with `_responses_spec_from_owui_tool_cfg`.
   - When `TOOL_EXECUTION_MODE="Pipeline"` and `ENABLE_STRICT_TOOL_CALLING=true`, each tool schema is strictified; on a streamed reply under `ask` approval in a saved or temporary chat the round is handed back and its schemas are never strictified, keeping the fields the request gave them (with the valve off the schema is not strictified and is sent with `strict: false`, and the executor filters a call's arguments against the names that untouched schema declares, with a root carried by `$ref` or `allOf` resolved for that purpose only, and the top-level property names an `allOf` branch spells out in plain text still declared when the resolver declines that root; a root that is not an object and is not advertised under the pipe's `value` envelope declares no names, so nothing is delivered for it):
     - Object nodes get `additionalProperties: false`.
     - All declared properties are marked required; a property that was not explicitly required becomes nullable, in whichever of the two shapes it was written in. A property that states a `type` gains `"null"` to it; a property that states none — a bare `$ref`, an `allOf` that unwrapped into one, a typeless `anyOf`/`oneOf` — gains a `{"type": "null"}` branch instead, the whole node becoming the first branch of the resulting `anyOf` (never a `type` beside the `$ref` or the composition, which would constrain rather than union). A node that already admits null is left alone, and the decision is made on the node's post-`allOf` form. A property that arrived with a concrete `default` is the one exemption: the author had already answered it, so it keeps its concrete type instead of gaining `null` and stays required with it — strict mode needs the value, and a `null` is the opposite of the default the author wrote. A `default` of `null` is not a default (Open WebUI's own schema cleaner deletes exactly that one), so such a property is still made nullable.
     - `$ref` and `$defs`/`definitions` are preserved: referenced definitions are strictified in place, a required `$ref` node passes through untouched, and single-`$ref` `allOf` wrappers are unwrapped. An *optional* `$ref` property is the one shape that is rewritten: it is wrapped in an `anyOf` whose second branch is `{"type": "null"}` so the model can leave it out, and its `$ref` and `$defs`/`definitions` survive inside that first branch. A node's own keys survive the unwrap, so a property keeps its `title` and `description` beside the `$ref` it resolves through, and a definition a nested node carries is hoisted into the root container under the same key — so `#/$defs/X` and `#/definitions/X` keep their spelling — and strictified there. A name the root already defines is the root's, and the nested body is hoisted beside it under a fresh name, with every pointer inside that same nested container following it. Multi-branch `allOf` is merged (local `$ref` branches are resolved from the schema's own definitions); unresolvable references leave the `allOf` untouched.
     - Keywords OpenAI strict mode rejects are stripped (`default`, `$schema`, `pattern`, length/numeric/array constraint keywords, `format`). The strip is final rather than positional: it runs again after each `allOf` is inlined, so a key that rode in on a branch is not grafted back on, whatever shape carried it and whatever route it arrived by.
     - A missing `type` is filled in so schemas remain valid, at all three places one can be missing: a property, an array's `items`, and an `anyOf`/`oneOf` branch. A node there whose values are pinned by `enum` or `const` and which states no `type` of its own is given the JSON type those values have (`string`, `integer`, `number`, `boolean` or `null`), so a schema stops shipping a sealed empty object that admits no value; a node that pins no values is still given `object`, or `array` where it declares `items`. A node that declares `anyOf`, `oneOf` or `allOf` is left alone at all three places, because its branches already state its type and a `type` beside them constrains it to a conjunction no value satisfies — an array whose `items` are a `list[str | int]` union admits no value at all that way, and an `items` node carrying only `allOf` would be advertised as an array of whatever was stamped over its resolution. A heterogeneous (`["a", 1]`) `enum` is given the union of the JSON types its own values have — `["integer", "string"]`, written in a stable order — because that is the only spelling that admits every value it pins; a node that pins no values at all, an empty (`[]`) `enum` included, keeps the `object` default and stays unsatisfiable exactly as it was authored; and an `enum` that pins a container value (`[{"k": "v"}]`) has no honest type at all, so it keeps its `enum` and is left without one — and therefore unsealed — the same verdict a composition-only node and a `$ref` node get.
     - If a schema cannot be serialized for strictification, it is sent unmodified (with a warning logged).
     - A small LRU cache (size 512) avoids repeated strictification work for identical schemas.
     - The advertised schema is what the model is sent and the names the executor filters the tool's arguments by are its own top-level property names, so the two name sets cannot drift apart: a tool whose root schema is not an object root is advertised as a single `value` property and its argument is delivered under that name, and arguments the model invents beyond those names are dropped before the tool runs. With the valve off the executor filters by the names the untouched schema declares, resolving a `$ref`/`allOf` root for that purpose only and falling back to the top-level property names an `allOf` branch spells out itself when the resolver declines it; a root that names no properties is not a filter that keeps everything, it is a filter that keeps nothing.
     - A tool the pipe advertises on the Responses route also carries `strict: true`, so the provider enforces the strictified schema; a tool the pipe does not strictify (Open WebUI tool mode, a streamed reply under `ask` approval in a saved or temporary chat, or the valve off) is sent there with an explicit `strict: false`, so that endpoint's own `true` default never applies to a schema the pipe did not strictify (except where the schema is free-form and cannot be made strict: an array whose `items` node declares no properties is left open, because sealing it could only be satisfied by an empty object); a provider that does not support strict tool calling rejects the request.

2. **Open WebUI Direct Tool Servers** (direct entries in `__metadata__["tools"]`)
   - These are user-configured OpenAPI tool servers that Open WebUI executes client-side.
   - Before calling the pipe, Open WebUI resolves the tools of the servers selected for the chat and adds each tool to `__metadata__["tools"]` as a direct entry carrying its spec and its server, and writes the same specs into the request's own `form_data["tools"]`. The pipe builds its browser-run tools from those entries, so a tool Open WebUI withholds stays withheld (for example, the shell tools of a personal Open Terminal while no shell is connected).
   - This pipe:
     - advertises the tools to the model under the names Open WebUI gives them (OpenAPI `operationId` values). Open WebUI keys a direct tool on that name byte for byte and its own `tools.get(name)` hand-back reads the same one, so the pipe keys and addresses each direct tool by the name Open WebUI gave it: two servers whose `operationId`s differ only in surrounding whitespace are two tools, and the name the pipe sends the browser is the one the server declared, so its `operationId` match resolves. Open WebUI's own collapse of two same-named servers happens upstream of the pipe, on a request the pipe receives as one entry, and is not undone here; when names collide among the tools the pipe receives, it disambiguates them with a source prefix (e.g. `direct__`), and
     - executes tool calls via the Socket.IO bridge (`__event_call__`) by emitting `execute:tool` so the browser performs the request.
     - filters the call it sends to the browser to the names the pipe advertised for that tool, which with `ENABLE_STRICT_TOOL_CALLING` off are the spec's own, since the pipe then does not strictify.

   The prefix is a provider-facing label only: the Open-WebUI hand-back reads the tool's origin name. The strip that withholds the pipe's own tools from a model the catalogue rules out for tool use matches on that same origin, whatever name the provider saw, so a renamed tool is withheld as surely as an un-renamed one. The tool card does not read the origin: with tool cards on (the default) it is named as the model saw the tool, prefix and all, because that is the name the call was made under and the name a replay pairs with; the one card published with cards off (a file shown inline through Open Terminal) is named with the origin instead. The registry the loop runs against is keyed by the advertised name, so the pipe runs a call under the name the model saw. Citation routing requires the registry entry to be one of Open WebUI's own builtins — a `type` of `builtin` with a `builtin:`-prefixed `tool_id`. That marker, not the name, is the whole test: a direct tool, an MCP tool or a user custom tool that merely carries a builtin's name never has it, whichever name the provider saw. A request-supplied tool is the one case that can carry it, and only because the executor it resolves to *is* Open WebUI's own builtin.
   - Direct tools are only advertised when `__event_call__` is available; without an active Socket.IO session there is no safe execution path, so the pipe skips them. A direct tool is therefore withheld from any request that carries no browser session — an API call, an automation, a background task — on the request-spec side as well as on the registry side.

3. **Extra tools** (`extra_tools`)
   - A caller-provided list of already OpenAI-format tool specs is offered under two different contracts, split by who runs it. An extra tool the pipe itself executes is advertised with the description and parameter schema of the executor it binds, so the schema on the wire is the schema the argument filter enforces. An extra tool that is handed back — one nothing binds, or any tool at all in passthrough mode — is offered as it arrived, because there the caller's own schema is the contract and nothing will run it against another one. In Pipeline mode an extra tool is offered only when a tool of that name can run it; a spec whose name several registry entries share is left out, as on the request route (non-dict entries are ignored).
   - An `extra_tools` entry is a pipe-local extension: it is a schema only. Under `function_calling: "legacy"` the round belongs to Open WebUI, which has no such field and cannot run one; on a reply that is not streamed in a saved or temporary chat under `tool_approval_mode: "ask"` the tools are withheld and nobody runs the round; inside a Fusion member they are withheld under `ask` on a streamed reply too. None is advertised in any of those — the same reason the request's own tools are withheld, and for the same reason: a name offered to a model nobody will answer for is a dead end. Under `legacy` the withheld set is also what the hand-back predicate consults, so a streamed reply that names one of those tools anyway is handed back to Open WebUI to run; a reply that is not streamed cannot be handed back at all, and is answered in the pipe's own loop instead. On a streamed reply in a saved or temporary chat under `ask` — where `legacy` is not also set, which clears the extras on its own — outside a Fusion member nothing is withheld: the extra is advertised with the rest, and its round is handed back to Open WebUI with every other call on that reply.
   - The `Tool ingest: … extra_tools=%d` debug line counts what was read off the request body on the way into the builder, not what went out on the wire. In ask mode on a reply that is not streamed in a saved or temporary chat it reads `0` by design — that is the reply whose tools ask withholds — and a `0` there in any other mode, `legacy` function calling or a Fusion member under `ask` being the other places the extras are withheld, is the real signal that the body carried none.

### Open WebUI Tool Search (0.12.2 and later)

With Tool Search on in Open WebUI, each tool whose definition is longer than the admin's threshold, and that is not on Open WebUI's always-loaded list, is held back (a built-in tool only while built-in tools may be deferred): the system prompt lists the held-back tools by name and a short description in an `<available_tools>` block, and the request carries Open WebUI's `search_tools` and `call_tool` builtins. The model looks a tool up with `search_tools` and calls it through `call_tool`, giving the tool's name and its arguments as a JSON string.

- **What the model is offered.** The pipe holds back exactly the tools Open WebUI holds back for the request, in either tool execution mode, so the token saving carries through. On 0.12.0 and 0.12.1, which have no `call_tool`, every tool is offered in full and Tool Search saves nothing through the pipe.
- **Running a looked-up tool.** On a round the pipe runs itself, each `call_tool` call is resolved with Open WebUI's own resolver and runs the tool it names the same way a direct call to that tool runs, under the pipe's breakers, timeouts and round cap. A call the resolver refuses (an unknown tool, malformed arguments, `call_tool` naming itself or `search_tools`) is answered with the resolver's own message, and nothing runs. In `Open-WebUI` mode a streamed reply's `call_tool` round goes back to Open WebUI, like any of its builtins.
- **Replay.** The stored round keeps the model's own `call_tool` call and replays as that call (see [History Reconstruction & Context Replay](history_reconstruction_and_context.md)); with `PERSIST_TOOL_RESULTS` off, the call keeps its name and its parameters and only the result is replaced by a note.
- **Where the list is dropped.** A request sent none of Open WebUI's tools (a non-streamed `ask` reply, a model ruled out for tool use) drops the `<available_tools>` block from its system prompt, and so does every Fusion member, which outside `ask` is offered its tools in full, without `search_tools` or `call_tool`. Open WebUI does not run Tool Search under legacy function calling.

### Duplicates and collisions

Two candidates that resolve to the *same* executor are advertised once, under the origin name, first candidate winning. Two candidates with *different* executors, or with none at all, both go out and take a source prefix plus a digest so neither loses its name. A name that differs from a registry entry's only by surrounding whitespace is a *different* tool, not another spelling of this one: the provider-facing name is the legalised one, while the hand-back and the origin keep the raw name Open WebUI gave it.

A replayed `function_call` is renamed so that it is never handed to the provider under a name the request does not offer under exactly one meaning. An origin carried by exactly one advertised tool is rewritten to that tool's advertised name, which is the name the model actually saw. An origin two advertised tools share cannot be resolved to either — nothing in the request says which of them ran, and picking one on the strength of a dictionary's iteration order would tell the model a specific tool ran — so it is renamed to a legal provider token *outside* the advertised set instead. A tool the request no longer offers at all is not ambiguous and keeps its bare legal name, so a support trace still matches the key Open WebUI ran. The three spellings of one origin behave the same way whatever the spelling: a legal token is renamed on the shared-origin arm, and an illegal or over-long one is renamed by the cleaning it already needed. A replayed item is never executed — the executor runs items out of the provider's fresh `output` array — so all of this is wire-and-card-text only.

## Tool execution lifecycle (Responses API loop)

Tool execution happens in the request loop that follows each Responses API call:

1. The pipe calls the provider (streaming mode for normal chats).
2. When a `response.completed` event arrives, the pipe inspects the response `output` list.
3. Any `output` items with `type == "function_call"` are treated as tool calls to execute locally.
4. The pipe executes the tools and converts each result into `function_call_output` items.
5. The `function_call` items (normalized) and their outputs are appended to the next request’s `input[]`, and the loop continues until either:
   - no more `function_call` items are returned, or
   - `MAX_FUNCTION_CALL_LOOPS` is reached — pending tool calls receive stub responses and the model gets one additional turn after them to synthesize a final answer, so a turn that reaches the cap bills `MAX_FUNCTION_CALL_LOOPS + 2` model requests. Each abandoned call is also shown to the person as a **failed** card, the shape a genuinely failed tool produces, when tool cards are on. A model that still asks for a tool on that last turn ends the reply with the note `Tool-call limit reached (<cap> iterations).`: in a saved chat it is the message's error on a streamed reply, and a reply returned whole, or streamed to a caller with no chat, carries it at the end of the answer text.

Notes:

- A round that names an offered tool the pipe has nothing to run behind goes back whole after exactly one upstream request: an API caller gets it back directly, and a streamed saved chat hands it to Open WebUI. Under the passthrough the pipe publishes that call as the `function_call` item Open WebUI renders, and Open WebUI's own after-stream call resolution in `streaming_chat_response_handler` is what keeps the list to one item of it. A name the request **withheld** from the model is handed back on the same terms and before the budget is ever consulted, because a withheld name is a name Open WebUI offered: under `legacy` a model that names one anyway — most often replayed from chat history — has its round handed back rather than answered, so neither `Tool not found` nor the skipped card is reachable for it. Under `ask` the withholding applies on a reply that is not streamed in a saved or temporary chat, and inside a Fusion member on a streamed reply as well; where nothing can be handed back, the pipe's own loop answers a name nothing offered. While the hand-back stands, the pipe never answers `Tool not found` for a name the request itself offered; once the hand-back budget is spent, a caller's own advertised schema with nothing behind it is answered `Tool not found` like any other name the pipe cannot run, because at that point the pipe is adjudicating calls in its own loop rather than sending them back.
- A reply's hand-back budget is charged only against that reply, and only a reply Open WebUI can re-ask is charged at all. The budget belongs to that user's spend as well as that reply: two users naming the same `chat_id` and `message_id` are charged to two budgets, and neither user's turns change the other's. A request that supplies both a `chat_id` and a `message_id` spends one turn of that reply's budget per turn, and once that budget is spent the pipe stops handing back and runs the remaining round itself, against the same tools it advertised. The exception is a round Open WebUI itself runs: a round of browser-run tools or Open WebUI's own builtins, any round at all under `ask` tool approval on a streamed reply in a saved or temporary chat, or a tool the request withheld under `legacy` function calling. Such a round is handed back whatever the budget says and the reply is bounded by Open WebUI's own `CHAT_RESPONSE_MAX_TOOL_CALL_ITERATIONS` instead — which is the point: for the withheld and builtin rounds because the pipe answering such a call is what would produce `Tool not found` for a name the request itself offered, and under `ask` because there the tools are offered and runnable, and the pipe must never run a call the person has not approved. A round mixing one of those with a call nobody can run falls to the pipe's cap outside `ask`, because a call with nothing behind it is not Open WebUI's to run either; under `ask` the whole round is handed back regardless. Anything else — an OpenAI-compatible API caller, a caller that supplies only one of the two ids, any internal Fusion member, and Open WebUI's own task requests such as follow-up and title generation on the same chat — is handed back once per request, so those requests no longer share a budget with each other or with a live reply. The budget ends when a turn ends the reply; a turn the person continues from — a Continue, or a tool prompt they answered — is a further turn of that same reply rather than the end of it, so it carries the budget on rather than resetting it. The pipe keeps a budget for at least as many replies as it admits requests at once (`MAX_CONCURRENT_REQUESTS`), so a reply in flight is never the one whose budget is dropped to make room. A temporary chat is charged as well, under a key whose chat-id slot is blank: its id is the browser's socket id, and the budget outlives the reply in a process-lifetime map. The blanking costs the reply nothing — `message_id` is still what tells two replies of one temporary chat apart, so the budget stays per-reply and is never a shared one.
- A name nobody offered is answered `Tool not found` inside the loop.
- A schema that will be handed back is never strictified, and it keeps the fields the request put on it (`cache_control`, `strict`). A caller's tool the pipe runs has its `strict` taken from the request - unless the valve is on and passthrough is off, in which case the pipe strictifies the schema and advertises `strict: true` itself. A tool that arrived in Chat Completions shape states its strictness explicitly, `false` when the request named no `strict`, because `/responses` reads an absent one as `true`; that stamp returns on the chat leg too, nested under `function`, where the endpoint already defaults to `false`. A tool that arrived in Responses shape is passed through with exactly the keys it arrived with.
- A tool receives only the arguments **the schema the pipe advertises** declares, as in Open WebUI's own tool loop: anything else the model sends is dropped before the tool runs, so it can never replace what Open WebUI bound into the tool (such as the user a built-in tool acts for).
- For a browser-run (direct) tool the argument filter is the only thing the model's arguments can influence: the operation and the server it reaches come from the tool's own registry entry, are captured in the closure, and are never taken from the model's arguments — so the model's arguments cannot point the call at another operation or server.
- Before each call the pipe hands the tool the chat's messages and files as the current request carries them (`__messages__`, `__files__`), as Open WebUI's own loop does; a Fusion panel model's tools see the person's chat.
- The pipe does not “stream” tool outputs mid-request. Tools are executed between Responses calls.
- `MAX_FUNCTION_CALL_LOOPS` applies whenever the pipe runs the calls, whatever the mode: a non-streamed reply, a Fusion panel model, a tool a request declared with nothing behind it, and every call except the ones Open WebUI runs under 'ask' approval, legacy function calling, or a model it holds back. Where Open WebUI runs the calls, it applies the cap of its own.

## Adaptive tool output budgeting

This section documents the dynamic context-budget guard. It runs on every request, in either tool execution mode; in `Pipeline` mode it also budgets each round's new results before the next call.

### Problem users observe

In long tool loops, the request can become context-saturated (large replayed artifacts + new tool outputs + reasoning state). A common symptom is:

- tool loops continue, but the model eventually returns no useful assistant text (or an incomplete response) because the prompt budget is exhausted.

### Conceptual fix

The pipe now applies **adaptive, model-aware budgeting** instead of fixed output caps:

- It derives prompt limits from model metadata: `max_prompt_tokens` when the catalog publishes it, otherwise the model's `context_length` less whatever reply allowance the request itself carries, with safe fallbacks, and a routing variant such as `base:nitro` resolves through its base's row. The provider's largest possible completion is not reserved — that is a ceiling the request never asked for, and on most of the catalog it put the budget far below the real window.
- It estimates request/input size and omits oversized `function_call_output` payloads by replacing them with a short model-visible stub that advises the model to retry with a narrower query. An attachment is charged by its block's type and not by how many base64 characters happened to carry it: a picture at a flat rate, and audio, video and documents at a bytes-per-token rate. The two wire spellings of a video block — `video_url` and the `input_video` the `/responses` rewrite produces — carry the same rate, so which one a turn sends never changes what the clip costs.
- The model retains full tool access throughout the conversation and can recover from oversized results by retrying with tighter parameters.

This keeps the loop alive, informs the model in-band, and lets the model decide whether to summarize, stop tools, or ask for narrower tool queries.

### User-visible behavior changes

- Some tool outputs may be replaced by an omission stub in the request sent to the model, when the full text would exceed the remaining context budget for that turn.
- The stub replaces the result only in what the model is sent, for the rest of that turn. A shown tool card and the saved message keep the full text, and a warning notification names the tools the model did not receive.
- On later turns the request is rebuilt and budgeted again. With `PERSIST_TOOL_RESULTS` on, an omitted result is handed over in full once it fits -- the context has room, or the chat moves to a larger model; with it off, an earlier turn's result -- or one from a round that arrived before the chat's first turn -- is only a note anyway.
- If tool loops complete without any assistant content growth and no actionable continuation remains, the pipe emits a fallback assistant message instead of staying silent.

### Operator guidance

To reduce omissions and improve reliability:

- Prefer tools that support tight server-side limits (`limit`, `top_k`, date ranges, filters).
- Have tools return concise summaries plus references/IDs instead of full raw blobs.
- For bulky outputs (search results, logs, traces), expose pagination/continuation parameters so the model can request smaller chunks.
- `PERSIST_TOOL_RESULTS` is off by default to keep long conversations lean; enable it (site-wide or per user) when chats need to reuse exact raw tool outputs on later turns instead of re-fetching.
- `TOOL_TURNS_TO_REMEMBER` (default `5`, from `0` to `100`) bounds how much tool history a long chat sends. A turn is one message a person sends plus the assistant's whole reply, however many tools it used; messages the person sends back to back belong to the same turn. The turn being answered always goes whole, with every tool round it has made so far. Of the turns before it, the most recent `TOOL_TURNS_TO_REMEMBER` keep their tool calls (and their results while `PERSIST_TOOL_RESULTS` is on); the kept span widens by one turn at a time up to twice the setting minus one and is then cut back to the setting, so the oldest kept turn moves only at those steps and the start of the request the provider caches stays unchanged between them. An older turn that used tools goes back as conversation text only: the person's messages and the assistant's answers, with no tool call, no tool result, no OpenRouter server-tool round (a web search or a fetched page, for example) and none of the thinking stored for it, because a provider can refuse thinking that is sent without the calls it belongs to. `0` sends no tool call from any earlier turn. Two things are never cut: a built-in `ask_user` question and the person's answer go back in every request, whatever the number is, and an older turn that used no tool at all goes back exactly as it would without the setting, its stored thinking included. The limit decides what the model is handed on both endpoints and in both tool execution modes; shown tool cards and the pipe's own copy of each round are not changed, so raising the number hands older rounds to the model again, and each message renews the retention date of the stored rows its conversation still points to, so a chat that is still in use keeps them (the rows of a deleted message expire as before). A user can set their own value, which wins for their chats. `TOOL_OUTPUT_RETENTION_TURNS` can shorten an output only in a turn that is still sent. Its cut boundary moves only every this-number-th turn: between moves the results of the last up to twice this number minus one turns, the one being answered included, go whole, and the start of the request the provider caches stays unchanged between the moves.

## Tool execution cards (`SHOW_TOOL_CARDS`)

When `SHOW_TOOL_CARDS` is on (the default), each tool the model uses appears in the chat as a collapsible card, exactly as Open WebUI shows a tool it runs itself:

- **In-progress cards** appear in a streamed reply together, once the model has named a round's calls and before the first of them starts, each showing its call's name and arguments. A reply that is not streamed shows its cards when it ends. In a streamed reply, Open WebUI's `ask_user` card stays hidden while its question is open, as Open WebUI keeps it, and shows as soon as the answer arrives; a reply that is not streamed shows it when the reply ends.
- **Completed cards** show the result once the tool, and every call before it in its round, has finished, except a call the pipe refused before running it, which is shown as soon as the refusal is made. A call that failed or timed out keeps its real status rather than being recorded as a success. Where its text alone would not show the failure, the text opens with `Error: the tool call did not complete.`; that judgement of the text is Open WebUI's own classifier, or the pipe's copy of it when that module could not be imported so that later turns still read the call as failed. As in Open WebUI's own tool loop, a picture that a tool call returns as image data goes only to the model, with that call's result, and is gated first — scheme, plain `http://`, and the address an `http(s)` link names — so a link the pipe cannot use is never forwarded and is named in the chat on the turn that round is answered on; a relative, host-less `/api/v1/files/…` reference is the one OWUI-path spelling the gates exempt, because it names no origin the provider could dial, and it is inlined from local storage rather than forwarded — while an absolute URL carrying that path is a link like any other and is put to the same checks; a picture Open WebUI has stored as a file, such as an MCP tool's, goes to the model with that result and stays in the chat, as Open WebUI does; the call's other files go only to the chat, each stored under a name built from the content type the tool answered with, and falling back to `tool_result.bin` for a type nothing can name. A file the pipe could not store — in a temporary chat, one past the fixed per-item receive ceiling, an undecodable payload, or a storage refusal — is not shown, and a warning names the tool that returned it, so a file that vanishes is never mistaken for a tool that returned nothing. The card shows the tool's text.

A shown card is saved with the message and reappears when the chat is reopened, because Open WebUI draws a card for every tool call saved in a message. That holds whether or not the reply was streamed, and when a reply ends in an error: a reply that is not streamed hands Open WebUI the same record a streamed one publishes. The exception is a reply that is not streamed and is stopped before it ends: it keeps no cards, because Open WebUI then receives no reply to save. Open WebUI also hands a saved round back to the model on later turns, for the earlier turns `TOOL_TURNS_TO_REMEMBER` keeps and for a built-in `ask_user` round of any earlier turn, and the pipe then sends no second copy of it. In a streamed reply, Stop keeps the calls before the first one still running: Open WebUI saves their cards as finished and hands them back, and with cards off the pipe's own copy does. The pipe writes a round's calls when the round starts and each result when its call returns, and the round comes back to the model in call order on that turn. A call the pipe refused before running it, such as one naming an unknown tool, is answered at once and on the turn it is answered is handed to the model in the order the round asked for it, because its answer is produced before any queued call has run; a round stored with cards on is written as the calls are answered, so a Continue replays that refused call's answer ahead of the results that were still to come; its card is shown as soon as it is answered. A call the model sends malformed is taken as Open WebUI's own tool loop takes it on the same route, and is kept with its card like any other: missing or blank arguments, and `null` on `/chat/completions`, count as `{}`; `null` on `/responses`, or any value that is not an object, is answered that the arguments must be a JSON object; arguments that are not JSON are read as a Python literal, or answered that they could not be parsed; several objects sent back to back run as one call each; a call without a name is not kept anywhere, and the model is told nothing about it. Files and embeds a tool returns travel on its card; with no card they appear with the message instead, so they reach the chat once either way.

With `SHOW_TOOL_CARDS` off, no card appears at any point: not while the answer streams, not after it finishes, and not on reload. That is only possible by keeping the tool round out of the saved message, since Open WebUI would otherwise draw it. The model still learns on later turns which tools it used, for as many earlier turns as `TOOL_TURNS_TO_REMEMBER` keeps and for the built-in `ask_user` questions of every earlier turn: the pipe keeps its own copy of each round, written as the round runs (a web search is written when the turn ends), and hands it back, so the model can tell an answer it looked up from one it made up. A temporary chat is the exception: the pipe keeps nothing for it, so with cards off the model does not learn of earlier rounds. The copy holds the call and its result in full, as a shown card does, except a web search, which holds its query (none on `/chat/completions`, where OpenRouter does not send the query back and the call has no arguments), its links and the excerpts the engine returned within the record caps, and a fetched page, which is cut at 150,000 characters with a note saying how much; `PERSIST_TOOL_RESULTS` decides whether a later turn gets the result or a note in its place, exactly as it does for a round that Open WebUI hands back, and a picture comes back in the same place, in Open WebUI's own images message. One card is kept all the same. Open WebUI draws a terminal file inline only from its saved `display_file` card, so for a person whose Open WebUI shows terminal files inline, the pipe keeps the card of a file the model shows through Open Terminal. Whether terminal files show inline comes from that person's own interface setting, or from the site's default when they have none. For everyone else, a file the model shows inline (`display_file` with `inline`) opens in the preview panel instead. Tools that internal Fusion's panel models run get no card, no preview and no file-browser refresh, whatever this setting says. What a tool returns feeds only the answer of the panel model that ran it, where a file it returns shows as a link. A link found in a tool result is **not** listed among the reply's sources: only a link from one of Open WebUI's own five citing tools, from the model's own `url_citation` annotation, or from a Fusion item is — and the five citing tools' own sources are withheld too while that model's `Citations` box is unticked, which is the same verdict Open WebUI reaches from the same model row. An MCP or tool-server web tool therefore keeps no citation chip, and there is no setting to bring the chip back. The pipe is here stricter than Open WebUI in one way: by tool identity. Open WebUI's own gate is by tool *name*, so any tool carrying a builtin's name would get a chip there — a tool-server entry named `fetch_url` does, and a custom tool named `fetch_url` displaces the real builtin in Open WebUI's registry and is cited in its place. On the capability the two now agree, and neither gates the provider's own annotations. The model still receives the tool's full result, and can name the link in its answer.

This setting is available as both an admin valve and a user valve (users can override the admin default).

**Scope:** cards for tools the pipe runs apply only when `TOOL_EXECUTION_MODE="Pipeline"`; in `Open-WebUI` mode Open WebUI runs those tools and draws its own cards, whatever this setting says. Cards for OpenRouter's server tools (web search, fetch, datetime, advisor, subagent) follow this setting in both modes.

## Tool history search (`TOOL_HISTORY_SEARCH`)

The pipe can offer the model three tools that read this chat's own earlier tool rounds: `search_tool_history` (keyword, exact-text or RE2 search over tool names, arguments and stored results, best matches first), `list_tool_history` (every call, newest first, no ranking) and `view_tool_call` (one call's result or arguments, in pages at the sizes of Open WebUI's own file viewer). They exist so a long chat stays small: `TOOL_TURNS_TO_REMEMBER` bounds what each request repeats, `PERSIST_TOOL_RESULTS` decides whether earlier results ride along at all, and the tools let the model fetch any older round of the current chat path on demand, whatever those two are set to. With the keep-results setting off, the note that stands in for each withheld result names the round's id (`[This call succeeded. Its result is not kept for later turns; view_tool_call 37.4 returns it.]`), so the model can read the stored result without anything being sent twice. The tools appear in a request once the chat holds an earlier tool round that the request does not repeat in full, on either endpoint, streamed or not, and the pipe runs their rounds through the ordinary executor, with its timeout, breaker, tool cards and record storage. An admin or the person whose chat it is switches the feature off with the same-named valve on each side; with it off, or wherever the tools are not offered, requests are exactly what the pipe sent before the feature existed.

The rounds the tools see are the ones the replay sees, decided by the same code: the conversation Open WebUI hands the pipe, plus, for a round that copy lacks (tool cards off, a round the pipe ran without Open WebUI answering it, a raw server item), the pipe's own stored copy, read lazily on the first history call of the reply through the replay's own loader and decryption, never the shortened form the request carries. The search stores nothing and builds no index; the catalog assembles from the request's own messages in memory, and the scan itself runs in a worker thread, so a reply whose model never calls the tools pays nothing beyond the offer check. What the tools do not reach: the history tools' own earlier rounds, reasoning, the rounds of turns Open WebUI's context compaction has summarised (the replies say so), and sibling branches of the chat - only the current path exists in the request. A tool's pictures are not returned; the reader returns the round's text. The tools' replies carry each hit's turn, the person's message that began it, the arguments and the matching line, so a hit can be checked against the conversation, and a zero result says what was searched. The ids are `turn.position` on the chat's current path: an edit, a deletion or a branch switch moves them, and the replies say that too. A history call that reads stored rows refreshes their retention date as any read does, and the tools' own rounds are stored, withheld and aged by the standing rules. Measured on a synthetic chat built to the production chat's shape (3,395 calls, about 24 million characters of result text) in a test container on a desktop CPU, the shipped module built its catalog in about 45 ms, answered keyword searches in a median of about 60 ms with the slowest observed query at 0.17 s, an exact search in about 17 ms, and a page read in under 1 millisecond, alike on Python 3.12.2 and 3.11.14; these are one container's observations, not a limit or a promise, and production's shared cores are slower per core. In the `Open-WebUI` tool mode the tools are offered only on a reply the pipe runs itself; a streamed reply there, or one the person approves call by call, is executed by Open WebUI, which does not know these names and would answer `Tool not found`, so the tools wait for a dev-box-proven hand-back before they are offered there.

## Concurrency, ordering, and timeouts (per request)

Tools are executed via a per-request worker pool backed by a bounded queue:

- Queue size: 50 batches per request (bounded). A round is put on it one batch at a time, each after the calls before it have ended, and a batch is one call or the round's `delegate_task` calls together, so a round of any width fits.
- Worker count: `MAX_PARALLEL_TOOLS_PER_REQUEST`, started when the request's first tool call is queued, so a turn that queues no call starts none, whether it made no tool call at all or had every one of them refused before queueing. A round has one batch in a worker's hands at a time, a single call or the whole `delegate_task` group; the other workers serve a call that follows one the pipe has stopped waiting for while its body still runs.
- Per-request semaphore: limits concurrent tool executions per request. A round's calls run one after another, so it limits the round's `delegate_task` calls, the calls of the internal Fusion models of one request, and calls whose bodies run on after the pipe stopped waiting for them.
- Global semaphore: `MAX_PARALLEL_TOOLS_GLOBAL` limits tool executions across all requests.
- Plain-function thread pool: a tool whose body runs synchronously — a plain function, including one Open WebUI hands the pipe wrapped in its async shell — is offloaded to a pool the pipe owns, `min(MAX_PARALLEL_TOOLS_GLOBAL, 8)` threads wide, while `Synchronous tools on threads` is on; with it off, the wrapped body runs on the event loop as before. The semaphores above are the gate that decides which calls are admitted; the pool is the isolation boundary that keeps an admitted blocking tool from taking the threads Open WebUI's own requests and this pipe's storage work use. Raising the valve above 8 therefore admits more calls without adding threads. One Tools file (every function that shares one Open WebUI tool id; the tool's name stands in for a tool that carries none) may hold at most `max(pool width - 2, min(pool width, MAX_PARALLEL_TOOLS_PER_REQUEST))` of those threads: 6 of 8 on the defaults, and nothing reserved when `MAX_PARALLEL_TOOLS_PER_REQUEST` is at least the width, so the calls of one request that run together are not slowed by the share. A thread counts as held until the body running on it returns, not until a time limit gives up on the call, so a Tools file whose calls hang cannot take every thread. Its further calls wait for a thread of its share, and a waiting call holds no request slot, no process-wide slot and no worker: it is parked outside the queue, so it never keeps another request's healthy tool from running (the calls after it in its own round wait for it, as they wait for every call before them), and when a body returns the longest-waiting calls that fit go through the queue again and take a slot like any call. A call that is running counts against `MAX_PARALLEL_TOOLS_PER_REQUEST` and `MAX_PARALLEL_TOOLS_GLOBAL` like any other. Nothing ends a parked call but its request ending, and after five minutes of waiting one WARNING per Tools file in five minutes names the file and how many of its calls wait and, when the pool is full of other files' bodies, which Tools files hold the threads. A change that alters the pool's width applies from the next synchronous tool call, and bodies still running on the old pool keep their threads there; a change that only moves the share applies once no call is waiting for or holding a tool thread.
- A synchronous tool body waits for an async result with `.result()` on the future that `run_coroutine_threadsafe(...)` returns, or, in a body Open WebUI wrapped in its async shell, that `asyncio.create_task(...)` returns; the coroutine runs on the loop the body left, and the same `.result()` on the loop thread deadlocks.
- Open WebUI's built-in `ask_user` takes no slot from either semaphore, because it waits on a person rather than doing work.

Order of a round's calls:

- A round is the tool calls the model asks for in one response. They run one after another, in the order the model asked for them, as in Open WebUI: the pipe queues a call only after the call before it has ended, and a call starts only after the call before it has returned, raised an error, been skipped or cancelled, or been cut by a time limit.
- Calls to `delegate_task`, Open WebUI's sub-agent tool, are the exception, as in Open WebUI. A call counts as one when the tool it resolves to is registered in Open WebUI under that name. They start together once every other call of the round has ended, as one group that `MAX_PARALLEL_TOOLS_PER_REQUEST` and `MAX_PARALLEL_TOOLS_GLOBAL` limit.
- Results go back to the model in the order the model asked, and a call's card fills in once that call and every call before it has finished, so a call listed after a `delegate_task` call is shown when that sub-agent has finished.
- A call that is still running when the pipe stops waiting for it can overlap the next call: a synchronous body on a pool thread cannot be stopped, a body that ignores its cancellation keeps running, and `TOOL_IDLE_TIMEOUT_SECONDS` does not stop the call it gives up on. The round's next call starts at once in each case, unless the calls still running hold every slot the request has or every worker it has (at `MAX_PARALLEL_TOOLS_PER_REQUEST` `1` one running call does), in which case it waits until one of them ends. A call `TOOL_IDLE_TIMEOUT_SECONDS` gave up on holds its slot and its worker until its body returns, and a body that ignores its cancellation holds its slot.
- Each call's result is handed back as soon as that call has finished. The same holds inside internal Fusion: each model's calls run one after another, the models run side by side, and each model that calls a tool gets as many tool workers as the chat request it answers, with all of those models sharing that request's slots.

Timeouts:

- Waiting never ends a call. A call that has not started -- behind the calls before it in its round, in the queue, waiting for a worker, for a request slot or a process-wide slot, for its Tools file's share of the pool's threads, inside Open WebUI's re-bind of the tool, or waiting for a thread -- is not limited by `TOOL_TIMEOUT_SECONDS`, `TOOL_BATCH_TIMEOUT_SECONDS` or `TOOL_IDLE_TIMEOUT_SECONDS`. It runs the moment what it waits for frees, however long that takes, and its answer reaches the model; when what it waits for never frees, the reply waits until the person presses Stop. A call that waits for a tool thread holds no slot and no worker meanwhile. A call that waits for a slot waits behind running calls, and every limit ends a running call except a tool body that ignores cancellation: such a body keeps its request slot and process-wide slot until it returns, and only Stop ends a call waiting behind it. A call stuck inside Open WebUI's re-bind of the tool holds its slots the same way, because no limit applies before the body starts. Every limit below counts from the call's own start.
- Stop withdraws exactly the calls that have not started. When a request ends -- the person presses Stop, a streamed API client drops the reply, or an error ends the request; closing the browser tab does not end a chat that Open WebUI runs in the background, only Stop does -- every call that has not started is withdrawn the moment the cancellation reaches the round, before the rest of the request has finished unwinding, and never starts: calls behind the one that was running are never queued, batches still in the queue are dropped, a call parked for a tool thread, a call waiting for a worker or a slot, and a call in Open WebUI's re-bind are cancelled, and a call that a pool thread has taken but not yet entered finds itself withdrawn and skips its body. Calls already running keep `TOOL_SHUTDOWN_TIMEOUT_SECONDS` to finish. A withdrawn call counts toward no tool's breaker. An error raised before a call's body can start, such as a thread that cannot be started, reaches the model at once with its own text and counts like any other error the call raises.
- Each tool call has a per-call timeout (`TOOL_TIMEOUT_SECONDS`), measured from when the call's body starts, never from when it starts waiting. When it expires the pipe stops waiting, the model reads `Tool '<name>' timed out after <N>s.`, the round's next call starts, and the timeout counts once toward that tool's breaker. An async tool is cancelled; a synchronous body -- a plain function, or, while `Synchronous tools on threads` is on, one Open WebUI hands the pipe wrapped in its async shell -- is not, and runs to its end on a thread of the pipe's own tool pool, whose width is `min(MAX_PARALLEL_TOOLS_GLOBAL, 8)`. That body keeps its thread until it returns, and a WARNING names its Tools file, the tool and how many tool threads that file holds (one WARNING per Tools file in five minutes; repeats within that time are logged at DEBUG).
- Each tool call runs exactly once. A tool that raises an error is never retried automatically, because tools can have side effects (an MCP tool that sends an email must not fire twice). The failure is reported to the model in Open WebUI's own form — a JSON object on two lines, `{` / `  "error": "<the exception's message>"` / `}` — which is the same text the person reads on the tool card, so the two never disagree. When the exception carries no message, the class name is used instead.
- If Open WebUI has already closed an MCP tool's client connection, the tool reports "no longer available in this session" rather than a raw error, and this does not count against its breaker.
- Each call is held to the batch limit (`TOOL_BATCH_TIMEOUT_SECONDS`, never shorter than the per-call timeout), counted from the moment that call starts. It is a backstop: it starts at the same moment as the per-call timeout and is never shorter, so it ends a started call only where the per-call timeout could not -- a body that ignores its cancellation, or a call stuck after its body returned, while its result is processed -- and it never ends a call that has not started. The tool breaker's out-of-service notice is bounded by that value measured from the moment the notice itself runs -- the notice a call sends when its tool opens between queueing and running is bounded by it alone, the notice sent when the round is queued also by whatever `TOOL_IDLE_TIMEOUT_SECONDS` leaves of the round's total -- so a round that has already spent that time can still deliver the line; a notice one of those bounds cuts is logged with the valve that cut it named, and the model is still told the reason for every call that was skipped. When the limit is reached for a call, that call is cancelled and reported as `Tool '<name>' exceeded <N>s and was cancelled.` unless it answered inside the five seconds below, where `<N>` is `TOOL_BATCH_TIMEOUT_SECONDS` unless an `ask_user` question window raised the limit above it, in which case the sentence says so and quotes `TOOL_BATCH_TIMEOUT_SECONDS` alongside. The round then stops waiting for that call as soon as it has had five seconds to acknowledge the cancellation; one that has not is dropped from the round and keeps running, holding its request slot and process-wide slot until it returns (a call waiting for one of them then waits until Stop), and its result never reaches the model. A cancelled call counts once toward the tool's breaker, except one that `TOOL_IDLE_TIMEOUT_SECONDS` had already given up on, one that answered inside those five seconds, or one whose own cancellation path raised an error.
- `TOOL_IDLE_TIMEOUT_SECONDS` (unset by default) caps how long the pipe waits for a call's result once the call has started, counted from that call's own start, so a call that started late -- after waiting for the calls before it, a worker, a slot, its Tools file's share or a thread -- gets its whole allowance from the moment it starts. The tool breaker's out-of-service notice is bounded by that allowance counted from when the model asked -- it gets what is left once it runs -- and a notice this limit cuts is logged with this valve named, every skipped call still answered and told why. When the time passes, a call that had started and has no result reads `Tool '<name>' timed out after <N>s (idle timeout).`, where that `<N>` is this setting's own value -- an open `ask_user` question raises the wait past it, and the number reported under that label does not change with it. A call that has not started is not given up on: it runs when it can, and its answer reaches the model. Giving up this way does not count toward the tool's breaker. A call that is already running is not stopped: it keeps running and holds its slot and its worker until it finishes, another limit ends it, or request cleanup cancels it after `TOOL_SHUTDOWN_TIMEOUT_SECONDS`. The round's next call starts at once, as the order rules above say. The model never receives the late result. Outside internal Fusion, files or embeds the call returns still appear in the chat: a streamed reply waits for the call, bounded by `TOOL_SHUTDOWN_TIMEOUT_SECONDS`, so a call that returns during that wait is read before the reply ends. When they do appear, a file the call shows through Open Terminal opens in the preview panel, or nowhere for a person whose Open WebUI shows terminal files inline: their browser ignores the preview request, and the call's card has already closed as timed out. The call's own later error or per-call timeout still counts toward the tool's breaker, and a later success clears the count. The tool workers remain for the whole request, except inside internal Fusion, where a model's workers and its running calls are cancelled as soon as that model's answer ends, without the `TOOL_SHUTDOWN_TIMEOUT_SECONDS` wait, and the calls that had not started never start.
- Open WebUI's built-in `ask_user` -- the built-in specifically, identified by the tool behind it and not by the name it is advertised under -- keeps its question open for the time the model asked for, as normalised by Open WebUI. Its per-call limit becomes that time plus 15 seconds, and the batch deadline and the idle limit are raised to at least that long. Since it takes no tool slot, its question does not wait for other requests' tools, though it still needs one of its own request's workers to be free. It waits for that worker as long as it takes, and its question window counts from the moment the question opens. Its timeout does not count toward the breaker. It runs alone: an `ask_user` call mixed with other calls, or repeated in the same response, is refused with Open WebUI's error text, and the other calls run. That "only tool call" rule is checked first, so a malformed `ask_user` that shares its turn with another call is refused with Open WebUI's own "runs alone" text, not with the pipe's argument text. The rule is Open WebUI's, applied to the name as the model sent it, so a spelling Open WebUI would not recognise as the built-in — a padded `" ask_user "`, or a collision-renamed `owui__ask_user` — does not get the rule: the pipe still resolves that call to the built-in and runs it, and the built-in resolves that name the same way (see the padding rule below). A call whose arguments Open WebUI's own normaliser rejects never reaches the builtin: alone in its turn it is refused with `Error: <Open WebUI's own message>`, and it neither counts toward the breaker nor starts a worker, so ask_user stays usable.

## Breakers (stability controls)

Three per-user breakers share `BREAKER_MAX_FAILURES` and `BREAKER_WINDOW_SECONDS`; each internal Fusion run also keeps one count per tool, shared by all of its models, which uses `BREAKER_MAX_FAILURES` but not the window. The per-user breakers count failures in two ways:

- **Per-user request breaker:** counts each failed chat call to OpenRouter within the trailing `BREAKER_WINDOW_SECONDS`, across the workers when the Redis cache is active (see [Concurrency Controls & Resilience](concurrency_controls_and_resilience.md)) and per worker otherwise, whether the failure is an error reply; a connection that cannot be opened, drops or times out; an accepted body lost before it finished arriving; an error OpenRouter reports after accepting the call (an error event in the stream, or an error body); or a stream that stops before its final event. A request the pipe retries automatically counts once, however many tries `TRANSIENT_RETRY_MAX_ATTEMPTS` spent on it. A `/responses` failure that the endpoint fallback repairs on `/chat/completions` is the one failure that counts none: its strike is taken back the moment the fallback is decided, not at the end of the turn, and only its own. A stream that ends as `response.incomplete` (for example, when the answer reaches its length limit) is a finished call, not a failure. A generation on a picture-only image model or a video model counts once, when it fails after being answered by OpenRouter, except a generation whose response arrived whole and was not an OpenRouter document — a body a proxy, CDN or WAF rewrote, or one that is not a JSON object at all, which is not a failure of the request and never counts toward the limit. A chat turn that completes without delivering anything the reader can use -- no assistant text, no named tool call and no emitted item -- is reported as an error and still counts nothing. A video generation whose clip the pipe's own download policy refused (address gate, insecure-HTTP policy, size cap, MIME allowlist) is another exception: it still fails, still shows the card, and is not a failure of the request either. A generation OpenRouter completed on a picture-only image model or a video model is a further exception: when none of its pictures or clips is stored, because Open WebUI's Max Upload Size (Admin Panel > Settings > Documents) refuses them or the upload fails, the card still shows, nothing is counted, and the user's failures are cleared as a delivered picture or clip clears them. OpenRouter's answer that no endpoint meets a request's data policy (a model with no Zero Data Retention endpoint under `ZDR_ENFORCE`, say) is a refusal rather than a failure: the card shows and nothing is counted or cleared. A request that ends without an error clears the count only if it also delivered something the reader can use (assistant text, a named tool call, or an emitted item), but a request to a picture-only image model or a video model clears it only once its result is delivered whole (a generation OpenRouter completed also clears it when none of its pictures or clips is stored), and a stream that breaks after the finished image arrived clears nothing, and a request the user stops does not clear it. Housekeeping tasks such as title generation neither count nor clear, and a request refused before anything is sent (such as a missing API key, or a model the pipe will not serve) neither counts nor clears; Open WebUI's merge-responses task counts but never clears. At `BREAKER_MAX_FAILURES`, that user's new requests are refused with "Temporarily disabled due to repeated errors. Please retry later." until the oldest failures age out of the window, or until a request that is still let through ends without an error and clears the count: one already under way when the limit was reached, or an exempt one. A request is exempt, and never refused by this breaker, when its last message is a tool result, or is Open WebUI's own message handing the model a tool's images directly after a tool result. That is how Open WebUI calls back after running its tools to finish an answer already under way. Open WebUI's own message consists of its fixed sentence followed only by the images. A question the user types, or a picture they attach, right after a turn that ended on a tool result is a new request, which the breaker refuses like any other. Inside internal Fusion, the run counts once: one failure when no panel model answered, none when one did, however many of its panel, judge or final-answer calls failed at OpenRouter; when the run ends, the count, including that run's own failure, is cleared if the run finishes and any panel model answered, and kept if none did or the user stopped the run.
- **Per-user, per-tool breaker:** counts a tool's failures in a row, keyed by tool type and the tool name it was looked up by, so other tools of the same type, including the rest of an MCP server's tools, keep working. A name the model padded with surrounding whitespace is the same tool and spends the same budget. A successful call clears the count, whichever spelling of the name it was sent under, and so does a gap longer than `BREAKER_WINDOW_SECONDS` between the tool's last failure and its next call. The gap is measured to the next call, not between failures, so a slow tool that keeps timing out still trips. Errors, per-call timeouts, running calls cancelled by the batch deadline (other than calls the idle limit had already given up on), and calls whose tool server cannot be reached or answers with an HTTP error status count; an `ask_user` timeout, a call to an MCP tool whose session already closed, a call that is waiting and a call withdrawn at a Stop do not -- they have not run and cannot have failed -- while a call that has started and reaches its limit counts once, and an error raised before a call's body can start (a thread that cannot be started, say) counts like any other error the call raises. A call that waited for a tool thread is not refused by the breaker when its turn comes, even if the tool has tripped in the meantime. A `SystemExit`, `KeyboardInterrupt` or `GeneratorExit` out of a tool is not a failure of that tool: it signals the process rather than the tool, so it shows as failed on its card but neither adds to the count nor clears it, and the tool is not skipped because of it. A failure that the tool reports in a result it returns normally, such as an error message inside a successful response, shows as failed on its card but neither adds to the count nor clears it, whether the judgement is made by Open WebUI's own classifier or by the pipe's copy of it. Each internal Fusion run keeps one count per tool, shared by all of its models: a tool that fails `BREAKER_MAX_FAILURES` times in a row within the run is skipped from then on. Unlike the user's own count, this one is never cleared by a quiet spell, only by a success; once the tool is skipped, only an already-running call to it can supply that success. Calls to that tool inside the run neither raise nor clear the user's own count for it, and are not skipped because of that count.
- **Per-user DB breaker:** counts failed database reads, writes and deletes of stored reasoning, tool results and session logs within the trailing window. A failure to refill the artifact cache after a read that already succeeded is not a database failure and is not counted, and neither is a failure sealing rows for storage on the way to the database, which drops the round before the database is asked for anything. A delete that faults counts here like any other database failure, which is what lets a database that has started refusing clean-ups open the breaker rather than being re-asked on every turn. A successful read or write clears the count; where Redis buffers writes, a write succeeds once Redis has taken it. Below the limit, a write the database refuses is announced to the person on the turn it happens, because the turn still completes and the loss is otherwise only visible on a later one. At the limit, the pipe skips that user's database reads and writes and shows the warning "DB ops skipped due to repeated errors." The operator-facing line that reports the skip is emitted once per episode per verb and user and repeats at DEBUG on a 300-second cooldown, so a long outage does not bury it; on a *write* refusal the notice to the person is emitted on every refusal regardless, while a *read* that the breaker refuses fires once per degraded episode and re-arms on the first read that succeeds. Chats still get answers, but that user's reasoning and tool results are neither saved to nor read from the database until failures age out of the window.

While a tool breaker is open, calls to that tool are skipped and the model is told why; outside internal Fusion, a best-effort status message is also sent to the UI, once per tool per round however many of its calls that round asked for before the round's calls were queued, bounded from the moment it runs and by whatever is left of `TOOL_IDLE_TIMEOUT_SECONDS`, and never dropped silently: if that bound ends it a WARNING names the request and the valve that ended it, and the model is still told the reason for every call that was skipped; a call the breaker takes out of service after that, when the call starts, gets its own status message for that call. A turn whose tool calls are all skipped this way does not count as a failed request.

## OpenRouter web search server tool

The web-search integration is attached as a server tool (not as a `tools` function or legacy `plugins` entry):

- When the **OpenRouter Web Tools** toggle (the filter's `WEB_SEARCH` user valve) is enabled for the request (per chat, or enabled by default via the model’s Default Filters), the pipe appends `{"type": "openrouter:web_search", ...}` to `tools`. One entry per type per request: a type the request body already lists is not sent a second time, and the filter's parameters are the ones that go out. Image-output and video-generation models are excluded because they do not receive the Web Tools filter.
- Search parameters (max results, engine, allowed/excluded domains, etc.) are controlled by the OpenRouter Web Tools filter’s admin valves.

Important: Open WebUI also has a separate built-in **Web Search** toggle (Open WebUI-native). OpenRouter Web Tools and Open WebUI Web Search are different systems.
See: [Web Search: OWUI vs OpenRouter](web_search_owui_vs_openrouter_search.md).
See: [OpenRouter Server Tools](openrouter_server_tools.md) for the full server tools reference.

## OpenRouter response-healing plugin (intentionally not exposed)

OpenRouter offers a response-healing plugin that can attempt to repair malformed outputs. This pipe does **not** expose that plugin on purpose:

- We prefer failing fast when a model returns malformed JSON or invalid structured output.
- Silent repairs can hide real model issues (bad prompts, low token budgets, provider quirks) and make debugging harder.

If you want auto-healing, integrate it explicitly in your own request layer so it is visible and auditable.

## Open WebUI Direct Tool Servers

Direct Tool Servers are configured and executed by Open WebUI, but advertised/executed through this pipe:

- Configure servers in **User Settings → External Tools → Manage Tool Servers** (and ensure the server is enabled/toggled).
- Select tool servers for a chat in the tool picker (Open WebUI sends the selected servers in `tool_servers`).
- When the model calls a direct tool, the pipe emits `execute:tool` via `__event_call__` and the browser performs the OpenAPI request.

Failure handling:
- Direct tool execution is wrapped in `try/except`; tool crashes never crash the pipe/session.
- On failure the tool returns an error payload to the model (and the pipe may emit an OWUI notification best-effort).
- A tool whose `operationId` carries surrounding whitespace is not the same tool as the un-padded spelling: the pipe sends the browser the name the server declared, so the browser's `operationId` match resolves, and Open WebUI's hand-back looks the tool up under that same name. If a name is only whitespace, no tool is built for it.

## MCP note (removed)

This pipe no longer implements “remote MCP server connectivity” (previously surfaced as `REMOTE_MCP_SERVERS_JSON`) because it bypasses Open WebUI’s tool server configuration surface and RBAC/permissions model.

If you want MCP tools in Open WebUI, use an MCP→OpenAPI proxy/aggregator (for example **MCPO** or **MetaMCP**) and add the resulting OpenAPI server through Open WebUI’s tool server UI so access control and future tool server changes remain centralized in OWUI.
