# Release notes pending

## Behaviour changes

- **Streamed replies to programs with no chat are built by Open WebUI's own chunk helper again on Open WebUI 0.13.0** - Open WebUI 0.13.0 renamed the helper (`openai_chat_chunk_message_template` is now `chat_completion_chunk_template`), so the pipe fell back to its own copy, whose chunk ids look different and carry no `logprobs` key. The pipe now uses the new name, the old one on Open WebUI 0.12, and its own copy only when neither exists.
- **On Open WebUI 0.13.0 an automatic update of the pipe is announced to event functions and webhooks again** - Open WebUI 0.13.0 publishes an event only for a request, and the dashboard's automatic update runs without one, so its `function.updated` event was dropped and the failure was logged only at debug level. The update now hands Open WebUI a request built around its app, the way Open WebUI announces its own start-up, and an announcement Open WebUI does not take is logged as a warning, once.
- **Open WebUI 0.13's "Auto" tool permission mode now works with the pipe** - Under Auto, Open WebUI reviews each tool call and asks the user when its review says a call needs approval. The pipe handed a turn to Open WebUI only under "Ask" and ran every call itself under "Auto", so no call was reviewed. Auto is now treated like Ask: on a streamed reply in a saved or temporary chat Open WebUI runs and reviews the calls, and where a turn cannot be handed to Open WebUI, Open WebUI's tools are not offered.
- **Tools run again with Open WebUI 0.13's Tool Call Labels on** - With Tool Call Labels on, Open WebUI adds a short label field to every tool's parameters for the model to fill, and removes it again before a tool runs. In the pipe's Pipeline mode the field reached the tool, which refused it, so every tool call failed. The pipe now removes it before the tool runs, as Open WebUI does, and its tool cards show the labels. The same applies to the review field Open WebUI's Auto tool permissions add.
- **A new question in a chat with Open WebUI 0.13's hidden context is treated as a new question again** - Since 0.13.1, Open WebUI sends the skills list, knowledge attached to the model and recalled memories as tool results right after the user's message. The pipe took such a question for Open WebUI coming back with a tool's results, so a user whose requests were being refused after repeated errors got through anyway, and in Open-WebUI tool mode the "Thinking…" status lines were skipped. The pipe now recognises Open WebUI's hidden results by the call ids Open WebUI lists for the request.
- **Tools found by Open WebUI 0.13's Tool Search run again in Pipeline mode** - Open WebUI 0.13.1 changed `call_tool` so that one call can run several looked-up tools at once, and the pipe still read it as a single call, so every looked-up tool failed with "call_tool requires tool_name and params." The pipe now runs each tool in the batch, shows a card for each, and answers the model's call with one combined result in Open WebUI's form, so the stored round replays as the call the model made.
- **The Pipe Dashboard works on every Open WebUI worker** - With several workers, a dashboard panel worked only when its browser connection landed on a worker that had already run the pipe: elsewhere it said "You are not authorized to view this dashboard." or waited forever, and its Usage, Config and Update tabs failed with "unknown pipe" or HTTP 405. The panel now sends its sign-up and every tab click over Open WebUI's own relay between workers (the one its direct connections use), so any worker running the pipe answers, and one worker at a time sends the live figures to every open panel through Open WebUI's Redis. Just after Open WebUI starts, before any worker has run the pipe, the panel says so after about fifteen seconds instead of waiting. Panels saved in chats by earlier releases keep their old requests; reopen the dashboard to get the new panel.
- **An update no longer stops the Pipe Dashboard on the worker that loads it** - Saving the pipe in Workspace → Functions, or updating it from the Update tab, loads the new version in one worker and closes the old one, which stopped that worker's dashboard until it next ran a chat or listed the models; meanwhile it refused panels and answered tab clicks with "unknown pipe". The first dashboard request such a worker receives now starts the new version's dashboard and is answered.
- **Synchronous workspace tools run again on Open WebUI 0.13** - Open WebUI 0.13.0 wraps every workspace tool in a check that the tool is still switched on, and that check reads the database. With "Synchronous tools on threads" on (the default), the pipe handed the whole wrapped tool to a worker thread, where that read cannot run, so every call of a synchronous tool failed with "An asyncio.Future, a coroutine or an awaitable is required". The pipe now runs Open WebUI's check on the event loop and only the tool's body on the thread; a tool switched off in Workspace is still refused with Open WebUI's own message.
- **An account's own preset shows the icon of the model it runs on** - an OpenRouter preset that the picker lists as `@preset/<slug>` got no icon in Open WebUI. The pipe chose the icon of an entry from the entry's own model id, and a preset's id names no model, while a `base_id@preset/slug` entry already showed its base model's icon. The pipe now reads which model a preset runs on (the model its saved configuration names, or the first model it lists) and gives the preset's entry the icon it gives that model's entry: the icon in OpenRouter's catalogue, or else the model maker's logo. This holds for a preset the pipe builds from the presets list and for a preset that OpenRouter's model list carries itself, after a full refresh and after the presets-only retry. A preset whose model has no icon, or whose saved configuration the pipe has not read yet, still gets none written. What is sent to OpenRouter and the preset itself do not change. With `Sync model icons` on, an icon that someone set by hand on a preset's entry, and that has no source URL stamped beside it, is replaced on the first pass that finds an icon for it, as on any other model entry; adding `disable_image_updates` to that entry's advanced parameters keeps it. The presets guide and the integrations guide say so.
